CPU的平均负载
---

# 1 如何理解CPU的平均负载？

当我们发现系统变慢时，通常第一件事就是执行 `top` 或 `uptime` 命令，来查看系统的负载情况。比如下面这个例子:

![top.png](images%2Ftop.png)

![uptime.png](images%2Fuptime.png)

它们输出的最后三个数字，也就是 `load average` 后面的三个值，就是我们要重点关注的平均负载。


## 1.1 平均活跃进程数

load average(平均负载)后面的三个数字分别表示CPU过去1分钟，5分钟，15分钟的平均负载。
简单来说，平均负载指的是单位时间内，系统处于可运行状态和不可中断状态的平均进程数，也就是平均活跃进程数，它和CPU使用率
并没有直接关系。


## 1.2 可运行状态和不可中断状态

所谓可运行状态的进程，指的是正在使用CPU的进程或者正在等待CPU的进程，也就是我们常用ps命令看到的，处于R状态(Running或Runnable)的进程。

不可中断状态的进程则是正处于内核态关键流程中的进程，并且这些流程是不可中断的，譬如最常见的就是等待硬件设备的I/O响应，也就是我们在ps命令
中看到的D状态(Uninterruptible Sleep, 也称为Disk Sleep)的进程。

比如，当一个进程向硬件设备读写数据时，为了保证数据的一致性，在得到磁盘回复前，它是不能被其他进程中断或者打断的，此时的进程就处于不可中断状态，
如果此时的进程被打断了，就容易出现磁盘数据与进程数据不一致的问题。

所以，不可中断状态实际上是系统对进程和硬件设备的一种保护机制。

这里有一个容易被忽视但非常关键的细节：**把不可中断状态(D)计入负载，是Linux特有的做法**。在传统的Unix系统里，平均负载只统计可运行状态(R)的进程，
衡量的是纯粹的"CPU需求"；而Linux从1993年起，额外把D状态的进程也纳入统计。因此Linux上的平均负载更应该被理解为"系统的整体需求"——
它既包含了对CPU的竞争，也包含了被I/O(乃至某些不可中断的内核锁)阻塞的进程。这也正是"平均负载很高，但CPU使用率却不高"这类现象的根源所在：
当磁盘、NFS、网络存储出现问题，大量进程卡在D状态时，即使CPU几乎空闲，平均负载也会被顶得很高。


## 1.3 平均负载是如何计算出来的？

很多人望文生义，以为"1分钟平均负载"就是把过去60秒每一时刻的活跃进程数做一次简单的算术平均，其实并非如此。

Linux内核并不会保存过去每一秒的采样，而是每隔约5秒(内核里的常量 `LOAD_FREQ = 5*HZ + 1`)采样一次当前"可运行 + 不可中断"的进程数，
然后用**指数加权移动平均(EWMA, Exponentially Weighted Moving Average)**去更新那三个值。其递推公式可以简化为：

```
load(t) = load(t-1) * EXP + n * (1 - EXP)
```

其中 `n` 是本次采样得到的活跃进程数，`EXP` 是一个小于1的衰减系数。对1/5/15分钟三个值，内核分别使用不同的衰减系数(以2048为定点分母)：

```
1  分钟: EXP_1  = 1884/2048 ≈ e^(-5/60)   ≈ 0.9200
5  分钟: EXP_5  = 2014/2048 ≈ e^(-5/300)  ≈ 0.9835
15 分钟: EXP_15 = 2037/2048 ≈ e^(-5/900)  ≈ 0.9945
```

由此可以得到两个重要结论：

其一，所谓"1分钟/5分钟/15分钟"，描述的并不是一个固定长度的统计窗口，而是这条平滑曲线的**时间常数**——1分钟的衰减系数最小，历史值遗忘得最快，
所以它对负载变化最敏感、反应最快；15分钟的系数最大，曲线最平滑、最能反映长期趋势。

其二，正因为是指数平滑，负载值的上升和下降都存在"惯性"，不会瞬间到位。比如把一个进程一直占满一个CPU，1分钟负载并不会立刻变成1，
而是需要几分钟才逐渐逼近1。

如果想直接读取内核维护的原始数据，可以查看 `/proc/loadavg` 这个虚拟文件（`uptime`、`top` 的负载值都源自这里）：

```shell
$ cat /proc/loadavg
0.45 0.30 0.25 2/1234 56789
```

它的五个字段含义如下：

- 前三个 `0.45 0.30 0.25`：1/5/15分钟的平均负载；
- `2/1234`：斜杠前是当前可运行(runnable)的进程/线程数，斜杠后是系统中当前存在的进程/线程总数；
- `56789`：系统最近一次创建的进程PID。


## 1.4 平均负载为多少时合理？

既然平均负载指的是平均活跃进程数，那么最理想的，就是每个CPU上都刚好运行着一个进程，如此每个CPU都得到了充分利用。比如当平均负载为2时，意味着什么？
在只有2个CPU的系统上，意味着所有的CPU都刚好运行着一个进程，刚好被完全占用。
在4个CPU的系统上，意味着CPU有50%的空闲。
而在只有1个CPU的系统中，则意味着有一半的进程竞争不到CPU。

需要特别强调的是，**Linux的平均负载不会按CPU核数做归一化**——它是一个绝对数值，而不是百分比。所以离开CPU个数去谈"负载3高不高"是没有意义的：
在4核机器上负载3很健康，在单核机器上负载3却意味着严重过载。同理，比较两台核数不同的机器的负载数值也没有意义，必须先各自除以自己的核数。

因此，评判平均负载情况时，首先你要知道系统有几个CPU。除了从文件 `/proc/cpuinfo` 中读取，更推荐直接使用 `nproc` 或 `lscpu`：

```shell
# 以下几种方式都可以拿到"逻辑CPU"的个数
nproc                                        # 最简洁
grep -c 'model name' /proc/cpuinfo           # 逐行统计
lscpu | grep '^CPU(s):'                      # 还能顺带看到物理核/超线程信息
getconf _NPROCESSORS_ONLN                    # POSIX 标准接口
```

要注意这里统计的是**逻辑CPU**（如果开启了超线程/SMT，一个物理核会被算成2个逻辑CPU），而平均负载的分母也正是逻辑CPU数，两者口径一致。

有了CPU个数，我们就可以判断出，当平均负载比CPU数还大的时候，就意味着系统已经出现了过载。
那平均负载有三个数值，到底该参考哪一个呢？
总的来说，我们应该观察平均负载的变化趋势。
如果过去1分钟，5分钟，15分钟的三个值基本相同或者说相差不大，那就说明系统负载很平稳；如果1分钟的值远小于15分钟的值，
说明系统最近1分钟的负载在减少，而过去15分钟内确有很大的负载；反之，如果1分钟的值远大于15分钟的值，则说明系统最近1分钟
的负载在增加，这种增加有可能只是临时性的，也有可能还会持续增加下去，所以就需要持续观察，一旦1分钟的平均负载接近或
超过了CPU个数，就意味着系统正在发生过载的问题，此时就需要分析调查是哪里导致的问题，并要想办法优化了。

那么，在实际生产环境中，平均负载多高时，需要我们重点关注呢？
一个常用的经验法则是：当平均负载高于CPU数量70%的时候，就应该分析排查负载高的问题了，一旦负载过高，就可能导致进程响应变慢，进而影响服务的正常功能。

不过要提醒的是，"70%"只是一个经验值，而非放之四海皆准的硬指标，落地时还需要结合业务特征来调整：

- 对**延迟敏感的在线服务**（如接口、数据库），队列一旦变长，响应时间就会明显抬升，往往在负载还没到核数时就应该告警，阈值可以设得更低；
- 对**吞吐优先的离线/批处理任务**，让CPU持续跑满反而是划算的，负载稳定在核数附近甚至略高都可以接受；
- 由于Linux负载还包含了D状态，**一个由I/O等待撑高的负载，通常不需要扩CPU，而应该去优化磁盘/存储**。所以看到负载高，第一步永远是先分清它是CPU导致的还是I/O导致的（见第2、3节）。


# 2 平均负载与CPU使用率

平均负载高，并不意味着CPU使用率高，这两者不是一个概念，不能相互混淆。
我们知道，平均负载指的是单位时间内，处于可运行状态和不可中断状态的进程数，所以，它不仅包括了正在使用CPU的进程，还包括等待
CPU和等待I/O的进程。
而CPU使用率，是单位时间内CPU繁忙情况的表征，跟平均负载并不一定完全对应。

我们可以按"负载的来源"把常见情形分成三类，它们和CPU使用率的对应关系并不相同：

| 负载来源 | 平均负载 | CPU使用率 | 说明 |
| --- | --- | --- | --- |
| CPU密集型进程 | 升高 | 升高 | 进程实打实地在消耗CPU，两者一致 |
| I/O密集型进程 | 升高 | 不一定高 | 大量进程卡在D状态等待I/O，CPU可能很空闲（%iowait高、%usr低） |
| 大量进程争抢CPU | 升高 | 升高 | 就绪队列很长，CPU被占满，且伴随大量上下文切换 |

可见，同样是"负载升高"，背后的原因可能截然不同。这也正是下一节要解决的问题：**当平均负载高时，如何进一步定位它到底是被谁、以哪种方式撑高的。**


# 3 当平均负载高时，如何排查分析平均负载的来源？

只知道负载高还不够，我们还需要把它拆解到具体的CPU和具体的进程上。常用的组合是 `mpstat` + `pidstat` + `vmstat`：先用 `mpstat` 看是CPU忙还是在等I/O，
再用 `pidstat` 找出是哪个进程，必要时用 `vmstat` 观察就绪队列长度和上下文切换。

这两个工具大多不是系统自带的，需要先安装（它们都来自 `sysstat` 软件包，`stress` 是用来做压测复现的工具）：

```shell
# Debian / Ubuntu
apt install -y stress sysstat
# CentOS / RHEL
yum install -y stress sysstat
```


## 3.1 常用工具与关键指标

**mpstat** 用来查看每个CPU的使用率明细：

![mpstat.png](images%2Fmpstat.png)

```shell
mpstat -P ALL 5
```

`-P ALL` 表示监控所有CPU，后面的数字5表示每隔5秒输出一组数据，`-u` 表示输出CPU相关指标（默认即为 `-u`）。它的关键列含义如下：

- `%usr`：用户态CPU使用率——业务代码本身在消耗CPU（CPU密集型的典型特征）；
- `%sys`：内核态CPU使用率——系统调用、内核处理占用的CPU；
- `%iowait`：等待I/O完成的时间占比——**这一列偏高，通常说明负载是被I/O撑起来的**；
- `%idle`：空闲时间占比；`%steal` 在虚拟机上表示被宿主机"偷走"的CPU时间。

如果你观察到某个CPU使用率(比如 `%usr`)接近100%，就可以进一步用 `pidstat` 定位到具体是哪个进程。

**pidstat** 用来查看每个进程的CPU使用情况：

![pidstat.png](images%2Fpidstat.png)

```shell
pidstat -u 5 1
```

除了 `%usr`、`%system`、`%CPU` 之外，`pidstat` 还有一个非常有用、却常被忽略的列 `%wait`——它表示进程**等待CPU（即在就绪队列里排队）**的时间占比。
当负载是由"大量进程争抢CPU"造成时，各进程的 `%wait` 会明显偏高，这是区分"进程在跑"还是"进程在等"的直接依据。

**vmstat** 则能从系统整体视角快速印证判断：

```shell
vmstat 5
```

重点看 `procs` 下的两列和 `cpu` 下的四列：

- `r`：就绪队列长度，即正在运行 + 等待CPU的进程数。`r` 持续大于CPU核数，说明CPU是瓶颈；
- `b`：处于不可中断睡眠(D状态)的进程数。`b` 偏大，说明进程被I/O等阻塞了；
- `us`/`sy`/`id`/`wa`：分别对应用户态/内核态/空闲/等待I/O的CPU占比，与mpstat口径一致。

下面用三个经典的压测案例，把这套排查方法串起来。


## 3.2 案例一：CPU密集型进程

在一个2核的机器上，我们用 `stress` 模拟一个把CPU占满的进程：

```shell
# 终端一：模拟 1 个 CPU 满载的进程，持续 600 秒
stress --cpu 1 --timeout 600
```

```shell
# 终端二：观察负载变化（-d 高亮变化的部分）
watch -d uptime
# ... load average: 1.00, 0.75, 0.39   —— 1分钟负载逐渐逼近 1.00
```

```shell
# 终端三：看是哪个 CPU 忙、忙在哪里
$ mpstat -P ALL 5 1
CPU    %usr   %nice    %sys %iowait   %idle
all   50.10    0.00    0.10    0.00   49.80
  0  100.00    0.00    0.00    0.00    0.00   # CPU0 用户态被打满
  1    0.20    0.00    0.20    0.00   99.60
```

`%usr` 高、`%iowait` 为0，说明这是CPU密集型负载。再用 `pidstat` 精确定位到进程：

```shell
$ pidstat -u 5 1
    UID       PID    %usr %system   %wait    %CPU  Command
      0      2312  100.00    0.00    0.00  100.00  stress   # 就是它
```

**特征小结**：负载升高 + `%usr` 高 + `%iowait` 低 + 元凶进程 `%CPU` 高。


## 3.3 案例二：I/O密集型进程

```shell
# 终端一：模拟 I/O 压力
stress -i 1 --timeout 600
```

```shell
# 终端二：负载同样会升高
watch -d uptime
# ... load average: 1.06, 0.58, 0.37
```

```shell
# 终端三：这次是 %iowait（或 %sys）升高，而不是 %usr
$ mpstat -P ALL 5 1
CPU    %usr   %nice    %sys %iowait   %idle
all    0.20    0.00   20.10   65.20   14.50   # 大量时间在等 I/O
```

此时 `%usr` 很低，说明CPU并不忙，负载是被卡在D状态等待I/O的进程撑高的。这正是第1.2节所说的、Linux把D状态计入负载的直接体现。

> **一个常见的坑**：`stress -i` 内部反复调用 `sync()`，在磁盘很快或数据都在缓存里的环境下，`sync()` 可能瞬间返回，于是你可能看到的是 `%sys` 升高而 `%iowait` 并不明显。
> 如果想稳定复现出高 `%iowait`，可以改用 `stress-ng -i 1 --hdd 1`，或直接用 `dd`、`fio` 制造真实的磁盘读写。这也提醒我们：压测工具的行为要结合具体环境来解读。


## 3.4 案例三：大量进程争抢CPU

当系统中运行的进程数远超CPU个数时，进程就会争抢CPU资源，导致就绪队列变长。仍然在2核机器上，我们启动8个CPU压测进程：

```shell
# 终端一：8 个进程争抢 2 个 CPU
stress -c 8 --timeout 600
```

```shell
# 终端二：负载会一路爬升到 8 附近
$ uptime
 ... load average: 7.30, 4.10, 1.80
```

```shell
# 终端三：每个进程只能分到约 25%（2 核 / 8 进程）的 CPU，而 %wait 很高
$ pidstat -u 5 1
    UID       PID    %usr %system   %wait    %CPU  Command
      0      3001   24.80    0.00   74.90   24.80  stress
      0      3002   25.00    0.00   75.10   25.00  stress
      ...（其余 6 个类似）
```

`%CPU` 只有25%左右，而 `%wait` 高达75%，说明进程大部分时间都在**排队等待CPU**，而不是在真正运行。用 `vmstat` 也能佐证：`r` 列会长期停留在8左右，`id`(空闲)接近0。

**特征小结**：负载(≈8)远超CPU数(2) + 各进程 `%CPU` 低但 `%wait` 高 + 就绪队列 `r` 很长，往往还伴随大量非自愿上下文切换（详见下一篇《CPU的上下文切换》）。


# 4 常见误区

- **把平均负载等同于CPU使用率**。二者不是一回事：负载高既可能是CPU忙，也可能是大量进程在等I/O。判断时务必先用 `mpstat` 区分 `%usr` 和 `%iowait`。
- **以为"1分钟负载"是过去60秒的简单平均**。它其实是指数加权移动平均，"1/5/15分钟"是平滑的时间常数，因此负载的升降都有惯性、不会瞬间到位（见1.3节）。
- **脱离CPU核数谈负载高低**。负载是绝对值、不做归一化，"负载3"在4核上很正常、在单核上却是过载；跨机器比较也必须先各自除以核数。
- **忽视D状态的贡献**。看到负载高就急着扩容CPU，可能南辕北辙——如果是I/O等待撑高的负载，正确的方向是优化磁盘/存储。
- **只盯着某一个数值**。应当看1/5/15分钟三者的趋势：三值相近说明平稳，1分钟远大于15分钟说明负载正在快速上升，需要持续观察。


# 5 小结

- 平均负载 = 单位时间内处于**可运行(R)**和**不可中断(D)**状态的平均进程数，反映的是系统的整体需求，与CPU使用率**不能划等号**。
- 它由内核每约5秒采样、以**指数加权移动平均**算出；`/proc/loadavg` 是其原始来源。
- 判读前先用 `nproc` 拿到CPU核数：负载接近核数即需关注，经验阈值约为核数的70%，但要结合业务(在线服务从严、离线任务从宽)调整。
- 排查三板斧：`mpstat -P ALL 5` 看是CPU忙(`%usr`高)还是等I/O(`%iowait`高) → `pidstat -u 5 1` 定位进程并看 `%wait`(是否在排队) → `vmstat 5` 看就绪队列 `r` 和阻塞数 `b`。
- 三种典型负载来源：CPU密集型(`%usr`高)、I/O密集型(`%iowait`高、`%usr`低)、大量进程争抢(负载>核数、`%wait`高)。
