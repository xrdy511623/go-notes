# 适配器模式详解

适配器（Adapter）是 Go 语言中最"隐形"的设计模式。得益于隐式接口（structural typing），很多在 Java 中需要显式编写 Adapter 类的场景，在 Go 中根本不需要——类型天然满足接口。而当你确实需要适配时，Go 提供了两种极轻量的方式：**函数类型适配器**和**结构体适配器**。`http.HandlerFunc` 就是函数类型适配器的教科书范例。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Convert the interface of a class into another interface clients expect. Adapter lets classes work together that couldn't otherwise because of incompatible interfaces.

翻译：将一个类的接口转换为客户端所期望的另一个接口。适配器让原本因接口不兼容而无法协作的类能够一起工作。

Go 中有两种适配器形式：

```
┌──────────────────────────────────────────────────────┐
│          函数类型适配器（Function Type Adapter）        │
│     为函数类型定义方法，让函数直接满足接口                │
├──────────────────────────────────────────────────────┤
│                                                       │
│  type Handler interface {                             │
│      ServeHTTP(ResponseWriter, *Request)              │
│  }                                                    │
│                                                       │
│  type HandlerFunc func(ResponseWriter, *Request)      │
│  func (f HandlerFunc) ServeHTTP(w, r) { f(w, r) }   │
│           ↑                                           │
│    函数类型 + 方法 = 接口实现                            │
│    普通函数通过类型转换即可满足接口                       │
│                                                       │
└──────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────┐
│          结构体适配器（Struct Adapter）                 │
│     持有被适配者，将调用转发并翻译为目标接口               │
├──────────────────────────────────────────────────────┤
│                                                       │
│  type Logger interface { Info(msg, ...any) }          │
│                                                       │
│  type StdAdapter struct { l *log.Logger }             │
│  func (a *StdAdapter) Info(msg, args...) {            │
│      a.l.Printf("[INFO] "+msg, args...)               │
│  }                                                    │
│           ↑                                           │
│    持有 *log.Logger，翻译调用为 Logger 接口              │
│                                                       │
└──────────────────────────────────────────────────────┘
```

### 与装饰器模式的区别

适配器和装饰器在代码结构上非常相似——都是"包一层"。但意图完全不同：

| 维度 | 适配器（Adapter） | 装饰器（Decorator） |
|------|-----------------|-------------------|
| 目标 | **转换**接口，让不兼容的类型协作 | **增强**接口，给已有类型添加功能 |
| 接口关系 | 输入和输出是**不同接口** | 输入和输出是**同一接口** |
| 典型场景 | `*log.Logger` → `Logger` 接口 | `io.Reader` → `io.Reader`（加缓冲） |
| 是否改变行为 | 不改变——只翻译调用方式 | 改变——增加新能力 |
| 可叠加 | 通常不叠加 | 可无限叠加 |

简单记忆：**适配器 = 翻译，装饰器 = 增强**。

## 2 标准库与生态中的先例

### 2.1 http.HandlerFunc — 函数类型适配器的典范

这是 Go 标准库中最经典的适配器，也是面试高频题：

```go
// 目标接口
type Handler interface {
    ServeHTTP(ResponseWriter, *Request)
}

// 函数类型适配器
type HandlerFunc func(ResponseWriter, *Request)

func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) {
    f(w, r)
}
```

效果：任何 `func(http.ResponseWriter, *http.Request)` 签名的函数，通过 `http.HandlerFunc(fn)` 即可适配为 `http.Handler` 接口：

```go
// 普通函数
func hello(w http.ResponseWriter, r *http.Request) {
    fmt.Fprint(w, "Hello")
}

// 通过 HandlerFunc 适配为 Handler 接口
http.Handle("/hello", http.HandlerFunc(hello))
```

### 2.2 sort.IntSlice — 类型适配器

`sort.Sort` 要求 `sort.Interface`（3 个方法），标准库为常见类型提供了适配器：

```go
type Interface interface {
    Len() int
    Less(i, j int) bool
    Swap(i, j int)
}

// 适配器：让 []int 满足 sort.Interface
type IntSlice []int

func (x IntSlice) Len() int           { return len(x) }
func (x IntSlice) Less(i, j int) bool { return x[i] < x[j] }
func (x IntSlice) Swap(i, j int)      { x[i], x[j] = x[j], x[i] }
```

使用时只需类型转换：

```go
s := []int{3, 1, 4, 1, 5}
sort.Sort(sort.IntSlice(s))  // IntSlice 是 []int 的适配器
```

同类适配器：`sort.Float64Slice`、`sort.StringSlice`。Go 1.8 之后 `sort.Slice` 用函数参数取代了这种方式，但适配器模式的思想保留了下来。

### 2.3 io.NopCloser — 组合适配

```go
func NopCloser(r io.Reader) io.ReadCloser
```

`io.NopCloser` 将 `io.Reader`（没有 Close 方法）适配为 `io.ReadCloser`（有 Close 方法），通过添加一个空操作的 `Close()` 方法。

这是适配器的"补缺"变体：原接口缺少目标接口要求的方法，适配器补上缺失部分。

### 2.4 strings.NewReader — 类型到接口的适配

```go
func NewReader(s string) *Reader  // *Reader 实现了 io.Reader
```

将 `string` 适配为 `io.Reader`——string 本身没有 `Read` 方法，`strings.Reader` 包装它并提供了 `Read`。这也是适配器模式，只是太常用了以至于很少被意识到。

同类适配器：`bytes.NewReader`、`bytes.NewBufferString`。

### 2.5 生态中的 Logger 适配器

几乎每个 Go 框架都有自己的 Logger 接口，适配器用来桥接不同日志库：

| 适配器 | 源 | 目标 |
|--------|-----|------|
| `go-kit/log.NewStdlibAdapter` | stdlib `log` | go-kit `log.Logger` |
| `go-logr/logr.FromSlogHandler` | `slog.Handler` | `logr.Logger` |
| `zap.NewStdLog` | `*zap.Logger` | stdlib `*log.Logger` |
| `grpclog.SetLoggerV2` | 自定义 Logger | gRPC 内部日志 |
| `slog.NewLogLogger` | `*slog.Logger` | stdlib `*log.Logger` |

这是适配器模式最高频的现实应用——不同库的日志接口互不兼容，适配器是唯一的胶水。

### 2.6 database/sql.Driver — 驱动适配

```go
type Driver interface {
    Open(name string) (Conn, error)
}
```

每种数据库驱动（MySQL、PostgreSQL、SQLite）都是一个适配器：将数据库特定的协议和 API 适配为 `database/sql` 统一的 `Driver` / `Conn` / `Stmt` 接口。

## 3 核心原理

### 3.1 Go 的隐式接口 = 天然适配器

Go 与 Java/C# 最大的区别：**接口是隐式满足的**。

```java
// Java：必须显式声明 implements
class MyHandler implements Handler {
    public void handle(Request r) { ... }
}
```

```go
// Go：有正确的方法就自动满足接口，不需要 implements
type MyHandler struct{}
func (h *MyHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) { ... }

var _ http.Handler = &MyHandler{} // 编译通过，无需任何适配器
```

这意味着 Go 中**大量的"适配"是自动发生的**——你写了一个有 `Read([]byte) (int, error)` 方法的类型，它就是 `io.Reader`，不需要任何适配器代码。

只有在以下情况才需要显式适配器：
1. **函数 → 接口**：函数本身没有方法，需要函数类型适配器（HandlerFunc 模式）
2. **接口 A → 接口 B**：两个接口方法签名不同，需要结构体适配器做翻译
3. **补缺**：类型缺少目标接口的某些方法（io.NopCloser 模式）

### 3.2 函数类型适配器的原理

Go 允许为**任何自定义类型**定义方法，包括函数类型：

```go
type MatcherFunc func(s string) bool

// 为函数类型定义方法——这是 Go 独有的能力
func (f MatcherFunc) Match(s string) bool { return f(s) }
```

编译器看到 `MatcherFunc` 类型有 `Match(string) bool` 方法，就认为它满足 `Matcher` 接口。调用 `Match` 时实际执行的是底层函数。

这个模式的威力在于：

```go
// 匿名函数直接使用（无需定义 struct）
var m Matcher = MatcherFunc(func(s string) bool {
    return len(s) > 10
})

// 闭包捕获状态（无需 struct 字段）
func MinLength(n int) Matcher {
    return MatcherFunc(func(s string) bool {
        return len(s) >= n
    })
}

// struct 实现（需要复杂状态时）
type RegexpMatcher struct { re *regexp.Regexp }
func (m *RegexpMatcher) Match(s string) bool { return m.re.MatchString(s) }
```

函数适配器和结构体适配器都满足同一接口——调用方完全无感知。

### 3.3 结构体适配器的原理

当两个接口的方法签名不同时，需要结构体适配器做"翻译"：

```go
// 源：stdlib *log.Logger（Printf 风格）
type Logger struct { ... }
func (l *Logger) Printf(format string, v ...any) { ... }

// 目标：应用的 Logger 接口（分级日志）
type AppLogger interface {
    Info(msg string, args ...any)
    Error(msg string, args ...any)
}

// 适配器：翻译调用
type StdAdapter struct { l *log.Logger }
func (a *StdAdapter) Info(msg string, args ...any) {
    a.l.Printf("[INFO] "+msg, args...)  // Printf → Info
}
func (a *StdAdapter) Error(msg string, args ...any) {
    a.l.Printf("[ERROR] "+msg, args...) // Printf → Error
}
```

结构体适配器的三个角色：
- **Target**：客户端期望的接口（`AppLogger`）
- **Adaptee**：现有的不兼容类型（`*log.Logger`）
- **Adapter**：桥接两者的中间层（`StdAdapter`）

## 4 本项目的实现

### 4.1 Matcher — 函数类型适配器

展示 `http.HandlerFunc` 模式的通用化应用：

```go
type Matcher interface {
    Match(s string) bool
}

type MatcherFunc func(s string) bool

func (f MatcherFunc) Match(s string) bool { return f(s) }
```

核心 API：

| 函数 | 返回类型 | 实现方式 | 对标标准库 |
|------|---------|---------|----------|
| `Contains(substr)` | `MatcherFunc` | 闭包 | `strings.Contains` |
| `HasPrefix(prefix)` | `MatcherFunc` | 闭包 | `strings.HasPrefix` |
| `HasSuffix(suffix)` | `MatcherFunc` | 闭包 | `strings.HasSuffix` |
| `MinLength(n)` | `MatcherFunc` | 闭包 | — |
| `NewRegexpMatcher(pat)` | `*RegexpMatcher` | 结构体 | `regexp.Regexp` |
| `All(m...)` | `MatcherFunc` | 组合 | — |
| `Any(m...)` | `MatcherFunc` | 组合 | — |
| `Not(m)` | `MatcherFunc` | 取反 | — |

关键展示：**函数适配器和结构体适配器对调用方完全透明**——`All`、`Any`、`Not` 接收的是 `Matcher` 接口，不关心底层是 `MatcherFunc` 还是 `*RegexpMatcher`。

使用方式：

```go
// 函数适配器 + 结构体适配器混合使用
dateMatcher, _ := matcher.NewRegexpMatcher(`^\d{4}-\d{2}-\d{2}$`)
m := matcher.All(
    dateMatcher,                  // struct-based
    matcher.Not(matcher.HasPrefix("0000")),  // function-based
    matcher.MinLength(10),        // function-based
)
m.Match("2024-01-15")  // true
m.Match("0000-00-00")  // false
```

### 4.2 LogAdapter — 结构体适配器

展示跨库接口桥接——不同日志库适配到统一接口：

```go
type Logger interface {
    Debug(msg string, args ...any)
    Info(msg string, args ...any)
    Error(msg string, args ...any)
}

func FromStd(l *log.Logger) *StdAdapter  { ... }
func FromSlog(l *slog.Logger) *SlogAdapter { ... }
func Nop() Logger                          { ... }
```

三种适配器覆盖了不同场景：

| 适配器 | 源 | 翻译方式 | 场景 |
|--------|-----|---------|------|
| `StdAdapter` | `*log.Logger` | Printf 添加级别前缀 | 简单项目、快速集成 |
| `SlogAdapter` | `*slog.Logger` | Sprintf 预格式化消息 | Go 1.21+ 结构化日志 |
| `nopLogger` | 无 | 丢弃所有消息 | 测试、禁用日志 |

使用方式：

```go
// 生产环境：用 slog
logger := logadapter.FromSlog(slog.Default())

// 简单场景：用 stdlib log
logger := logadapter.FromStd(log.Default())

// 测试：不输出
logger := logadapter.Nop()

// 业务代码只依赖 Logger 接口
func ProcessOrder(logger logadapter.Logger, orderID string) {
    logger.Info("processing order %s", orderID)
}
```

### 4.3 反面示例：多余的适配器 — `trap/needlessadapter/`

从 Java 转来最常犯的错误——为已经满足接口的类型创建适配器：

```go
type FileLogger struct{ Path string }
func (f *FileLogger) Write(p []byte) (int, error) { ... }

// ❌ 多余！FileLogger 已经有 Write 方法，天然就是 io.Writer
type FileLoggerWriterAdapter struct{ logger *FileLogger }
func (a *FileLoggerWriterAdapter) Write(p []byte) (int, error) {
    return a.logger.Write(p)  // 纯粹转发
}

// ✅ 直接用
var w io.Writer = &FileLogger{Path: "/var/log/app.log"}
```

Go 的隐式接口意味着：如果类型已经有了接口要求的方法，**它就是那个接口**。写适配器只是多了一层无意义的间接。

## 5 设计决策解析

### 5.1 函数类型适配器 vs 结构体适配器

| 维度 | 函数类型适配器 | 结构体适配器 |
|------|-------------|------------|
| 代码量 | 极少（2 行类型 + 方法） | 较多（struct + 多个方法） |
| 适用条件 | 目标接口只有 **1 个方法** | 目标接口有 **多个方法** |
| 状态管理 | 闭包捕获 | struct 字段 |
| 匿名使用 | ✅ 内联 lambda | ❌ 必须定义命名类型 |
| 标准库范例 | `http.HandlerFunc` | `sort.IntSlice`、日志适配器 |

经验法则：
- **1 个方法**的接口 → 优先函数类型适配器
- **2+ 方法**的接口 → 结构体适配器
- 需要持有**复杂状态**（如编译后的正则）→ 结构体适配器

### 5.2 Go 的隐式接口为何减少了适配器需求？

在 Java 中，即使类有正确的方法，也必须显式声明 `implements`：

```java
// Java: 必须显式适配
class MyWriter { void write(byte[] b) { ... } }
// MyWriter 不是 Writer，除非声明 implements Writer

class MyWriterAdapter implements Writer {
    private MyWriter inner;
    public void write(byte[] b) { inner.write(b); }  // 手动转发
}
```

```go
// Go: 零适配成本
type MyWriter struct{}
func (w *MyWriter) Write(p []byte) (int, error) { ... }

var w io.Writer = &MyWriter{}  // 直接赋值，编译器自动匹配
```

Go 的隐式接口在编译时检查方法集——如果匹配就满足，不匹配就报错。没有中间态，不需要 `implements` 声明，也不需要适配器类。

这意味着 Go 程序中看到的适配器，通常是在做**真正的翻译**（方法签名不同），而非 Java 式的"为了满足类型系统的仪式性代码"。

### 5.3 适配器 vs 装饰器 — 代码层面的区分

两者在代码结构上很像，区分的关键是**接口关系**：

```go
// 适配器：不同接口之间的桥梁
type StdAdapter struct { l *log.Logger }  // 持有 *log.Logger（源接口）
func (a *StdAdapter) Info(msg string, args ...any) { ... }  // 实现 Logger（目标接口）
// *log.Logger ≠ Logger

// 装饰器：同一接口的增强
type CountingReader struct { r io.Reader }  // 持有 io.Reader（同一接口）
func (c *CountingReader) Read(p []byte) (int, error) { ... }  // 实现 io.Reader（同一接口）
// 输入 io.Reader = 输出 io.Reader
```

如果 `struct` 持有的类型与自身实现的接口**相同** → 装饰器。
如果 `struct` 持有的类型与自身实现的接口**不同** → 适配器。

### 5.4 组合器模式：适配器的延伸

本项目的 `All`、`Any`、`Not` 展示了适配器的一个强大延伸——**组合器**（Combinator）：

```go
func All(matchers ...Matcher) Matcher {
    return MatcherFunc(func(s string) bool {
        for _, m := range matchers {
            if !m.Match(s) { return false }
        }
        return true
    })
}
```

组合器接收多个 Matcher，返回一个新 Matcher——通过函数类型适配器实现。这与 `http.HandlerFunc` 的思路一脉相承：函数类型是粘合剂，让所有东西都能组合。

### 5.5 何时需要适配器、何时不需要？

| 场景 | 需要适配器？ | 原因 |
|------|-----------|------|
| 类型已有接口要求的方法 | ❌ | Go 隐式接口自动匹配 |
| 函数需要满足接口 | ✅ 函数类型适配器 | 函数不能有方法 |
| 两个库接口不兼容 | ✅ 结构体适配器 | 方法签名不同需要翻译 |
| 类型缺少某个方法 | ✅ 补缺适配器 | 如 `io.NopCloser` 添加 Close |
| 需要改变调用语义 | ✅ 结构体适配器 | 如 printf → structured logging |

## 6 适用场景与局限

### 适用

- **HTTP 处理函数**：`http.HandlerFunc` 适配普通函数为 `http.Handler`——Go Web 开发的基石
- **排序接口**：`sort.IntSlice` / `sort.StringSlice` 适配切片为 `sort.Interface`
- **日志桥接**：统一不同日志库到应用层接口——每个生产项目都会遇到
- **数据库驱动**：`database/sql.Driver` 适配不同数据库的 wire protocol
- **I/O 补缺**：`io.NopCloser` 为 Reader 补上 Close 方法
- **测试 mock**：函数类型适配器天然支持匿名函数 mock，无需 mock 框架

### 局限

- **过度适配**：如果类型已经满足接口，不需要适配器——Go 隐式接口是最好的适配器
- **语义损失**：适配器做翻译时可能丢失信息（如 printf → slog 丢失结构化参数）
- **增加间接层**：每个适配器增加一次函数调用。在 99.9% 场景可忽略，但要意识到
- **大接口适配成本高**：如果目标接口有 10+ 方法，适配器需要实现全部——应考虑拆分接口

## 7 适配器 vs 门面 vs 桥接

三者都涉及"包装"，但意图不同：

| 维度 | 适配器 (Adapter) | 门面 (Facade) | 桥接 (Bridge) |
|------|-----------------|--------------|--------------|
| **意图** | 让不兼容的接口协作 | 简化复杂子系统的调用 | 将抽象与实现分离 |
| **接口数量** | 转换 1:1 | 将 N 个接口统一为 1 个 | 抽象和实现各自变化 |
| **方向** | 源接口 → 目标接口 | 多个子系统 → 统一入口 | 抽象层 ↔ 实现层 |
| **Go 标准库** | `http.HandlerFunc` | `http.ListenAndServe` | `database/sql` (Driver 接口) |
| **判断口诀** | 两个接口不兼容→适配器 | 调用太复杂想简化→门面 | 两个维度独立变化→桥接 |

### 反例：为隐式接口硬造适配层

```go
// ❌ 不需要适配器——Go 的隐式接口已经做了
type MyWriter struct{}
func (w *MyWriter) Write(p []byte) (int, error) { ... }

// 多余！MyWriter 天然满足 io.Writer
type MyWriterAdapter struct{ w *MyWriter }
func (a *MyWriterAdapter) Write(p []byte) (int, error) { return a.w.Write(p) }
```

Go 的隐式接口意味着：**如果方法签名匹配，就不需要适配器**。只有方法签名不同时才需要翻译。

从 Java 转来的开发者最容易犯这个错误——在 Java 中你必须写 `implements`，在 Go 中完全不需要。

|---------|---------|
| 函数类型适配 | `MatcherFunc(fn).Match(s)` 等价于直接调用 fn |
| 结构体适配透传 | 适配器调用了底层被适配者的方法 |

| Nop 不输出 | Nop() logger 不写入任何内容 |
| 反例验证 | 验证不需要适配器的场景确实不需要 |

## 9 成本模型

### 何时值得用适配器

- 两个库的接口不兼容，需要桥接（如统一日志接口）
- 函数需要满足接口（`http.HandlerFunc` 模式）
- 类型缺少目标接口的某些方法（`io.NopCloser` 模式）

### 何时是过度设计

- 类型已经满足接口——Go 隐式接口就是最好的适配器
- 只有一个地方需要适配——内联转换比定义适配器更简单
- 适配器只是纯粹转发，没有任何翻译——多余的间接层
