# 状态机模式 (State Machine / Finite State Machine)

## 一句话定义

> **有限状态机（FSM）用一组状态、事件和转换规则来描述对象的生命周期，使复杂的条件分支变为声明式的状态图。**

---

## 核心价值

| 问题 | 状态机的解法 |
|------|-------------|
| 大量嵌套的 `if/switch` 判断状态 | 用 **转换表** 替代分支，O(1) 查找 |
| 非法状态转换难以发现 | 转换规则声明式定义，**运行时自动拒绝非法事件** |
| 状态变更时需要执行副作用 | **OnEnter / OnLeave / OnTransition** 回调，解耦状态逻辑与副作用 |
| 并发环境下状态不一致 | 状态机内部加锁，**保证转换的原子性** |

---

## 标准库与生态中的 FSM

### 1. `net/http` 连接状态

```go
// net/http/server.go 中的 ConnState
type ConnState int
const (
    StateNew    ConnState = iota  // 新连接
    StateActive                    // 正在处理请求
    StateIdle                      // keep-alive 等待
    StateHijacked                  // 被劫持（WebSocket）
    StateClosed                    // 已关闭
)
```

`http.Server.ConnState` 就是一个典型的状态机回调：

```go
srv := &http.Server{
    ConnState: func(conn net.Conn, state http.ConnState) {
        log.Printf("conn %s → %s", conn.RemoteAddr(), state)
    },
}
```

转换规则：`New → Active → Idle → Active → ... → Closed`。

### 2. `bufio.Scanner` 状态转换

Scanner 内部维护了隐式状态机：

| 状态 | 描述 |
|------|------|
| scanning | `Scan()` 返回 true，可继续 |
| done | 到达 EOF，`Scan()` 返回 false |
| error | 遇到错误，后续 `Scan()` 始终返回 false |

一旦进入 `done` 或 `error`，**不可逆转**——这是典型的 FSM 终态。

### 3. `database/sql.Tx` 事务状态

```
Active ──[Commit]──→ Committed
   │
   └──[Rollback]──→ RolledBack
```

Commit/Rollback 后再调用任何方法都返回 `ErrTxDone`——这就是 FSM 对非法事件的拒绝。

### 4. 开源库：`looplab/fsm`

Go 生态最流行的 FSM 库，API 示例：

```go
f := fsm.NewFSM(
    "closed",
    fsm.Events{
        {Name: "open", Src: []string{"closed"}, Dst: "opened"},
        {Name: "close", Src: []string{"opened"}, Dst: "closed"},
    },
    fsm.Callbacks{
        "enter_opened": func(ctx context.Context, e *fsm.Event) {
            log.Println("door opened")
        },
    },
)
f.Event(context.Background(), "open")
```

本项目的实现简化了 looplab/fsm 的 API，保留核心语义：
- `Events` 数组 → `[]Transition`（每条规则一个 From，更显式）
- `Callbacks` map → `OnEnter` / `OnLeave` / `OnTransition` 方法
- `Event()` → `Fire()`

### 核心 API（fsm 包）

```go
// 类型
type State string
type Event string
type Callback func(event Event, from, to State)
type Transition struct {
    Event Event
    From  State
    To    State
}

// 构造（重复的 Event+From 组合会返回错误）
func New(initial State, transitions []Transition) (*FSM, error)

// 触发事件
func (f *FSM) Fire(event Event) error

// 查询
func (f *FSM) Current() State
func (f *FSM) Is(state State) bool
func (f *FSM) Can(event Event) bool
func (f *FSM) AvailableEvents() []Event

// 回调注册
func (f *FSM) OnEnter(state State, cb Callback)
func (f *FSM) OnLeave(state State, cb Callback)
func (f *FSM) OnTransition(cb Callback)

// 重置（不触发回调）
func (f *FSM) Reset(state State)
```

### 三个具体状态机

#### 1. order — 订单工作流

```
Created ──[pay]──→ Paid ──[ship]──→ Shipped ──[deliver]──→ Delivered
   │                 │
   └──[cancel]──→ Cancelled ←──[cancel]──┘
```

- 5 个状态、4 个事件、5 条转换
- 已发货不可取消——FSM 自动拒绝

#### 2. conn — 网络连接（对标 net/http ConnState）

```
Idle ──[open]──→ Active ──[park]──→ Idle
  │                 │
  └──[close]──→ Closed ←──[close]──┘
```

- `Closed` 是终态，所有事件在此状态下都返回错误
- `park` 对应 HTTP keep-alive 的空闲回池

#### 3. turnstile — 经典闸机

```
Locked ←──[push]──→ Unlocked
  ↑                    ↑
  └────[push]──────────┘ (自转换)
               [coin]──→ (自转换)
```

- 包含自转换：投币后再投币、锁住时推门
- CS 教科书经典示例，用于教学和测试

## 设计决策

### 1. `sync.Mutex` 而非 `sync.RWMutex`

`Fire()` 需要写锁，`Current()` 需要读锁。但 FSM 的典型使用场景中：
- 读写比例接近 1:1（查询状态通常紧跟触发事件）
- `RWMutex` 在低竞争场景下开销反而大于 `Mutex`
- looplab/fsm 也使用 `sync.Mutex`

### 2. 回调在持锁期间执行

```go
func (f *FSM) Fire(event Event) error {
    f.mu.Lock()
    defer f.mu.Unlock()
    // ... OnLeave → 更新状态 → OnEnter → OnTransition
}
```

**好处**：保证回调看到的状态是一致的，不会被其他 goroutine 的 Fire 插入。

**约束**：回调内不能调用 `Fire` / `Reset` / `Current`（`sync.Mutex` 不可重入 → 死锁）。回调已接收 `event, from, to` 三个参数，无需回查 FSM。

替代方案（eventbus 的 snapshot 模式）：先快照回调再释放锁，回调在锁外执行。但对 FSM 来说，回调是转换的一部分，在锁内执行更自然。

### 3. 类型化常量而非 `iota`

```go
const Idle  fsm.State = "idle"    // ✅ 可读性好，日志直接输出
const Close fsm.Event = "close"   // ✅ 类型安全，编译期检查
```

Go 没有 enum，`iota` 方案需要 `stringer` 代码生成。字符串类型别名是最佳平衡点：
- 编译期类型检查（不能把 `Event` 传给 `State` 参数）
- 运行时可读性（日志 / 错误信息直接输出字符串）
- 无需代码生成

### 4. 转换表用 `map[transKey]State`

`transKey` 是 `{event, from}` 二元组，查找复杂度 O(1)。

对比 looplab/fsm 的 `map[eKey]Transition`（本质相同），但本实现更简洁：
- looplab/fsm 支持一个 Event 对应多个 Src → 遍历 Src 数组
- 本实现每条 `Transition` 一个 From → 直接 map 查找

### 5. `Reset()` 不触发回调

Reset 是管理操作（测试重置、故障恢复），不是业务事件。触发回调会混淆正常转换和管理操作。

## 陷阱

### 裸字符串状态（trap/stringstate）

```go
// ❌ 裸字符串
current := "idle"
if current == "idel" { ... }  // 拼写错误，编译期不报错

fsm.Fire("colse")  // 运行时才发现 ErrUnknownEvent
```

```go
// ✅ 类型化常量
const Idle fsm.State = "idle"
const Close fsm.Event = "close"
m.Fire(Close)  // 编译器保证 Close 存在
```

## 与相关模式的对比

| 维度 | 状态机 (FSM) | 策略 (Strategy) | 状态模式 (GoF State) |
|------|-------------|----------------|---------------------|
| 关注点 | **转换规则** + 生命周期 | **算法可替换** | **每个状态独立封装行为** |
| 状态数量 | 有限且预知 | 不涉及状态 | 有限且预知 |
| Go 实现 | 转换表 + Fire | 接口 / 函数类型 | 接口 + 组合 |
| 适用场景 | 工作流、协议、连接 | 支付、排序、重试 | 每个状态逻辑复杂 |
| 状态转换 | 集中在 FSM 中 | 不涉及 | 分散在各 State 实现中 |

**何时用 FSM vs GoF State？**
- 状态转换逻辑简单、状态较多 → FSM（声明式转换表）
- 每个状态行为差异大、需要多态 → GoF State（每个状态一个接口实现）
- 两者可结合：FSM 管理转换，每个状态委托给 State 接口实现

## 适用场景

- 订单/工单/审批工作流
- TCP / HTTP 连接生命周期
- 游戏角色状态（idle / walk / attack / dead）
- 编译器/解析器状态（lexer tokenizer）
- CI/CD 流水线阶段

## 局限

- **状态爆炸**：状态过多时转换表难以维护 → 考虑层次状态机（HSM）
- **回调死锁**：持锁期间回调不能回调 FSM → 设计约束
- **不支持守卫条件**：`Fire(event)` 不接受参数 → 需要在回调中检查外部条件
- **不支持并行状态**：经典 FSM 同一时刻只有一个状态 → 考虑 Statechart

## FSM vs GoF State 模式

GoF State 模式和 FSM（有限状态机）经常被混为一谈，但它们的实现和适用场景不同：

| 维度 | FSM（本项目） | GoF State |
|------|-------------|-----------|
| **状态存储** | 枚举/常量（`State string`） | 每个状态一个接口实现（`type LockedState struct{}`） |
| **转换逻辑** | 集中在转换表（`map[{event,from}]to`） | 分散在各 State 实现中 |
| **行为差异** | 通过回调（OnEnter/OnLeave） | 每个 State 直接实现不同行为 |
| **新增状态** | 加一行转换规则 | 新增一个 struct + 接口实现 |
| **新增事件** | 加转换规则 | 每个 State 都要处理新事件 |
| **适合场景** | 状态多、转换简单 | 状态少、每个状态行为差异大 |

### 何时用 FSM（转换表）

- 状态 > 5 个
- 每个状态的行为差异主要在"允许哪些转换"，而非"如何处理"
- 转换规则可能动态变化（配置驱动）

### 何时用 GoF State

- 状态 < 5 个
- 每个状态的行为显著不同（如 TCP 的 Listen/Established/Closing 处理逻辑完全不同）
- 需要利用类型系统保证每个状态都处理了所有事件

### 状态爆炸与分层状态机

当状态数量超过 15-20 个时，转换表变得难以维护。解法：

1. **分层状态机 (HSM)**：状态可以嵌套（如"Active"包含"Loading"和"Ready"子状态）
2. **并行状态**：多个独立的状态维度（如"连接状态"和"认证状态"各自独立）
3. **状态图 (Statechart)**：UML Statechart 扩展了 FSM，支持层次、并行和历史状态

Go 生态中没有成熟的 HSM 库，大多数项目通过"多个 FSM 组合"来近似实现分层效果。

## 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| 合法转换 | 每条转换规则都能正确执行 |
| 非法事件拒绝 | 在错误状态下触发事件返回 error |
| 回调触发 | OnEnter/OnLeave/OnTransition 在正确时机调用 |
| 回调参数 | 回调收到正确的 event, from, to 值 |
| 并发安全 | 多 goroutine 同时 Fire 不 race |
| Reset | Reset 后回到初始状态，不触发回调 |
| 终态 | 终态下所有事件都返回 error |
| Can/AvailableEvents | 查询 API 与实际可执行的事件一致 |

## 成本模型

### 何时值得用状态机

- 对象有明确的生命周期（订单、连接、工单）
- 状态转换规则需要集中管理（而非散落在 if/switch 中）
- 需要运行时自动拒绝非法转换
- 状态变更时需要触发副作用（通知、日志、指标）

### 何时是过度设计

- 只有 2-3 个状态——if/switch 更清晰
- 状态转换没有约束——不需要"拒绝非法转换"的能力
- 状态变更不需要副作用——不需要回调机制
