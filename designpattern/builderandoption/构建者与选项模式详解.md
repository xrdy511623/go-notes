# 构建者与选项模式详解

当一个对象有大量可选参数时，构造函数会变得臃肿且难以维护。Go 语言中有两种主流方案解决这个问题：**Builder 模式**（分步构建 + 链式调用）和**Functional Options 模式**（函数选项 + 变长参数）。本目录同时实现了两种方案，并深入对比它们的设计取舍。

---

## 1 模式定义

### Builder 模式

GoF《设计模式》中的定义：

> Separate the construction of a complex object from its representation so that the same construction process can create different representations.

翻译：将复杂对象的构建与其表示分离，使同样的构建过程可以创建不同的表示。

```
NewBuilder(host, port)
    .ReadTimeout(10s)
    .MaxConnections(5000)
    .TLS(cert, key)
    .Build()              ──→ *Server
```

### Functional Options 模式

这不是 GoF 模式，而是 Go 社区的原创惯用法，由 Rob Pike 和 Dave Cheney 推广：

> Use closures to implement optional configuration, accepting them as variadic arguments to constructor functions.

```
NewServer(host, port,
    WithReadTimeout(10s),
    WithMaxConnections(5000),
    WithTLS(cert, key),
)                         ──→ *Server
```

两者解决同一个问题 — **复杂对象的可选参数构建** — 但方式截然不同。

## 2 标准库与生态中的先例

### Builder 模式

| 场景 | Builder | 说明 |
|------|---------|------|
| `strings.Builder` | `b.WriteString("..."); b.String()` | 分步构建字符串 |
| `net/url` | `url.URL{Scheme: "https", Host: "..."}` | 结构体字面量（Go 的"轻量 Builder"） |
| `bytes.Buffer` | `buf.Write(...); buf.Bytes()` | 分步构建字节序列 |
| protobuf | `proto.MessageBuilder` | 复杂消息的分步构建 |
| testify | `suite.Suite` + 链式断言 | 测试用例的分步构造 |

### Functional Options 模式

| 场景 | 函数签名 | 说明 |
|------|---------|------|
| gRPC | `grpc.Dial(addr, ...DialOption)` | 连接选项 |
| go-zero | `rest.NewServer(cfg, ...RunOption)` | 服务器选项 |
| uber-go/zap | `zap.New(core, ...Option)` | 日志选项 |
| net/http | `http.Server{...}` | 虽然用结构体，但概念类似 |
| Go 标准库提案 | `crypto/tls.Config` | 社区持续讨论是否改为 Options |

gRPC 是 Functional Options 的教科书级应用：

```go
conn, err := grpc.Dial("localhost:50051",
    grpc.WithTransportCredentials(creds),
    grpc.WithBlock(),
    grpc.WithTimeout(5*time.Second),
)
```

每个 `grpc.With*` 函数返回一个 `DialOption`，`Dial` 内部依次应用这些选项。

## 3 本项目的实现 — Builder

### 3.1 Builder 结构

```go
type Builder struct {
    server Server
    err    error      // 延迟错误：首个错误被记录，后续调用直接跳过
}

func NewBuilder(host string, port int) *Builder { ... }

func (b *Builder) ReadTimeout(d time.Duration) *Builder { ... }
func (b *Builder) WriteTimeout(d time.Duration) *Builder { ... }
func (b *Builder) MaxConnections(n int) *Builder { ... }
func (b *Builder) TLS(certFile, keyFile string) *Builder { ... }

func (b *Builder) Build() (*Server, error) { ... }
```

核心 API：

| 方法 | 作用 | 返回 |
|------|------|------|
| `NewBuilder(host, port)` | 创建 Builder，设置必填参数和默认值 | `*Builder` |
| `.ReadTimeout(d)` | 设置读超时 | `*Builder`（链式） |
| `.WriteTimeout(d)` | 设置写超时 | `*Builder`（链式） |
| `.MaxConnections(n)` | 设置最大连接数 | `*Builder`（链式） |
| `.TLS(cert, key)` | 启用 TLS | `*Builder`（链式） |
| `.Build()` | 校验并返回最终实例 | `(*Server, error)` |

### 3.2 使用方式

```go
srv, err := builder.NewBuilder("0.0.0.0", 443).
    ReadTimeout(10 * time.Second).
    WriteTimeout(15 * time.Second).
    MaxConnections(5000).
    TLS("cert.pem", "key.pem").
    Build()
```

必填参数（host、port）在 `NewBuilder` 中传入，可选参数通过链式方法设置。`Build()` 做最终校验并返回不可变的 `*Server`。

## 4 本项目的实现 — Functional Options

### 4.1 Option 类型与构造函数

```go
type Option func(*Server) error

func WithReadTimeout(d time.Duration) Option { ... }
func WithWriteTimeout(d time.Duration) Option { ... }
func WithMaxConnections(n int) Option { ... }
func WithTLS(certFile, keyFile string) Option { ... }

func NewServer(host string, port int, opts ...Option) (*Server, error) { ... }
```

核心 API：

| 函数 | 作用 |
|------|------|
| `NewServer(host, port, opts...)` | 创建 Server，必填参数 + 变长选项 |
| `WithReadTimeout(d)` | 返回设置读超时的 Option |
| `WithWriteTimeout(d)` | 返回设置写超时的 Option |
| `WithMaxConnections(n)` | 返回设置最大连接数的 Option |
| `WithTLS(cert, key)` | 返回启用 TLS 的 Option |

### 4.2 使用方式

```go
srv, err := option.NewServer("0.0.0.0", 443,
    option.WithReadTimeout(10 * time.Second),
    option.WithWriteTimeout(15 * time.Second),
    option.WithMaxConnections(5000),
    option.WithTLS("cert.pem", "key.pem"),
)
```

必填参数是普通函数参数，可选参数是变长的 `...Option`。不传任何 Option 时，所有可选参数使用默认值。

## 5 设计决策解析

### 5.1 为什么 Builder 使用延迟错误？

```go
func (b *Builder) ReadTimeout(d time.Duration) *Builder {
    if b.err != nil {
        return b       // 已有错误，跳过
    }
    if d <= 0 {
        b.err = fmt.Errorf("builder: read timeout must be positive, got %v", d)
        return b
    }
    b.server.ReadTimeout = d
    return b
}
```

延迟错误（deferred error）策略：首个错误被记录在 `b.err` 中，后续的链式调用全部跳过，最终 `Build()` 返回该错误。

替代方案是每个方法都返回 `(*Builder, error)`，但这会破坏链式调用：

```go
// ❌ 每步都要检查 error，无法链式调用
b, err := NewBuilder("localhost", 8080).ReadTimeout(10 * time.Second)
if err != nil { ... }
b, err = b.MaxConnections(5000)
if err != nil { ... }
```

延迟错误是 Builder 模式的经典技巧 — `strings.Builder`、`bytes.Buffer`、`bufio.Writer` 都采用相同策略（延迟到 `String()`、`Bytes()`、`Flush()` 时返回错误）。

### 5.2 为什么 Option 返回 error？

```go
type Option func(*Server) error    // 本项目选择

// 对比不返回 error 的版本
type Option func(*Server)          // gRPC、go-micro 等
```

两种都是主流做法：

| 维度 | `func(*T) error` | `func(*T)` |
|------|------------------|------------|
| 参数校验 | Option 内部校验，返回错误 | 无法校验，或 panic |
| 使用复杂度 | 构造函数需处理 error | 构造函数更简洁 |
| 代表库 | uber-go/zap | gRPC、go-micro |
| 适用场景 | 参数可能非法（来自配置/用户输入） | 参数总是合法（硬编码常量） |

本项目选择返回 error，因为 Server 配置可能来自外部配置文件，参数非法是正常情况，不应 panic。

### 5.3 为什么必填参数不用 Option？

```go
// ✅ 必填参数是普通参数
func NewServer(host string, port int, opts ...Option) (*Server, error)

// ❌ 必填参数也用 Option
func NewServer(opts ...Option) (*Server, error)
```

将 host 和 port 放在 Option 中会引入"忘记设置必填参数"的运行时错误。作为普通参数，编译器会强制调用方传入，消除了这类 bug。

经验法则：**必填参数用普通参数，可选参数用 Option**。

### 5.4 为什么 Build() 返回副本？

```go
func (b *Builder) Build() (*Server, error) {
    ...
    srv := b.server    // 值拷贝
    return &srv, nil   // 返回副本的指针
}
```

如果直接返回 `&b.server`，多次调用 `Build()` 会返回同一个实例，修改一个会影响另一个。值拷贝保证每次 `Build()` 返回独立实例。

### 5.5 为什么默认值在构造函数中设置？

```go
func NewBuilder(host string, port int) *Builder {
    return &Builder{
        server: Server{
            Host:           host,
            Port:           port,
            ReadTimeout:    30 * time.Second,    // 默认值
            WriteTimeout:   30 * time.Second,    // 默认值
            MaxConnections: 1000,                // 默认值
        },
    }
}
```

两种策略的对比：

| 策略 | 说明 | 优劣 |
|------|------|------|
| 构造函数中设默认值 | 所有默认值集中在一处 | ✅ 一目了然，易于维护 |
| 零值即默认值 | 依赖 Go 的零值语义 | ❌ 零值通常不是合理的默认值（如 timeout=0） |
| Build/NewServer 中设默认值 | 在最终构建时补充 | ❌ 与用户显式设置的值难以区分 |

本项目选择在构造函数中集中设置默认值，与 `http.Server`、`grpc.ServerOption` 的做法一致。

### 5.6 为什么 With* 函数返回闭包而非直接修改？

```go
// ✅ 返回闭包
func WithReadTimeout(d time.Duration) Option {
    return func(s *Server) error {
        s.ReadTimeout = d
        return nil
    }
}

// ❌ 直接修改
func SetReadTimeout(s *Server, d time.Duration) {
    s.ReadTimeout = d
}
```

闭包的关键优势是**延迟执行** — Option 在创建时捕获参数值，在 `NewServer` 内部才真正应用。这允许：

- 提前组合 Option 列表，稍后统一应用
- 将 Option 列表存储在配置中，运行时动态选择
- Option 之间互不干扰，顺序清晰

```go
// 可以提前组合，稍后使用
commonOpts := []option.Option{
    option.WithReadTimeout(10 * time.Second),
    option.WithMaxConnections(5000),
}
srv, _ := option.NewServer("localhost", 8080, commonOpts...)
```

## 6 Builder vs Functional Options

两种模式解决同一个问题，但各有取舍：

```
Builder：
  NewBuilder(host, port) → 设置属性 A → 设置属性 B → Build()
  （分步构建，链式调用，最终一次性校验）

Functional Options：
  NewServer(host, port, WithA(...), WithB(...))
  （一步完成，选项列表，即时校验）
```

| 维度 | Builder | Functional Options |
|------|---------|-------------------|
| API 风格 | 链式方法调用 | 变长函数参数 |
| 代码量 | 多（Builder struct + 每个属性一个方法 + Build） | 少（每个属性一个 With 函数） |
| 必填 vs 可选 | 均通过方法设置，区分不明显 | 必填是参数，可选是 Option，泾渭分明 |
| 校验时机 | 延迟到 Build() | 每个 Option 即时校验 |
| 可组合性 | Builder 实例不易传递和复用 | Option 列表可存储、合并、传递 |
| IDE 支持 | `.` 触发补全，可发现性强 | `With` 前缀补全，也不错 |
| Go 惯用性 | 较少使用（`strings.Builder` 是例外） | **主流做法**（gRPC、zap、go-zero） |
| 适合场景 | 构建过程有顺序依赖或多步骤 | 参数独立，无顺序依赖 |

### 如何选择？

```
构建过程是否有顺序依赖？（如：先设置 A 才能设置 B）
├── 是 → Builder（链式方法天然表达顺序）
└── 否 → 参数是否独立？
    ├── 是 → Functional Options（Go 社区首选）
    └── 否 → Builder
```

实际项目中，Functional Options 是 Go 的**事实标准**。Builder 在需要复杂构建逻辑（如条件分支、循环追加）时更合适。

## 7 Functional Options 的变体

Go 生态中 Functional Options 有几种常见变体：

### 7.1 不返回 error 的 Option

```go
type Option func(*Server)    // gRPC 风格

func WithTimeout(d time.Duration) Option {
    return func(s *Server) {
        s.Timeout = d
    }
}
```

更简洁，但无法在 Option 内校验参数。适合参数总是合法的场景。

### 7.2 接口式 Option

```go
type Option interface {
    apply(*Server)
}

type timeoutOption struct{ d time.Duration }
func (o timeoutOption) apply(s *Server) { s.Timeout = o.d }

func WithTimeout(d time.Duration) Option {
    return timeoutOption{d: d}
}
```

gRPC 内部实际使用这种方式。优势是 Option 有具体类型，可以做类型断言和去重。劣势是代码量更大。

### 7.3 带默认值的 Option 组

```go
func WithProduction() Option {
    return func(s *Server) error {
        s.ReadTimeout = 30 * time.Second
        s.MaxConnections = 10000
        s.TLSEnabled = true
        return nil
    }
}

// 使用："生产环境预设 + 自定义覆盖"
NewServer("0.0.0.0", 443, WithProduction(), WithMaxConnections(20000))
```

将多个选项打包成一个"预设"，调用方可以在预设基础上覆盖个别参数。后面的 Option 覆盖前面的 — 顺序即优先级。

## 8 适用场景与局限

### 适用

- **服务器/客户端配置**：HTTP server、gRPC client、数据库连接池 — 有大量可选参数
- **SDK 构建**：公开 API 时，Functional Options 让调用方只关心需要的参数
- **测试构造**：用 Builder 或 Options 构建测试 fixture，比手写结构体更清晰
- **配置驱动**：Option 列表可以从配置文件动态生成
- **向后兼容**：新增 Option 不破坏已有调用方（无需修改函数签名）

### 局限

- **Builder 代码量大**：每个可选参数需要一个方法，参数多时 Builder 本身变得臃肿
- **Functional Options 学习成本**：对 Go 新手不直观，闭包 + 变长参数 + 高阶函数组合在一起有一定门槛
- **缺少编译期检查**：两种模式都无法在编译期强制"必须设置某个参数"（除非放在构造函数的普通参数中）
- **调试困难**：Functional Options 中出错时，堆栈指向闭包内部，不如结构体字段赋值直观
- **不适合简单对象**：如果只有 1-2 个参数，直接用构造函数参数即可，引入 Builder/Options 是过度设计
