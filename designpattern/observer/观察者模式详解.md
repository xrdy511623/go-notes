# 观察者模式详解

观察者模式（Observer Pattern）是最常用的行为型设计模式之一。它在对象之间建立**一对多**的依赖关系，当被观察者状态发生变化时，所有观察者自动收到通知。Go 语言的 interface + goroutine 为这一模式提供了天然的表达力。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

翻译：在对象之间定义一个一对多的依赖，当一个对象状态改变的时候，所有依赖的对象都会自动收到通知。

模式由三个角色组成：

```
┌──────────────┐   Subscribe(topic, obs)   ┌──────────────┐
│  Observer A   │ ────────────────────────→  │              │
└──────────────┘                             │   EventBus   │
┌──────────────┐   Subscribe(topic, obs)   │  (Subject)   │
│  Observer B   │ ────────────────────────→  │              │
└──────────────┘                             └──────┬───────┘
┌──────────────┐   Subscribe(topic, obs)            │
│  Observer C   │ ────────────────────────→          │
└──────────────┘                                     │
                                              Publish(event)
                                                     │
                                                     ▼
                                            通知所有已订阅的
                                              观察者
```

- **Subject（被观察者）**：维护观察者列表，提供订阅/取消订阅/通知方法
- **Observer（观察者）**：定义统一的回调接口，接收事件通知
- **Event（事件）**：携带 topic 和 payload，描述"发生了什么"

## 2 标准库与生态中的先例

观察者模式的思想在 Go 标准库和生态中广泛存在：

| 场景 | 机制 | 说明 |
|------|------|------|
| `sync.Cond` | `Broadcast()` / `Signal()` | 最底层的通知原语，唤醒等待的 goroutine |
| `context.Context` | 取消传播 | 父 context 取消时，所有子 context 自动收到通知 |
| `net/http` | `Handler` 注册 | 路由注册本质上是"URL 事件"到"处理器"的映射 |
| `fsnotify` | 文件系统事件 | 监听文件变化，通知订阅者 |
| `database/sql` | `DB.Stats()` / driver events | 连接池事件通知 |
| NATS / Kafka | Pub/Sub 消息队列 | 分布式场景下的观察者模式 |
| K8s Informer | Watch + Event Handler | 监听资源变化，通知多个 handler |

`sync.Cond` 是最直接的标准库等价物：

```go
cond := sync.NewCond(&sync.Mutex{})

// 观察者：等待通知
go func() {
    cond.L.Lock()
    cond.Wait()       // 阻塞，直到收到通知
    cond.L.Unlock()
    fmt.Println("got signal")
}()

// 被观察者：发出通知
cond.Broadcast()      // 唤醒所有等待者
```

但 `sync.Cond` 过于底层 — 没有 topic 区分、没有 payload 传递、无法动态增减观察者。本项目的 `EventBus` 提供了更实用的抽象。

## 3 本项目的实现

### 3.1 观察者接口与事件总线 — `eventbus/eventbus.go`

```go
// Event 表示系统中发生的一个事件。
type Event struct {
    Topic   string
    Payload interface{}
}

// Observer 是观察者接口。
type Observer interface {
    OnEvent(event Event)
    Name() string
}

// EventBus 是被观察者（Subject）。
type EventBus struct {
    mu        sync.RWMutex
    observers map[string][]Observer   // topic → 观察者列表
}
```

核心 API：

| 方法 | 作用 | 对标概念 |
|------|------|---------|
| `Subscribe(topic, obs)` | 注册观察者到指定 topic | Attach / AddListener |
| `Unsubscribe(topic, name)` | 按名称移除观察者 | Detach / RemoveListener |
| `Publish(event)` | 同步通知所有订阅者 | Notify / Emit |
| `PublishAsync(event)` | 并发通知，返回完成信号 | Go 特有的异步变体 |
| `Topics()` | 列出所有活跃 topic | 便于调试和监控 |
| `Observers(topic)` | 列出 topic 下的观察者名称 | 便于调试和监控 |

### 3.2 具体观察者 — 以日志观察者为例

```go
// logger/logger.go
package logger

type LogObserver struct {
    prefix string
}

func New(prefix string) *LogObserver {
    return &LogObserver{prefix: prefix}
}

func (l *LogObserver) OnEvent(event eventbus.Event) {
    fmt.Printf("[%s] topic=%s payload=%v\n", l.prefix, event.Topic, event.Payload)
}

func (l *LogObserver) Name() string {
    return "logger:" + l.prefix
}
```

要点：
- 实现 `Observer` 接口的两个方法即可接入
- `Name()` 返回唯一标识，用于管理订阅关系
- 结构体字段不导出 → 调用方必须通过 `New()` 构造

本项目提供了三个具体观察者，展示不同的关注点：

| 观察者 | 包 | 职责 |
|--------|------|------|
| `LogObserver` | `logger/` | 打印事件日志 |
| `MetricsObserver` | `metrics/` | 统计事件计数（原子操作，并发安全） |
| `NotifyObserver` | `notifier/` | 模拟发送通知（邮件/短信/Webhook） |

### 3.3 调用方

```go
import (
    "go-notes/designpattern/observer/eventbus"
    "go-notes/designpattern/observer/logger"
    "go-notes/designpattern/observer/metrics"
    "go-notes/designpattern/observer/notifier"
)

func main() {
    bus := eventbus.New()

    log := logger.New("APP")
    met := metrics.New("order")
    ntf := notifier.New("email")

    bus.Subscribe("order.created", log)
    bus.Subscribe("order.created", met)
    bus.Subscribe("order.created", ntf)

    // 发布事件 → 三个观察者都会收到通知
    bus.Publish(eventbus.Event{Topic: "order.created", Payload: "order-123"})

    // 取消通知观察者的订阅
    bus.Unsubscribe("order.created", ntf.Name())

    // 再次发布 → 只有 log 和 met 收到
    bus.Publish(eventbus.Event{Topic: "order.created", Payload: "order-456"})
}
```

调用方完全通过 `Observer` 接口操作，不需要知道具体观察者的实现细节。新增一种观察者只需实现接口并 `Subscribe`，无需修改 EventBus 或其他观察者。

## 4 设计决策解析

### 4.1 为什么 Subscribe 返回 error 而不是 panic？

```go
func (eb *EventBus) Subscribe(topic string, obs Observer) error {
    if topic == "" {
        return fmt.Errorf("eventbus: topic must not be empty")
    }
    ...
}
```

与注册工厂的 `Register` 不同，`Subscribe` 可能在运行时动态调用（而非仅在 `init()` 阶段）：

- topic 可能来自配置文件或用户输入
- 观察者可能在运行过程中动态加入/移除
- 调用方需要决定如何处理错误（重试、忽略、降级）

因此返回 `error` 比 `panic` 更合理。

### 4.2 为什么 Publish 使用快照模式？

```go
func (eb *EventBus) Publish(event Event) {
    eb.mu.RLock()
    snapshot := make([]Observer, len(eb.observers[event.Topic]))
    copy(snapshot, eb.observers[event.Topic])
    eb.mu.RUnlock()

    for _, obs := range snapshot {
        obs.OnEvent(event)     // 不持有锁
    }
}
```

如果在持有锁的情况下调用 `OnEvent`，而回调中又调用了 `Subscribe` 或 `Unsubscribe`，就会产生**死锁**。快照模式的流程：

1. 加读锁 → 复制观察者列表 → 释放锁
2. 遍历快照逐个通知（此时不持有任何锁）

这是观察者模式实现中的经典技巧，Java 的 `CopyOnWriteArrayList` 也是同一思路。

### 4.3 为什么用 RWMutex？

- `Subscribe` / `Unsubscribe` 是写操作（加写锁）
- `Publish` / `Topics` / `Observers` 是读操作（加读锁）
- 典型场景：订阅关系建立后很少变化，事件发布非常频繁 → **读多写少**

`sync.RWMutex` 允许多个 `Publish` 并发读取观察者列表，只在订阅变更时互斥。

### 4.4 为什么提供 PublishAsync？

```go
func (eb *EventBus) PublishAsync(event Event) <-chan struct{} {
    ...
    for _, obs := range snapshot {
        go func(o Observer) {
            defer wg.Done()
            o.OnEvent(event)
        }(obs)
    }
    ...
    return done
}
```

同步 `Publish` 的问题：如果某个观察者的 `OnEvent` 很慢（比如发送 HTTP 请求），会阻塞后续观察者的通知。`PublishAsync` 为每个观察者启动独立 goroutine，返回的 channel 在全部完成后关闭，调用方可以：

```go
<-bus.PublishAsync(event)   // 等待全部完成
```

或者 fire-and-forget：

```go
bus.PublishAsync(event)     // 不等待，继续执行
```

这是 Go 语言相比 Java/C++ 的天然优势 — goroutine 的创建成本极低，异步通知几乎是免费的。

### 4.5 Observer 为什么是 interface 而非 func？

Go 中单方法接口也可以用函数类型替代：

```go
type ObserverFunc func(Event)   // 替代方案
```

选择 interface 的理由：

- `Name()` 方法提供了管理能力（按名称取消订阅、列表展示）
- 观察者通常需要维护状态（如 `MetricsObserver` 的计数器）
- interface 更利于测试 — 可以用 mock 实现
- 如果只需要简单回调，可以封装一个 adapter

## 5 经典观察者 vs 发布订阅

虽然常被混为一谈，两者有本质区别：

```
经典观察者模式：
  Observer ←→ Subject
  （观察者直接知道被观察者，耦合较紧）

发布订阅模式：
  Publisher → Broker(EventBus) ← Subscriber
  （发布者和订阅者通过中间层解耦，互不知道对方）
```

| 维度 | 经典观察者 | 发布订阅 |
|------|-----------|---------|
| 耦合度 | 观察者持有 Subject 引用 | 发布者和订阅者完全解耦 |
| 通信方式 | Subject 直接调用 Observer | 通过 Broker / EventBus 中转 |
| 过滤机制 | 通常无（所有变化都通知） | 按 topic/channel 过滤 |
| 典型实现 | Java `Observable` | Redis Pub/Sub, Kafka, 本项目 |
| 适用规模 | 进程内少量观察者 | 进程内/跨进程大量订阅者 |

本项目的实现属于**发布订阅**变体（有 topic 过滤、通过 EventBus 中转），但核心思想与经典观察者一致。在 Go 社区中，两个术语经常交替使用。

## 6 Go channel 作为观察者模式的替代

Go channel 本身就是天然的通知机制，很多场景可以直接用 channel 替代观察者模式：

```go
// 最简单的 channel 观察者
type ChannelObserver struct {
    Ch chan Event
}

// 发布者向 channel 发送
for _, obs := range observers {
    obs.Ch <- event
}

// 订阅者从 channel 接收
for event := range obs.Ch {
    handle(event)
}
```

### 何时用 channel，何时用 Observer 接口？

| 维度 | channel | Observer 接口 |
|------|---------|-------------|
| 异步性 | 天然异步，自带缓冲 | 默认同步，需手动加 goroutine |
| 背压控制 | 缓冲区满时阻塞发送者 | 无内置背压 |
| 生命周期 | 需要手动 close | 无需管理 channel |
| 灵活性 | 固定的 send/recv 语义 | 回调内可做任意逻辑 |
| 适用场景 | 流式数据、生产者-消费者 | 事件通知、插件系统 |

本项目选择 Observer 接口，因为它更通用、更接近经典模式定义、更容易测试。在实际项目中，两者可以结合 — 用 channel 在 goroutine 间传递事件，用 Observer 接口做业务回调。

## 7 适用场景与局限

### 适用

- **事件驱动架构**：订单状态变化、用户行为事件、系统告警
- **插件系统**：核心框架发布事件，插件作为观察者响应
- **跨模块解耦**：模块 A 不直接调用模块 B，而是发布事件让 B 自行响应
- **日志/审计/监控**：作为观察者挂载，不侵入业务逻辑
- **GUI 框架**：按钮点击、输入变化等 UI 事件处理

### 局限

- **调试困难**：事件流是间接的，`Publish` 到 `OnEvent` 之间没有显式调用链，难以追踪
- **顺序不保证**：同步 `Publish` 按订阅顺序通知，但 `PublishAsync` 无法保证顺序
- **错误处理**：如果某个观察者的 `OnEvent` panic，会影响后续观察者（需加 recover）
- **内存泄漏**：忘记 `Unsubscribe` 会导致观察者无法被 GC 回收
- **级联风险**：观察者 A 收到事件后又发布新事件，可能形成事件风暴
