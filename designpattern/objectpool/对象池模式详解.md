# 对象池模式详解

对象池（Object Pool）是性能优化中最常用的创建型模式。在 Go 语言中，对象池有两种截然不同的形态：标准库的 `sync.Pool`（GC 感知的临时对象池）和以 `database/sql` 为代表的有界资源池。理解两者的区别，是写出高性能 Go 程序的基本功。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Manage a pool of reusable objects to avoid the cost of creating and destroying them repeatedly.

翻译：管理一组可重用的对象，避免反复创建和销毁的开销。

Go 中有两种对象池，解决完全不同的问题：

```
┌──────────────────────────────────────────────────────────┐
│           临时对象池（sync.Pool）                          │
│       目的：减少 GC 压力，降低分配频率                      │
├──────────────────────────────────────────────────────────┤
│                                                           │
│  • 无容量限制——按需创建，GC 时自动回收                      │
│  • 不保证持久性——每次 GC 都可能清空                         │
│  • 适合临时对象：bytes.Buffer、编解码器、临时切片            │
│  • 标准库典型：encoding/json、fmt、net/http 内部            │
│                                                           │
└──────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│           资源池（Connection / Worker Pool）               │
│       目的：复用昂贵资源，控制并发上限                       │
├──────────────────────────────────────────────────────────┤
│                                                           │
│  • 有界——固定容量，超出时阻塞或拒绝                         │
│  • 持久——资源不受 GC 影响，显式创建和销毁                    │
│  • 有生命周期——健康检查、空闲超时、优雅关闭                  │
│  • 标准库典型：database/sql.DB、net/http.Transport          │
│                                                           │
└──────────────────────────────────────────────────────────┘
```

一句话区分：**sync.Pool 管"便宜但频繁"的对象，资源池管"昂贵且有限"的资源**。

## 2 标准库与生态中的先例

### 2.1 sync.Pool — GC 感知的临时对象池

```go
var bufPool = sync.Pool{
    New: func() any {
        return new(bytes.Buffer)
    },
}

func process(data []byte) string {
    buf := bufPool.Get().(*bytes.Buffer)
    defer bufPool.Put(buf)
    buf.Reset()
    buf.Write(data)
    return buf.String()
}
```

sync.Pool 的核心语义：
- `Get()`：优先从本地缓存获取，没有则调用 `New` 创建
- `Put()`：归还对象到本地缓存
- 每次 GC 可能清空所有缓存的对象

标准库中大量使用 sync.Pool：

| 包 | 用途 | 池对象 |
|---|------|-------|
| `encoding/json` | JSON 编码 | `*encodeState`（内含 bytes.Buffer） |
| `fmt` | 格式化输出 | `*pp`（打印状态机） |
| `net/http` | 读写缓冲区 | `*bufio.Reader` / `*bufio.Writer` |
| `compress/gzip` | 压缩/解压 | `*Writer` |
| `regexp` | 正则匹配 | `*machine`（NFA 状态机） |
| `log/slog` | 结构化日志 | `*handleState` |

### 2.2 database/sql.DB — 连接池

`database/sql.DB` 是 Go 标准库中最经典的资源池实现：

```go
db, _ := sql.Open("mysql", "user:pass@tcp(127.0.0.1:3306)/mydb")

// 连接池配置
db.SetMaxOpenConns(25)       // 最大连接数（有界）
db.SetMaxIdleConns(10)       // 最大空闲连接数
db.SetConnMaxLifetime(5*time.Minute) // 连接最大存活时间
db.SetConnMaxIdleTime(1*time.Minute) // 空闲连接超时

rows, _ := db.Query("SELECT ...")  // 从池中获取连接
defer rows.Close()                  // 归还连接到池
```

db.Query 内部的流程：

```
Query() → 从空闲池取连接 → 执行 SQL → 归还连接
              ↓ 空闲池为空
         创建新连接（不超过 MaxOpenConns）
              ↓ 已达上限
         阻塞等待（connRequest 队列）
```

关键特性：有界（MaxOpenConns）、持久（连接不受 GC 影响）、有生命周期（Lifetime / IdleTime）、健康检查（PingContext）。

### 2.3 net/http.Transport — HTTP 连接池

```go
transport := &http.Transport{
    MaxIdleConns:        100,             // 全局最大空闲连接
    MaxIdleConnsPerHost: 10,              // 每个 host 最大空闲连接
    MaxConnsPerHost:     0,               // 每个 host 最大连接（0=无限）
    IdleConnTimeout:     90*time.Second,  // 空闲超时
}

client := &http.Client{Transport: transport}
resp, _ := client.Get("https://api.example.com/data")
defer resp.Body.Close()
```

Transport 内部维护了一个 `map[connectMethodKey][]*persistConn` 连接池，按 host+scheme+proxy 分桶管理 keep-alive 连接。每次请求优先复用空闲连接，没有时才建立新 TCP 连接。

### 2.4 valyala/bytebufferpool — 自适应 Buffer Pool

fasthttp 作者实现的 buffer pool，比直接使用 sync.Pool 更智能：

```go
var pool bytebufferpool.Pool

func handler(ctx *fasthttp.RequestCtx) {
    buf := pool.Get()
    defer pool.Put(buf)
    buf.WriteString("Hello, World!")
    ctx.SetBody(buf.Bytes())
}
```

核心创新：**自适应容量校准**。它统计 Put 回来的 buffer 大小分布，动态调整一个"合理大小"阈值，超过此阈值的 buffer 不回池——比硬编码 64KB 上限更精准。

### 2.5 valyala/fasthttp — Worker Pool

fasthttp 的高性能秘密之一是 workerPool：

```go
type workerPool struct {
    // 复用 workerChan 而非每次创建新 goroutine
    ready   []*workerChan
    // ...
}
```

每个连接不创建新 goroutine，而是从池中获取一个空闲 worker，处理完后归还。这避免了 goroutine 创建/销毁的开销，在高连接数场景下显著降低延迟。

### 2.6 panjf2000/ants — Goroutine Pool

Go 生态中最流行的 goroutine 池：

```go
pool, _ := ants.NewPool(1000)  // 最多 1000 个 goroutine
defer pool.Release()

pool.Submit(func() {
    // 任务在池中的 goroutine 上执行
})
```

特性：有界容量、非阻塞提交（可配置）、预分配 worker、优雅关闭。与本项目的 workerpool 是同一模式，但生产级实现更完善。

## 3 核心原理

### 3.1 sync.Pool 内部结构

sync.Pool 通过 per-P 分片 + victim cache 实现高性能：

```
       P0                  P1                  P2
  ┌──────────┐        ┌──────────┐        ┌──────────┐
  │ private  │        │ private  │        │ private  │
  │ (1 slot) │        │ (1 slot) │        │ (1 slot) │
  ├──────────┤        ├──────────┤        ├──────────┤
  │ shared   │        │ shared   │        │ shared   │
  │ (chain)  │◄─steal─│ (chain)  │◄─steal─│ (chain)  │
  └──────────┘        └──────────┘        └──────────┘

                      ┌──────────┐
                      │  victim  │  ← 上一轮 GC 的池
                      │  cache   │  ← 再一轮 GC 后清空
                      └──────────┘
```

**Get 路径**（从快到慢）：
1. 检查当前 P 的 private slot（无锁，最快）
2. 从当前 P 的 shared chain 弹出（CAS 操作）
3. 从其他 P 的 shared chain 偷取（work-stealing）
4. 从 victim cache 获取（上一轮 GC 留存的对象）
5. 调用 New 函数创建（最慢，涉及堆分配）

**Put 路径**：
1. 放入当前 P 的 private slot（如果为空）
2. 追加到当前 P 的 shared chain

**GC 时**：
1. 将当前所有 pool 降级为 victim cache
2. 清空上一轮的 victim cache
3. 结果：对象最多存活 **2 轮 GC**

### 3.2 临时对象池的生命周期

```
         ┌─────┐  pool.Get()  ┌──────┐  使用   ┌───────┐  pool.Put()  ┌─────┐
         │ Pool │────────────→│ 调用方 │───────→│ Reset │────────────→│ Pool │
         └─────┘              └──────┘         └───────┘             └─────┘
            │                                                           │
            │ New()                                              GC 可能回收
            ↓
    ┌───────────────┐
    │ 新对象（堆分配）│
    └───────────────┘
```

关键：Reset 是必须的。不 Reset 就 Put = 数据泄漏隐患（见 `trap/poolmisuse/`）。

### 3.3 资源池的生命周期

```
                ┌──────────────────────────────────────────────┐
                │              资源池（有界）                    │
   Submit()     │  ┌────┐ ┌────┐ ┌────┐ ... ┌────┐           │
  ────────────→ │  │ W1 │ │ W2 │ │ W3 │     │ Wn │           │
   或 Acquire() │  └────┘ └────┘ └────┘     └────┘           │
                │       ↑                                      │
                │       │ 空闲 worker 领取任务                  │
                │       │ 或 空闲连接被分配给请求                │
                │                                              │
                │  如果全忙 → 阻塞等待（背压 / backpressure）    │
                └──────────────────────────────────────────────┘
                                    │
                              Close() / Release()
                                    ↓
                         所有资源优雅释放，goroutine 退出
```

关键区别：资源池必须显式 Close，否则 goroutine/连接泄漏。sync.Pool 不需要 Close——GC 负责回收。

## 4 本项目的实现

### 4.1 BufferPool — sync.Pool 封装

展示 sync.Pool 的最佳实践——类型安全封装 + 防御性清理 + 超大对象丢弃：

```go
type Pool struct {
    pool sync.Pool
}

func New(initCap int) *Pool { ... }
func (p *Pool) Get() *bytes.Buffer { ... }
func (p *Pool) Put(buf *bytes.Buffer) { ... }
```

核心 API：

| 函数 | 作用 | 关键行为 |
|------|------|---------|
| `New(initCap)` | 创建池，指定 buffer 初始容量 | 预分配避免扩容 |
| `Get()` | 获取已重置的 buffer | **自动 Reset**，防止数据泄漏 |
| `Put(buf)` | 归还 buffer | 容量 > 64KB 的直接丢弃 |

Get 时 Reset 而非 Put 时 Reset，原因在 5.1 节解释。

使用方式：

```go
pool := bufferpool.New(512)

// 获取 → 使用 → 归还
buf := pool.Get()
buf.WriteString("request body")
data := buf.Bytes()
pool.Put(buf)
```

### 4.2 WorkerPool — 有界工作池

展示资源池模式——固定数量的常驻 goroutine 执行任务：

```go
type Pool struct {
    tasks chan func()
    wg    sync.WaitGroup
}

func New(size int) *Pool  { ... }
func (p *Pool) Submit(task func()) { ... }
func (p *Pool) Close()             { ... }
```

核心 API：

| 函数 | 作用 | 关键行为 |
|------|------|---------|
| `New(size)` | 创建 size 个 worker | goroutine 立即启动，从 channel 领取任务 |
| `Submit(task)` | 提交任务 | 全忙时**阻塞**（背压机制） |
| `Close()` | 关闭池 | 等待所有任务完成，所有 goroutine 退出 |

WorkerPool 与 sync.Pool 的对比：

| 维度 | sync.Pool (BufferPool) | WorkerPool |
|------|----------------------|------------|
| 管理对象 | 临时 buffer | 常驻 goroutine |
| 容量 | 无限（GC 自动调节） | 有限（创建时固定） |
| 持久性 | GC 可能清空 | 持久存在到 Close |
| 背压 | 无（总能 Get） | 有（全忙时 Submit 阻塞） |
| 关闭 | 不需要 | 必须 Close |

使用方式：

```go
pool := workerpool.New(4)

for i := range 100 {
    pool.Submit(func() {
        processItem(i)
    })
}

pool.Close()  // 等待所有任务完成
```

### 4.3 反面示例 — `trap/poolmisuse/`

四种最常见的 sync.Pool 误用：

**❌ 误用 1：存值类型而非指针**

```go
pool := sync.Pool{
    New: func() any { return bytes.Buffer{} },  // ❌ 值类型
}
buf := pool.Get().(bytes.Buffer)  // interface{} 装箱 → 堆分配
pool.Put(buf)                      // 再次装箱 → 堆分配
```

每次 Get/Put 都涉及 interface{} 装箱拷贝，完全抵消了对象池的意义。应存 `*bytes.Buffer`。

**❌ 误用 2：依赖 Pool 在 GC 后保持对象**

```go
for range 10 { pool.Put(new(bytes.Buffer)) }
runtime.GC()
runtime.GC()
// 池已清空——所有对象被回收
```

两轮 GC 后 sync.Pool 完全清空。不能用它管理需要持久化的资源。

**❌ 误用 3：归还脏对象**

```go
buf.WriteString("secret-token")
pool.Put(buf)  // ❌ 没有 Reset
// 下一个 Get 拿到的 buffer 包含 "secret-token"
```

数据泄漏风险。正确做法：Get 时 Reset（防御性）或 Put 前 Reset。

**❌ 误用 4：用 sync.Pool 做连接池**

```go
pool := sync.Pool{New: func() any { return openDBConn() }}
conn := pool.Get().(*DBConn)
pool.Put(conn)
runtime.GC()  // 连接被回收，但没有 Close！资源泄漏
```

sync.Pool 没有 Close 回调、没有容量上限、没有健康检查——这些都是连接池的刚需。用 `database/sql.DB` 或自定义资源池。

## 5 设计决策解析

### 5.1 为什么 Get 时 Reset 而非 Put 时？

```go
// 方案 A：Get 时 Reset（本项目选择）
func (p *Pool) Get() *bytes.Buffer {
    buf := p.pool.Get().(*bytes.Buffer)
    buf.Reset()  // ← 防御性清理
    return buf
}

// 方案 B：Put 时 Reset
func (p *Pool) Put(buf *bytes.Buffer) {
    buf.Reset()
    p.pool.Put(buf)
}
```

选择方案 A 的理由：

| 维度 | Get 时 Reset | Put 时 Reset |
|------|-------------|-------------|
| 安全性 | ✅ 即使调用方忘记 Reset 也安全 | ❌ 依赖调用方规范 |
| 浪费的 Reset | 无——每个 Get 出来的都会被使用 | 有——GC 回收的对象白 Reset 了 |
| 数据泄漏 | 不可能 | Put 前若忘记，数据泄漏 |

**防御性编程优先**。标准库 `encoding/json` 也采用 Get 时重置的策略。

### 5.2 为什么丢弃超大 Buffer？

```go
func (p *Pool) Put(buf *bytes.Buffer) {
    if buf.Cap() > 64<<10 {  // > 64KB
        return  // 丢弃，让 GC 回收
    }
    p.pool.Put(buf)
}
```

场景：一个 HTTP 服务器通常处理 1-10KB 的请求，但偶尔有一个 10MB 的文件上传请求。如果不丢弃，这个 10MB 的 buffer 会常驻池中，被下一个 1KB 的请求取出——浪费 ~10MB 内存。

这在长时间运行的服务中会导致**内存膨胀**：池中最大的 buffer 决定了常驻内存的下限。

生产级方案参考：
- 硬编码阈值（本项目：64KB，简单可靠）
- 统计校准（valyala/bytebufferpool：根据使用分布动态调整阈值）
- 分级池（小/中/大 buffer 使用不同的池）

### 5.3 为什么 WorkerPool 用 channel 而非 sync.Pool？

```go
// WorkerPool：channel 分发任务
tasks: make(chan func())

// 如果用 sync.Pool？
pool := sync.Pool{New: func() any { go worker(); return <-ready }}  // ❌ 荒谬
```

sync.Pool 管理的是**无状态的可替换对象**——buffer A 和 buffer B 完全等价，取到哪个都行。

WorkerPool 管理的是**有状态的持久资源**——goroutine 需要持续运行、需要被调度、需要优雅关闭。这不是 sync.Pool 能解决的问题。

更本质的区别：
- sync.Pool 是**被动的**——调用方 Get 时才可能创建对象
- WorkerPool 是**主动的**——worker goroutine 持续运行，主动从 channel 拉取任务

### 5.4 sync.Pool 适合什么、不适合什么？

| ✅ 适合 | ❌ 不适合 |
|---------|----------|
| 高频创建/销毁的临时对象 | 需要持久化的资源（连接、文件句柄） |
| 无状态或可轻松重置的对象 | 有复杂生命周期的资源（需要 Close） |
| 分配开销大于 Get/Put 开销的对象 | 需要容量上限的场景 |
| 并发环境下的缓冲区复用 | 需要健康检查的资源 |

经验法则：如果你需要调用 `Close()` 或控制数量，就不要用 `sync.Pool`。

### 5.5 WorkerPool 为什么用无缓冲 channel？

```go
tasks: make(chan func())  // 无缓冲
```

无缓冲 channel 的语义：Submit 直到有 worker 取走任务才返回。这意味着：

- **精确背压**：Submit 阻塞 = 所有 worker 都在忙 = 调用方自然减速
- **公平调度**：没有排队，先到先得
- **可预测延迟**：任务不会在缓冲区中等待不确定时间

如果改为 `make(chan func(), size)` 有缓冲：
- Submit 不阻塞（只要缓冲区未满）
- 允许突发流量暂存在缓冲区
- 但延迟不可预测——缓冲区深的任务可能等很久

无缓冲是最安全的默认选择。如果需要应对突发流量，可以加缓冲区，但要谨慎设置大小。

### 5.6 为什么 database/sql 不用 sync.Pool？

`database/sql.DB` 完全不使用 `sync.Pool`，而是自己维护一个 `freeConn []*driverConn` 切片 + `connRequests map[uint64]chan connRequest` 等待队列：

| 需求 | sync.Pool | database/sql |
|------|-----------|-------------|
| 最大连接数限制 | ❌ 无上限 | ✅ `MaxOpenConns` |
| 空闲连接回收 | ❌ GC 随机清空 | ✅ `ConnMaxIdleTime` |
| 连接存活时间 | ❌ 无概念 | ✅ `ConnMaxLifetime` |
| 健康检查 | ❌ 无 | ✅ `PingContext` |
| 优雅关闭 | ❌ 无 Close | ✅ `db.Close()` 关闭所有连接 |
| 等待队列 | ❌ 无 | ✅ `connRequests` FIFO 队列 |

这就是为什么资源池需要专门实现，不能用 sync.Pool 凑合。

## 6 适用场景与局限

### 适用

- **HTTP 处理链中的缓冲区**：请求/响应序列化、压缩/解压、日志格式化——高频、短生命周期
- **编解码器复用**：JSON/Protobuf/MessagePack 的编解码状态——分配一次，Reset 后复用
- **数据库连接池**：`database/sql.DB`——昂贵资源的有界管理
- **HTTP 客户端连接池**：`http.Transport`——TCP keep-alive 连接复用
- **Goroutine 池**：限制并发 goroutine 数量，避免 OOM 和调度开销
- **正则匹配状态机**：`regexp` 包内部——NFA 状态机分配昂贵，Pool 复用效果显著

### 局限

- **sync.Pool 不保证复用**：GC 后池可能为空，不能假设 Get 总返回旧对象
- **sync.Pool 不适合昂贵资源**：连接、文件句柄需要生命周期管理，sync.Pool 做不到
- **对象必须可重置**：如果 Reset 成本接近创建成本（如深拷贝复杂对象），Pool 无意义
- **过早优化陷阱**：先用 pprof 确认分配是瓶颈，再引入 Pool。盲目池化增加代码复杂度
- **WorkerPool 容量设置难**：过少 → 吞吐不够，过多 → 浪费资源。需要压测确定
- **竞态风险**：归还后继续使用对象 = use-after-free 的 Go 版本。Pool 不防止此类 bug

## 7 所有权与归还契约

对象池最危险的 bug 是**使用已归还的对象**（use-after-put）：

```go
buf := pool.Get()
pool.Put(buf)     // 归还
buf.WriteString("oops") // ❌ buf 可能已被另一个 goroutine Get 走并使用
```

Go 没有编译期的所有权检查（不像 Rust 的 borrow checker），归还契约只能靠**编码规范**保证：

1. **Put 后立即将变量置为 nil**

```go
buf := pool.Get()
defer func() { pool.Put(buf); buf = nil }()
```

2. **用 defer 确保归还**

```go
buf := pool.Get()
defer pool.Put(buf)
// 使用 buf...
```

3. **不要将池对象传递给异步操作**

```go
buf := pool.Get()
go processAsync(buf) // ❌ goroutine 结束时间不确定，何时 Put？
pool.Put(buf)        // ❌ processAsync 可能还在使用
```

### 什么时候 pool 会让程序更慢

| 场景 | 原因 | 建议 |
|------|------|------|
| 对象创建极便宜（如小 struct） | Get/Put 的 overhead > 创建成本 | 直接 new |
| 池对象很少被复用（GC 频繁清空） | sync.Pool 每轮 GC 可能清空 | 检查 pool miss 率 |
| 高竞争（大量 goroutine 竞争同一 P） | 跨 P steal 开销 | 考虑分片或 per-goroutine 缓存 |
| Reset 成本接近创建成本 | 池复用无意义 | 直接创建新对象 |

**度量方法**：先跑 benchmark 对比 Pool vs 无 Pool 的 `allocs/op`，确认分配确实减少了再使用。

## 8 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| Get 返回可用对象 | Get 后 buffer 已 Reset，长度为 0 |
| Put + Get 复用 | Put 后再 Get 可能拿到同一对象（不保证） |
| 超大 buffer 丢弃 | 容量 > 64KB 的 buffer Put 后被丢弃 |
| 并发安全 | 多 goroutine 同时 Get/Put 不 race |
| WorkerPool 全量执行 | 提交 N 个任务后全部执行完成 |
| WorkerPool 并发上限 | 同时运行的任务不超过 pool size |
| WorkerPool 关闭 | Close 后所有 worker 退出 |
| GC 后 Pool 可用 | runtime.GC() 后 Get 仍返回有效对象（通过 New） |

## 9 成本模型

### 何时值得用 sync.Pool

- 对象分配频繁且分配开销 > Get/Put 开销
- pprof 显示 `allocs/op` 或 GC 压力是瓶颈
- 对象可以安全 Reset 后复用

### 何时值得用 WorkerPool

- 需要限制并发 goroutine 数量
- 需要背压（Submit 在全忙时阻塞）
- 需要优雅关闭（等待所有任务完成）

### 何时是过度设计

- 对象创建便宜——Pool 的 overhead 反而更大
- 没有 pprof 证据表明分配是瓶颈——过早优化
- goroutine 数量本身就不多——不需要 Pool 来限制
