# 舱壁模式详解

舱壁模式（Bulkhead Pattern）是一种弹性设计模式，灵感来自船舶的水密隔舱：即使一个隔舱进水，其他隔舱不受影响，船不会沉没。在软件中，舱壁将资源池隔离开来，防止一个故障依赖耗尽所有共享资源，拖垮整个系统。

---

## 1 模式定义

核心思想：**为不同的下游依赖分配独立的资源池**，使故障隔离在单个池中。

```
                    ┌─────────────────────────────┐
                    │         Application          │
                    │                              │
  Request ─────────→│  ┌──────────────────────┐   │
  (Service A)       │  │  Bulkhead A (max=10)  │──→│──→ Service A (slow!)
                    │  │  [■■■■■■■■■■] FULL    │   │
                    │  └──────────────────────┘   │
                    │                              │
  Request ─────────→│  ┌──────────────────────┐   │
  (Service B)       │  │  Bulkhead B (max=5)   │──→│──→ Service B (healthy)
                    │  │  [■■□□□] 2/5          │   │
                    │  └──────────────────────┘   │
                    │                              │
                    └─────────────────────────────┘
```

**关键效果**：Service A 变慢导致 Bulkhead A 的 10 个令牌全部被占用，但 Bulkhead B 不受影响，Service B 的请求正常处理。如果没有隔离，所有请求共享同一个线程/goroutine 池，慢 Service A 会耗尽所有资源。

两种常见实现：

| 方式 | 机制 | 特点 |
|------|------|------|
| **信号量舱壁** | 用计数信号量限制并发数 | 轻量，无额外 goroutine 开销 |
| **工作池舱壁** | 固定大小的 goroutine 池 + 任务队列 | 内存可预测，天然限制 goroutine 数 |

## 2 标准库与生态中的先例

Go 标准库和生态中多处体现了资源隔离的思想：

| 场景 | 机制 | 说明 |
|------|------|------|
| `database/sql.DB.SetMaxOpenConns` | 连接池大小限制 | 防止单个数据库连接耗尽所有 fd |
| `net/http.Transport.MaxIdleConnsPerHost` | 每个 host 的连接数限制 | 隔离不同下游服务的连接使用 |
| `net/http.Server.MaxHeaderBytes` | 请求头大小限制 | 防止恶意大请求耗尽内存 |
| `golang.org/x/sync/semaphore` | 加权信号量 | 标准库扩展的通用并发限制 |
| `golang.org/x/sync/errgroup.SetLimit` | 有界并发 | 限制 errgroup 中的并发 goroutine 数 |
| Netflix Hystrix / resilience4j | 线程池 / 信号量隔离 | JVM 生态的经典舱壁实现 |
| `github.com/sony/gobreaker` | 熔断器 | 常与舱壁组合使用 |

`database/sql` 是最直接的先例 —— `SetMaxOpenConns(10)` 本质上就是一个信号量舱壁：最多 10 个并发查询，超出的请求排队等待。

```go
db, _ := sql.Open("mysql", dsn)
db.SetMaxOpenConns(10)   // 信号量舱壁：最多 10 个并发连接
db.SetMaxIdleConns(5)    // 空闲连接池
```

## 3 本项目的实现

### 3.1 信号量舱壁 — `semaphore/semaphore.go`

```go
type Bulkhead struct {
    name    string
    sem     chan struct{}     // buffered channel 作信号量
    timeout time.Duration
}

func (b *Bulkhead) Execute(ctx context.Context,
    fn func(ctx context.Context) error) error {
    // 1. 尝试获取令牌（向 channel 发送）
    // 2. 满了就等待 timeout 或 ctx 取消
    // 3. 获取成功 → 执行 fn → defer 释放令牌（从 channel 接收）
}
```

核心 API：

| 方法 | 作用 |
|------|------|
| `New(name, max, timeout)` | 创建舱壁，指定名称、最大并发、等待超时 |
| `Execute(ctx, fn)` | 在舱壁保护下执行函数 |
| `ActiveCount()` | 当前正在执行的请求数 |
| `MaxConcurrent()` | 最大并发数 |

### 3.2 工作池舱壁 — `pool/pool.go`

```go
type WorkerPool struct {
    tasks chan func()     // 任务队列
    quit  chan struct{}
    wg    sync.WaitGroup
}

func NewWorkerPool(workers, queueSize int) *WorkerPool {
    // 启动 workers 个 goroutine，从 tasks channel 消费任务
}
```

| 方法 | 作用 |
|------|------|
| `NewWorkerPool(workers, queueSize)` | 创建并启动工作池 |
| `Submit(fn)` | 提交任务，队列满时阻塞 |
| `TrySubmit(fn)` | 尝试提交，队列满时立即返回 false |
| `Shutdown()` | 优雅关闭，等待已提交任务完成 |

### 3.3 两种实现的对比

| 维度 | 信号量舱壁 | 工作池舱壁 |
|------|-----------|-----------|
| goroutine 开销 | 调用方的 goroutine，无额外创建 | 预创建固定数量的 goroutine |
| 内存模型 | 按需使用 | 固定占用 |
| 任务排队 | 通过 timeout 控制等待 | 通过 queueSize 控制缓冲 |
| 超时控制 | 内置 timeout + context | 需要调用方自行处理 |
| 适合场景 | 已有 goroutine 的场景（如 HTTP handler） | 需要控制 goroutine 总量的场景 |

### 3.4 调用方

```go
import "go-notes/designpattern/bulkhead/semaphore"

// 为不同下游创建独立舱壁
orderBH := semaphore.New("order-service", 10, 200*time.Millisecond)
payBH   := semaphore.New("payment-service", 5, 500*time.Millisecond)

// HTTP handler 中使用
func handleCheckout(w http.ResponseWriter, r *http.Request) {
    err := orderBH.Execute(r.Context(), func(ctx context.Context) error {
        return callOrderService(ctx, orderID)
    })
    if errors.Is(err, semaphore.ErrBulkheadFull) {
        http.Error(w, "order service busy", http.StatusServiceUnavailable)
        return
    }
}
```

## 4 设计决策解析

### 4.1 为什么用 buffered channel 而不是 `golang.org/x/sync/semaphore`？

```go
sem := make(chan struct{}, maxConcurrent)   // ✅ 本项目
sem := semaphore.NewWeighted(int64(max))    // ❌ 未选择
```

理由：
- 本项目只需要**等权重**的令牌（每个请求占 1 个），无需加权信号量
- buffered channel 是 Go 标准库的一部分，无外部依赖
- channel + select 的超时和取消语义天然与 Go 的并发模型契合
- `x/sync/semaphore` 的 API 更复杂（`Acquire` 返回 error，需要显式 `Release`）

如果需要**加权**并发控制（如大请求占 3 个令牌，小请求占 1 个），则应使用 `x/sync/semaphore`。

### 4.2 为什么 Execute 内置 timeout 而不只依赖 context？

```go
func New(name string, maxConcurrent int, timeout time.Duration) *Bulkhead
```

两个理由：
- **语义明确**：timeout 表达的是"等待令牌的超时"，而非"整个操作的超时"
- **使用便利**：调用方传入的 ctx 通常是请求级的（包含整个请求的 deadline），而令牌等待超时是舱壁策略的一部分，应该在创建时就固定下来

`Execute` 同时尊重 timeout 和 ctx.Done()，取较先到达者。

### 4.3 为什么 panic 后仍需释放令牌？

```go
func (b *Bulkhead) Execute(ctx context.Context, fn func(...) error) error {
    b.acquire(ctx)
    defer b.release()   // ← 即使 fn panic，defer 仍然执行
    return fn(ctx)
}
```

如果 `fn` panic 但令牌未释放，该令牌就**永久丢失**。随着 panic 累积，可用令牌逐渐减少，最终舱壁完全堵死。`defer` 保证了无论 fn 正常返回、返回错误还是 panic，令牌都会归还。

注意：`Execute` 本身不 recover panic —— 它只保证令牌释放。panic 的恢复应由调用方（如 HTTP middleware）负责。

### 4.4 为什么 WorkerPool 使用固定 goroutine 而不是按需创建？

固定 goroutine 池的优势：
- **内存可预测**：10 个 worker = ~80KB 栈内存（每个 goroutine 初始 8KB），不会因流量波动而变化
- **无 goroutine 泄漏风险**：goroutine 数量固定，不可能失控增长
- **GC 压力稳定**：不会因为大量 goroutine 创建/销毁导致 GC 抖动

### 4.5 acquire 的两阶段 select

```go
func (b *Bulkhead) acquire(ctx context.Context) error {
    select {
    case b.sem <- struct{}{}:
        return nil      // 快速路径：直接获取
    default:
    }
    // 慢路径：等待 timeout 或 ctx
    timer := time.NewTimer(b.timeout)
    defer timer.Stop()
    select { ... }
}
```

第一个 select 是无阻塞尝试（快速路径），避免了大多数情况下创建 timer 的开销。只有在令牌不可用时才进入慢路径。

## 5 与相近模式的对比

| 维度 | 舱壁（Bulkhead） | 限流器（Rate Limiter） | 熔断器（Circuit Breaker） | 对象池（Object Pool） |
|------|----------------|---------------------|------------------------|---------------------|
| **防什么** | 资源耗尽 | 过高吞吐 | 故障扩散 | 创建成本 |
| **控制对象** | 并发请求数 | 单位时间请求数 | 失败率 | 可复用对象数 |
| **机制** | 信号量 / 固定池 | 令牌桶 / 滑动窗口 | 状态机（closed/open/half-open） | 借出 / 归还 |
| **有状态** | 无（计数器） | 有（令牌/窗口） | 有（failure count, state） | 有（pool） |
| **拒绝策略** | 等待超时 → reject | 立即 reject | open 时 reject | 等待 / 创建新对象 |
| **组合方式** | 常与熔断器组合 | 独立使用 | 常与舱壁组合 | 独立使用 |

典型的弹性链路：

```
Request → Rate Limiter → Bulkhead → Circuit Breaker → Downstream
          (限制吞吐)     (隔离资源)   (检测故障)        (实际调用)
```

- **舱壁**回答：同一时间最多几个请求并发访问这个依赖？
- **限流器**回答：每秒最多允许几个请求？
- **熔断器**回答：这个依赖是否已经挂了，要不要短路？

## 6 常见陷阱 / 反例

### 6.1 无限制 goroutine 派生（参考 `trap/unboundedspawn/`）

```go
func (h *BadHandler) Handle(req Request) {
    go processRequest(req)   // ❌ 无并发上限
}
```

问题链：
1. 流量突增 → goroutine 数量暴涨
2. 下游变慢 → goroutine 阻塞堆积
3. 内存耗尽 → OOM → 进程被 kill

### 6.2 所有依赖共享同一个舱壁

```go
shared := semaphore.New("shared", 20, timeout)

// ❌ Service A 和 B 共享舱壁，没有隔离效果
shared.Execute(ctx, callServiceA)
shared.Execute(ctx, callServiceB)
```

这违背了舱壁的核心价值 —— **隔离**。正确做法是每个依赖独立舱壁。

### 6.3 舱壁容量设置过小

```go
bh := semaphore.New("order", 1, timeout)   // ❌ 只允许 1 个并发
```

容量过小会导致大量合理请求被拒绝。需要通过**负载测试**来确定合适的容量：

- 观察下游的 P99 延迟和吞吐
- 容量 ≈ 期望吞吐 × P99 延迟（Little's Law）
- 留 20-30% 余量应对突发

### 6.4 舱壁没有超时

```go
bh := semaphore.New("order", 10, 0)   // ❌ timeout=0，永不超时
```

如果下游完全挂死，所有 10 个令牌被永久占用，后续请求永远等待。必须设置合理的超时。

### 6.5 不处理 ErrBulkheadFull

```go
err := bh.Execute(ctx, callDownstream)
if err != nil {
    log.Println(err)   // ❌ 只是打了个日志，没有给调用方反馈
}
```

正确做法：返回 503 Service Unavailable 或触发降级逻辑。

## 7 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| 正常执行 | fn 被调用，返回 nil |
| 并发上限 | max+1 个并发请求时，最后一个返回 ErrBulkheadFull |
| context 取消 | 等待令牌时 ctx 取消，返回 context.Canceled |
| fn 错误传播 | fn 返回的 error 被 Execute 原样返回 |
| panic 恢复 | fn panic 后令牌仍然归还，后续请求可正常执行 |
| ActiveCount | 并发执行时计数准确，完成后归零 |
| 令牌复用 | 串行执行多次，每次都能获取令牌 |
| 超时等待 | timeout 到期后返回 ErrBulkheadFull，耗时符合预期 |
| 并发安全 | 大量 goroutine 同时 Execute 不 panic |

## 8 成本模型

### 何时值得使用舱壁

- **调用多个下游服务**，各服务有不同的 SLA 和可靠性
- **需要故障隔离**：一个慢/挂的服务不能拖垮其他服务
- **流量不可预测**：无法保证请求速率恒定
- **已经遇到**资源耗尽导致的级联故障

### 何时是过度设计

- **只有一个下游服务**：无需隔离，用限流器即可
- **已有限流器**：且下游故障不会阻塞（如快速失败）
- **低流量系统**：并发请求永远不超过 5 个，舱壁是多余的
- **无状态计算**：纯 CPU 计算不占用外部资源，用 `errgroup.SetLimit` 更简单

### 性能考量

- 信号量舱壁的获取/释放开销：channel send/recv ≈ 50-100ns
- 快速路径（令牌可用时）不创建 timer，接近零开销
- WorkerPool 的固定 goroutine 开销：每个 worker ~8KB 栈内存
- 对比业务逻辑的网络 IO（通常 1-100ms），舱壁开销可以忽略

## 9 适用场景与局限

### 适用场景

| 场景 | 舱壁配置建议 |
|------|------------|
| 微服务间调用 | 每个下游服务一个独立舱壁 |
| 数据库访问 | 与 `sql.DB.SetMaxOpenConns` 配合使用 |
| 第三方 API | 根据 API 限额和 SLA 设置容量 |
| 文件 I/O | 限制并发磁盘操作，避免 I/O 拥塞 |
| 消息队列消费 | 控制消费者并发数，避免下游过载 |

### 局限

- **增加延迟**：排队等待令牌引入额外延迟
- **容量难调优**：需要负载测试和持续监控来确定最佳值
- **不解决根因**：舱壁只是隔离故障，不修复下游问题
- **静态配置**：本实现的容量在创建时固定，无法动态调整（生产环境可考虑结合配置中心）
- **无优先级**：所有请求平等竞争令牌，重要请求可能被拒
