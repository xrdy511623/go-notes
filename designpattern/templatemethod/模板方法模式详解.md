# 模板方法模式详解

模板方法模式（Template Method Pattern）是最古老的行为型设计模式之一。它在一个方法中定义**算法的骨架**，将某些步骤延迟到子类（Go 中是接口实现者）中。模板方法使得子类可以在不改变算法结构的情况下，重新定义算法的某些步骤。

Go 没有继承，因此经典的"抽象基类 + 子类覆写"模式无法直接使用。但 Go 的 **interface + 自由函数** 天然提供了更优雅的模板方法实现——本文将这种方式称为「Go 式模板方法」。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Define the skeleton of an algorithm in an operation, deferring some steps to subclasses.

翻译：在一个操作中定义算法的骨架，将某些步骤延迟到子类中实现。

经典模板方法（Java/C++）vs Go 式模板方法：

```
经典模板方法（继承）：                    Go 式模板方法（组合）：

┌────────────────────┐               ┌──────────────┐     ┌───────────────┐
│  AbstractClass     │               │  «interface»  │     │  Export()      │
│ ─────────────────  │               │  Exporter     │     │  （模板函数）   │
│ + templateMethod() │←── 继承 ──     │ ─────────────  │←──  │  固定算法骨架  │
│ # step1()  abstract│               │ + Header()    │     └───────────────┘
│ # step2()  abstract│               │ + FormatRecord│
└────────┬───────────┘               │ + Footer()    │
         │                           └──────┬────────┘
    ┌────┴────┐                              │
    │ Concrete │                    ┌────────┼────────┐
    │ Class    │                    │        │        │
    └─────────┘                  CSV      JSON   Markdown
```

Go 式的优势：
- **无继承耦合**：实现者不需要知道模板函数的存在
- **可测试**：接口天然可 mock
- **可组合**：同一个 Exporter 可以被不同的模板函数使用
- **零成本抽象**：接口方法调用通过 itab 间接调用，与虚函数等价

## 2 标准库与生态中的先例

Go 标准库中模板方法无处不在——只是因为没有"继承"语法，很少有人意识到它们：

| 场景 | 接口（可变步骤） | 模板函数（固定骨架） | 说明 |
|------|-----------------|-------------------|------|
| `sort.Sort` | `sort.Interface`（Len/Less/Swap） | 快速排序 + 插入排序 | 最经典的 Go 式模板方法 |
| `encoding/json` | `json.Marshaler` / `json.Unmarshaler` | Marshal/Unmarshal 算法 | 序列化骨架固定，格式化步骤可定制 |
| `encoding/binary` | `io.Reader` / `io.Writer` | `binary.Read` / `binary.Write` | 二进制编解码的固定流程 |
| `database/sql` | `driver.Driver` / `driver.Conn` | `sql.DB` 连接管理算法 | 连接池 + 事务管理的固定流程 |
| `net/http` | `http.Handler` | `http.Server.Serve` | 请求处理的固定骨架（accept → read → handle → write） |
| `testing` | `*testing.T` 的 test 函数 | `go test` 运行器 | 测试发现 → 执行 → 报告的固定流程 |
| `hash` | `hash.Hash`（Write/Sum/Reset） | 调用方的 hash 计算流程 | 哈希算法可变，使用方式固定 |

### 2.1 sort.Sort — 最经典的 Go 式模板方法

```go
// 接口定义可变步骤
type Interface interface {
    Len() int
    Less(i, j int) bool
    Swap(i, j int)
}

// sort.Sort 是模板函数：算法骨架固定，步骤由 Interface 提供
func Sort(data Interface) {
    // 固定的排序算法（快排 + 插入排序 + 堆排序混合）
    // 内部调用 data.Len()、data.Less()、data.Swap()
}
```

使用时只需实现接口：

```go
type ByAge []Person

func (a ByAge) Len() int           { return len(a) }
func (a ByAge) Less(i, j int) bool { return a[i].Age < a[j].Age }
func (a ByAge) Swap(i, j int)      { a[i], a[j] = a[j], a[i] }

sort.Sort(ByAge(people)) // 固定算法 + 自定义比较
```

注意：Go 1.21 引入的 `slices.SortFunc` 使用函数参数替代接口，这是模板方法的"函数变体"：

```go
slices.SortFunc(people, func(a, b Person) int {
    return cmp.Compare(a.Age, b.Age)
})
```

### 2.2 encoding 系列 — 序列化的模板方法

```go
// encoding/json 的模板方法：
// Marshal 是固定算法（遍历字段 → 序列化 → 输出 JSON）
// 如果类型实现了 json.Marshaler，使用自定义序列化步骤
type Marshaler interface {
    MarshalJSON() ([]byte, error)
}

// encoding.TextMarshaler 更通用：
type TextMarshaler interface {
    MarshalText() (text []byte, err error)
}
```

标准库的 `encoding/json`、`encoding/xml`、`encoding/gob` 都遵循同一模式：
1. **固定骨架**：遍历结构体字段、处理嵌套、输出格式
2. **可变步骤**：如果类型实现了 `Marshaler` 接口，使用自定义逻辑

## 3 Go 式模板方法的三种变体

Go 没有继承，但有三种方式实现模板方法。选择哪种取决于"步骤"的复杂度：

### 变体 1：接口 + 自由函数（推荐）

```go
type Exporter interface {
    Header(columns []string) ([]byte, error)
    FormatRecord(index int, record Record, columns []string) ([]byte, error)
    Footer(totalRecords int) ([]byte, error)
}

func Export(e Exporter, columns []string, records []Record) ([]byte, error) {
    // 固定骨架：Header → FormatRecord × N → Footer
}
```

适用：步骤有多个方法、实现者需要维护状态、有多种实现。这是 `sort.Sort` 的方式。

### 变体 2：函数字段结构体

```go
type ExportFunc struct {
    HeaderFn func(columns []string) ([]byte, error)
    RecordFn func(index int, record Record, columns []string) ([]byte, error)
    FooterFn func(totalRecords int) ([]byte, error)
}
```

适用：一次性使用、测试场景、步骤之间无共享状态。类似 `http.Server` 的 `Handler` 字段。

### 变体 3：高阶函数

```go
func Export(
    columns []string, records []Record,
    header func([]string) []byte,
    format func(int, Record, []string) []byte,
    footer func(int) []byte,
) []byte { ... }
```

适用：步骤只有一个、最轻量、不需要接口。这是 `slices.SortFunc` 的方式。

### 三种变体的对比

| 维度 | 接口 + 函数 | 函数字段结构体 | 高阶函数 |
|------|-----------|-------------|---------|
| 适合步骤数 | 多个 | 多个 | 1-2 个 |
| 可测试性 | ✅ mock 接口 | ✅ 替换字段 | ✅ 传入 stub |
| 类型安全 | ✅ 编译期检查 | ⚠️ nil 字段需防御 | ✅ 编译期检查 |
| 可复用性 | ✅ 具名类型可复用 | ⚠️ 通常一次性 | ⚠️ 通常一次性 |
| 标准库代表 | `sort.Sort` | `http.Server` | `slices.SortFunc` |

## 4 本项目的实现

### 4.1 核心接口与模板函数 — `export/export.go`

```go
type Exporter interface {
    Header(columns []string) ([]byte, error)
    FormatRecord(index int, record Record, columns []string) ([]byte, error)
    Footer(totalRecords int) ([]byte, error)
}

func Export(e Exporter, columns []string, records []Record) ([]byte, error) {
    // 1. Header
    header, err := e.Header(columns)
    buf.Write(header)

    // 2. FormatRecord × N
    for i, rec := range records {
        line, err := e.FormatRecord(i, rec, columns)
        buf.Write(line)
    }

    // 3. Footer
    footer, err := e.Footer(len(records))
    buf.Write(footer)

    return buf.Bytes(), nil
}
```

核心要点：
- `Export()` 是模板函数——定义固定的 Header → Records → Footer 骨架
- `Exporter` 接口定义三个可变步骤
- `index` 参数传递上下文信息（JSON 导出用它处理逗号分隔）

同时提供 `ExportFunc` 适配器，允许用函数字段快速构建 Exporter：

```go
e := &export.ExportFunc{
    HeaderFn: func(cols []string) ([]byte, error) { return []byte("..."), nil },
    RecordFn: func(i int, r export.Record, cols []string) ([]byte, error) { ... },
}
export.Export(e, columns, records)
```

### 4.2 具体实现 — 三种导出格式

本项目提供了三个 Exporter 实现，展示同一模板产生不同输出：

| 实现 | 包 | 输出格式 |
|------|------|---------|
| `Exporter` | `csvexport/` | CSV（逗号分隔值） |
| `Exporter` | `jsonexport/` | JSON 数组 |
| `Exporter` | `mdexport/` | Markdown 表格 |

同一份数据通过不同 Exporter：

```
CSV:                    JSON:                   Markdown:
name,age                [                       | name | age |
Alice,30                  {"age":"30",...},      | --- | --- |
Bob,25                    {"age":"25",...}       | Alice | 30 |
                        ]                       | Bob | 25 |
                                                *2 records*
```

### 4.3 调用方

```go
records := []export.Record{
    {Fields: map[string]string{"name": "Alice", "age": "30"}},
    {Fields: map[string]string{"name": "Bob", "age": "25"}},
}
columns := []string{"name", "age"}

// 同一模板，不同导出格式
csvOut, _ := export.Export(csvexport.New(), columns, records)
jsonOut, _ := export.Export(jsonexport.New(), columns, records)
mdOut, _ := export.Export(mdexport.New(), columns, records)
```

调用方通过 `Exporter` 接口操作，不关心具体格式的实现细节。新增格式只需实现接口，无需修改 `Export()` 模板函数。

## 5 为什么 embedding 不能实现模板方法

这是 Go 新手（尤其是 Java/C++ 背景）最常犯的错误：

```go
type BaseExporter struct{}
func (b *BaseExporter) Format(data string) string { return "base:" + data }
func (b *BaseExporter) Export(data string) string {
    return b.Format(data) // ← 永远调用 BaseExporter.Format
}

type CSVExporter struct{ BaseExporter }
func (c *CSVExporter) Format(data string) string { return "csv:" + data }

csv := &CSVExporter{}
csv.Export("hello")
// 输出: "base:hello"（不是 "csv:hello"！）
```

**原因**：Go 没有虚方法表（vtable）。`BaseExporter.Export` 内部的 `b.Format()` 在编译期就绑定到了 `(*BaseExporter).Format`。embedding 只是字段提升（promotion），不是继承。

**正确做法**：用 interface + 自由函数。模板函数通过接口调用步骤方法，Go 的接口调用天然是动态分派（通过 itab），这就是"虚方法调度"的等价物。

详见 `trap/embedoverride/` 中的完整示例。

## 6 设计决策解析

### 6.1 为什么 Export 是自由函数而非方法？

```go
// 自由函数（本项目）
func Export(e Exporter, columns []string, records []Record) ([]byte, error)

// 方法（备选方案）
func (e *SomeStruct) Export(columns []string, records []Record) ([]byte, error)
```

自由函数的优势：
- **不绑定具体类型**：任何实现 `Exporter` 的类型都能传入
- **与 sort.Sort 一致**：`sort.Sort(data)` 不是 `data.Sort()`
- **可测试**：模板函数本身可以用 mock Exporter 测试
- **组合自由**：不需要 struct embedding 或继承来使用模板

### 6.2 为什么 FormatRecord 接收 index 参数？

```go
FormatRecord(index int, record Record, columns []string) ([]byte, error)
```

`index` 不是所有格式都需要（CSV 忽略它），但 JSON 导出用它来处理元素间的逗号分隔。这是模板方法向步骤传递上下文信息的标准做法——`sort.Interface.Less(i, j)` 的 `i, j` 也是同理。

### 6.3 为什么提供 ExportFunc 适配器？

```go
type ExportFunc struct {
    HeaderFn func(columns []string) ([]byte, error)
    RecordFn func(index int, record Record, columns []string) ([]byte, error)
    FooterFn func(totalRecords int) ([]byte, error)
}
```

`ExportFunc` 桥接了"接口变体"和"函数字段变体"，类似 `http.HandlerFunc` 的角色：
- 测试中快速构建 mock Exporter
- 一次性场景无需定义新类型
- nil 字段安全处理（返回空输出）

### 6.4 为什么用 `[]byte` 而非 `io.Writer`？

教学目的选择了 `[]byte` 返回值，使测试断言更直观。
生产代码中应使用 `io.Writer` 参数——这也是 `encoding/json.Encoder` 的做法：

```go
// 生产变体
func Export(w io.Writer, e Exporter, columns []string, records []Record) error
```

## 7 模板方法 vs 策略模式

两者都使用接口来注入可变行为，经常被混淆：

| 维度 | 模板方法 | 策略模式 |
|------|---------|---------|
| **意图** | 定义算法骨架，步骤可定制 | 整个算法可替换 |
| **骨架** | 有固定骨架，步骤在骨架内被调用 | 无骨架，策略是完整的算法 |
| **粒度** | 细粒度：多个步骤方法 | 粗粒度：一个方法 |
| **控制权** | 模板函数控制流程 | 调用方控制何时调用策略 |
| **Go 标准库** | `sort.Sort` + `sort.Interface` | `http.Handler`（Server 不控制 Handler 内部） |
| **本项目** | `export.Export` + `Exporter` | `payment.Checkout` + `Strategy` |

简单判断：如果接口有**多个方法**，且它们被一个**固定的算法**按特定顺序调用 → 模板方法。如果接口只有**一个方法**，代表一个**完整的行为** → 策略。

## 8 适用场景与局限

### 适用

- **数据导出/序列化**：固定的遍历 → 格式化 → 输出流程，格式可变
- **编译器/解释器**：固定的 词法分析 → 语法分析 → 代码生成 流程
- **HTTP 框架**：固定的 路由匹配 → 中间件 → 处理 → 响应 流程
- **测试框架**：固定的 Setup → Test → Teardown 流程
- **ETL 管道**：固定的 Extract → Transform → Load 流程，每步可定制

### 局限

- **步骤耦合**：所有步骤必须通过同一接口定义，新增步骤需要修改接口
- **粒度固定**：算法骨架一旦定义就不易修改（这是 feature 也是 limitation）
- **过度设计**：简单场景直接写一个函数更清晰，不需要模板
- **调试复杂**：模板函数和步骤实现分布在不同包中，追踪流程需要跨文件

## 9 模板方法 vs Hooks vs Callback Pipeline

三种"固定骨架 + 可变步骤"的实现方式：

| 方式 | 步骤定义 | 步骤数量 | 适合场景 |
|------|---------|---------|---------|
| **模板方法** | 接口多方法 | 多步 | 步骤之间有共享上下文 |
| **Hooks** | 函数字段 (可选) | 少量 | 大部分默认行为，少量定制 |
| **Callback Pipeline** | 函数切片 | 动态 | 步骤数量不固定 |

### Hooks 示例（http.Server 风格）

```go
type Processor struct {
    BeforeProcess func(data []byte) []byte  // hook：可选
    AfterProcess  func(result []byte)       // hook：可选
}

func (p *Processor) Run(data []byte) []byte {
    if p.BeforeProcess != nil {
        data = p.BeforeProcess(data)
    }
    result := process(data) // 固定骨架
    if p.AfterProcess != nil {
        p.AfterProcess(result)
    }
    return result
}
```

### 清理/收尾步骤如何建模

模板方法经常需要"无论成功失败都执行清理"：

```go
func Export(e Exporter, columns []string, records []Record) ([]byte, error) {
    header, err := e.Header(columns)
    if err != nil { return nil, err }

    // ... records ...

    footer, err := e.Footer(len(records))
    if err != nil { return nil, err }

    // 如果 Exporter 有 Cleanup 方法，在最后调用
    if c, ok := e.(interface{ Cleanup() }); ok {
        defer c.Cleanup()
    }
    // ...
}
```

用接口检测（鸭子类型）发现可选的 Cleanup 步骤——不强制所有实现者都必须提供清理逻辑。

## 10 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| 骨架顺序 | Header → Records → Footer 的调用顺序正确 |
| 步骤回调 | 每个步骤方法都被调用了正确的次数 |
| 错误传播 | 某步骤返回 error 时模板函数立即返回 |
| 不同实现 | 三种 Exporter 产生正确的 CSV/JSON/Markdown |
| ExportFunc 适配 | 函数字段方式等价于接口方式 |
| nil 步骤安全 | ExportFunc 的 nil 字段不 panic |
| 空输入 | 空 records 只输出 Header + Footer |

## 11 成本模型

### 何时值得用模板方法

- 算法骨架固定，步骤可定制（如 ETL、数据导出）
- 多种实现共享相同流程但细节不同
- 需要保证步骤执行顺序

### 何时是过度设计

- 算法只有一种实现——直接写一个函数
- 步骤之间没有固定顺序——用策略模式或责任链
- 只有一个可变步骤——高阶函数参数更简单
