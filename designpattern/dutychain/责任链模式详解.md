# 责任链模式详解

责任链（Chain of Responsibility）是最实用的行为型设计模式之一。在 Go 语言中，它以 **HTTP 中间件**的形式无处不在 — 几乎每个 Go Web 框架的核心都是一条责任链。理解这个模式，就理解了 Go Web 生态的底层架构。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Avoid coupling the sender of a request to its receiver by giving more than one object a chance to handle the request. Chain the receiving objects and pass the request along the chain until an object handles it.

翻译：避免请求的发送者与接收者耦合，让多个对象都有机会处理请求。将接收对象串成链，沿链传递请求，直到有对象处理它。

Go 中间件是这一模式的函数式变体 — 每个中间件都有机会处理请求，可以选择**继续传递**（调用 next）或**短路中断**（不调用 next）：

```
请求 ──→ Logging ──→ Auth ──→ Recovery ──→ Handler
               │          │         │           │
               │          │         │           │
响应 ←── Logging ←── Auth ←── Recovery ←── Handler
```

每个中间件在调用 next 之前执行"前置逻辑"，在 next 返回后执行"后置逻辑"，形成经典的**洋葱模型**：

```
            ┌─────────────────────────────────┐
            │         Logging (耗时统计)        │
            │   ┌─────────────────────────┐   │
            │   │       Auth (鉴权)        │   │
            │   │   ┌─────────────────┐   │   │
            │   │   │  Recovery (恢复) │   │   │
            │   │   │   ┌─────────┐   │   │   │
 Request ──→│──→│──→│──→│ Handler │──→│──→│──→│──→ Response
            │   │   │   └─────────┘   │   │   │
            │   │   └─────────────────┘   │   │
            │   └─────────────────────────┘   │
            └─────────────────────────────────┘
```

三个角色：
- **Middleware（处理者）**：接收 handler、返回增强后的 handler
- **Chain（链构造器）**：将多个 Middleware 组合成一条链
- **Handler（最终处理者）**：执行实际的业务逻辑

## 2 标准库与生态中的先例

责任链/中间件模式在 Go 生态中极为普遍：

| 场景 | 类型签名 | 说明 |
|------|---------|------|
| `net/http` | `func(http.Handler) http.Handler` | 标准库原生支持 handler 包装 |
| gin | `gin.HandlerFunc` chain | `Use()` 添加中间件，`Next()` 传递 |
| chi | `func(http.Handler) http.Handler` | 与标准库完全兼容 |
| echo | `echo.MiddlewareFunc` | `next(c)` 传递请求 |
| go-zero | `rest.Middleware` | `func(next http.HandlerFunc) http.HandlerFunc` |
| gRPC | `UnaryServerInterceptor` | 拦截器链 = RPC 层的责任链 |
| Kubernetes | Admission Webhooks | 请求依次经过多个准入控制器 |

### net/http — 标准库的 handler 包装

```go
func loggingHandler(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        log.Printf("%s %s", r.Method, r.URL.Path)
        next.ServeHTTP(w, r)
    })
}

func main() {
    handler := loggingHandler(http.DefaultServeMux)
    http.ListenAndServe(":8080", handler)
}
```

标准库没有提供 `Chain` 工具，需要手动嵌套：`logging(auth(recovery(handler)))` — 嵌套层数多时可读性差。本项目的 `Chain` 和 `Apply` 解决了这个问题。

### gRPC — 拦截器链

```go
grpc.NewServer(
    grpc.ChainUnaryInterceptor(
        loggingInterceptor,
        authInterceptor,
        recoveryInterceptor,
    ),
)
```

gRPC 的 `ChainUnaryInterceptor` 与本项目的 `Chain` 完全同构 — 将多个拦截器组合成一条链，按顺序执行。

## 3 核心原理

### 3.1 函数装饰/嵌套

责任链的 Go 实现本质是**函数装饰**：每个中间件接收一个函数，返回一个增强后的函数。

```go
type Middleware func(http.HandlerFunc) http.HandlerFunc
```

调用 `middleware(handler)` 返回一个新函数，这个新函数内部会先执行中间件逻辑，再调用原始 handler。多层嵌套后形成一条链：

```go
// 手动嵌套
final := logging(auth(recovery(handler)))

// 等价于 Chain 组合
final := Chain(logging, auth, recovery)(handler)
```

### 3.2 洋葱模型

每个中间件在调用 `next` 的前后都可以执行逻辑，形成对称的"进入-退出"结构：

```go
func timingMiddleware(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()          // ← 进入：记录开始时间
        next(w, r)                   // ← 传递给下一个处理者
        log.Println(time.Since(start)) // ← 退出：计算耗时
    }
}
```

请求从外层向内层传递，响应从内层向外层返回 — 就像剥洋葱一样，先进后出。

### 3.3 短路机制

中间件可以选择**不调用 next** 来中断链：

```go
func authMiddleware(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        if r.Header.Get("Authorization") == "" {
            http.Error(w, "Unauthorized", 401)
            return    // ← 短路：不调用 next，后续中间件和 handler 都不会执行
        }
        next(w, r)
    }
}
```

这是责任链的核心能力 — 每个处理者自主决定是否继续传递。鉴权失败、限流触发、缓存命中等场景都需要短路。

## 4 本项目的实现

### 4.1 Middleware 类型与链构造 — `middleware/middleware.go`

```go
type Middleware func(http.HandlerFunc) http.HandlerFunc

func Chain(middlewares ...Middleware) Middleware { ... }
func Apply(handler http.HandlerFunc, middlewares ...Middleware) http.HandlerFunc { ... }
```

核心 API：

| 函数 | 作用 | 对标生态 |
|------|------|---------|
| `Chain(mw...)` | 组合多个 Middleware 为一个 | `alice.New` / `chi.Chain` |
| `Apply(handler, mw...)` | 将 Middleware 链应用到 handler | `alice.Then` |

`Chain` 返回的也是 `Middleware` — 因此链可以嵌套组合：

```go
common := Chain(logging, recovery)        // 通用链
api    := Chain(common, auth, rateLimit)  // API 链 = 通用链 + 额外中间件
```

### 4.2 具体中间件

本项目提供了三个具体中间件，展示不同的责任链行为：

| 中间件 | 包 | 行为 | 链操作 |
|--------|------|------|--------|
| `LoggingMiddleware` | `logging/` | 记录请求方法、路径和耗时 | 透传（始终调用 next） |
| `AuthMiddleware` | `auth/` | 验证 Authorization 头 | 可能短路（token 无效时中断） |
| `RecoveryMiddleware` | `recovery/` | 捕获 panic，返回 500 | 透传 + defer recover |

三者代表了中间件的三种典型模式：
- **logging**：纯观察，不改变请求/响应流程
- **auth**：门卫，决定是否放行
- **recovery**：保护网，兜底异常

### 4.3 使用方式

```go
import (
    "go-notes/designpattern/dutychain/middleware"
    "go-notes/designpattern/dutychain/logging"
    "go-notes/designpattern/dutychain/auth"
    "go-notes/designpattern/dutychain/recovery"
)

func main() {
    // 组合中间件链
    chain := middleware.Chain(
        logging.New(),
        auth.New("valid_token"),
        recovery.New(),
    )

    // 应用到业务 handler
    handler := chain(func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintf(w, "Hello, World!")
    })

    http.HandleFunc("/", handler)
    http.ListenAndServe(":8080", nil)
}
```

或者使用 `Apply` 便捷函数：

```go
handler := middleware.Apply(
    myHandler,
    logging.New(),
    auth.New("valid_token"),
    recovery.New(),
)
```

## 5 设计决策解析

### 5.1 为什么用函数类型而非 interface？

```go
// 方案 A：函数类型（本项目选择）
type Middleware func(http.HandlerFunc) http.HandlerFunc

// 方案 B：接口
type Handler interface {
    Handle(r *Request)
    SetNext(h Handler)
}
```

Go 社区的共识是函数式中间件优于接口式：

| 维度 | 函数类型 | 接口 |
|------|---------|------|
| 代码量 | 一个闭包即可 | 需定义 struct + 方法 |
| 组合性 | `Chain(a, b, c)` | 需手动 `a.SetNext(b); b.SetNext(c)` |
| 匿名使用 | 支持内联 lambda | 必须定义命名类型 |
| 标准库兼容 | 与 `http.HandlerFunc` 天然一致 | 需要适配层 |

Go 的 `http.HandlerFunc` 本身就是函数类型（`func(ResponseWriter, *Request)`），中间件自然也用函数表达。这是 Go 语言"小接口 + 函数式"哲学的体现。

### 5.2 为什么 Chain 反向遍历？

```go
func Chain(middlewares ...Middleware) Middleware {
    return func(final http.HandlerFunc) http.HandlerFunc {
        for i := len(middlewares) - 1; i >= 0; i-- {
            final = middlewares[i](final)
        }
        return final
    }
}
```

`Chain(A, B, C)(handler)` 的构建过程：

```
i=2: final = C(handler)        → C 包裹 handler
i=1: final = B(C(handler))     → B 包裹 C
i=0: final = A(B(C(handler)))  → A 包裹 B
```

请求路径：A → B → C → handler。**传入顺序 = 执行顺序** — 这是最符合直觉的 API。如果正向遍历，结果会变成 C → B → A → handler，与传入顺序相反，容易混淆。

### 5.3 为什么 Chain 返回 Middleware 而非 http.HandlerFunc？

```go
func Chain(middlewares ...Middleware) Middleware  // 返回 Middleware
// 而不是
func Chain(handler http.HandlerFunc, middlewares ...Middleware) http.HandlerFunc
```

返回 `Middleware` 使 Chain 本身也是可组合的：

```go
common := Chain(logging, recovery)
api    := Chain(common, auth)       // 链嵌套链
web    := Chain(common, csrf)       // 另一条链复用 common

apiHandler := api(myAPIHandler)
webHandler := web(myWebHandler)
```

如果直接返回 `HandlerFunc`，就无法实现这种组合复用。`Apply` 作为便捷函数，在不需要组合时直接返回最终 handler。

### 5.4 短路机制：不调用 next 即可中断

Go 中间件的短路是**隐式的** — 不调用 `next` 即可中断。对比其他框架的显式短路：

```go
// Go：不调用 next = 短路
func authMW(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        if !valid {
            http.Error(w, "Unauthorized", 401)
            return  // 不调用 next
        }
        next(w, r)
    }
}

// gin：显式调用 c.Abort()
func authMW(c *gin.Context) {
    if !valid {
        c.AbortWithStatus(401)
        return
    }
    c.Next()
}
```

隐式短路的优势：无需额外 API，函数的正常返回流就是控制流。劣势：代码审查时不容易一眼看出哪里短路了。

### 5.5 为什么每个具体中间件用独立包？

与简单工厂（单包）不同，中间件使用独立包：

```
dutychain/
├── middleware/    ← 核心
├── logging/       ← 独立包
├── auth/          ← 独立包
└── recovery/      ← 独立包
```

理由：
- 中间件是**开放集合** — 项目中随时可能新增中间件（限流、CORS、tracing...）
- 独立包允许调用方**按需导入** — 不需要鉴权的内部服务不必引入 auth
- 与 Go 生态一致 — chi、echo 等框架都将中间件放在独立包中
- 测试隔离 — 每个中间件可以独立测试

### 5.6 Logging 中间件为什么在 next 之后记录耗时？

```go
func New() middleware.Middleware {
    return func(next http.HandlerFunc) http.HandlerFunc {
        return func(w http.ResponseWriter, r *http.Request) {
            start := time.Now()
            next(w, r)                                              // handler 执行
            log.Printf("[%s] %s — %v", r.Method, r.URL.Path,
                time.Since(start))                                  // handler 完成后记录
        }
    }
}
```

如果在 `next` 之前记录，只能记录"请求到达时间"，无法获得"响应耗时"。利用洋葱模型的"进入-退出"对称性，在 `next` 返回后计算 `time.Since(start)` 就是完整的处理耗时。

## 6 经典责任链 vs 中间件链

GoF 原始定义中的责任链是"链表式"的 — 每个处理者持有下一个处理者的引用。Go 中间件是"函数嵌套式"的。两者是同一模式的不同实现：

```
经典责任链（链表式）：
  Handler A → Handler B → Handler C
  每个 handler 显式持有 next 指针

中间件链（函数嵌套式）：
  A(B(C(handler)))
  每个中间件通过闭包捕获 next
```

| 维度 | 经典责任链 | 中间件链 |
|------|-----------|---------|
| 结构 | 链表（每个节点有 next 指针） | 函数嵌套（闭包捕获 next） |
| 构建方式 | `a.SetNext(b); b.SetNext(c)` | `Chain(a, b, c)` |
| 执行模型 | 单向传递（处理或转发） | 洋葱模型（前置 + 后置逻辑） |
| 动态修改 | 可运行时插入/删除节点 | 构建后不可修改 |
| Go 惯用性 | 较少使用 | 标准做法 |

**经典责任链**适合"找到第一个能处理的"场景（如异常处理链、审批流）。**中间件链**适合"每个都处理一部分"场景（如 HTTP 请求管道）。

经典链表式在 Go 中的写法：

```go
type Handler interface {
    Handle(req *Request)
    SetNext(h Handler)
}

type BaseHandler struct{ next Handler }

func (b *BaseHandler) SetNext(h Handler) { b.next = h }
func (b *BaseHandler) passToNext(req *Request) {
    if b.next != nil {
        b.next.Handle(req)
    }
}
```

对比之下，函数式中间件在 Go 中代码量更少、组合性更强、与标准库契合度更高。这是本项目选择函数式实现的原因。

## 7 中间件链 vs 装饰器模式

中间件链和装饰器模式看起来非常相似 — 都是"包一层"：

```go
// 中间件
logging(auth(handler))

// 装饰器
buffered(compressed(writer))
```

但两者的**意图和关注点**不同：

| 维度 | 中间件链（责任链） | 装饰器 |
|------|------------------|--------|
| 意图 | 让多个处理者依次处理请求 | 给对象动态添加职责 |
| 关注点 | **流程控制**（传递、短路、顺序） | **功能增强**（添加行为） |
| 短路能力 | ✅ 可以中断链 | ❌ 通常不中断 |
| 洋葱模型 | ✅ 前置 + 后置逻辑 | 通常只有前置或后置 |
| Go 中的典型形式 | HTTP 中间件 | `io.Writer` 包装（如 `bufio.Writer`、`gzip.Writer`） |

关键区分：如果你关心的是"请求是否继续传递"，那是责任链；如果你关心的是"给对象加一层能力"，那是装饰器。

标准库中的装饰器例子：

```go
var w io.Writer = os.Stdout
w = bufio.NewWriter(w)    // 添加缓冲能力
w = gzip.NewWriter(w)     // 添加压缩能力
```

这里没有"短路"的概念，每一层都是必经的。而 HTTP 中间件中，auth 可以拒绝请求、rate limiter 可以返回 429 — 短路是核心特征。

## 8 适用场景与局限

### 适用

- **HTTP 请求管道**：日志、鉴权、限流、CORS、压缩、tracing — 所有 Web 框架的标配
- **gRPC 拦截器**：与 HTTP 中间件同构，用于 RPC 层的横切关注点
- **审批流程**：经理 → 总监 → VP → CEO，每级自主决定是否需要上级审批
- **事件处理管道**：消息队列消费时的过滤、转换、校验链
- **CLI 命令管道**：命令执行前的参数校验、环境检查、权限验证

### 局限

- **调试困难**：请求经过多层中间件，难以在调试器中追踪完整路径
- **顺序敏感**：`Chain(auth, logging)` 和 `Chain(logging, auth)` 行为不同。鉴权失败时，前者不会记录日志，后者会
- **错误传播**：标准 `http.HandlerFunc` 没有返回 error，中间件只能通过 `http.Error` 写响应，无法向上层传递结构化错误
- **性能开销**：每层中间件增加一次函数调用。在极端高性能场景（如 L7 代理），深层嵌套可能有可测量的开销
- **不可变链**：构建后无法动态插入/删除中间件。如果需要运行时调整链结构，需用链表式实现
