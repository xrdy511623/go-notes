# 状态模式详解

状态模式（State Pattern）是 GoF 23 种经典设计模式中的行为型模式。它将对象在不同状态下的行为封装到独立的状态类中，让对象在运行时通过切换状态对象来改变自身行为，看起来就像改变了类本身。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Allow an object to alter its behavior when its internal state changes. The object will appear to change its class.

翻译：允许一个对象在其内部状态改变时改变其行为。对象看起来似乎修改了它的类。

模式由三个角色组成：

```
                        ┌───────────────────┐
                        │     Context        │
                        │    (Player)        │
                        │                   │
                        │  state State ──────┼──┐
                        │  Play()            │  │
                        │  Pause()           │  │
                        │  Stop()            │  │
                        └───────────────────┘  │
                                                │
                    ┌───────────────────────────┘
                    │
                    ▼
          ┌─────────────────┐
          │   <<interface>>  │
          │      State       │
          │                  │
          │  Play(p *Player) │
          │  Pause(p *Player)│
          │  Stop(p *Player) │
          │  String() string │
          └────────┬─────────┘
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
┌────────────┐ ┌────────────┐ ┌────────────┐
│ IdleState  │ │PlayingState│ │PausedState │
│            │ │            │ │            │
│ Play → ●   │ │ Play → nop │ │ Play → ●   │
│ Pause→ nop │ │ Pause→ ●   │ │ Pause→ nop │
│ Stop → nop │ │ Stop → ●   │ │ Stop → ●   │
└────────────┘ └────────────┘ └────────────┘
```

核心特征：**状态转换由各状态对象自身决定**，Context 只负责委托调用。

## 2 标准库与生态中的先例

Go 标准库和生态中多处使用了状态模式的思想：

| 场景 | 机制 | 说明 |
|------|------|------|
| `net/http` 连接状态 | `connState`（idle/active/hijacked/closed） | 每种状态决定连接的可用操作 |
| `bufio.Scanner` | 内部 `scanFunc` 切换 | scanning → done → error，不同状态下 `Scan()` 行为不同 |
| `context.Context` | cancelCtx / timerCtx | active → canceled → deadline，取消后所有操作返回错误 |
| `crypto/tls.Conn` | 握手状态机 | 未握手 → 握手中 → 已建立，不同状态下 Read/Write 行为不同 |
| `net.TCPConn` | TCP 状态 | LISTEN → ESTABLISHED → CLOSE_WAIT 等，内核维护的状态机 |
| `database/sql.Tx` | 事务状态 | active → committed/rolled back，提交后再操作返回 `ErrTxDone` |

`net/http` 中 `connState` 的处理是最接近 GoF State 的例子：Server 在连接状态变化时调用 `ConnState` 钩子，不同状态下允许的操作不同。

## 3 本项目的实现

### 3.1 状态接口与上下文 — `player/player.go`

```go
// State 是播放器状态的接口。
type State interface {
    Play(p *Player)
    Pause(p *Player)
    Stop(p *Player)
    String() string
}

// Player 是媒体播放器（Context 角色）。
type Player struct {
    state   State
    track   string
    history []string
}
```

Player 把所有操作委托给当前 state：

```go
func (p *Player) Play()  { p.state.Play(p) }
func (p *Player) Pause() { p.state.Pause(p) }
func (p *Player) Stop()  { p.state.Stop(p) }
```

### 3.2 三个具体状态 — `states/`

状态转移图：

```
         Play()           Pause()
  ┌──────────────┐  ┌──────────────┐
  │              ▼  │              ▼
┌──────┐     ┌────────┐     ┌────────┐
│ Idle │     │Playing │     │Paused  │
└──┬───┘     └───┬────┘     └───┬────┘
   │             │              │
   │  Stop()     │   Stop()     │  Play()
   │◄────────────┘              │──────────┐
   │◄───────────────────────────┘          │
   │                                       │
   │              ┌────────┐               │
   │              │Playing │◄──────────────┘
   │              └────────┘
   ▼
```

| 当前状态 | Play() | Pause() | Stop() |
|---------|--------|---------|--------|
| Idle | → Playing | 空操作 | 空操作 |
| Playing | 空操作 | → Paused | → Idle |
| Paused | → Playing | 空操作 | → Idle |

每个状态是零值结构体，无需分配：

```go
// states/playing.go
type PlayingState struct{}

func (s PlayingState) Play(_ *player.Player) {}  // 已在播放，空操作
func (s PlayingState) Pause(p *player.Player) { p.SetState(PausedState{}) }
func (s PlayingState) Stop(p *player.Player)  { p.SetState(IdleState{}) }
func (s PlayingState) String() string         { return "playing" }
```

### 3.3 调用方

```go
import (
    "go-notes/designpattern/state/player"
    "go-notes/designpattern/state/states"
)

func main() {
    p := player.New("song.mp3", states.IdleState{})

    p.Play()   // idle → playing
    p.Pause()  // playing → paused
    p.Play()   // paused → playing（恢复播放）
    p.Stop()   // playing → idle

    fmt.Println(p.History()) // [idle playing paused playing idle]
}
```

调用方不需要知道状态转换的细节，只需调用 Player 的方法即可。

## 4 设计决策解析

### 4.1 为什么 State 接口定义在 player 包而不是 states 包？

如果把 `State` 接口定义在 `states` 包中，`player` 需要导入 `states`（使用接口），`states` 也需要导入 `player`（访问 `Player` 类型）—— 产生**循环导入**。

```
player → states  (使用 IdleState 等)
states → player  (State.Play(p *Player))
```

Go 的解法是将接口定义在使用方（consumer）而非实现方：

- `State` 接口 + `Player` 类型都在 `player` 包
- `states` 包单向导入 `player` 包来实现接口
- 调用方只需导入两个包，无循环依赖

### 4.2 为什么状态是零值结构体而不是单例？

```go
type PlayingState struct{}           // ✅ 零值，无需构造
var Playing = &PlayingState{}        // ❌ 包级变量单例
```

选择零值结构体的理由：
- 零值即可用，无需构造函数或初始化
- 值类型语义，赋值即复制，无共享状态，天然并发安全
- 编译器可以优化掉零大小结构体的分配
- 如果将来某个状态需要携带数据，只需加字段，无需改接口

### 4.3 为什么记录 history？

`history` 字段的唯一目的是**可测试性**。状态模式的行为全靠副作用（状态切换），如果没有 history，测试只能断言最终状态，无法验证中间的转换路径是否正确。

### 4.4 为什么无效操作是空操作而不是返回错误？

媒体播放器的用户体验：按下播放键时如果已在播放，什么都不该发生。这是**领域语义**决定的，不是技术限制。

在其他领域（如订单状态机），无效操作应当返回错误。State 接口的方法签名可以根据业务需求调整为 `Play(p *Player) error`。

### 4.5 为什么 New 接受 initState 参数？

```go
func New(track string, initState State) *Player
```

如果 `New` 内部直接创建 `states.IdleState{}`，`player` 包就必须导入 `states` 包，形成循环依赖。通过参数注入初始状态，依赖方向保持单向：

```
调用方 → player（定义接口）
调用方 → states（实现接口）
states → player（单向）
```

## 5 与相近模式的对比

本项目同时包含 GoF State（`state/`）和 FSM（`statemachine/`），两者经常混淆。加上 Strategy 模式，对比如下：

| 维度 | GoF State | FSM（有限状态机） | Strategy |
|------|-----------|----------------|----------|
| **谁控制转换** | 状态对象自己决定下一个状态 | 外部转换表定义所有合法转换 | 不涉及转换（算法不变） |
| **行为在哪里** | 分散在各状态对象中 | 集中在转换表/处理函数中 | 分散在各策略对象中 |
| **新增状态** | 加一个 State 实现（OCP） | 改转换表 | — |
| **新增动作** | 改 State 接口（所有实现） | 加事件类型 | — |
| **状态数据** | 状态对象可携带数据 | 通常只有状态标识 | — |
| **适合场景** | 状态有复杂行为差异 | 状态转换规则复杂 | 算法可替换 |
| **本项目** | `state/` | `statemachine/` | — |

关键区分：

- **GoF State**：`PlayingState.Pause()` 里面写 `p.SetState(PausedState{})` —— 状态自己决定转到哪里
- **FSM**：转换表写 `{From: "playing", Event: "pause", To: "paused"}` —— 外部定义转换规则
- **Strategy**：调用方主动选择 `sort.Interface` 的实现，对象自己不会切换策略

## 6 常见陷阱 / 反例

### 6.1 switch/case 管理状态（参考 `trap/switchstate/`）

```go
func (p *BadPlayer) Play() {
    switch p.state {
    case "idle":
        p.state = "playing"
    case "playing":
        // 已在播放
    case "paused":
        p.state = "playing"
    // 新增 "buffering" 状态？必须在 Play()、Pause()、Stop() 都加 case
    }
}
```

问题：
- 新增状态需要修改所有动作方法（M 个状态 × N 个动作 = M×N 个 case）
- 编译器不会提醒遗漏的 case（string 类型的 switch 无穷尽检查）
- 状态相关逻辑散落在不同方法中，无法一眼看清某个状态的完整行为

### 6.2 状态爆炸

当状态数量超过 10 个时，状态模式的类数量会急剧增长。考虑：
- **层次状态机**（HSM）：用状态继承/嵌套减少重复
- **FSM + 转换表**：当行为差异不大时，转换表更紧凑

### 6.3 循环导入

Go 最常见的实现陷阱。错误的做法：

```
states/idle.go:    import "player"   // states → player
player/player.go:  import "states"   // player → states  ← 循环！
```

正确做法：接口定义在 consumer（`player`）包中，实现在 `states` 包中，`states` 单向导入 `player`。

### 6.4 状态对象持有可变数据

```go
type PlayingState struct {
    position time.Duration  // ❌ 可变数据 → 并发不安全
}
```

如果状态对象持有可变数据，在并发场景下需要额外的同步。更好的做法是将可变数据放在 Context（Player）中，状态对象保持无状态。

## 7 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| 初始状态 | `New()` 后状态为 idle |
| 有效转换 | idle → playing、playing → paused、paused → playing、playing → idle、paused → idle |
| 空操作 | idle 下 Pause/Stop、playing 下 Play、paused 下 Pause 不产生转换 |
| 转换历史 | `History()` 完整记录从初始到最终的所有状态 |
| 防御性拷贝 | `History()` 返回副本，外部修改不影响内部 |
| 曲目不变 | 状态切换不影响 `Track()` 返回值 |

测试策略：
- 每个有效转换一个独立测试函数，命名清晰表达前置条件和预期结果
- 空操作测试通过检查 history 长度不变来验证
- 全流程测试验证完整转换路径

## 8 成本模型

### 何时值得使用状态模式

- **5 个以上状态**，且各状态的行为差异显著
- **频繁新增状态**，需要遵守开闭原则
- **状态行为复杂**，每个状态的逻辑足以独占一个文件
- **需要状态携带数据**（如 Playing 状态记录播放进度）

### 何时是过度设计

- **2-3 个简单状态**，switch/case 更直观
- **状态转换规则复杂但行为简单**，用 FSM（转换表）更清晰
- **状态只有标识意义**，无行为差异（用 enum/const 即可）
- **单人项目且不会扩展**，YAGNI 原则

### 性能考量

- 零值结构体的状态对象不产生堆分配
- 方法调用通过接口间接分发，相比直接调用多一次 itab 查找（约 1-2ns）
- 与 switch/case 相比，状态模式的运行时开销可以忽略不计

## 9 适用场景与局限

### 适用场景

| 场景 | 状态示例 |
|------|---------|
| 媒体播放器 | idle / playing / paused / buffering |
| 文档编辑器 | draft / review / published / archived |
| 游戏角色 | idle / walking / running / jumping / attacking |
| UI 组件 | normal / hover / pressed / disabled / focused |
| 网络连接 | connecting / connected / disconnecting / closed |
| 订单系统 | created / paid / shipped / delivered / refunded |

### 局限

- **类数量膨胀**：N 个状态 = N 个结构体 + N 个文件（states 包）
- **转换逻辑分散**：要了解完整的转换图，需要阅读所有状态的代码
- **接口变更成本高**：新增动作（如 `FastForward()`）需要修改 State 接口及所有实现
- **调试间接性**：`Player.Play()` → `state.Play()` → `p.SetState()`，调用链比 switch 更长
