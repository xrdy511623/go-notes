# 依赖注入模式详解

依赖注入（Dependency Injection, DI）不是 GoF 23 种设计模式之一，而是 SOLID 原则中**依赖倒置原则（DIP）**的具体实践手段。核心思想只有一句话：**不要自己创建依赖，让外部传进来。**

Go 语言的 interface 隐式实现 + 构造函数惯例，让依赖注入成为最自然不过的编码方式——甚至很多 Go 程序员在使用 DI 而不自知。

---

## 1 模式定义

### 什么是依赖注入

> Don't look for things — have them handed to you.

一个对象不应该自行创建或查找它的依赖，而应该**通过构造函数、方法参数或接口**从外部接收。

```
不用 DI：
  ┌──────────────┐
  │   Service     │
  │  ┌──────────┐ │
  │  │ new MySQL│ │  ← Service 自己创建了 MySQL 依赖
  │  └──────────┘ │    Service 和 MySQL 紧耦合
  └──────────────┘

使用 DI：
  Creator（main / container）负责组装
       │
       │  NewMySQL(dsn)──→ repo（UserRepo 接口）
       │                       │
       │  NewUserService(repo)──→ svc
       │                           │
       └──→ App{UserService: svc}
                │
                ▼
         所有依赖从外部注入
         Service 只依赖接口
```

### DI（模式） vs DI Container（工具）

| 概念 | 定义 | 示例 |
|------|------|------|
| **依赖注入** | 一种编码模式——通过构造函数接收依赖 | `NewUserService(repo UserRepo)` |
| **DI 容器** | 自动化组装依赖图的工具 | google/wire, uber/fx, samber/do |

很多人误以为 DI = DI 容器。实际上，DI 是模式，容器是可选工具。Go 社区的主流做法是**手动注入 + 可选代码生成（Wire）**，而非运行时容器。

## 2 标准库与生态中的先例

Go 标准库中依赖注入的思想无处不在：

| 场景 | 注入方式 | 说明 |
|------|---------|------|
| `net/http.Server{Handler: h}` | 字段注入 | Server 不关心 Handler 的具体实现 |
| `database/sql.Open(driver, dsn)` | 工厂函数 | 驱动通过 `sql.Register` 注册，Open 按名称查找 |
| `log.New(out io.Writer, ...)` | 构造函数注入 | 日志输出目标由调用方决定 |
| `testing.T` | 参数注入 | 测试框架将 T 传给测试函数 |
| `context.Context` | 参数注入 | 请求级别的依赖通过 Context 传递 |
| `io.Copy(dst Writer, src Reader)` | 参数注入 | 函数不关心 Reader/Writer 的具体类型 |

### 生态中的 DI 工具

| 工具 | 方式 | 特点 |
|------|------|------|
| [google/wire](https://github.com/google/wire) | 编译期代码生成 | 无运行时开销，类型安全，社区主流 |
| [uber/fx](https://github.com/uber-go/fx) | 运行时反射 | 功能强大，适合大型项目，有学习曲线 |
| [samber/do](https://github.com/samber/do) | 运行时泛型 | 利用 Go 1.18 泛型，API 简洁 |
| 手动装配 | 纯代码 | 零依赖，最容易理解，本项目采用 |

## 3 本项目的实现

### 3.1 三层架构

```
repo（数据访问层）          service（业务逻辑层）         app（应用容器）
┌────────────────┐       ┌──────────────────┐       ┌────────────┐
│  UserRepo 接口  │◄──────│   UserService    │◄──────│    App     │
│  ├─ mysqlRepo  │       │   (依赖 UserRepo) │       │ (持有 Svc) │
│  └─ inMemory   │       └──────────────────┘       └────────────┘
└────────────────┘
```

依赖方向：`App → Service → Repo（接口）`。具体实现（mysqlRepo / inMemoryRepo）由 container 包在启动时选择。

### 3.2 仓储层 — `repo/repo.go`

```go
// UserRepo 定义用户数据访问接口。
type UserRepo interface {
    FindByID(id string) (*User, error)
    Save(u *User) error
}

// NewMySQL 创建基于 MySQL 的 UserRepo（生产环境）。
func NewMySQL(dsn string) UserRepo { ... }

// NewInMemory 创建基于内存 map 的 UserRepo（测试环境）。
func NewInMemory() UserRepo { ... }
```

要点：
- `UserRepo` 是接口——上层代码只依赖接口，不依赖具体实现
- `mysqlRepo` 和 `inMemoryRepo` 都不导出——调用方必须通过 `NewXxx()` 构造
- `inMemoryRepo` 使用 `sync.RWMutex` 保护 map，返回副本防止内部状态被外部修改

### 3.3 业务层 — `service/service.go`

```go
type UserService struct {
    repo repo.UserRepo    // 通过构造函数注入
}

func NewUserService(r repo.UserRepo) *UserService {
    return &UserService{repo: r}
}
```

`UserService` 提供三个业务方法：

| 方法 | 职责 |
|------|------|
| `GetUser(id)` | 按 ID 查询用户，包装底层错误 |
| `CreateUser(name, email)` | 校验参数、生成 ID、持久化 |
| `UpdateEmail(id, newEmail)` | 查找用户 → 修改邮箱 → 保存 |

### 3.4 依赖装配 — `container/wiremanual.go`

```go
// 生产环境：使用 MySQL
func InitializeApp(cfg Config) *app.App {
    userRepo := repo.NewMySQL(cfg.MySQLDSN)
    userSvc  := service.NewUserService(userRepo)
    return &app.App{UserService: userSvc}
}

// 测试环境：使用 InMemory
func InitializeTestApp() *app.App {
    userRepo := repo.NewInMemory()
    userSvc  := service.NewUserService(userRepo)
    return &app.App{UserService: userSvc}
}
```

这就是"手动版 Wire"——用纯 Go 代码描述依赖图。google/wire 生成的代码与此几乎一模一样。

### 3.5 调用方

```go
// main.go
func main() {
    cfg := container.Config{MySQLDSN: os.Getenv("MYSQL_DSN")}
    app := container.InitializeApp(cfg)
    u, _ := app.UserService.GetUser("123")
    fmt.Println(u)
}

// xxx_test.go
func TestSomething(t *testing.T) {
    app := container.InitializeTestApp()
    // 使用内存存储，无需数据库
}
```

## 4 设计决策解析

### 4.1 为什么用构造函数注入而非字段注入？

```go
// ✅ 构造函数注入——编译期强制要求提供依赖
svc := NewUserService(repo)

// ❌ 字段注入——编译器不会阻止你遗漏依赖
svc := &UserService{}
svc.Repo = repo   // 容易忘记这一行，运行时 nil pointer panic
```

| 维度 | 构造函数注入 | 字段注入 |
|------|------------|---------|
| 编译期安全 | ✅ 缺少参数 = 编译错误 | ❌ 遗漏字段仅在运行时暴露 |
| 不可变性 | ✅ 字段小写不导出，创建后不可修改 | ❌ 导出字段随时可被覆盖 |
| 可读性 | ✅ 依赖在签名中一目了然 | ❌ 需查看所有字段赋值才知道完整依赖 |
| Go 惯例 | ✅ `NewXxx()` 是 Go 标准构造方式 | ❌ 非惯用 |

### 4.2 为什么手动装配而非使用 DI 容器？

| 维度 | 手动装配 | Wire（代码生成） | fx（运行时容器） |
|------|---------|----------------|----------------|
| 理解成本 | 极低——纯 Go 代码 | 低——需学习 Provider/Injector | 中——需学习 Module/Provide/Invoke |
| IDE 支持 | ✅ 完整跳转和重构 | ⚠️ 生成代码可跳转，Provider 声明不直观 | ❌ 反射实现，无法静态分析 |
| 编译期检查 | ✅ 类型安全 | ✅ 类型安全 | ❌ 运行时才发现缺失依赖 |
| 维护成本 | 依赖多时冗长 | 自动生成，低 | 低 |
| 适用规模 | 小中型（< 20 个依赖） | 中大型 | 大型（微服务框架级） |

本项目采用手动装配：依赖少（只有 repo → service → app），手动装配最直观。当依赖图膨胀到 20+ 个节点时，推荐引入 Wire。

### 4.3 为什么 Repo 用接口而 Service 用结构体？

```go
// Repo 有多个实现 → 用接口
type UserRepo interface { ... }

// Service 是唯一的业务实现 → 用结构体
type UserService struct { ... }
```

**接口是为了多态——当且仅当存在多个实现时才需要接口。** 如果只有一个实现，直接用结构体。

- `UserRepo` 有 `mysqlRepo` 和 `inMemoryRepo` 两个实现 → 接口
- `UserService` 只有一个实现，测试时通过替换它的依赖（Repo）来隔离 → 结构体

Go 谚语：**Accept interfaces, return structs.**

### 4.4 为什么 Config 用结构体而非多个参数？

```go
// ✅ Config 结构体——易于扩展
func InitializeApp(cfg Config) *app.App

// ❌ 多个参数——每加一个配置项就要改签名
func InitializeApp(mysqlDSN string, redisAddr string, ...) *app.App
```

Config 结构体的优点：
- 新增配置项不破坏现有调用方
- 可以为字段设默认值、加校验
- 可以从 JSON/YAML/ENV 反序列化

## 5 与相近模式的对比

### 5.1 四种依赖获取方式

```
                    依赖由谁提供？
                        │
            ┌───────────┴───────────┐
         调用方主动获取           外部传入
            │                       │
     ┌──────┴──────┐         ┌──────┴──────┐
  全局单例     服务定位器    构造函数注入    参数注入
  (最差)      (较差)        (推荐)        (推荐)
```

### 5.2 对比矩阵

| 维度 | 全局单例 | 服务定位器 | 工厂方法 | 依赖注入 |
|------|---------|----------|---------|---------|
| **耦合度** | 极高——直接依赖全局变量 | 高——依赖定位器 + 名称 | 中——依赖工厂接口 | 低——只依赖抽象接口 |
| **可测试性** | 差——全局状态污染 | 差——需管理注册表 | 中——需 mock 工厂 | 优——直接注入 mock |
| **编译期安全** | ⚠️ 类型安全但耦合 | ❌ 运行时类型断言 | ✅ 类型安全 | ✅ 类型安全 |
| **依赖可见性** | ❌ 完全隐藏 | ❌ 隐藏在函数体内 | ⚠️ 部分可见 | ✅ 签名中一目了然 |
| **样板代码** | 极少 | 少 | 中 | 中（手动）/ 少（Wire） |
| **并行测试** | ❌ 不安全 | ❌ 需隔离 | ⚠️ 取决于实现 | ✅ 天然隔离 |

### 5.3 决策流程

```
需要获取一个依赖？
    │
    ├─ 只有 1 个实现，且永远不需要测试替换？
    │   └─→ 直接 new，不需要 DI
    │
    ├─ 有多个实现，或需要测试时替换？
    │   └─→ 依赖注入（构造函数传接口）
    │
    ├─ 依赖图太复杂（20+ 个节点）？
    │   └─→ 依赖注入 + Wire / fx 辅助
    │
    └─ 想偷懒用全局变量或 Service Locator？
        └─→ 不要。
```

## 6 常见陷阱 / 反例

### 6.1 全局单例 — `trap/globalsingleton/`

```go
var db *sql.DB

func InitDB(dsn string) { db, _ = sql.Open("mysql", dsn) }
func GetDB() *sql.DB    { return db }

// Service 直接使用全局 db
func (s *UserService) GetUserByID(id string) {
    conn := GetDB()   // 隐式依赖！
    conn.QueryRow(...)
}
```

问题：
- **测试污染**：所有测试共享同一个 db，TestA 的写入影响 TestB
- **不能并行测试**：`go test -race` 会报告数据竞争
- **依赖不可见**：`GetUserByID(id string)` 签名看不出它需要数据库
- **无法替换**：测试时想用 SQLite？必须修改全局变量

### 6.2 服务定位器 — `trap/service_locator/`

```go
locator := NewServiceLocator()
locator.Register("userRepo", mysqlRepo)

// Service 从定位器中按名称取依赖
func NewOrderService(locator *ServiceLocator) *OrderService { ... }

func (s *OrderService) CreateOrder(userID string) error {
    repo := s.locator.Resolve("userRepo").(UserRepo)  // 运行时断言！
    ...
}
```

问题：
- **编译期不报错**：忘记注册 "userRepo"？编译通过，运行 panic
- **类型不安全**：`Resolve` 返回 `any`，断言失败 = panic
- **依赖隐藏**：`NewOrderService(locator)` 看不出实际依赖了什么
- **注册顺序**：必须先注册再使用，跨包时顺序难以保证

### 6.3 接口污染

```go
// ❌ 只有一个实现，却定义了接口——过度抽象
type UserServiceInterface interface {
    GetUser(id string) (*User, error)
    CreateUser(name, email string) (*User, error)
}

type userServiceImpl struct { ... }
```

Go 谚语：**The bigger the interface, the weaker the abstraction.** 只在有多个实现或需要 mock 时才定义接口。

### 6.4 循环依赖

```
ServiceA 依赖 ServiceB
ServiceB 依赖 ServiceA
→ Go 编译器直接报错：import cycle not allowed
```

解法：
- 提取公共接口到独立包
- 用事件/回调解耦
- 重新审视职责划分

### 6.5 过度注入（God Constructor）

```go
// ❌ 构造函数参数超过 5 个——说明 Service 职责太多
func NewOrderService(
    userRepo UserRepo,
    orderRepo OrderRepo,
    inventoryRepo InventoryRepo,
    paymentGateway PaymentGateway,
    notifier Notifier,
    logger Logger,
    cache Cache,
    config Config,
) *OrderService { ... }
```

解法：将大 Service 拆分为多个更小、更聚焦的 Service，或将相关依赖组合为一个 Options 结构体。

## 7 测试要点

| 测试场景 | 验证内容 | 对应测试函数 |
|---------|---------|------------|
| 创建用户成功 | ID/Name/Email 正确填充 | `TestCreateUser_Success` |
| 创建用户参数校验 | 空 name/email 返回 error | `TestCreateUser_EmptyName` |
| 查询已有用户 | 创建后能按 ID 查回 | `TestGetUser_Found` |
| 查询不存在用户 | 返回 error，不返回 nil 用户 | `TestGetUser_NotFound` |
| 更新邮箱成功 | 再次查询时 Email 已变更 | `TestUpdateEmail_Success` |
| 更新不存在用户 | 返回 error | `TestUpdateEmail_UserNotFound` |
| 生产环境装配 | App 和 UserService 非 nil | `TestInitializeApp_Production` |
| 多实例隔离 | 两个 TestApp 不共享状态 | `TestIsolation_MultipleApps` |

测试的关键点：

1. **每个测试创建独立的 App 实例** — `InitializeTestApp()` 每次返回全新的内存存储
2. **无需外部依赖** — InMemory 实现让测试可以在任何环境运行
3. **可并行执行** — 无共享状态，`t.Parallel()` 安全
4. **只使用标准库** — `t.Fatal`、`t.Errorf` 即可，无需 testify

## 8 成本模型

### 何时值得使用依赖注入

| 场景 | 原因 |
|------|------|
| Service 依赖外部资源（DB/Redis/MQ） | 测试时需要用 mock/内存实现替换 |
| 需要测试隔离 | 每个测试用独立依赖实例，不互相污染 |
| 同一接口有 3+ 种实现 | MySQL/PostgreSQL/SQLite/InMemory |
| 微服务架构 | 服务间通过接口解耦，方便独立部署和测试 |
| 插件系统 | 通过接口扩展功能，无需修改核心代码 |

### 何时是过度设计

| 场景 | 原因 |
|------|------|
| 简单 CLI 工具 | 没有外部依赖，直接调用即可 |
| 一次性脚本 | 不需要测试，不需要替换实现 |
| 只有一个实现且永远不会变 | 加接口和注入增加复杂度但不带来收益 |
| 性能极端敏感的热路径 | 接口调用有微小的间接开销（通常可忽略） |

### 成本对比

```
                简单          中等          复杂
                │              │              │
  直接 new      ●──── 最简单    │              │
                │              │              │
  手动 DI       │    ●──── 适中  │              │
                │              │              │
  Wire 生成     │              ●──── 自动化     │
                │              │              │
  fx 运行时     │              │        ●──── 功能最多
                │              │              │
  复杂度 ──────────────────────────────────────→
```

**经验法则**：如果你的 `InitializeApp` 函数超过 50 行，考虑引入 Wire。

## 9 适用场景与局限

### 适用场景

- **Web 服务（DB/Cache/MQ）**：最经典的 DI 场景。Service 依赖 Repo 接口，Repo 有 MySQL/Redis/InMemory 等实现
- **微服务**：服务间通过 gRPC/HTTP 客户端接口通信，测试时替换为 mock client
- **插件系统**：核心定义接口，插件实现接口并注册
- **命令行工具**：需要不同输出目标（stdout/file/network）时，注入 `io.Writer`
- **中间件链**：HTTP 中间件、gRPC 拦截器通过 DI 组合

### 局限

| 局限 | 说明 |
|------|------|
| 更多样板代码 | 每个依赖需要定义接口 + 构造函数 + 装配代码 |
| 理解依赖图 | 依赖关系分散在多个包中，需要阅读装配代码才能理解全貌 |
| 调试间接性 | 接口调用多了一层间接，断点需要跳到具体实现 |
| 过度抽象风险 | 容易为"未来可能"的需求创建不必要的接口 |

**缓解方法**：
- 用 Wire 减少样板代码
- 将装配逻辑集中在 `container/` 包，作为依赖图的"地图"
- 遵循 YAGNI——只在真正需要时才引入接口
