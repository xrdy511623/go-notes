# 享元模式 (Flyweight)

## 一句话定义

> **享元模式通过共享不可变的内在状态（intrinsic state），让大量细粒度对象复用同一份数据，大幅减少内存占用。**

---

## 核心价值

| 问题 | 享元的解法 |
|------|-----------|
| 百万级对象各自持有重复字符串 | **字符串驻留**：相同内容只保留一份，其余共享指针 |
| 渲染引擎中每个元素都复制样式/颜色 | **共享不可变对象**：工厂返回同一 *Style/*Color 指针 |
| 子串持有大缓冲区的引用导致 GC 无法回收 | `strings.Clone` **隔离**子串，享元池只保留最小分配 |
| 高并发下重复创建短生命周期对象 | 驻留池 + `sync.RWMutex` 下的**读写锁二次检查** |

---

## 内在状态 vs 外在状态

这是享元模式的核心区分：

| | 内在状态 (Intrinsic) | 外在状态 (Extrinsic) |
|---|---|---|
| **定义** | 对象自身不可变的、可共享的数据 | 依赖上下文的、每次使用都不同的数据 |
| **存储** | 享元对象内部 | 调用方持有或作为参数传入 |
| **示例** | 图标的位图数据、字体名称、颜色 RGBA | 图标的 x/y 坐标、缩放比例 |
| **生命周期** | 与享元工厂一致 | 与调用方一致 |

## 标准库与生态中的享元

### 1. `sync.Pool` — GC 感知的临时对象复用

```go
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

buf := bufPool.Get().(*bytes.Buffer)
buf.Reset()
// ... use buf ...
bufPool.Put(buf)
```

`sync.Pool` 是享元思想的变体：复用对象以减少分配。但它不是经典享元——Pool 中的对象**可变**且随时可能被 GC 清除。

### 2. `net/textproto` — HTTP header key 驻留

```go
// net/textproto/reader.go
// CanonicalMIMEHeaderKey 内部维护了一个 commonHeader map，
// 对常见 header key（"Content-Type"、"Accept" 等）返回预驻留字符串。
key := textproto.CanonicalMIMEHeaderKey("content-type")
// key == "Content-Type"（从全局 map 中返回，零分配）
```

### 3. `regexp` — 编译一次，复用多次

```go
// 包级别编译，所有 goroutine 共享同一个 *Regexp
var emailRe = regexp.MustCompile(`^[a-zA-Z0-9._%+-]+@[a-zA-Z0-9.-]+$`)

func validate(email string) bool {
    return emailRe.MatchString(email) // 不重复编译
}
```

### 4. 生态实践

| 库 | 享元技术 |
|---|---|
| **Prometheus client_golang** | 标签值 interner，避免每次 Observe 分配新字符串 |
| **Thanos** | `labels.Builder` + interner 去重高基数标签 |
| **go-json** | 结构体字段名缓存，编码时零分配 |
| **fasthttp** | header key/value 内部池化复用 |

### 核心 API（intern 包）

```go
type Interner struct { /* ... */ }

func New() *Interner

func (p *Interner) Get(s string) string   // 驻留并返回规范副本
func (p *Interner) Len() int              // 池中唯一字符串数
func (p *Interner) Hits() int64           // 累计命中次数
func (p *Interner) Misses() int64         // 累计未命中次数
func (p *Interner) Evict(s string) bool   // 移除指定条目
func (p *Interner) Reset()                // 清空并重置计数器
```

### 三个具体享元

#### 1. icon — 图标工厂

```go
factory := icon.NewFactory()
loader := func(name string) []byte { return loadBitmap(name) }

star := factory.Get("star", loader)   // 首次加载
star2 := factory.Get("star", loader)  // 复用，star == star2
render(star, x, y, scale)             // 外在状态作为参数
```

- `Data []byte` 是内在状态（共享的位图数据）
- 位置、缩放是外在状态（调用方持有）
- `loader` 函数实现**懒加载**：只在首次访问时执行

#### 2. style — 文本样式注册表

```go
reg := style.NewRegistry()
s1 := reg.Get("Arial", "red", 14, false)
s2 := reg.Get("Arial", "red", 14, false)
// s1 == s2（同一指针）
```

- `Style` 结构体**同时用作 map key 和返回值**——所有字段构成唯一标识
- 适用于文档渲染：1000 个段落可能只有 5 种样式

#### 3. color — 命名颜色调色板

```go
pal := color.NewPalette()
red := pal.Get("red", 255, 0, 0, 255)
red2 := pal.Get("red", 255, 0, 0, 255)
// red == red2（同一指针）
```

- 以名称为 key 的简单享元
- 适用于渲染引擎中大量元素引用少量命名颜色

## 设计决策

### 1. `strings.Clone` 隔离子串

```go
cloned := strings.Clone(s)
p.pool[cloned] = cloned
```

调用方传入的字符串可能是某个大缓冲区的子串（例如从文件中按行读取）。直接驻留子串会导致整个缓冲区无法被 GC 回收。`strings.Clone`（Go 1.20+）创建独立副本，只保留实际内容的分配。

### 2. RWMutex 下的读写锁二次检查

```go
func (p *Interner) Get(s string) string {
    p.mu.RLock()
    if canonical, ok := p.pool[s]; ok {  // 快速路径：读锁
        p.mu.RUnlock()
        return canonical
    }
    p.mu.RUnlock()

    p.mu.Lock()                           // 慢路径：写锁
    defer p.mu.Unlock()
    if canonical, ok := p.pool[s]; ok {   // 再次检查（避免竞态）
        return canonical
    }
    // ... insert
}
```

热路径（cache hit）只需 `RLock`，不阻塞其他读者。升级到写锁后再次检查，避免两个 goroutine 同时 miss 导致重复插入。

### 3. 结构体用作 map key（style 包）

```go
type Style struct { Font string; Size int; Color string; Bold bool }
styles map[Style]*Style
```

Go 的结构体如果所有字段都是 comparable 的，就可以作为 map key。这比手动拼接字符串 key 更类型安全、更高效（省去 fmt.Sprintf 的分配）。

### 4. Loader 函数实现懒加载（icon 包）

```go
func (f *Factory) Get(name string, loader func(string) []byte) *Icon
```

加载逻辑由调用方提供（依赖倒置），工厂只负责缓存。这样 `icon` 包不依赖任何 I/O 库。

### 5. `atomic.Int64` 计数器

`Hits()` / `Misses()` 不需要获取互斥锁即可读取。写入时虽然已持有 `mu`，但使用 atomic 保证与无锁读取的可见性。

## 享元 vs 对象池 vs 缓存

| 维度 | 享元 (Flyweight) | 对象池 (Object Pool) | 缓存 (Cache) |
|------|-----------------|---------------------|-------------|
| **核心目标** | 共享不可变数据减少内存 | 复用可变对象减少分配 | 避免重复计算/IO |
| **对象可变性** | ❌ 不可变 | ✅ 可变（Get/Reset/Put） | 通常不可变 |
| **生命周期** | 与工厂一致（长期持有） | 借出/归还（短期借用） | TTL / LRU 淘汰 |
| **Go 典型** | string intern | `sync.Pool` | `groupcache` |
| **所有权** | 共享（多个引用者） | 独占（借出期间） | 共享（只读） |

---

## 陷阱

### 共享可变对象（trap/mutableflyweight）

```go
type MutableIcon struct {
    Name  string
    Data  []byte
    Scale float64  // ❌ 可变字段
}

a := factory.Get("star")
b := factory.Get("star")
a.Scale = 2.0
// b.Scale == 2.0 ← b 被意外修改！
```

**规则**：享元对象**必须不可变**。可变的外在状态由调用方自己管理，不存储在享元中。

---

## 适用场景

- 日志系统中的级别字符串驻留（"error" / "warning" / "info"）
- HTTP header key 规范化缓存
- 游戏引擎中的纹理/图标共享
- 文档渲染中的字体/样式去重
- 编译器中的符号表（标识符驻留）

## 局限

- **内存泄漏风险**：驻留池只增不减时需要 `Evict` 或 TTL 淘汰策略
- **不适合高基数数据**：如果每个字符串都是唯一的，驻留反而增加开销（map + Clone）
- **线程安全开销**：高竞争场景下 `RWMutex` 成为瓶颈 → 考虑分片（sharded map）
- **不可变约束**：调用方必须遵守"不修改共享对象"的契约，编译器无法强制（Go 没有 const 引用）

---

## 享元 vs 缓存的失效策略

享元和缓存都是"存起来复用"，但失效策略完全不同：

| 维度 | 享元 (Flyweight) | 缓存 (Cache) |
|------|-----------------|-------------|
| **失效策略** | 通常不失效（永久驻留） | TTL / LRU / LFU 淘汰 |
| **数据特征** | 不可变（创建后不变） | 可变（源数据可能更新） |
| **一致性** | 无需考虑（不可变 = 永远一致） | 需要失效策略保证一致性 |
| **内存管理** | 需要 Evict 或 Reset 手动管理 | 自动淘汰 |

### 高基数场景为什么不该驻留

享元的前提是"大量对象共享少量唯一值"。如果唯一值数量极大（高基数），享元反而是负优化：

```
低基数（适合享元）：
  100万条日志 × 5 个级别字符串 → 驻留 5 个字符串，省 999,995 次分配

高基数（不适合享元）：
  100万条日志 × 100万个唯一 request ID → 驻留 100万个字符串
  → map 本身占用大量内存
  → 每次 Get 都是 miss，零复用
  → RWMutex 竞争成为瓶颈
```

判断标准：`唯一值数量 / 总引用数量`（基数比）：
- < 0.01（1%）：非常适合享元
- 0.01 - 0.1：可能有收益，需要度量
- \> 0.1：通常不值得

## 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| 驻留唯一性 | 相同字符串返回同一指针 |
| 不同字符串独立 | 不同内容返回不同指针 |
| Hit/Miss 计数 | 首次 Get 是 miss，第二次是 hit |
| Evict 有效 | Evict 后再 Get 是 miss |
| Reset 清空 | Reset 后 Len() 为 0 |
| 并发安全 | 多 goroutine 同时 Get 不 race |
| 子串隔离 | 驻留子串不持有原大缓冲区的引用 |
| 可变享元陷阱 | 验证共享可变对象的修改会影响其他引用者 |

## 成本模型

### 何时值得用享元

- 大量对象引用少量唯一值（低基数）
- 对象不可变——共享安全
- 内存是瓶颈——pprof 显示字符串/对象分配占用大量堆

### 何时是过度设计

- 唯一值数量接近总引用数量（高基数）——驻留无收益
- 对象是可变的——共享可变对象是 bug 工厂
- 内存不是瓶颈——过早优化
- 对象生命周期短——享元池会让它们活得更久，反而增加内存占用
