# 装饰器 / 包装器模式详解

装饰器模式（Decorator / Wrapper Pattern）是 Go 语言中最自然的设计模式。得益于隐式接口和组合优于继承的设计哲学，Go 的标准库本身就是一座装饰器模式的教科书——`io.Reader` / `io.Writer` 的层层包装体系是这一模式的灵魂所在。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.

翻译：动态地为对象附加额外职责。装饰器为扩展功能提供了一种比子类化更灵活的替代方案。

Go 中的装饰器不需要继承，也不需要抽象类：

```
┌──────────────────────────────────────────────────┐
│                  io.Reader                        │
│              Read(p []byte) (int, error)          │
└──────────────────────────────────────────────────┘
        ▲              ▲              ▲
        │              │              │
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ strings.Reader│ │CountingReader│ │ProgressReader│
│  (数据源)     │ │  (计数装饰)   │ │  (进度装饰)   │
└──────────────┘ └──────────────┘ └──────────────┘
                       │              │
                       │  内部持有      │ 内部持有
                       │  io.Reader    │ io.Reader
                       ▼              ▼
                  任意 io.Reader  任意 io.Reader
```

核心约束：

- **接口一致性**：装饰器的输入和输出是**同一接口**——接收 `io.Reader`，自身也实现 `io.Reader`
- **透明组合**：调用方无需感知装饰器的存在，可以无限叠加
- **职责单一**：每个装饰器只增加一种能力（计数、缓冲、压缩、加密……）

### 与责任链模式的区别

两者都涉及"链式处理"，但意图截然不同：

| 维度 | 装饰器（Decorator） | 责任链（Chain of Responsibility） |
|------|--------------------|---------------------------------|
| 目标 | **增强**同一接口的能力 | **传递**处理权，直到被处理 |
| 调用关系 | 必定调用内层（透明转发） | 可以不调用 next（短路中断） |
| 返回类型 | 与被装饰对象**相同接口** | 不要求相同接口 |
| 典型场景 | `bufio.NewReader(r)` 增加缓冲 | Auth 中间件拒绝未授权请求 |
| 组合方式 | 嵌套包装 `D3(D2(D1(obj)))` | 链式传递 `A → B → C → handler` |
| 客户端感知 | 不感知（接口相同） | 不感知（统一入口） |

简单记忆：**装饰器 = 增强，责任链 = 筛选**。

## 2 标准库与生态中的先例

### 2.1 io.Reader / io.Writer — 装饰器模式的灵魂

Go 的 I/O 体系是装饰器模式最经典的实践：

```go
// 原始数据源
var r io.Reader = file

// 层层包装，每层增加一种能力
r = bufio.NewReader(r)           // +缓冲：减少系统调用次数
r = gzip.NewReader(r)            // +解压：透明处理 gzip 格式
r = json.NewDecoder(r)           // +解码：将字节流解析为 JSON

// 调用方只看到 io.Reader，不关心中间有几层包装
```

这就是 Rob Pike 所说的"小接口的力量"——`io.Reader` 只有一个方法，却能通过装饰器组合出无限功能。

标准库中的 Reader/Writer 装饰器：

| 装饰器 | 增加的能力 | 签名 |
|--------|----------|------|
| `bufio.NewReader` | 缓冲读取 | `func(io.Reader) *bufio.Reader` |
| `bufio.NewWriter` | 缓冲写入 | `func(io.Writer) *bufio.Writer` |
| `gzip.NewReader` | gzip 解压 | `func(io.Reader) (*gzip.Reader, error)` |
| `gzip.NewWriter` | gzip 压缩 | `func(io.Writer) *gzip.Writer` |
| `io.LimitReader` | 限制读取字节数 | `func(io.Reader, int64) io.Reader` |
| `io.TeeReader` | 读取同时写入 | `func(io.Reader, io.Writer) io.Reader` |
| `cipher.StreamReader` | 流式解密 | 包装 `io.Reader` + `cipher.Stream` |
| `base64.NewDecoder` | Base64 解码 | `func(io.Encoding, io.Reader) io.Reader` |

关键洞察：这些装饰器的构造函数都遵循同一模式——**接收接口，返回实现了同一接口的具体类型**。

### 2.2 http.ResponseWriter 包装

标准库的 `http.ResponseWriter` 接口不提供读取状态码和响应大小的方法，但日志和监控中间件需要这些信息。解决方案：用装饰器包装。

```go
type ResponseRecorder struct {
    http.ResponseWriter          // 嵌入原始接口
    statusCode   int             // 捕获状态码
    bytesWritten int64           // 统计响应体大小
}

func (r *ResponseRecorder) WriteHeader(code int) {
    r.statusCode = code
    r.ResponseWriter.WriteHeader(code)  // 转发给底层
}

func (r *ResponseRecorder) Write(b []byte) (int, error) {
    n, err := r.ResponseWriter.Write(b) // 转发给底层
    r.bytesWritten += int64(n)          // 额外统计
    return n, err
}
```

几乎每个 Go Web 框架的监控中间件都采用这种方式：

- **Gin**：`gin.ResponseWriter` 包装了 `http.ResponseWriter`，额外记录 `Status()` 和 `Size()`
- **Chi**：`middleware.WrapResponseWriter` 同一思路
- **Prometheus**：`promhttp.InstrumentHandlerResponseSize` 用装饰器统计响应大小

### 2.3 go-kit endpoint.Middleware

go-kit 的 `endpoint.Middleware` 是装饰器模式在服务层的应用：

```go
type Endpoint func(ctx context.Context, request interface{}) (interface{}, error)
type Middleware func(Endpoint) Endpoint
```

每个 Middleware 接收一个 `Endpoint`，返回一个增强后的 `Endpoint`——与 `io.Reader` 装饰器如出一辙：

```go
// 层层包装 Endpoint
var ep endpoint.Endpoint = makeOrderEndpoint(svc)
ep = loggingMiddleware(logger)(ep)     // +日志
ep = instrumentingMiddleware(hist)(ep) // +监控
ep = rateLimitMiddleware(limiter)(ep)  // +限流
ep = circuitBreaker(breaker)(ep)       // +熔断
```

### 2.4 Prometheus InstrumentHandler

Prometheus 提供了一组 HTTP Handler 装饰器：

```go
handler := http.HandlerFunc(myHandler)
handler = promhttp.InstrumentHandlerDuration(hist, handler)    // +延迟统计
handler = promhttp.InstrumentHandlerCounter(counter, handler)  // +请求计数
handler = promhttp.InstrumentHandlerResponseSize(size, handler) // +响应大小
```

每一层都是标准的 `http.Handler` → `http.Handler` 装饰器。

## 3 本项目的实现

### 3.1 io.Reader 装饰器 — `reader/reader.go`

实现了两个 Reader 装饰器，展示装饰器模式的核心思想：

**CountingReader** — 统计累计读取字节数：

```go
type CountingReader struct {
    r     io.Reader
    count int64
}

func NewCountingReader(r io.Reader) *CountingReader {
    return &CountingReader{r: r}
}

func (c *CountingReader) Read(p []byte) (int, error) {
    n, err := c.r.Read(p)
    atomic.AddInt64(&c.count, int64(n))  // 额外能力：原子计数
    return n, err                         // 透明转发
}
```

核心 API：

| 函数 | 作用 | 说明 |
|------|------|------|
| `NewCountingReader(r)` | 包装任意 Reader | 返回的 `*CountingReader` 也实现 `io.Reader` |
| `BytesRead()` | 读取累计字节数 | 并发安全（atomic） |

**ProgressReader** — 进度回调：

```go
type ProgressReader struct {
    r          io.Reader
    total      int64
    read       int64
    onProgress func(bytesRead, total int64)
}
```

典型场景：文件上传进度条、大文件处理监控。

**装饰器组合**：

```go
// 组合多个装饰器：ProgressReader 先上报进度，CountingReader 再统计总量
base := strings.NewReader(data)
progress := reader.NewProgressReader(base, total, reportFunc)
counting := reader.NewCountingReader(progress)

result, _ := io.ReadAll(counting)
fmt.Printf("总字节数: %d\n", counting.BytesRead())
```

每一层都是 `io.Reader`，可以无限叠加，调用方完全无感。

### 3.2 http.ResponseWriter 包装器 — `responsewriter/responsewriter.go`

生产级的 ResponseWriter 装饰器：

```go
type ResponseRecorder struct {
    http.ResponseWriter
    statusCode   int
    bytesWritten int64
    wroteHeader  bool
}
```

核心 API：

| 函数 | 作用 | 说明 |
|------|------|------|
| `NewResponseRecorder(w)` | 包装 ResponseWriter | 默认状态码 200 |
| `StatusCode()` | 获取响应状态码 | WriteHeader 未调用时返回 200 |
| `BytesWritten()` | 获取响应体大小 | 累计所有 Write 调用 |
| `Unwrap()` | 返回底层 Writer | 配合 Go 1.20+ ResponseController |

设计细节：

1. **幂等的 WriteHeader**：重复调用只取第一次（与 `net/http` 行为一致）
2. **隐式 200**：直接 Write 不调 WriteHeader 时自动设为 200
3. **零缓冲**：数据直接写入底层 Writer，不缓存到内存
4. **Unwrap 支持**：避免装饰器导致的接口丢失（见 3.3）

在中间件中使用：

```go
func LoggingMiddleware(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        rr := responsewriter.NewResponseRecorder(w)
        next(rr, r)  // handler 看到的是 http.ResponseWriter，无感知装饰器
        log.Printf("[%s] %s → %d (%d bytes)",
            r.Method, r.URL.Path, rr.StatusCode(), rr.BytesWritten())
    }
}
```

### 3.3 反面示例：接口丢失 — `trap/interfaceloss/`

Go 的 `http.ResponseWriter` 底层实现（`*http.response`）同时实现了 `http.Flusher` 和 `http.Hijacker`。但如果装饰器只声明实现 `http.ResponseWriter`，这些可选接口会**静默丢失**：

```go
type NaiveWrapper struct {
    http.ResponseWriter  // 只有 Header/Write/WriteHeader
    statusCode int
}

func DemoInterfaceLoss(w http.ResponseWriter) {
    wrapped := WrapNaive(w)

    // w 是 Flusher ✅
    _, ok1 := w.(http.Flusher)          // true

    // wrapped 不是 Flusher ❌
    _, ok2 := interface{}(wrapped).(http.Flusher)  // false
}
```

**为什么这是危险的？**

- SSE（Server-Sent Events）依赖 `Flusher.Flush()` 推送实时数据
- WebSocket 升级依赖 `Hijacker.Hijack()` 接管连接
- 接口丢失不会编译报错，只在运行时静默失效——这是最难排查的 bug 之一

**正确做法**：实现 `Unwrap() http.ResponseWriter` 方法。Go 1.20+ 的 `http.ResponseController` 会递归调用 `Unwrap()` 发现底层的可选接口。本项目的 `ResponseRecorder` 已实现此方法。

### 3.4 调用方

```go
import (
    "go-notes/designpattern/decorator/reader"
    "go-notes/designpattern/decorator/responsewriter"
)

func main() {
    // io.Reader 层层包装
    base := strings.NewReader(data)
    progress := reader.NewProgressReader(base, total, reportFunc)
    counting := reader.NewCountingReader(progress)
    result, _ := io.ReadAll(counting)

    // http.ResponseWriter 装饰器（用在中间件中）
    rr := responsewriter.NewResponseRecorder(w)
    next(rr, r)
    log.Printf("status=%d size=%d", rr.StatusCode(), rr.BytesWritten())
}
```

## 4 设计决策解析

### 4.1 为什么 Go 的装饰器比 Java 更自然？

Java 的装饰器需要抽象类 + 继承：

```java
// Java: 需要 4 层类继承
abstract class ReaderDecorator extends Reader {
    protected Reader wrapped;
    ReaderDecorator(Reader r) { this.wrapped = r; }
}
class CountingReader extends ReaderDecorator { ... }
```

Go 只需要组合 + 隐式接口：

```go
// Go: 持有接口，实现接口，完事
type CountingReader struct {
    r io.Reader  // 组合，不是继承
}
func (c *CountingReader) Read(p []byte) (int, error) { ... }
```

Go 的优势：

1. **无需声明实现**：只要有 `Read` 方法就是 `io.Reader`，不用写 `implements`
2. **无类层次**：不需要 `AbstractDecorator` → `ConcreteDecorator` 的继承链
3. **小接口**：`io.Reader` 只有 1 个方法，实现装饰器的成本极低
4. **组合优于继承**：Go 的设计哲学天然支持装饰器模式

### 4.2 小接口原则 — 装饰器模式的基石

装饰器的实现成本与接口方法数成正比。Go 标准库的接口普遍很小：

| 接口 | 方法数 | 装饰器实现成本 |
|------|--------|--------------|
| `io.Reader` | 1 | 极低 |
| `io.Writer` | 1 | 极低 |
| `http.Handler` | 1 | 极低 |
| `http.ResponseWriter` | 3 | 低 |
| `sort.Interface` | 3 | 低 |
| `database/sql.Driver` | 1 | 极低 |

这不是巧合——Go 的设计者有意将接口保持在最小规模，正是为了让装饰器和其他组合模式能低成本地实现。

引用 Go Proverbs：

> The bigger the interface, the weaker the abstraction.

接口越大，抽象越弱。大接口（10+ 方法）会让装饰器变得笨重——每个方法都需要转发，即使只想增强其中一个。

### 4.3 嵌入接口 vs 持有接口

两种实现装饰器的方式：

```go
// 方式 A：嵌入接口（struct embedding）
type RecorderA struct {
    http.ResponseWriter  // 嵌入
    statusCode int
}

// 方式 B：持有接口（字段引用）
type RecorderB struct {
    w          http.ResponseWriter  // 持有
    statusCode int
}
```

| 维度 | 嵌入接口 | 持有接口 |
|------|---------|---------|
| 未覆盖的方法 | 自动转发 | 必须手动转发 |
| 代码量 | 少（只写想覆盖的方法） | 多（每个方法都要转发） |
| 接口丢失风险 | 低（嵌入字段的方法被提升） | 无此问题 |
| 适用场景 | 接口方法较多时 | 接口方法 1-2 个时 |

本项目的选择：
- `ResponseRecorder` 使用**嵌入接口**——`http.ResponseWriter` 有 3 个方法，只需覆盖 `Write` 和 `WriteHeader`，`Header()` 自动转发
- `CountingReader` 使用**持有接口**——`io.Reader` 只有 1 个方法，没有可省略的转发

### 4.4 Unwrap 模式 — Go 1.20+ 的标准解法

Go 1.20 引入了 `http.ResponseController`，它通过递归调用 `Unwrap()` 方法来发现被装饰器隐藏的可选接口：

```go
// Go 标准库的逻辑（简化）
func findFlusher(w http.ResponseWriter) (http.Flusher, bool) {
    for {
        if f, ok := w.(http.Flusher); ok {
            return f, true
        }
        u, ok := w.(interface{ Unwrap() http.ResponseWriter })
        if !ok {
            return nil, false
        }
        w = u.Unwrap()  // 剥开一层装饰器
    }
}
```

这与 Go 1.13 的 `errors.Unwrap()` 是同一设计思路——通过约定的 `Unwrap()` 方法支持链式解包。

### 4.5 装饰器 vs 中间件 — 概念辨析

在 Go 社区中，"中间件"（Middleware）这个词经常被混用。严格来说：

```
装饰器（Decorator）：
  func(io.Reader) io.Reader          ← 增强同一接口
  func(http.Handler) http.Handler    ← 增强同一接口

责任链式中间件（Chain of Responsibility）：
  func(http.HandlerFunc) http.HandlerFunc  ← 可以短路
```

实际上，Go 的 HTTP 中间件同时具有两种模式的特征：
- 当它**总是调用 next**（如 logging、metrics）→ 行为是装饰器
- 当它**可能不调用 next**（如 auth、rate-limit）→ 行为是责任链

这种"混血"设计是 Go 的务实风格——不执着于理论分类，关注实际效果。

## 5 适用场景与局限

### 适用

- **I/O 管道**：缓冲、压缩、加密、编码——标准库的 Reader/Writer 体系
- **HTTP 监控**：记录状态码、统计响应大小、计算请求延迟
- **日志增强**：给 Writer 增加前缀、时间戳、颜色
- **服务治理**：限流、熔断、重试、超时——go-kit Middleware 体系
- **数据库驱动**：SQL 日志记录、慢查询告警、连接池统计

### 局限

- **接口丢失**：包装后可能丢失底层的可选接口（如 `http.Flusher`），需要 `Unwrap()` 或条件转发
- **调试困难**：多层装饰器嵌套后，堆栈跟踪变深，错误来源难以定位
- **性能开销**：每层装饰器增加一次虚方法调用，极端场景（高频 I/O）下可能可测量（但通常可忽略）
- **不适合大接口**：如果接口有 10+ 方法，装饰器的转发代码会非常冗长

## 6 完整接口透传清单

Go 的 `http.ResponseWriter` 底层实现同时满足多个可选接口。装饰器必须注意透传：

| 接口 | 用途 | 丢失后果 |
|------|------|---------|
| `http.Flusher` | SSE、流式响应 | SSE 数据不推送 |
| `http.Hijacker` | WebSocket 升级 | WebSocket 连接失败 |
| `http.Pusher` | HTTP/2 Server Push | Push 功能静默失效 |
| `io.ReaderFrom` | `io.Copy` 零拷贝优化 | 性能退化（回退到缓冲区拷贝） |

### 反例：只包主接口导致能力丢失

```go
// ❌ NaiveWrapper 只实现 ResponseWriter，Flusher 丢失
type NaiveWrapper struct {
    http.ResponseWriter
    statusCode int
}

// SSE handler 拿到 NaiveWrapper 后：
flusher, ok := w.(http.Flusher) // false! SSE 静默失败
```

### 正确做法

**方案 A：实现 Unwrap()（推荐，Go 1.20+）**

```go
func (r *ResponseRecorder) Unwrap() http.ResponseWriter {
    return r.ResponseWriter
}
// http.ResponseController 会递归调用 Unwrap() 找到底层的 Flusher
```

**方案 B：条件实现可选接口**

```go
type flusherRecorder struct {
    *ResponseRecorder
}

func (f *flusherRecorder) Flush() {
    if fl, ok := f.ResponseWriter.(http.Flusher); ok {
        fl.Flush()
    }
}

func NewResponseRecorder(w http.ResponseWriter) http.ResponseWriter {
    rr := &ResponseRecorder{ResponseWriter: w}
    if _, ok := w.(http.Flusher); ok {
        return &flusherRecorder{rr}
    }
    return rr
}
```

## 8 成本模型

### 何时值得用装饰器

- `io.Reader` / `io.Writer` 增强——Go 标准库的设计就是装饰器
- HTTP ResponseWriter 包装——监控、日志中间件的标配
- 需要无限叠加、自由组合的场景

### 何时是过度设计

- 目标接口有 10+ 方法——转发代码太多，考虑用代码生成或嵌入
- 只增加一次功能且不需要复用——直接内联更清晰
- 性能极端敏感——每层装饰器增加一次虚方法调用（99.9% 场景可忽略）
