# 简单工厂模式详解

简单工厂（Simple Factory）是最直观的创建型模式：一个工厂函数根据输入参数，决定创建哪种具体实现。Go 语言中虽然没有 class 和继承，但接口 + switch 天然适合这种模式。它是所有工厂模式的基础，也是实际项目中最高频出现的创建模式。

---

## 1 模式定义

GoF《设计模式》将工厂相关模式归类为**创建型模式**：

> Define an interface for creating an object, but let subclasses decide which class to instantiate.

简单工厂是工厂方法的简化版 — 不通过子类多态，而是在**单个函数内用条件分支**决定创建哪种实例。严格来说它不在 GoF 23 种模式之列，但因为极其实用，被广泛视为工厂模式家族的入门成员。

模式由三个角色组成：

```
                                    ┌──────────────┐
                              ┌───→ │ dingDingSender │
                              │     └──────────────┘
┌────────┐  scene   ┌────────┤     ┌──────────────┐
│ 调用方  │ ───────→ │ 工厂函数 ├───→ │ weixinSender  │
└────────┘          └────────┤     └──────────────┘
                              │     ┌──────────────┐
                              └───→ │ feishuSender  │
                                    └──────────────┘
                                          │
                                          ▼
                                     返回 Sender 接口
```

- **接口（Product）**：定义产品的统一行为 — `Sender`
- **具体实现（Concrete Product）**：实现接口的不同变体 — `dingDingSender`、`weixinSender`、`feishuSender`
- **工厂函数（Factory）**：根据参数创建并返回具体实现 — `NewSender(scene)`

调用方只依赖接口，不关心具体类型 → **面向接口编程**。

## 2 标准库与生态中的先例

简单工厂的思想在 Go 标准库和生态中无处不在：

| 场景 | 工厂函数 | 选择依据 | 说明 |
|------|---------|---------|------|
| `errors` | `errors.New(text)` | 文本内容 | 最简单的工厂 — 一个参数创建一个对象 |
| `net/http` | `http.NewRequest(method, ...)` | HTTP 方法 | 根据 method 构造不同的请求 |
| `crypto` | `crypto.Hash.New()` | 哈希算法常量 | `crypto.SHA256.New()` 返回对应的 hash.Hash |
| `encoding/json` | `json.NewEncoder(w)` | Writer 类型 | 根据输出目标创建编码器 |
| `log/slog` | `slog.New(handler)` | Handler 实现 | 根据不同 handler 创建 logger |
| `go-zero` | `logx.NewWriter(cfg)` | 配置参数 | 根据配置选择日志输出后端 |
| K8s client | `client.New(config)` | 集群配置 | 根据不同配置连接不同集群 |

### errors.New — 最简形式

```go
err := errors.New("something went wrong")
```

严格来说 `errors.New` 没有分支逻辑，但它体现了工厂的核心思想：**调用方不需要知道底层类型**（`*errors.errorString`），只通过 `error` 接口交互。

### crypto.Hash — 枚举驱动的工厂

```go
import (
    "crypto"
    _ "crypto/sha256" // 注册 SHA256 实现
)

func main() {
    h := crypto.SHA256.New() // 枚举常量 → hash.Hash 实例
    h.Write([]byte("hello"))
    fmt.Printf("%x\n", h.Sum(nil))
}
```

`crypto.Hash` 是一个 `uint` 类型的枚举，`New()` 方法内部就是一个简单工厂 — 根据枚举值查找对应的实现。这与本项目的 `Scene` + `NewSender` 思路一致。

## 3 核心原理

### 3.1 依赖反转

简单工厂模式的根基是**依赖反转原则（DIP）**：

```
❌ 没有工厂：调用方直接依赖具体类型

  main.go → dingDingSender
  main.go → weixinSender
  main.go → feishuSender
  （新增渠道 → 修改 main.go 的 import 和构造逻辑）

✅ 有工厂：调用方只依赖接口

  main.go → Sender 接口 ← dingDingSender
                         ← weixinSender
                         ← feishuSender
  （新增渠道 → 只修改工厂的 switch）
```

修改范围从"所有调用方"收缩到"一个工厂函数" — 这是简单工厂最核心的价值。

### 3.2 隐藏构造细节

工厂函数封装了"选择哪个实现"的决策。调用方不需要知道：
- 有哪些具体结构体
- 它们的构造方式
- 选择逻辑的细节

调用方只需要传入一个标识（Scene），拿回一个接口。这使得**底层实现可以自由演化**，不影响调用方。

### 3.3 单一入口

所有创建都经过工厂函数，形成一个**统一入口**。这带来几个好处：
- **日志/监控**：可以在工厂中记录创建了哪种实例
- **校验**：可以在工厂中做前置检查（如参数校验）
- **缓存**：如果需要，可以在工厂中实现实例复用
- **测试**：可以替换工厂函数来注入 mock

## 4 本项目的实现

### 4.1 接口与场景定义

```go
type Scene int

const (
    SceneDingDing Scene = iota + 1
    SceneWeixin
    SceneFeishu
)

type Sender interface {
    Send(message string) error
}
```

设计要点：
- `Scene` 是自定义类型而非裸 `int` → 类型安全，编译器阻止传入无关整数
- `iota + 1` 从 1 开始 → 零值 `Scene(0)` 表示未初始化，工厂会拒绝
- `String()` 方法让 Scene 在日志和错误信息中可读

核心 API：

| 函数 | 作用 | 对标标准库 |
|------|------|-----------|
| `NewSender(scene)` | 根据场景创建 Sender（返回 error） | `crypto.Hash.New()` |
| `MustNewSender(scene)` | 根据场景创建 Sender（失败 panic） | `regexp.MustCompile` |
| `Scenes()` | 列出所有已定义的场景 | `sql.Drivers()` |
| `Scene.String()` | 场景的可读名称 | `fmt.Stringer` |

### 4.2 工厂函数

```go
func NewSender(scene Scene) (Sender, error) {
    switch scene {
    case SceneDingDing:
        return &dingDingSender{}, nil
    case SceneWeixin:
        return &weixinSender{}, nil
    case SceneFeishu:
        return &feishuSender{}, nil
    default:
        return nil, fmt.Errorf("simplefactory: unknown scene %v", scene)
    }
}
```

设计要点：
- 返回 `(Sender, error)` 而非裸 `Sender` → 未知场景返回错误，不会导致 nil-pointer panic
- 具体结构体不导出（小写开头） → 强制通过工厂创建
- 错误信息使用 `%v`，自动调用 `Scene.String()` 输出可读名称

### 4.3 具体实现

```go
type dingDingSender struct{}

func (d *dingDingSender) Send(message string) error {
    fmt.Printf("Using DingDing to send message: %v\n", message)
    return nil
}
```

本项目提供了三个具体实现，模拟不同的消息渠道：

| 实现 | 场景常量 | 职责 |
|------|---------|------|
| `dingDingSender` | `SceneDingDing` | 钉钉消息发送 |
| `weixinSender` | `SceneWeixin` | 微信消息发送 |
| `feishuSender` | `SceneFeishu` | 飞书消息发送 |

所有实现遵循相同模式：实现 `Sender` 接口，结构体不导出。三者结构完全一致 — 真实项目中，不同实现的 `Send` 逻辑会有显著差异（HTTP 调用、SDK 封装等）。

### 4.4 使用方式

```go
// 标准用法：处理可能的错误
s, err := simplefactory.NewSender(simplefactory.SceneDingDing)
if err != nil {
    log.Fatal(err)
}
s.Send("Hello")

// 启动阶段：已知场景，失败即 panic
s := simplefactory.MustNewSender(simplefactory.SceneDingDing)
s.Send("Hello")

// 遍历所有场景
for _, scene := range simplefactory.Scenes() {
    fmt.Printf("Available: %v\n", scene)
}
```

## 5 设计决策解析

### 5.1 为什么用 Scene 类型而非字符串？

```go
// 方案 A：字符串
func NewSender(name string) (Sender, error)
// 调用：NewSender("dingding") — 拼写错误只能运行时发现

// 方案 B：自定义类型（本项目选择）
func NewSender(scene Scene) (Sender, error)
// 调用：NewSender(SceneDingDing) — 编译器检查常量名
```

简单工厂的实现是**封闭集合**（已知的有限几种），用枚举常量比字符串更安全。如果实现是**开放集合**（可动态扩展），则应该用注册工厂模式。

| 维度 | 枚举常量（Scene） | 字符串（string） |
|------|-----------------|-----------------|
| 编译期安全 | ✅ `SceneDingding` 拼错编译报错 | ❌ `"dingding"` 拼错运行时才发现 |
| IDE 支持 | ✅ 自动补全、跳转到定义 | ❌ 无法补全字符串 |
| 配置驱动 | ❌ 不能直接从 JSON/YAML 读取 | ✅ 天然支持 |
| 扩展性 | 需修改常量定义 | 任何字符串都行 |

### 5.2 为什么 iota + 1 而非从 0 开始？

```go
const (
    SceneDingDing Scene = iota + 1  // 值为 1
    SceneWeixin                      // 值为 2
    SceneFeishu                      // 值为 3
)
```

如果从 0 开始，`Scene` 的零值 `Scene(0)` 就等于 `SceneDingDing` — 这意味着一个**未初始化的变量**会被当作有效的场景处理：

```go
var scene Scene             // 零值 Scene(0)
s, err := NewSender(scene)  // 如果 iota 从 0 开始，这会返回 dingDingSender
                             // 而不是报错，是一个静默的 bug
```

`iota + 1` 让零值落入 `default` 分支，返回错误。这是 Go 社区的最佳实践 — proto3、gRPC status code、HTTP status 都遵循"零值 = 无效/未知"的约定。

### 5.3 为什么返回 error 而非 panic？

```go
func NewSender(scene Scene) (Sender, error) {
    ...
    default:
        return nil, fmt.Errorf("simplefactory: unknown scene %v", scene)
    }
}
```

尽管 `Scene` 是枚举类型，但仍可能出现无效值：

```go
NewSender(Scene(42))          // 强制类型转换，绕过了枚举约束
NewSender(Scene(config.Type)) // 配置值转换后可能不在枚举范围内
```

返回 `error` 让调用方可以优雅处理，而不是程序直接崩溃。同时提供 `MustNewSender` 作为"已知场景"的便捷变体。

### 5.4 为什么提供 Scene.String()？

```go
func (s Scene) String() string {
    switch s {
    case SceneDingDing: return "dingding"
    case SceneWeixin:   return "weixin"
    case SceneFeishu:   return "feishu"
    default:            return fmt.Sprintf("Scene(%d)", int(s))
    }
}
```

实现 `fmt.Stringer` 接口带来三个好处：

1. **错误信息可读**：`unknown scene dingding` 比 `unknown scene 1` 更易排查
2. **日志友好**：`fmt.Printf("using %v", scene)` 自动输出名称
3. **测试输出**：测试失败时显示名称而非数字，定位更快

未知值回退到 `Scene(42)` 格式，不会丢失数值信息。

### 5.5 为什么具体结构体不导出？

```go
type dingDingSender struct{} // 小写 → 包外不可见
```

如果导出（`DingDingSender`），调用方可以绕过工厂直接构造：

```go
s := &simplefactory.DingDingSender{} // 绕过了工厂
```

这破坏了工厂的意义 — 集中管理创建逻辑。不导出保证了工厂是**唯一入口**。

如果未来某个实现的构造需要额外初始化（如建立连接、校验配置），所有变更都在工厂内部完成，调用方无需感知。

### 5.6 为什么所有代码放在同一个包？

与注册工厂将每个实现放在独立包不同，简单工厂将接口、工厂、所有实现放在**同一个包**中。这是刻意为之：

```
注册工厂：
  sender/          ← 注册中心（独立包）
  dingding/        ← 实现 A（独立包）
  feishu/          ← 实现 B（独立包）

简单工厂：
  simplefactory/   ← 接口 + 工厂 + 所有实现（同一个包）
```

理由：
- 简单工厂的前提是**工厂知道所有实现** — 它们天然是紧耦合的
- 独立包反而增加了不必要的 import 路径和认知负担
- 所有实现共享 `Sender` 接口定义，放在一起更内聚

如果发现实现越来越多、变化越来越频繁，说明该升级为注册工厂了。

## 6 与注册工厂模式的对比

本项目同时包含 `simplefactory/` 和 `registerfactory/`，它们解决同一个问题但策略截然不同：

```
简单工厂：
  调用方 ──→ 工厂函数 ──switch──→ 所有具体实现
  （工厂必须知道所有实现，依赖方向：工厂 → 实现）

注册工厂：
  具体实现 ──init()──→ 注册中心 ←──New(name)── 调用方
  （实现主动注册，依赖方向：实现 → 注册中心 ← 调用方）
```

| 维度 | 简单工厂 | 注册工厂 |
|------|---------|---------|
| 选择机制 | switch/case 编译期确定 | 注册表运行时查找 |
| 新增实现 | 修改工厂函数的 switch | 新增包 + init() 注册 |
| 开闭原则 | 违反（每次新增要改工厂） | 遵循（新增包即可） |
| 编译期安全 | ✅ 枚举常量 + 编译器检查 | ❌ 字符串名称，运行时校验 |
| 依赖方向 | 工厂 → 所有实现 | 实现 → 注册中心 |
| 全局状态 | 无 | 有（全局注册表） |
| 复杂度 | 低 | 中 |
| 适用场景 | 实现固定、数量少 | 实现可扩展、插件化 |

### 如何选择？

```
实现种类是否固定且数量少（< 10 种）？
├── 是 → 简单工厂（本目录）
│        编译期确定，类型安全，一目了然
└── 否 → 注册工厂（registerfactory/）
         运行时可扩展，符合开闭原则
```

实际项目中，很多模块从简单工厂起步，随着需求演化升级为注册工厂 — 这也是为什么本项目同时展示两种模式。

## 7 简单工厂 vs 策略模式

简单工厂和策略模式经常被混淆 — 两者都用接口实现多态，但关注点不同：

```
简单工厂：
  关注点 = 如何创建对象
  调用方 → NewSender(scene) → 拿到 Sender → 使用

策略模式：
  关注点 = 如何使用对象
  调用方 → 设置策略 → 上下文使用策略执行
```

| 维度 | 简单工厂 | 策略模式 |
|------|---------|---------|
| 核心问题 | "创建哪个" | "用哪个算法" |
| 接口角色 | 产品接口 | 策略接口 |
| 选择时机 | 创建时一次性决定 | 运行时可动态切换 |
| 切换能力 | 创建后类型固定 | 可随时替换策略 |
| 典型代码 | `s := NewSender(scene)` | `ctx.SetStrategy(s); ctx.Execute()` |

用消息发送场景做对比：

```go
// 简单工厂：创建后就固定了
s, _ := NewSender(SceneDingDing)
s.Send("hello")  // 永远走钉钉

// 策略模式：可以切换
dispatcher := NewDispatcher()
dispatcher.SetSender(dingDingSender)
dispatcher.Send("hello")              // 走钉钉
dispatcher.SetSender(feishuSender)
dispatcher.Send("hello again")        // 切换到飞书
```

本项目的简单工厂选择在**创建时**确定实现，适合"选定后不变"的场景。如果需要运行时切换发送渠道，应考虑策略模式。实际项目中两者常组合使用 — 用简单工厂创建策略对象，再注入到上下文中。

## 8 适用场景与局限

### 适用

- **策略选择**：根据配置或参数选择算法（排序、压缩、加密方式）
- **渠道分发**：消息推送、支付网关、通知渠道等固定集合的选择
- **协议适配**：根据协议类型创建对应的解析器/编码器
- **环境切换**：根据环境变量选择 mock/real 实现（开发 vs 生产）
- **快速原型**：在项目早期快速实现多态，后续按需升级为注册工厂

### 局限

- **违反开闭原则**：每新增一种实现都要修改工厂函数。对于频繁新增的场景，应使用注册工厂
- **工厂膨胀**：如果实现超过 10 种，switch/case 变得冗长，可读性下降
- **无法传递不同参数**：所有实现通过相同的工厂函数创建。如果不同实现需要不同的构造参数，简单工厂难以优雅处理（此时考虑 Builder 模式或注册工厂 + Config）
- **单包耦合**：工厂必须导入或包含所有实现，实现间无法独立编译和部署
- **String 同步风险**：新增 Scene 常量时，需同步更新 `String()` 方法和 `Scenes()` 函数，容易遗漏
