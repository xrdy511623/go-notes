# 熔断器模式详解

熔断器模式（Circuit Breaker Pattern）是微服务治理中最核心的稳定性模式。它通过**监测下游服务的健康状况**，在故障累积到阈值时自动"断开电路"——快速拒绝请求，避免级联故障（雪崩效应）。当下游恢复后，自动"闭合电路"恢复流量。

---

## 1 模式定义

Michael Nygard 在《Release It!》中首次提出：

> The Circuit Breaker pattern prevents an application from performing an operation that's likely to fail.

翻译：熔断器模式阻止应用程序执行很可能失败的操作。

熔断器是一个三态状态机：

```
                 连续失败 >= MaxFailures
    ┌──────────┐ ────────────────────→ ┌──────────┐
    │  Closed   │                       │   Open    │
    │ （正常放行）│ ←──────────────────── │（全部拒绝）│
    └──────────┘   探测成功              └────┬─────┘
         ↑                                    │
         │         超时 Timeout               │
         │         ┌──────────┐               │
         └──────── │ HalfOpen  │ ←────────────┘
           探测成功 │（有限放行）│   探测失败
                   └──────────┘ ─────────────→ Open
```

- **Closed（闭合）**：正常状态，所有请求通过。记录成功/失败计数
- **Open（断开）**：熔断状态，所有请求**立即失败**，不调用下游。持续 Timeout 时间
- **HalfOpen（半开）**：试探状态，放行少量请求。成功 → Closed，失败 → Open

核心价值：**fail fast** — 明知会失败的请求，不如直接拒绝。这保护了：
1. 调用方的线程/goroutine（不会阻塞在超时等待上）
2. 下游服务（减少压力，给它恢复的时间）
3. 整个系统（防止一个服务的故障扩散到所有上游）

## 2 标准库与生态中的先例

Go 标准库没有内置熔断器，但生态中有大量实现：

| 库 | 特点 | Star |
|------|------|------|
| `sony/gobreaker` | 最流行，API 简洁，支持自定义 ReadyToTrip | 2.9k+ |
| `go-zero/core/breaker` | go-zero 框架内置，Google SRE 算法 | 29k+ |
| `afex/hystrix-go` | Netflix Hystrix 的 Go 移植 | 4.2k+ |
| `mercari/go-circuitbreaker` | 支持自适应阈值 | — |
| `rubyist/circuitbreaker` | 最早的 Go 实现之一 | — |

### 2.1 sony/gobreaker — 业界标杆

```go
cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name:        "upstream-api",
    MaxRequests: 3,                        // HalfOpen 最多放行 3 个请求
    Interval:    10 * time.Second,         // Closed 状态下计数器重置间隔
    Timeout:     30 * time.Second,         // Open → HalfOpen 的等待时间
    ReadyToTrip: func(counts gobreaker.Counts) bool {
        return counts.ConsecutiveFailures > 5 // 自定义熔断条件
    },
    OnStateChange: func(name string, from, to gobreaker.State) {
        log.Printf("[breaker] %s: %s → %s", name, from, to)
    },
})

result, err := cb.Execute(func() (interface{}, error) {
    return http.Get("https://api.example.com/data")
})
```

gobreaker 的设计亮点：
- `ReadyToTrip` 回调让用户定义熔断条件（不限于连续失败，可以看失败率）
- `Interval` 定期重置 Closed 状态的计数，避免历史错误影响当前判断
- `Execute` 返回 `(interface{}, error)` — 通用的结果类型
- 内部使用 generation 计数器避免并发状态竞争

### 2.2 go-zero 内置 breaker — Google SRE 算法

```go
// go-zero 的 breaker 使用 Google SRE 的自适应算法
// 不是传统的 Closed/Open/HalfOpen 三态，而是基于成功率的概率拒绝
brk := breaker.NewBreaker()
err := brk.DoWithAcceptable(func() error {
    return callUpstream()
}, func(err error) bool {
    // 自定义哪些错误算"可接受"（不触发熔断）
    return err == sql.ErrNoRows
})
```

go-zero 的算法：`丢弃概率 = max(0, (requests - K * accepts) / (requests + 1))`

其中 K 是倍率系数（默认 1.5）。当成功率下降时，丢弃概率平滑上升——不需要显式的三态切换。这是与传统熔断器的主要区别。

### 2.3 配套设施：限流与重试

熔断器很少单独使用，通常与限流和重试组成**微服务治理三板斧**：

| 机制 | 保护对象 | Go 生态 |
|------|---------|---------|
| **限流** | 保护**自身**不被打爆 | `golang.org/x/time/rate`、`uber-go/ratelimit`、`juju/ratelimit` |
| **熔断** | 保护**下游**不被雪崩 | `sony/gobreaker`、`go-zero/breaker` |
| **重试** | 应对**瞬时**错误 | `cenkalti/backoff`、`avast/retry-go` |

`golang.org/x/time/rate` 是 Go 官方的限流器实现：

```go
limiter := rate.NewLimiter(rate.Limit(100), 10) // 100 req/s, burst 10

if !limiter.Allow() {
    http.Error(w, "rate limited", http.StatusTooManyRequests)
    return
}
// 处理请求...
```

三者的执行顺序决定了系统行为：

```
请求 → [1.限流] → [2.重试循环 → [3.熔断 → fn()]]
       ↑              ↑              ↑
   保护自身       应对瞬时错误     保护下游
```

- 限流在最外层：被限流的请求不计入熔断统计
- 熔断在重试内层：熔断打开时立即返回，不再重试
- 重试只针对瞬时错误：`ErrBreakerOpen` 不重试（下游已知不可用）

## 3 本项目的实现

### 3.1 熔断器状态机 — `breaker/breaker.go`

```go
type Breaker struct {
    settings     Settings
    mu           sync.Mutex
    state        State
    counts       Counts
    openSince    time.Time
    halfOpenReqs int64
}

type Settings struct {
    MaxFailures     int64         // 连续失败阈值（默认 5）
    Timeout         time.Duration // Open 持续时间（默认 10s）
    HalfOpenMaxReqs int64         // HalfOpen 最多放行（默认 1）
    OnStateChange   func(from, to State)
}
```

核心 API：

| 方法 | 作用 | 对标 gobreaker |
|------|------|---------------|
| `Do(fn)` | 通过熔断器执行 fn | `Execute(fn)` |
| `State()` | 返回当前有效状态 | `State()` |
| `Counts()` | 返回请求统计快照 | `Counts()` |
| `Reset()` | 重置为 Closed | `Reset()` （go-zero 无此方法） |

`Do` 方法的核心逻辑：

```go
func (b *Breaker) Do(fn func() error) error {
    b.mu.Lock()
    if err := b.beforeRequest(); err != nil {
        b.mu.Unlock()
        return err   // Open 或 HalfOpen 已满 → 快速失败
    }
    b.mu.Unlock()

    defer func() {
        if r := recover(); r != nil {
            b.afterRequest(false) // panic 也计为失败
            panic(r)
        }
    }()

    err := fn()
    b.afterRequest(err == nil)
    return err
}
```

### 3.2 令牌桶限流器 — `ratelimiter/ratelimiter.go`

```go
type Limiter struct {
    rate     float64   // tokens per second
    burst    float64   // max bucket capacity
    mu       sync.Mutex
    tokens   float64
    lastTime time.Time
}

func (l *Limiter) Allow() bool {
    // 1. 根据时间差补充令牌
    // 2. 令牌充足 → 消耗一个，返回 true
    // 3. 令牌不足 → 返回 false
}
```

这是 `golang.org/x/time/rate.Limiter.Allow()` 的简化版本。
完整的 `x/time/rate` 还支持 `Reserve()`（预留令牌）和 `Wait()`（阻塞等待）。

### 3.3 弹性组合 — `resilience/resilience.go`

```go
type Config struct {
    Breaker    *breaker.Breaker
    Limiter    *ratelimiter.Limiter
    MaxRetries int
    Backoff    func(attempt int) time.Duration
}

func Do(ctx context.Context, cfg Config, fn func() error) error {
    if cfg.Limiter != nil && !cfg.Limiter.Allow() {
        return ErrRateLimited        // 1. 限流拒绝
    }

    for i := range maxAttempts {
        err := cfg.Breaker.Do(fn)
        if err == nil {
            return nil               // 2. 成功
        }
        if errors.Is(err, breaker.ErrBreakerOpen) {
            return err               // 3. 熔断打开，不重试
        }
        // 4. 普通错误，退避后重试
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-time.After(cfg.Backoff(i)):
        }
    }
    return lastErr
}
```

### 3.4 调用方

```go
import (
    "go-notes/designpattern/circuitbreaker/breaker"
    "go-notes/designpattern/circuitbreaker/ratelimiter"
    "go-notes/designpattern/circuitbreaker/resilience"
)

func main() {
    cb := breaker.New(breaker.Settings{
        MaxFailures: 5,
        Timeout:     30 * time.Second,
        OnStateChange: func(from, to breaker.State) {
            log.Printf("breaker: %s → %s", from, to)
        },
    })
    lim := ratelimiter.New(100, 10) // 100 req/s, burst 10

    err := resilience.Do(ctx, resilience.Config{
        Breaker:    cb,
        Limiter:    lim,
        MaxRetries: 3,
        Backoff:    func(i int) time.Duration { return time.Duration(i+1) * 100 * time.Millisecond },
    }, func() error {
        return callUpstreamService()
    })
}
```

## 4 设计决策解析

### 4.1 为什么用 mutex 而非 atomic？

gobreaker 也用 mutex。原因：

- 状态转换涉及多个字段（`state`、`counts`、`openSince`、`halfOpenReqs`）
- 这些字段之间有一致性要求：读取 `state` 和 `openSince` 必须是同一时刻的快照
- `atomic` 只能保证单个字段的原子性，不能保证多字段一致

在熔断器场景下，mutex 的开销完全可以接受——`beforeRequest` 只读取状态，持锁时间 < 100ns。

### 4.2 为什么 panic 计为失败而不是忽略？

```go
defer func() {
    if r := recover(); r != nil {
        b.afterRequest(false) // 记录失败
        panic(r)              // 重新抛出
    }
}()
```

如果 fn 内部 panic，说明下游出现了严重异常。忽略它会导致：
1. 熔断器无法感知真实的失败率
2. 异常请求持续到达下游，加剧问题

先记录失败再 re-panic，既保证了状态机的正确性，又不改变调用方的 panic 处理逻辑。这是 sony/gobreaker 的做法。

### 4.3 为什么 State() 和 Do() 的状态判断不一致？

```go
func (b *Breaker) State() State {
    if b.state == StateOpen && time.Since(b.openSince) >= b.settings.Timeout {
        return StateHalfOpen // 虚拟状态，不触发 OnStateChange
    }
    return b.state
}
```

`State()` 是观测方法，返回"有效状态"（Open 超时后报告为 HalfOpen）。而 `Do()` 的 `beforeRequest()` 才真正触发状态转换（并调用 `OnStateChange`）。

这样设计的好处：
- 监控系统看到的状态是准确的（Open 超时后确实"逻辑上"是 HalfOpen）
- 但状态转换只在有请求通过时才真正发生（避免空转）

### 4.4 为什么限流器放在熔断器外面？

考虑两种顺序：

```
方案 A（本项目）：限流 → 熔断 → fn()
方案 B（反过来）：熔断 → 限流 → fn()
```

方案 B 的问题：被限流的请求也会计入熔断器的"失败"统计，可能导致误熔断。
方案 A 更合理：限流是保护自身的手段，被限流的请求根本不应该到达熔断器。

### 4.5 为什么 ErrBreakerOpen 时不重试？

```go
if errors.Is(lastErr, breaker.ErrBreakerOpen) {
    return lastErr // 不重试
}
```

重试的前提是"这次失败可能是瞬时的，下次可能成功"。但 `ErrBreakerOpen` 意味着下游已经被判定为不可用，重试只是白白消耗 goroutine 和等待时间。等到 HalfOpen 自动恢复后再重试才有意义。

## 5 与现有模式的关系

熔断器模式与本项目中的其他模式有密切关系：

| 模式 | 关系 |
|------|------|
| **策略模式**（`strategy/retry`） | 退避策略是重试的核心。`resilience.Config.Backoff` 就是一个策略函数 |
| **代理模式**（`proxy/`） | 熔断器本质上是一种"保护代理"——它控制对下游服务的访问 |
| **装饰器模式**（`decorator/`） | gRPC Interceptor 用装饰器模式包装 RPC 调用，注入熔断逻辑 |
| **责任链模式**（`dutychain/`） | HTTP 中间件链中，限流→熔断→业务逻辑就是一条责任链 |
| **观察者模式**（`observer/`） | `OnStateChange` 回调本质是观察者模式——状态变化时通知订阅者 |

## 6 适用场景与局限

### 适用

- **微服务调用**：调用下游 HTTP/gRPC 服务时，防止超时累积和级联故障
- **数据库访问**：数据库连接池耗尽时快速失败，避免所有请求阻塞
- **第三方 API**：调用外部 API（支付、短信）时，处理限流和不可用
- **消息队列**：向 Kafka/RabbitMQ 生产消息时，broker 不可用时快速降级
- **DNS/配置中心**：配置中心宕机时使用本地缓存，不持续重试

### 局限

- **阈值难调**：`MaxFailures` 和 `Timeout` 需要根据实际流量调整，没有银弹
- **冷启动问题**：服务刚启动时失败率可能较高，容易误熔断
- **单点 vs 全局**：进程内熔断器只看到本进程的请求，无法反映全局状态
- **不适合幂等检查**：熔断器不关心请求是否幂等，重试时需要调用方保证幂等性
- **监控必要**：没有监控的熔断器是黑盒——必须配合 `OnStateChange`、Prometheus 指标等

## 7 生产实践建议

### 7.1 参数经验值

| 参数 | 建议值 | 说明 |
|------|--------|------|
| MaxFailures | 5-10 | 太低容易误熔断，太高保护不及时 |
| Timeout | 10-60s | 根据下游恢复时间调整 |
| HalfOpenMaxReqs | 1-3 | 太多会给刚恢复的下游太大压力 |

### 7.2 必须配合降级

熔断打开后，调用方不能简单地向用户返回 500。必须准备降级方案：

- **缓存降级**：返回上次成功的结果
- **默认值降级**：返回空列表或默认配置
- **排队降级**：将写请求放入队列，稍后重试

### 7.3 区分错误类型

不是所有错误都应该触发熔断：

| 错误类型 | 是否熔断 | 示例 |
|---------|---------|------|
| 超时/连接拒绝 | ✅ | `context.DeadlineExceeded` |
| 5xx 错误 | ✅ | 502 Bad Gateway |
| 4xx 业务错误 | ❌ | 400 参数错误、404 未找到 |
| 限流拒绝 | ❌ | 429 Too Many Requests |

详见 `trap/nofallback/` 中的反模式说明。

## 8 超时 / 重试 / 限流 / 熔断的推荐执行顺序

微服务治理四板斧的最佳执行顺序：

```
请求 → ① 限流 → ② 重试循环 [ → ③ 超时 → ④ 熔断 → fn() ]
```

| 层次 | 机制 | 保护对象 | 位置 |
|------|------|---------|------|
| ① 限流 | 令牌桶/漏桶 | 保护**自身**不被打爆 | 最外层 |
| ② 重试 | 退避 + 最大次数 | 应对**瞬时**错误 | 包裹单次调用 |
| ③ 超时 | `context.WithTimeout` | 防止**无限等待** | 每次调用的 context |
| ④ 熔断 | 三态状态机 | 保护**下游** | 包裹实际 fn 调用 |

### 顺序错误的后果

| 错误顺序 | 后果 |
|---------|------|
| 熔断在限流外面 | 被限流的请求计入熔断失败统计 → 误熔断 |
| 重试在熔断外面 | 熔断 Open 时仍然重试 → 浪费时间 |
| 没有超时 | 下游卡住时调用方 goroutine 永远阻塞 |

### 半开探测的并发控制

HalfOpen 状态的核心挑战：只允许少量请求通过探测，其余请求仍然快速失败。

```go
func (b *Breaker) beforeRequest() error {
    switch b.state {
    case StateClosed:
        return nil
    case StateOpen:
        if time.Since(b.openSince) < b.settings.Timeout {
            return ErrBreakerOpen
        }
        b.state = StateHalfOpen
        b.halfOpenReqs = 0
        fallthrough
    case StateHalfOpen:
        if b.halfOpenReqs >= b.settings.HalfOpenMaxReqs {
            return ErrBreakerOpen // 探测名额已满
        }
        b.halfOpenReqs++
        return nil
    }
}
```

`HalfOpenMaxReqs` 通常设为 1-3：
- 太小（0）：永远无法恢复
- 太大（100）：给刚恢复的下游太大压力，可能再次击垮

## 9 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| Closed → Open | 连续失败达 MaxFailures 后状态变为 Open |
| Open 快速失败 | Open 状态下 Do 直接返回 ErrBreakerOpen |
| Open → HalfOpen | 超过 Timeout 后放行探测请求 |
| HalfOpen → Closed | 探测成功后恢复 |
| HalfOpen → Open | 探测失败后重新打开 |
| OnStateChange | 每次状态变化都触发回调 |
| panic 计为失败 | fn panic 后 re-panic 且计数+1 |
| 并发安全 | 多 goroutine 同时 Do 不 race |
| 限流拒绝 | 超过 rate 时返回 ErrRateLimited |
| 组合正确 | resilience.Do 的限流→熔断→重试顺序正确 |
| Reset | Reset 后恢复 Closed 状态 |

## 10 成本模型

### 何时值得用熔断器

- 调用下游微服务/第三方 API
- 下游可能不可用或响应缓慢
- 需要 fail-fast 保护调用方资源
- 需要自动恢复（而非人工介入）

### 何时是过度设计

- 调用的是本地函数——不存在"下游不可用"
- 下游有自己的限流/熔断——双重熔断增加复杂度
- 错误率极低且稳定——熔断器永远不会触发
- 没有降级方案——熔断打开后调用方也无计可施
