# 命令模式 (Command Pattern)

## 一句话定义

> **将请求封装为对象**，从而可以参数化客户端、排队执行、记录日志，以及支持撤销/重做操作。

命令模式将「做什么」（Command 对象）和「谁来做」（Receiver）以及「何时做」（Invoker）解耦。Go 中最直观的映射：

| 角色 | 本项目实现 | 标准库 / 生态 |
|------|-----------|--------------|
| **Command** | `editor.Command` / `transaction.Action` | `cobra.Command` / `http.Request` |
| **Receiver** | `editor.Document` / `transaction.Store` | 业务逻辑 / `database/sql.DB` |
| **Invoker** | `editor.Editor` / `transaction.Transaction` | CLI 框架 / `database/sql.Tx` |

---

## 标准库与生态中的先例

### 1. `cobra.Command` — CLI 框架

```go
// cobra 将每个子命令封装为一个 Command 对象
var rootCmd = &cobra.Command{
    Use:   "app",
    Short: "My CLI application",
    Run: func(cmd *cobra.Command, args []string) {
        // Receiver: 业务逻辑
    },
}

// Invoker: cobra.Execute() 根据用户输入派发到对应 Command
rootCmd.Execute()
```

cobra 的设计完美体现了命令模式：
- 每个 `cobra.Command` 封装了一个操作（`Run` 函数 = Receiver 的调用）
- `rootCmd.AddCommand(subCmd)` — 组合命令树
- 框架在运行时根据 CLI 参数选择并执行对应命令

### 2. `database/sql.Tx` — 事务批量执行 + 回滚

```go
tx, _ := db.Begin()

tx.Exec("UPDATE accounts SET balance = balance - 100 WHERE id = 1")
tx.Exec("UPDATE accounts SET balance = balance + 100 WHERE id = 2")

if err != nil {
    tx.Rollback() // 回滚所有已执行的操作
    return err
}
tx.Commit()
```

这正是命令模式的「批量执行 + 回滚」变体：
- 每个 `Exec` 调用 = 一个 Command
- `tx.Commit()` = 批量提交
- `tx.Rollback()` = 撤销所有已应用的操作

### 3. `http.Request` — 请求即对象

```go
req, _ := http.NewRequest("POST", "/api/orders", body)
req.Header.Set("Content-Type", "application/json")

// 请求被封装为对象，可以传递、重试、记录日志
client.Do(req)
```

`http.Request` 是只读命令 — 不可撤销，但它将请求参数化为对象，可以排队、记录、重试。

### 变体 1：文本编辑器 — 撤销/重做 (`editor/`)

**核心接口：**

```go
type Command interface {
    Execute() error
    Undo() error
    String() string
}
```

**Receiver — Document：**

```go
type Document struct {
    content string
}

func (d *Document) Insert(pos int, text string) error
func (d *Document) Delete(pos, length int) (string, error)
```

**Concrete Commands：**

```go
// InsertCommand: Execute 插入文本，Undo 删除刚插入的文本
type InsertCommand struct {
    doc  *Document
    pos  int
    text string
}

// DeleteCommand: Execute 删除并保存副本，Undo 重新插入副本
type DeleteCommand struct {
    doc     *Document
    pos     int
    length  int
    deleted string  // Execute 时保存，Undo 时使用
}
```

**Invoker — Editor（管理 undo/redo 双栈）：**

```go
type Editor struct {
    doc       *Document
    undoStack []Command
    redoStack []Command
}

func (e *Editor) execute(cmd Command) error {
    if err := cmd.Execute(); err != nil {
        return err
    }
    e.undoStack = append(e.undoStack, cmd)
    e.redoStack = nil  // 新操作清空 redo 栈
    return nil
}

func (e *Editor) Undo() error  // pop undo → cmd.Undo() → push redo
func (e *Editor) Redo() error  // pop redo → cmd.Execute() → push undo
```

**undo/redo 栈状态变化：**

```
操作              文档      undo 栈                  redo 栈
初始              ""        []                       []
Insert(0,"Hi")    "Hi"      [Insert(0,"Hi")]         []
Insert(2," Go")   "Hi Go"   [Insert, Insert]         []
Undo              "Hi"      [Insert(0,"Hi")]         [Insert(2," Go")]
Redo              "Hi Go"   [Insert, Insert]         []
Delete(0,3)       "Go"      [Insert, Insert, Del]    []  ← redo 被清空
```

### 变体 2：事务 — 批量操作 + 自动回滚 (`transaction/`)

**核心接口：**

```go
type Action interface {
    Apply() error
    Rollback() error
    String() string
}
```

**Concrete Actions：**

```go
Set(store, "key", "val")  // 保存旧值，Rollback 恢复旧值
Del(store, "key")         // 保存旧值，Rollback 重新插入
```

**Transaction（批量 Invoker）：**

```go
func (tx *Transaction) Commit() error {
    for i, a := range tx.actions {
        if err := a.Apply(); err != nil {
            // 失败时逆序回滚所有已应用的 action
            for j := len(tx.applied) - 1; j >= 0; j-- {
                tx.applied[j].Rollback()
            }
            return fmt.Errorf("action %d failed, rolled back: %w", i, err)
        }
        tx.applied = append(tx.applied, a)
    }
    tx.committed = true
    return nil
}
```

**回滚示意：**

```
Step 1: Set("name", "Bob")      ✓ applied    旧值 "Alice" 已保存
Step 2: Set("status", "active") ✓ applied    旧值 (不存在) 已保存
Step 3: Del("missing_key")      ✗ 失败

自动回滚：
  → Rollback Step 2: 移除 "status"
  → Rollback Step 1: "name" 恢复为 "Alice"
```

## 设计决策解析

### 1. 为什么 Command 返回 error？

与教科书中的 `void Execute()` 不同，Go 惯用法将错误作为返回值。这让 Invoker 可以决策：

```go
// 编辑器收到错误 → 不入栈
func (e *Editor) execute(cmd Command) error {
    if err := cmd.Execute(); err != nil {
        return err  // 失败的命令不进入 undo 栈
    }
    e.undoStack = append(e.undoStack, cmd)
    ...
}
```

### 2. 为什么 DeleteCommand 在 Execute 时保存被删除的文本？

这是命令模式的核心技巧 — **命令自身携带 undo 所需的上下文**。`deleted` 字段不在构造时填充（此时还没执行），而是在 `Execute()` 时由 receiver 返回并保存：

```go
func (c *DeleteCommand) Execute() error {
    c.deleted, err = c.doc.Delete(c.pos, c.length)
    return err
}

func (c *DeleteCommand) Undo() error {
    return c.doc.Insert(c.pos, c.deleted)
}
```

### 3. 新操作为什么要清空 redo 栈？

遵循所有主流编辑器的行为：undo 后执行新操作意味着用户选择了新的编辑分支，旧的 redo 历史不再有意义。如果不清空，redo 可能让文档进入不一致状态。

### 4. editor.Command vs transaction.Action — 为什么用不同的接口名？

语义不同：
- `Command.Execute/Undo` — 强调「执行与撤销」，用于交互式场景
- `Action.Apply/Rollback` — 强调「应用与回滚」，用于事务批量场景

方法名传达意图，即使底层机制相同。

### 5. Transaction 的 Commit 为什么自动回滚？

对标 `database/sql.Tx`：要么全部成功（commit），要么全部不生效（rollback）。这是原子性（Atomicity）的核心保证。手动回滚也暴露为 `Rollback()` 方法，用于「提交后发现业务错误需要撤销」的场景。

## 命令模式 vs 策略模式

| 维度 | 命令模式 | 策略模式 |
|------|---------|---------|
| **核心意图** | 封装请求，支持排队/撤销/日志 | 封装算法，运行时切换 |
| **接口形状** | `Execute() + Undo()` | 单方法（如 `Pay(amount)`） |
| **状态** | 命令通常持有状态（receiver 引用、参数、undo 数据） | 策略通常无状态 |
| **生命周期** | 被创建、排队、执行、保存（用于 undo） | 被注入、调用、替换 |
| **典型场景** | 编辑器 undo/redo、事务、任务队列 | 支付方式、排序算法、重试退避 |

## 适用场景

| 场景 | 说明 |
|------|------|
| **撤销/重做** | 文本编辑器、绘图工具、IDE 操作历史 |
| **事务** | 数据库事务、批量配置变更 |
| **任务队列** | 将 Command 序列化后入队，异步执行 |
| **宏录制** | 记录一系列命令，一键回放 |
| **审计日志** | 每个命令自带 `String()` 描述，天然可审计 |
| **CLI 框架** | cobra 的子命令树就是命令模式 |

## 局限

| 问题 | 说明 |
|------|------|
| **类爆炸** | 每种操作一个 struct；Go 中可用 `func` 类型缓解 |
| **undo 状态管理** | 复杂命令的 undo 数据可能很大（见 `trap/undoleak/`） |
| **不可逆操作** | 发送邮件、调用外部 API 等无法真正 undo |
| **并发安全** | 本实现未加锁；多 goroutine 共享 Editor 需额外同步 |

## Undo、补偿与回滚的边界

| 场景 | 可逆性 | Go 中的实现 |
|------|--------|-----------|
| 内存中文本编辑 | ✅ 完全可逆 | 保存删除文本副本，Undo 时插入回去 |
| 数据库事务 | ✅ 可逆（Rollback） | `sql.Tx.Rollback()` 回滚所有变更 |
| 发送邮件 | ❌ 不可逆 | 只能发"撤回通知"，不是真正 Undo |
| HTTP API 调用 | ⚠️ 需要补偿接口 | 调用"取消订单" API 作为补偿 |
| 文件删除 | ⚠️ 软删除可逆 | 标记为已删除，Undo 时恢复标记 |

设计 Undo 时的三个问题：
1. **Undo 需要保存什么**？DeleteCommand 必须保存被删除的文本——这是 Execute 时的副产品
2. **Undo 栈应该多大**？无界栈会内存泄漏（见 `trap/undoleak/`），生产中应限制大小
3. **外部副作用能 Undo 吗**？发送邮件、调用 API 只能用补偿操作近似，不是真正撤销

### 命令可序列化 / 可重放的前提

命令模式天然支持持久化——将命令序列化后存储，可以：
- **审计日志**：记录所有操作历史
- **事件溯源**：重放命令序列重建状态
- **分布式事务**：跨服务的 Saga 模式

但序列化有前提：
1. 命令的所有参数必须可序列化（不能有 `func`、`chan`、`*os.File`）
2. Receiver 的状态必须可确定性重建（重放时从相同初始状态开始）
3. 命令必须是**确定性的**——相同输入产生相同结果

## 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| Execute 正确 | Insert 后文档内容符合预期 |
| Undo 恢复 | Undo 后文档恢复到 Execute 前的状态 |
| Redo 重做 | Redo 后文档恢复到 Undo 前的状态 |
| 新操作清空 Redo | Execute 后 redo 栈为空 |
| 空栈 Undo | 没有可撤销的操作时返回 error |
| 事务原子性 | Commit 中某步失败时前面的步骤全部回滚 |
| 事务 Rollback | 手动 Rollback 恢复所有变更 |
| 并发安全 | 多 goroutine 操作 Editor 需要外部同步 |

## 成本模型

### 何时值得用命令模式

- 需要 undo/redo 功能
- 需要事务性批量操作 + 回滚
- 需要命令队列、延迟执行、宏录制
- 需要审计日志（命令自带 String() 描述）

### 何时是过度设计

- 操作不需要撤销——直接调用方法更简单
- 只有少量固定操作——不需要将每个操作封装为对象
- 命令没有状态——用函数类型（`func() error`）更轻量
