# 注册工厂模式详解

注册工厂（Register Factory）是 Go 语言中最具特色的创建型模式变体。它利用 `init()` + 匿名导入包实现**编译期可插拔**的组件注册，是 Go 标准库和生态中广泛采用的惯用模式。

---

## 1 模式定义

GoF《设计模式》将工厂模式归类为**创建型模式**：

> Define an interface for creating an object, but let subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses.

注册工厂是工厂方法的一种演变 — 不通过子类继承，而是通过**全局注册表 + 名称查找**来延迟实例化决策。在 Go 中没有继承机制，这种基于注册的变体反而成为最自然的表达方式。

模式由三部分组成：

```
┌─────────────┐      init() 阶段注册       ┌──────────────┐
│  具体实现包   │ ──────────────────────────→ │   注册中心     │
│  (driver)    │    Register(name, factory)  │  (registry)   │
└─────────────┘                              └──────┬───────┘
┌─────────────┐      init() 阶段注册                │
│  具体实现包   │ ──────────────────────────→         │
│  (driver)    │    Register(name, factory)         │
└─────────────┘                              New(name) 查找
┌─────────────┐      init() 阶段注册                │
│  具体实现包   │ ──────────────────────────→         │
│  (driver)    │    Register(name, factory)         ▼
└─────────────┘                              ┌──────────────┐
                                             │   调用方      │
                                             │  (consumer)   │
                                             └──────────────┘
```

- **注册中心**：定义接口 + 维护 `map[string]Factory` 全局注册表
- **具体实现包**：在 `init()` 中调用 `Register()` 注册自身的工厂函数
- **调用方**：通过匿名导入（`import _ "pkg/driver"`）触发注册，再用 `New(name)` 按名称创建实例

关键洞察：**依赖方向是反转的** — 不是注册中心导入所有实现，而是每个实现主动向注册中心注册自己。这正是"依赖反转原则"在 Go 中的惯用体现。

## 2 标准库中的先例

这不是自创模式，而是 Go 标准库的经典设计：

| 标准库 | 注册函数 | 驱动示例 | 查找函数 |
|--------|---------|---------|---------|
| `database/sql` | `sql.Register(name, driver)` | `_ "github.com/lib/pq"` | `sql.Open(name, ...)` |
| `image` | `image.RegisterFormat(...)` | `_ "image/png"` | `image.Decode(r)` |
| `crypto` | `crypto.RegisterHash(...)` | `_ "crypto/sha256"` | `crypto.SHA256.New()` |

### database/sql — 最经典的示例

```go
import (
    "database/sql"
    _ "github.com/lib/pq" // init() 中调用 sql.Register("postgres", &Driver{})
)

func main() {
    db, err := sql.Open("postgres", connStr) // 按名称查找已注册的驱动
}
```

整个流程：
1. `github.com/lib/pq` 包的 `init()` 调用 `sql.Register("postgres", &pq.Driver{})`
2. 调用方通过 `_ "github.com/lib/pq"` 触发导入（执行 init）
3. `sql.Open("postgres", ...)` 从注册表中查找驱动并创建连接

### image — 格式自动检测

```go
import (
    "image"
    _ "image/png"  // 注册 PNG 解码器
    _ "image/jpeg" // 注册 JPEG 解码器
)

func main() {
    // Decode 自动根据文件头匹配已注册的格式
    img, format, err := image.Decode(reader)
    fmt.Println(format) // "png" 或 "jpeg"
}
```

`image` 包更进一步 — 注册时还包含格式检测函数（magic bytes），`Decode` 可以自动匹配格式，调用方甚至不需要知道文件是什么格式。

## 3 本项目的实现

### 3.1 接口与注册中心 — `sender/sender.go`

```go
// Sender 是消息发送的统一接口。
type Sender interface {
    Send(message string) error
}

// Config 是创建 Sender 时传入的配置参数。
// 使用 map[string]string：可直接从 JSON/YAML/env 反序列化，对标 sql.Open(name, dsn)。
// nil Config 合法，向后兼容无参工厂。
type Config map[string]string

// Factory 是创建 Sender 实例的参数化工厂函数。
// 接受 Config 参数，返回 Sender 和可能的构造错误。
type Factory func(cfg Config) (Sender, error)

// Closer 可选接口，有资源需释放的 Sender 实现它。
// 对标 http.Flusher、http.Hijacker 的可选接口断言模式。
type Closer interface {
    Close() error
}

// HealthChecker 可选接口，支持健康检查的 Sender 实现它。
type HealthChecker interface {
    HealthCheck() error
}

var (
    registry = make(map[string]Factory)
    mu       sync.RWMutex
)
```

核心 API：

| 函数 | 作用 | 对标标准库 |
|------|------|-----------|
| `Register(name, factory)` | 注册工厂函数（init 阶段） | `sql.Register` |
| `New(name, cfg)` | 按名称+配置创建实例（返回 error） | `sql.Open` |
| `MustNew(name, cfg)` | 按名称+配置创建实例（失败 panic） | `regexp.MustCompile` |
| `Unregister(name)` | 从注册表移除工厂（返回 bool） | 热替换/降级 |
| `List()` | 列出所有已注册名称（字典序） | `sql.Drivers` |
| `Count()` | 返回已注册的工厂数量 | 便于监控和断言 |
| `CloseAll(senders)` | 关闭所有实现了 Closer 的 Sender | 优雅关闭 |
| `Reset()` | 清空注册表（仅测试用） | — |

### 3.2 具体实现 — 以钉钉为例

```go
// dingding/dingding.go
package dingding

type dingSender struct {
    webhook string
    token   string
}

func (d *dingSender) Send(message string) error {
    fmt.Printf("Using DingDing send message: %v (webhook=%s)\n", message, d.webhook)
    return nil
}

func (d *dingSender) Close() error       { fmt.Println("DingDing sender closed"); return nil }
func (d *dingSender) HealthCheck() error  {
    if d.webhook == "" { return fmt.Errorf("dingding: webhook not configured") }
    return nil
}

func init() {
    sender.Register("dingding", func(cfg sender.Config) (sender.Sender, error) {
        webhook := cfg["webhook"]
        if webhook == "" {
            webhook = "https://oapi.dingtalk.com/robot/send" // 合理默认值
        }
        return &dingSender{webhook: webhook, token: cfg["token"]}, nil
    })
}
```

要点：
- 结构体 `dingSender` 不导出 → 调用方无法直接构造，必须通过注册中心
- `init()` 在包被导入时自动执行 → 注册是声明式的
- 工厂函数每次返回新实例 → 无共享状态
- Config 有合理默认值，`nil` config 照常工作（map 的零值行为：取值返回零值字符串）
- 工厂验证配置，返回有意义的 error
- `Close()` 和 `HealthCheck()` 是可选接口，非强制实现
- `init()` 仍然只做注册，不做资源分配

本项目提供了三个具体实现，模拟不同的消息渠道：

| 实现 | 包 | 注册名称 | 职责 |
|------|------|---------|------|
| `dingSender` | `dingding/` | `"dingding"` | 钉钉消息发送 |
| `feishuSender` | `feishu/` | `"feishu"` | 飞书消息发送 |
| `weixinSender` | `weixin/` | `"weixin"` | 微信消息发送 |

三者结构完全一致 — 这正是注册工厂的优势：新增渠道只需复制模板、改名、实现接口。

### 3.3 调用方

```go
import (
    "go-notes/designpattern/registerfactory/sender"
    _ "go-notes/designpattern/registerfactory/dingding" // 触发注册
    _ "go-notes/designpattern/registerfactory/weixin"
    _ "go-notes/designpattern/registerfactory/feishu"
)

func main() {
    // 参数化构造 — 传入配置
    s, err := sender.New("dingding", sender.Config{
        "webhook": "https://oapi.dingtalk.com/robot/send",
        "token":   "my-token",
    })
    if err != nil { ... }
    s.Send("Hello")

    // 生命周期管理 — 可选接口断言
    if c, ok := s.(sender.Closer); ok {
        defer c.Close()
    }

    // 动态注销
    sender.Unregister("dingding")
    fmt.Println(sender.List()) // [feishu weixin]
}
```

匿名导入 `_ "pkg"` 的语义是：**执行该包的 init()，但不直接使用其导出符号**。这正是注册的触发机制。

调用方只依赖 `sender` 包（接口 + 注册中心），不依赖任何具体实现包。匿名导入行是唯一的"配置点" — 增删一行导入就能增删一个渠道，无需修改任何业务代码。

## 4 设计决策解析

### 4.1 为什么 Register 在出错时 panic？

```go
func Register(name string, factory Factory) {
    if name == "" {
        panic("sender: Register name must not be empty")
    }
    if factory == nil {
        panic("sender: Register factory must not be nil")
    }
    if _, exists := registry[name]; exists {
        panic(fmt.Sprintf("sender: duplicate Register called for %q", name))
    }
    registry[name] = factory
}
```

这是 Go 标准库的惯例（`sql.Register`、`http.Handle` 都如此）。理由：

1. `Register` 只在 `init()` 阶段调用，此时程序尚未进入主逻辑
2. 重复注册或空名称是**编程错误**（bug），不是运行时异常
3. 越早暴露越好 — 启动即 panic 比运行时静默覆盖更安全

对比 `Subscribe` 返回 error 的设计（见观察者模式）：`Register` 在 `init()` 阶段调用，调用方无法有意义地"处理"错误；而 `Subscribe` 在运行时动态调用，调用方需要决策。

### 4.2 为什么提供 New 和 MustNew 两个变体？

```go
func New(name string, cfg Config) (Sender, error) {
    factory, ok := registry[name]
    if !ok {
        return nil, fmt.Errorf("sender: unknown sender %q (forgotten import?)", name)
    }
    return factory(cfg) // 工厂错误也通过 New 传播
}

func MustNew(name string, cfg Config) Sender {
    s, err := New(name, cfg)
    if err != nil {
        panic(err)
    }
    return s
}
```

两者适用于不同场景：

| 场景 | 选择 | 理由 |
|------|------|------|
| 名称来自配置文件/用户输入 | `New` | 名称可能有误，需要优雅处理 |
| 名称是硬编码常量 | `MustNew` | 失败意味着编程错误，应立即暴露 |
| 程序启动阶段初始化 | `MustNew` | 启动失败比运行时失败更安全 |
| 运行时动态选择 | `New` | 调用方需要 fallback 或重试 |

这是 Go 社区的常见模式：`regexp.Compile` / `regexp.MustCompile`、`template.Parse` / `template.Must`、`strconv.Atoi` / `strconv.MustAtoi`（非标准库但常见）。

### 4.3 为什么用 RWMutex？

注册在 `init()` 阶段完成（写少），`New` / `MustNew` / `List` 在运行时频繁调用（读多）。`sync.RWMutex` 允许多个读操作并发进行，只在写时互斥。

```
时间线：
init() 阶段  │  Register("dingding")  → 写锁
             │  Register("feishu")    → 写锁
             │  Register("weixin")    → 写锁
─────────────┼─────────────────────────────────
运行时       │  New("dingding")       → 读锁 ─┐
             │  New("feishu")         → 读锁 ─┤ 可并发
             │  List()                → 读锁 ─┘
```

如果用普通 `sync.Mutex`，运行时所有 `New` 调用都会串行化 — 在高并发场景下是不必要的瓶颈。

### 4.4 Factory 是函数而非单例

```go
type Factory func(cfg Config) (Sender, error)  // 每次调用返回新实例
```

而不是：

```go
var registry = map[string]Sender{}  // ❌ 所有调用方共享同一实例
```

区别：
- **工厂函数**：每次 `New` 返回独立实例，无状态共享，天然并发安全
- **单例**：所有调用方共享实例，需要自行保证并发安全

本项目选择工厂函数，与 `database/sql` 的设计一致 — `sql.Open` 每次返回新的 `*sql.DB`，而不是返回同一个连接。

如果确实需要单例（如全局配置），可以在工厂函数中使用 `sync.Once`：

```go
var once sync.Once
var instance *dingSender

func init() {
    sender.Register("dingding", func(cfg sender.Config) (sender.Sender, error) {
        once.Do(func() { instance = &dingSender{webhook: cfg["webhook"]} })
        return instance, nil
    })
}
```

### 4.5 为什么用 string 而非 iota/类型 作为注册键？

注册表使用 `map[string]Factory`，键是字符串而非枚举常量或类型。对比：

```go
// 方案 A：string 键（本项目采用）
registry = map[string]Factory{}
sender.New("dingding")

// 方案 B：iota 常量
const ( DingDing = iota; FeiShu; WeiXin )
registry = map[int]Factory{}

// 方案 C：类型键
registry = map[reflect.Type]Factory{}
```

选择 string 的理由：

| 维度 | string | iota | reflect.Type |
|------|--------|------|-------------|
| 可读性 | `"dingding"` 自解释 | `0` 需要查常量定义 | 需要了解反射 |
| 可配置 | 可来自 JSON/YAML/环境变量 | 不能直接从配置文件读取 | 不能直接从配置文件读取 |
| 编译期安全 | ❌ 拼写错误运行时才发现 | ✅ 编译器检查 | ✅ 编译器检查 |
| 扩展性 | 任何包都能注册 | 新增需修改常量定义 | 新增需引入类型 |

string 牺牲了编译期安全性，换来了**配置驱动**和**完全解耦**。这是 `database/sql` 做出的相同权衡 — `sql.Open("postgres", ...)` 而不是 `sql.Open(sql.Postgres, ...)`。

### 4.6 为什么 Reset 只用于测试？

```go
func Reset() {
    mu.Lock()
    defer mu.Unlock()
    registry = make(map[string]Factory)
}
```

全局注册表在测试间共享状态 — 如果测试 A 注册了 `"email"`，测试 B 再注册 `"email"` 就会 panic。`Reset()` 通过 `t.Cleanup` 在每个测试结束后清空注册表：

```go
func TestSomething(t *testing.T) {
    t.Cleanup(func() { Reset() })
    Register("email", newStubFactory("email"))
    // ...
}
```

`Reset` 不应在生产代码中调用 — 运行时清空注册表会导致所有后续 `New` 调用失败。因此它没有出现在"核心 API"表中，只在测试文件中使用。

## 5 与简单工厂的对比

本项目同时包含 `simplefactory/` 和 `registerfactory/`，两者的本质区别：

```
简单工厂：
  调用方 → switch/case → 具体实现
  （工厂必须知道所有实现，依赖方向：工厂 → 实现）

注册工厂：
  具体实现 → init() 注册 → 注册中心 ← New(name) ← 调用方
  （实现主动注册，依赖方向：实现 → 注册中心 ← 调用方）
```

| 维度 | 简单工厂 | 注册工厂 |
|------|---------|---------|
| 依赖方向 | 工厂 → 所有具体实现 | 具体实现 → 注册中心 |
| 新增实现 | 修改工厂的 switch | 新增包 + init() 注册 |
| 开闭原则 | 违反（每次新增要改工厂） | 遵循（新增包即可） |
| 编译期耦合 | 工厂包导入所有实现 | 调用方选择导入哪些 |
| 编译期安全 | ✅ 枚举/常量有编译器检查 | ❌ 字符串运行时才校验 |
| 适用场景 | 实现固定、数量少 | 实现可扩展、插件化 |

简单工厂中添加一个新的发送渠道需要修改 `NewSendMessageService`：

```go
// simplefactory — 每次新增都要改这里
switch scene {
case dingdingScene: impl = new(DingDing)
case weixinScene:   impl = new(Weixin)
case feishuScene:   impl = new(Feishu)
case newScene:      impl = new(NewChannel) // ← 必须修改工厂
}
```

注册工厂中只需要新增一个包：

```go
// newchannel/newchannel.go — 无需修改任何已有代码
func init() {
    sender.Register("newchannel", func(cfg sender.Config) (sender.Sender, error) {
        return &newChannelSender{endpoint: cfg["endpoint"]}, nil
    })
}
```

调用方只需多加一行匿名导入。

## 6 init() 的生命周期与陷阱

注册工厂的核心机制是 `init()`，理解其生命周期至关重要。

### 6.1 执行顺序

Go 规范保证的 init() 执行规则：

```
1. 所有被导入的包先初始化（递归）
2. 包级别变量按声明顺序初始化
3. 同一文件中多个 init() 按声明顺序执行
4. 同一包中多个文件按文件名字典序处理
5. 所有 init() 在 main() 之前完成
```

```
导入顺序（main.go）：
  _ "dingding" ─→ init() ─→ Register("dingding", ...)
  _ "feishu"   ─→ init() ─→ Register("feishu", ...)
  _ "weixin"   ─→ init() ─→ Register("weixin", ...)
  "sender"     ─→ (已在上面的包中被间接导入，不会重复初始化)

  main() 执行时，注册表已包含所有三个工厂
```

### 6.2 常见陷阱

**陷阱 1：忘记匿名导入**

```go
import (
    "go-notes/designpattern/registerfactory/sender"
    // 忘了 _ "go-notes/designpattern/registerfactory/dingding"
)

func main() {
    s, err := sender.New("dingding")
    // err: sender: unknown sender "dingding" (forgotten import?)
}
```

编译器不会报错 — `sender.New("dingding")` 在语法上完全合法。错误只在运行时暴露。错误信息中的 `(forgotten import?)` 是专门为这种情况设计的提示。

**陷阱 2：匿名导入被 IDE 自动删除**

大多数 IDE（GoLand、VS Code + gopls）会自动删除"未使用的导入"。匿名导入 `_ "pkg"` 没有被任何代码直接引用，可能被误删。

防御措施：
- 在匿名导入旁添加注释说明用途
- 在 CI 中运行集成测试验证所有渠道可用
- 使用 `sender.List()` 在启动时打印已注册渠道

```go
import (
    _ "go-notes/designpattern/registerfactory/dingding" // 注册钉钉发送渠道
)
```

**陷阱 3：init() 中的副作用**

`init()` 应该只做注册，不应该有其他副作用（如建立网络连接、读取文件）：

```go
// ❌ 错误：init 中做了不该做的事
func init() {
    conn, err := net.Dial("tcp", "api.dingding.com:443")  // 网络操作
    if err != nil {
        log.Fatal(err)  // 启动失败
    }
    sender.Register("dingding", func() sender.Sender {
        return &dingSender{conn: conn}
    })
}

// ✅ 正确：init 只注册，连接在创建时建立
func init() {
    sender.Register("dingding", func(cfg sender.Config) (sender.Sender, error) {
        return &dingSender{webhook: cfg["webhook"]}, nil  // 连接在 Send() 时按需建立
    })
}
```

**陷阱 4：循环导入**

如果实现包 A 需要导入另一个实现包 B，就会形成循环依赖：

```
sender ← dingding ← feishu ← sender  // ❌ 循环导入，编译失败
```

注册工厂的架构天然避免了这个问题 — 所有实现包只依赖 `sender`（注册中心），实现包之间互不依赖。这也是为什么注册中心必须是独立包的原因。

## 7 注册工厂 vs 依赖注入

注册工厂和依赖注入（DI）都解决"如何创建和获取依赖"的问题，但思路不同：

```
注册工厂：
  实现 → init() 注册 → 全局注册表 → New(name) → 调用方
  （实现自注册，调用方按名称查找）

依赖注入：
  容器/框架 → 分析依赖图 → 构造并注入 → 调用方
  （外部决定给谁什么依赖）
```

| 维度 | 注册工厂 | 依赖注入（Wire/fx） |
|------|---------|-------------------|
| 依赖声明 | 匿名导入 + string 名称 | 构造函数参数（类型安全） |
| 实例管理 | 每次 New 创建新实例 | 容器管理生命周期（单例/请求级） |
| 编译期检查 | ❌ 名称拼错运行时报错 | ✅ Wire 在编译期生成代码 |
| 复杂度 | 极低（一个 map + 几个函数） | 较高（需学习框架 API） |
| 全局状态 | 有（全局注册表） | 无（容器是显式传递的） |
| 适用规模 | 驱动/插件（少量抽象） | 大型服务（数十个依赖） |

### 何时用注册工厂？

- **实现是可插拔的**：用户选择 MySQL 驱动还是 PostgreSQL 驱动
- **实现数量会增长**：新团队可以独立新增渠道/驱动
- **选择权在调用方**：调用方通过导入行决定包含哪些实现

### 何时用依赖注入？

- **依赖关系复杂**：服务 A 依赖 B、C，B 又依赖 D、E
- **生命周期管理**：需要单例、请求级作用域、优雅关闭
- **测试需要替换**：需要在测试中注入 mock 实现

### 组合使用

实际项目中两者可以结合：

```go
// 注册工厂负责"发现"驱动
import _ "github.com/lib/pq"

// 依赖注入负责"组装"服务
func NewOrderService(db *sql.DB, cache *redis.Client) *OrderService {
    return &OrderService{db: db, cache: cache}
}
```

注册工厂解决**驱动层**的可插拔性，依赖注入解决**业务层**的依赖管理。

## 8 适用场景与局限

### 适用

- **驱动/插件架构**：数据库驱动、消息渠道、存储后端、编码格式
- **配置驱动选择**：运行时根据配置文件中的名称选择实现
- **多团队协作**：各团队独立开发自己的实现包，只需遵循接口约定
- **二进制裁剪**：不导入某个包 = 不编译该实现，减小二进制体积
- **渐进式迁移**：新旧实现共存，通过切换名称逐步迁移

### 局限

- **编译时绑定，不可运行时加载**：见下方 §8.1 详述
- **隐式依赖**：匿名导入不会出现在常规代码路径中，容易被遗忘或误删
- **配置类型受限**：`Config` 使用 `map[string]string`，复杂嵌套配置需要自行解析。权衡：类型安全 + 可从 JSON/env 直接反序列化 > 泛型灵活性
- **运行时发现**：编译器不会检查 `"dingding"` 这个字符串是否真的被注册了。类型错误在编译期捕获，名称错误只能在运行时报错
- **测试需 Reset**：全局注册表在测试间共享状态，需要 `Reset()` 函数清理
- **全局状态**：注册表是包级全局变量，大型项目中需要治理；见下方 §8.2 详述

### 8.1 编译时绑定 — "可插拔"的边界在哪里？

注册工厂的"可插拔"只在**编译进二进制的实现**中成立。和 Java 的 classpath 扫描、Python 的 `importlib.import_module()` 不同，Go 没有运行时动态加载包的能力：

```
                    Java / Python                Go
                    ─────────────                ──
发现新实现          运行时扫描 classpath /        编译时 import
                    动态 import
新增实现需要         放 jar/py 到对应目录          重新编译二进制
热加载              ✅ 可以                       ❌ 不可以
```

这意味着：

1. **新增一个 Sender 实现**需要修改 `main.go`（或某个入口文件）的 import 行并重新编译
2. 不可能"部署一个 .so 插件到目录里就自动生效"（Go 的 `plugin` 包功能有限且几乎没有生产使用）
3. 配置文件中写 `sender: "dingding"` 只是从已编译进来的实现中选择，而不是动态加载

这个限制在实践中并不严重 — Go 的编译速度足够快，CI/CD 流水线重新编译即可。但要**对读者明确这个边界**，避免把注册工厂误解为"真正的插件系统"。

### 8.2 大型项目中避免全局注册表扩散

当项目规模增长，不同领域（消息渠道、存储后端、序列化格式……）各自用包级全局 `map` 做注册表时，会出现几个问题：

**问题 1：全局状态散落各处**

```go
// sender/sender.go
var registry = make(map[string]Factory)     // 全局注册表 1

// storage/storage.go
var backends = make(map[string]BackendFactory)  // 全局注册表 2

// codec/codec.go
var codecs = make(map[string]CodecFactory)      // 全局注册表 3
```

每个注册表都是独立的包级变量，项目里散落着 N 个全局 map + N 个 `Register` + N 个 `Reset`。测试需要逐一清理。

**问题 2：与 DI 容器产生概念冲突**

如果项目同时使用 Wire 或 fx 做依赖注入，全局注册表和 DI 容器各管一部分依赖，容易造成"有些依赖从注册表拿，有些从容器拿"的混乱。

**解法：用 `Registry` 结构体代替包级变量**

将注册表封装为显式传递的对象，而非包级全局状态：

```go
// registry.go — 通用的类型安全注册表
type Registry[T any] struct {
    mu       sync.RWMutex
    factories map[string]func() T
}

func NewRegistry[T any]() *Registry[T] {
    return &Registry[T]{factories: make(map[string]func() T)}
}

func (r *Registry[T]) Register(name string, factory func() T) { ... }
func (r *Registry[T]) New(name string) (T, error)              { ... }
```

```go
// 使用方式：注册表是显式创建、显式传递的
senderRegistry := registry.NewRegistry[Sender]()
storageRegistry := registry.NewRegistry[Storage]()

// 注册
senderRegistry.Register("dingding", newDingDing)

// 注入到需要的地方
app := NewApp(senderRegistry, storageRegistry)
```

这种方式在小型项目中是 over-engineering，但在大型单体仓库中可以：
- 让注册表的生命周期由调用方控制（测试中无需全局 `Reset`）
- 与 DI 容器无冲突（注册表本身就是被注入的依赖）
- 通过泛型避免重复写 N 套 Register/New/List

标准库采用包级全局变量是因为它面向的场景（数据库驱动、图片格式）天然是全局唯一的。**业务代码中是否需要同样的设计，取决于项目规模和团队约定。**

## 9 显式注册 vs init() 注册

本项目使用 `init()` 注册——这是标准库的惯例（`database/sql`、`image`）。但还有另一种方式：

### 显式注册

```go
func main() {
    sender.Register("dingding", dingding.NewFactory())
    sender.Register("feishu", feishu.NewFactory())
    // 显式列出所有注册——可读性更好
}
```

### 两种方式的对比

| 维度 | init() 注册 | 显式注册 |
|------|-------------|---------|
| 触发方式 | 匿名导入 `_ "pkg"` | 在 main 或初始化函数中手动调用 |
| 可读性 | 差——注册隐藏在 init 中 | 好——所有注册集中可见 |
| IDE 支持 | 差——跳转不直观 | 好——普通函数调用 |
| 测试隔离 | 需要 `Reset()` | 每个测试显式注册需要的实现 |
| 标准库采用 | `database/sql`、`image` | — |
| 适合场景 | 框架/库（用户只需 import） | 应用层（开发者完全控制） |

### 测试隔离与全局注册表污染

全局注册表在测试间共享状态，这是 `init()` 注册的主要痛点：

```go
// 测试 A 注册了 "email"
func TestA(t *testing.T) {
    sender.Register("email", emailFactory)
    // ...
}

// 测试 B 也注册 "email" → panic: duplicate Register
func TestB(t *testing.T) {
    sender.Register("email", emailFactory) // 💥
}
```

解法：
1. **`Reset()` + `t.Cleanup`**：每个测试后清空注册表（本项目的做法）
2. **显式注册**：不用 init()，测试中只注册需要的实现
3. **`Registry` 实例**：用结构体替代包级全局变量（§8.2 已详述）

## 11 成本模型

### 何时值得用注册工厂

- 实现是开放集合，新增实现不应修改已有代码
- 需要配置驱动：运行时根据字符串名称选择实现
- 插件/驱动架构：多团队独立开发实现包
- 二进制裁剪：不导入某包 = 不编译该实现

### 何时是过度设计

- 实现种类固定且少（< 5 种）——简单工厂更直观
- 对编译期安全要求高——注册工厂的字符串键无法在编译期检查
- 项目规模小，没有跨团队协作——全局注册表的复杂度不值得
- 测试中需要频繁替换实现——依赖注入比全局注册表更干净

## 12 参数化工厂演进

### 从 `func() Sender` 到 `func(Config) (Sender, error)`

最初的 Factory 签名简洁但有限：

```go
// v1：无参工厂 — 适合教学，无法处理实际场景
type Factory func() Sender
```

实际系统中，创建 Sender 几乎总是需要配置（webhook URL、token、超时时间），且构造可能失败（配置缺失、格式非法）。这导致两个问题：

1. **配置只能走全局变量 / 环境变量** — 工厂函数拿不到参数，只能读包级变量或 `os.Getenv`
2. **错误无法传播** — `func() Sender` 没有 error 返回值，配置错误只能 panic 或返回哑对象

演进后的签名：

```go
// v2：参数化工厂 + 错误返回 — 对标 sql.Open(driverName, dataSourceName)
type Config map[string]string
type Factory func(cfg Config) (Sender, error)
```

**为什么用 `map[string]string` 而非 `any` 或结构体？**

| 方案 | 优点 | 缺点 |
|------|------|------|
| `any` | 极度灵活 | 类型断言散落各处，无法从 JSON 直接反序列化 |
| 具体结构体 | 编译期类型安全 | 每个工厂需要不同结构体，注册中心无法统一签名 |
| `map[string]string` | 可直接从 JSON/YAML/env 反序列化，键值自解释 | 复杂嵌套需要自行解析 |

`map[string]string` 是实用主义选择 — 覆盖 90% 的配置场景（URL、token、端口、开关），与 `sql.Open` 的 DSN 字符串精神一致。

**nil Config 合法**：

```go
// nil map 取值返回零值字符串，不会 panic
webhook := cfg["webhook"] // cfg 为 nil 时 webhook == ""
```

这保证了向后兼容 — 无需配置的工厂直接传 `nil`：`sender.New("simple", nil)`。

## 13 生命周期管理

### 可选接口断言模式

Go 标准库中，`net/http` 包大量使用可选接口：

```go
// 标准库中的可选接口
type Flusher interface { Flush() }
type Hijacker interface { Hijack() (net.Conn, *bufio.ReadWriter, error) }
```

`http.ResponseWriter` 不嵌入这些接口，但具体实现（如 `http.response`）可以选择实现它们。调用方通过类型断言检测能力：

```go
if f, ok := w.(http.Flusher); ok {
    f.Flush()
}
```

本项目对 Sender 采用相同模式：

```go
// 可选接口 — 不嵌入 Sender，由具体实现选择实现
type Closer interface { Close() error }
type HealthChecker interface { HealthCheck() error }
```

**为什么不把 `Close()` 嵌入 Sender 接口？**

如果 Sender 接口包含 `Close()`，所有实现都必须提供 Close 方法 — 即使它无资源需释放。这会产生大量空方法实现，违反接口隔离原则。可选接口让每个实现按需选择：

```go
// 有资源需释放的实现
type dingSender struct { conn net.Conn }
func (d *dingSender) Close() error { return d.conn.Close() }

// 无资源的实现 — 不需要实现 Close
type logSender struct{}
```

### CloseAll — 优雅关闭

```go
func CloseAll(senders []Sender) error {
    var firstErr error
    for _, s := range senders {
        if c, ok := s.(Closer); ok {
            if err := c.Close(); err != nil && firstErr == nil {
                firstErr = err
            }
        }
    }
    return firstErr
}
```

设计要点：
- 只关闭实现了 `Closer` 的 Sender — 跳过无资源的实现
- **返回第一个错误，但尝试关闭所有** — 一个失败不应阻止其他资源释放
- 调用方在 `main()` 退出或收到信号时调用

## 14 动态注销与热替换

### Unregister

```go
func Unregister(name string) bool {
    mu.Lock()
    defer mu.Unlock()
    _, exists := registry[name]
    if exists {
        delete(registry, name)
    }
    return exists
}
```

**返回 bool 而非 panic** — 与 `Register` 不同，`Unregister` 是运行时操作。调用方可能不确定某个名称是否存在，返回 bool 让它自行决策。

**不关闭已创建的实例** — Unregister 只从注册表移除工厂函数。已经通过 `New` 创建的 Sender 实例由调用方管理生命周期。这避免了 Unregister 需要追踪所有已创建实例的复杂性。

### 使用场景

**热替换**：

```go
// 用新版本替换旧版本
sender.Unregister("dingding")
sender.Register("dingding", newDingDingV2Factory)
```

**A/B 测试**：

```go
// 运行时根据实验组切换实现
if experiment.Group() == "B" {
    sender.Unregister("notification")
    sender.Register("notification", newExperimentalFactory)
}
```

**优雅降级**：

```go
// 某渠道不可用时移除，避免后续创建失败
if !healthCheck("dingding") {
    sender.Unregister("dingding")
    log.Warn("dingding sender disabled due to health check failure")
}
```

## 15 配置驱动组装

注册工厂使用字符串键的核心价值之一是**配置驱动** — 部署时通过 JSON/YAML 决定创建哪些 Sender，而非硬编码在源码中。

### config 包

```go
package config

type AppConfig struct {
    Senders []SenderEntry `json:"senders"`
}

type SenderEntry struct {
    Name   string        `json:"name"`
    Config sender.Config `json:"config"`
}

func BuildSenders(app AppConfig) (map[string]sender.Sender, error) {
    result := make(map[string]sender.Sender, len(app.Senders))
    for _, entry := range app.Senders {
        s, err := sender.New(entry.Name, entry.Config)
        if err != nil {
            return nil, fmt.Errorf("config: failed to create sender %q: %w", entry.Name, err)
        }
        result[entry.Name] = s
    }
    return result, nil
}
```

### JSON 配置示例

```json
{
  "senders": [
    {
      "name": "dingding",
      "config": {
        "webhook": "https://oapi.dingtalk.com/robot/send",
        "token": "prod-token-xxx"
      }
    },
    {
      "name": "feishu",
      "config": {
        "webhook": "https://open.feishu.cn/open-apis/bot/v2/hook",
        "secret": "feishu-secret-xxx"
      }
    }
  ]
}
```

### 核心教学点

这展示了"注册工厂 + 字符串键 = 配置驱动组装"的完整闭环：

```
JSON 配置文件
    ↓ json.Unmarshal
AppConfig{Senders: [...]}
    ↓ BuildSenders
for each entry:
    sender.New(entry.Name, entry.Config)
        ↓ 注册表查找
    registry[name](cfg)
        ↓ 工厂创建
    具体 Sender 实例
```

部署时只需修改 JSON 配置，无需重新编译（前提是所有可能的实现已通过匿名导入编译进二进制）。
