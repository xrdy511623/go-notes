# 组合模式详解

组合模式（Composite Pattern）是最重要的结构型设计模式之一。它将对象组织为**树形结构**，让客户端以统一的方式处理叶子节点和组合节点。Go 语言的小接口 + 类型断言为这一模式提供了极其简洁的表达。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly.

翻译：将对象组合成树形结构以表示"部分-整体"的层次关系，使得客户端对单个对象和组合对象的使用具有一致性。

模式由三个角色组成：

```
           ┌──────────────┐
           │  Component    │ ← 统一接口
           │  Name()       │
           │  Size()       │
           └──────┬───────┘
                  │
        ┌─────────┴─────────┐
        │                   │
┌───────┴──────┐   ┌────────┴───────┐
│  File (Leaf) │   │  Directory     │
│              │   │  (Composite)   │
│  Name()      │   │                │
│  Size() → n  │   │  Name()        │
└──────────────┘   │  Size() → Σ    │ ← 递归聚合
                   │  Add(child)    │
                   │  Children()    │
                   └────────────────┘
                          │
                    ┌─────┼─────┐
                    │     │     │
                  File  File  Directory
                                │
                              File
```

- **Component（组件）**：统一接口，叶子和组合都实现
- **Leaf（叶子）**：没有子节点的终端对象
- **Composite（组合）**：包含子节点的容器对象，操作递归委托给子节点

核心价值：**调用方不需要区分叶子和组合**。`component.Size()` 对文件返回文件大小，对目录返回所有后代的大小之和——接口完全相同。

## 2 标准库与生态中的先例

组合模式在 Go 标准库中无处不在：

| 场景 | Leaf | Composite | 统一接口 |
|------|------|-----------|---------|
| `io.MultiReader` | 单个 `io.Reader` | `MultiReader` 包含 `[]Reader` | `io.Reader` |
| `io.MultiWriter` | 单个 `io.Writer` | `MultiWriter` 包含 `[]Writer` | `io.Writer` |
| `net/http.ServeMux` | `http.HandlerFunc` | `ServeMux` 路由到多个 Handler | `http.Handler` |
| `os.FileInfo` / `fs.FS` | 文件 | 目录（包含文件和子目录） | `fs.DirEntry` |
| `go/ast` | `*ast.Ident`, `*ast.BasicLit` | `*ast.BlockStmt`, `*ast.File` | `ast.Node` |
| `encoding/xml` | `CharData`, `Comment` | `StartElement` + children | `xml.Token` |
| K8s API | Pod | Deployment → ReplicaSet → Pod | `runtime.Object` |

`io.MultiWriter` 是标准库中最纯粹的组合模式：

```go
// 标准库源码（简化）
func MultiWriter(writers ...Writer) Writer {
    return &multiWriter{writers: writers}
}

type multiWriter struct {
    writers []Writer
}

// 一次 Write 调用，扇出到所有子 Writer ← 递归委托
func (t *multiWriter) Write(p []byte) (n int, err error) {
    for _, w := range t.writers {
        n, err = w.Write(p)
        if err != nil {
            return
        }
    }
    return len(p), nil
}
```

关键洞察：`MultiWriter` 本身也实现了 `io.Writer`，所以它可以作为另一个 `MultiWriter` 的子节点——**这正是组合模式的递归本质**。

```go
// MultiWriter 可以嵌套：组合中包含组合
inner := io.MultiWriter(fileWriter, networkWriter)
outer := io.MultiWriter(inner, stdoutWriter)
outer.Write(data)  // → fileWriter + networkWriter + stdoutWriter
```

## 3 本项目的实现

本项目提供两个变体，覆盖经典树形结构和实用校验器组合：

| 变体 | 包 | Leaf | Composite | 统一接口 |
|------|------|------|-----------|---------|
| 文件树 | `fstree/` | `File` | `Directory` | `Component` |
| 校验器 | `validator/` | `NonEmpty`, `MinLength`, ... | `And`, `Or`, `Not` | `Validator` |

### 3.1 文件树 — `fstree/fstree.go`

```go
// Component 是叶子和组合的统一接口。
type Component interface {
    Name() string
    Size() int64
}

// File 是叶子节点。
type File struct {
    name string
    size int64
}

// Directory 是组合节点。
type Directory struct {
    name     string
    children []Component    // ← 递归：子节点也是 Component
}
```

`Directory.Size()` 是组合模式的核心方法——**递归聚合**：

```go
func (d *Directory) Size() int64 {
    var total int64
    for _, child := range d.children {
        total += child.Size()    // 不区分 File 还是 Directory
    }
    return total
}
```

树操作：

| 函数 | 作用 |
|------|------|
| `Walk(c, fn)` | 深度优先遍历树中所有节点 |
| `Search(c, name)` | 按名称搜索所有匹配节点 |
| `PrintTree(w, c)` | 输出 `tree(1)` 风格的可视化 |

`Walk` 使用接口检测来识别组合节点，无需依赖具体类型：

```go
func Walk(c Component, fn func(Component)) {
    fn(c)
    type container interface{ Children() []Component }
    if dir, ok := c.(container); ok {        // 鸭子类型：任何有 Children() 的都是组合
        for _, child := range dir.Children() {
            Walk(child, fn)
        }
    }
}
```

### 3.2 校验器组合 — `validator/validator.go`

```go
type Validator interface {
    Validate(value string) error
}
```

叶子校验器检查单条规则，组合校验器将多个子校验器组成树：

| 类型 | 角色 | 语义 |
|------|------|------|
| `NonEmpty()`, `MinLength(n)`, `MaxLength(n)`, `Matches(re)` | Leaf | 单条规则 |
| `And(validators...)` | Composite | 全部通过才通过（短路求值） |
| `Or(validators...)` | Composite | 任一通过即通过 |
| `Not(v, msg)` | Composite | 取反 |

组合可以嵌套，形成任意深度的校验树：

```go
// 用户名: 非空 AND 长度3-20 AND 纯字母数字
usernameRule := validator.And(
    validator.NonEmpty(),
    validator.MinLength(3),
    validator.MaxLength(20),
    validator.Matches(`^[a-zA-Z0-9]+$`),
)

// 密码: 非空 AND 长度8-64 AND (含字母 AND 含数字)
passwordRule := validator.And(
    validator.NonEmpty(),
    validator.MinLength(8),
    validator.And(validator.Matches(`[a-zA-Z]`), validator.Matches(`[0-9]`)),
)

err := usernameRule.Validate("alice42")  // nil
err := passwordRule.Validate("secret")   // "does not match [0-9]"
```

`And` 的 `Validate` 实现与 `Directory.Size()` 结构完全一致——遍历子节点，递归委托：

```go
func (a *andValidator) Validate(value string) error {
    for _, v := range a.validators {
        if err := v.Validate(value); err != nil {
            return err    // 短路：第一个失败就返回
        }
    }
    return nil
}
```

### 3.3 调用方

```go
import (
    "go-notes/designpattern/composite/fstree"
```

调用方通过统一接口操作树中的任何节点。新增叶子类型（如 `Symlink`）或组合类型（如 `VirtualDirectory`）只需实现接口，无需修改现有代码。

## 4 设计决策解析

### 4.1 为什么 Component 接口只有两个方法？

```go
type Component interface {
    Name() string
    Size() int64
}
```

Go 的接口哲学是**小而精**。经典 GoF 将 `Add`、`Remove`、`GetChild` 全部放在 Component 接口中：

```java
// Java 经典实现（安全性差）
interface Component {
    String name();
    long size();
    void add(Component c);      // ← 叶子节点必须空实现或抛异常
    void remove(Component c);   // ← 叶子节点必须空实现或抛异常
    List<Component> children(); // ← 叶子节点返回空列表
}
```

Go 的方案：**统一接口只放共有操作，管理操作放在具体类型上**。

```go
// Component: 叶子和组合都有的操作
type Component interface { Name(); Size() }

// Directory: 只有组合才有的操作
func (d *Directory) Add(children ...Component) *Directory
func (d *Directory) Children() []Component
```

需要操作子节点时，用类型断言或接口检测：

```go
if dir, ok := c.(*Directory); ok {
    dir.Add(newFile)
}
```

这比 Java 的"叶子节点抛 UnsupportedOperationException"安全得多——**编译期就知道 File 没有 Add 方法**。

### 4.2 Walk 为什么用接口检测而非类型断言？

```go
// 方式一：类型断言（绑定具体类型）
if dir, ok := c.(*Directory); ok { ... }

// 方式二：接口检测（鸭子类型 ✓）
type container interface{ Children() []Component }
if dir, ok := c.(container); ok { ... }
```

方式二的优势：

- **开放扩展**：任何实现了 `Children() []Component` 的类型都能被 Walk 遍历
- 不需要修改 Walk 就能支持新的组合类型（如 `VirtualDirectory`、`ArchiveEntry`）
- 这是 Go 的核心设计理念——**接口由使用方定义，而非实现方**

### 4.3 为什么 validator.And 短路求值？

```go
func (a *andValidator) Validate(value string) error {
    for _, v := range a.validators {
        if err := v.Validate(value); err != nil {
            return err    // ← 第一个失败就返回
        }
    }
    return nil
}
```

与布尔表达式的 `&&` 一致：左边为 false 就不评估右边。好处：

- **性能**：跳过不必要的校验（后续规则可能是昂贵的正则匹配）
- **错误清晰**：返回第一个不满足的规则，而非所有失败的列表
- **语义直觉**：`NonEmpty() AND MinLength(3)` —— 空字符串应该报"不能为空"而非"长度不足"

如果需要收集所有错误（表单校验场景），可以实现一个 `AndAll` 变体。

### 4.4 PrintTree 为什么是函数而非方法？

```go
func PrintTree(w io.Writer, c Component)  // 函数
// vs
func (c Component) PrintTree(w io.Writer) // 方法（不可能：Go 不允许给接口加方法实现）
```

Go 中接口不能有默认实现。将 `PrintTree` 定义为函数有两个好处：

- **不污染接口**：Component 保持 `{ Name(); Size() }` 的最小化
- **可组合**：`PrintTree` 可以用 `Walk` 实现，独立于 Component 的具体类型

这是 Go 社区推崇的 **"接受接口，返回结构体"** + **"行为放在函数中"** 的惯用法。

## 5 组合模式 vs 装饰器模式

两个模式经常被混淆，因为它们的结构相似——都涉及"包装"和接口委托。

```
组合模式：                          装饰器模式：
  Directory                           CountingReader
    ├── File                            └── ProgressReader
    ├── File                                └── strings.Reader
    └── Directory
        └── File
```

| 维度 | 组合模式 | 装饰器模式 |
|------|---------|-----------|
| 目的 | 表示**部分-整体**树形结构 | **增强**已有对象的行为 |
| 子节点数 | **多个**（一对多） | **一个**（一对一链式包装） |
| 接口方法 | 所有节点实现相同接口 | 包装者和被包装者实现相同接口 |
| 递归方向 | 向下：`Size()` 聚合子节点 | 向内：`Read()` 委托给内层 |
| 标准库 | `io.MultiWriter`（多个子 Writer） | `bufio.Reader`（增强 Reader） |
| 本项目 | `fstree/`、`validator/` | `decorator/reader/`、`decorator/responsewriter/` |

简单判断法：
- **一个包多个** → 组合模式
- **一个包一个，增加功能** → 装饰器模式

## 6 适用场景与局限

### 适用

- **文件系统**：文件和目录的树形结构（`os`、`fs.FS`）
- **UI 组件树**：容器包含子组件（React 组件树、Android ViewGroup）
- **配置树**：YAML/JSON 的嵌套结构（叶子是标量，组合是 map/array）
- **校验规则**：And/Or/Not 组合校验器
- **权限系统**：角色包含子角色和权限项，`HasPermission()` 递归检查
- **组织架构**：部门包含子部门和员工
- **AST**：编译器的抽象语法树（`go/ast` 包）

### 局限

- **循环引用**：A 包含 B，B 包含 A → `Size()` 无限递归 → stack overflow（详见 `trap/circularref/`）
- **类型限制困难**：Component 接口不限制谁能做谁的子节点，需要在 Add 中运行时检查
- **遍历效率**：深树的递归遍历可能导致栈深过深（极端情况需改为迭代）
- **并发安全**：多 goroutine 同时 Add 和遍历需要加锁

## 7 透明式 vs 安全式组合

GoF 组合模式有两种变体：

| 变体 | Add/Remove 定义在 | 优点 | 缺点 |
|------|-----------------|------|------|
| **透明式** | Component 接口 | 叶子和组合完全统一 | 叶子的 Add 必须空实现或 panic |
| **安全式** | 仅 Composite 类型 | 叶子不暴露无意义的方法 | 需要类型断言才能操作子节点 |

本项目选择**安全式**——Go 的隐式接口天然支持：

```go
// Component 接口只有共有操作
type Component interface { Name() string; Size() int64 }

// Add 只在 Directory 上定义——File 不需要
func (d *Directory) Add(children ...Component) *Directory
```

Java 通常用透明式（因为需要 instanceof 做类型判断成本高），Go 用安全式更自然。

### 树结构中的循环引用与防御性遍历

循环引用是组合模式的头号敌人：

```go
a := NewDirectory("a")
b := NewDirectory("b")
a.Add(b)
b.Add(a)  // 循环！

a.Size()  // 无限递归 → stack overflow
```

防御措施：

1. **visited 集合**：遍历时记录已访问节点

```go
func SafeWalk(c Component, visited map[Component]bool, fn func(Component)) {
    if visited[c] { return }
    visited[c] = true
    fn(c)
    if dir, ok := c.(interface{ Children() []Component }); ok {
        for _, child := range dir.Children() {
            SafeWalk(child, visited, fn)
        }
    }
}
```

2. **深度限制**：超过最大深度时终止
3. **构建时检查**：Add 时检测是否会形成环

## 9 成本模型

### 何时值得用组合模式

- 数据天然是树形结构（文件系统、UI 组件、组织架构）
- 需要统一处理叶子和容器（递归 Size/Validate/Render）
- 需要嵌套组合（And/Or/Not 校验规则）

### 何时是过度设计

- 数据是扁平的列表——不需要树形结构
- 叶子和容器的操作完全不同——强行统一接口反而增加复杂度
- 只有一层嵌套——直接用 `[]Item` 就够了
