# 代理模式详解

代理模式（Proxy Pattern）是最常用的结构型设计模式之一。它为另一个对象提供**替身或占位符**，以控制对该对象的访问。代理与真实主体实现同一接口，调用方无法区分两者——这就是代理的透明性。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Provide a surrogate or placeholder for another object to control access to it.

翻译：为另一个对象提供一个替身或占位符，以控制对它的访问。

模式由三个角色组成：

```
┌──────────────┐                 ┌──────────────┐
│    Client     │                 │  «interface»  │
│  （调用方）    │ ──────────────→ │   Fetcher     │
└──────────────┘                 └──────┬───────┘
                                        │
                         ┌──────────────┴──────────────┐
                         │                              │
                  ┌──────▼──────┐               ┌──────▼──────┐
                  │   Proxy     │ ─ real ──────→│  RealSubject │
                  │ （代理）     │               │ （真实主体）  │
                  └─────────────┘               └─────────────┘
```

- **Subject（抽象主体）**：定义统一接口（Go 中是 `interface`）
- **RealSubject（真实主体）**：实际的业务逻辑实现
- **Proxy（代理）**：持有 RealSubject 引用，实现同一接口，在转发前后执行控制逻辑

---

## 2 代理的三种经典类型

| 类型 | 核心行为 | 是否可能不调用真实主体 | 本项目对应 |
|------|---------|---------------------|-----------|
| **缓存代理**（Caching Proxy） | 缓存真实主体的结果，避免重复调用 | ✅ 缓存命中时不调用 | `cacheproxy/` |
| **保护代理**（Protection Proxy） | 鉴权/授权，拒绝未授权请求 | ✅ 权限不足时不调用 | `protectproxy/` |
| **远程代理**（Remote Proxy） | 让远程服务看起来像本地调用 | ❌ 总是转发到远端 | 标准库 `httputil.ReverseProxy` |
| **日志/度量代理**（Logging Proxy） | 记录调用行为，不改变结果 | ❌ 总是转发 | `metricsproxy/` |
| **虚拟代理**（Virtual Proxy） | 延迟初始化昂贵的真实主体 | ✅ 初始化前可能失败 | — |

核心判断标准：**代理可能不调用真实主体**。缓存命中时跳过、权限不足时拒绝——这就是"控制访问"。

## 3 标准库与生态中的先例

代理模式的思想在 Go 标准库和生态中广泛存在：

| 场景 | 机制 | 代理类型 |
|------|------|---------|
| `httputil.ReverseProxy` | 接收客户端请求，转发到后端服务 | 远程代理 |
| `net/rpc.Client` | 把远程函数调用包装成本地方法 | 远程代理 |
| `database/sql.DB` | 管理连接池，代理真实的 driver 连接 | 虚拟代理 + 缓存代理 |
| gRPC Interceptor | 在 RPC 调用前后注入鉴权/日志/重试 | 保护代理 + 日志代理 |
| Envoy sidecar | 透明代理服务间通信（mTLS、限流、观测） | 远程代理 + 保护代理 |
| Istio VirtualService | 流量路由、故障注入、A/B 测试 | 远程代理 |

### 3.1 httputil.ReverseProxy — 标准库的远程代理

```go
target, _ := url.Parse("http://backend:8080")
proxy := httputil.NewSingleHostReverseProxy(target)

// proxy 实现了 http.Handler 接口
// 调用方（客户端）看到的是本地 HTTP 服务
// 实际请求被透明转发到 backend:8080
http.ListenAndServe(":3000", proxy)
```

`ReverseProxy` 是教科书级的远程代理：
- 与 `http.Handler` 接口一致（透明性）
- 调用方不知道请求被转发到了另一台服务器
- 可以在转发前修改请求（`Director` 函数）
- 可以在收到响应后修改响应（`ModifyResponse` 函数）

### 3.2 net/rpc — 远程过程调用代理

```go
// 服务端注册
rpc.Register(new(Arith))
rpc.HandleHTTP()

// 客户端调用 — 看起来像本地方法
client, _ := rpc.DialHTTP("tcp", "server:1234")
var reply int
client.Call("Arith.Multiply", &Args{A: 7, B: 8}, &reply)
// reply == 56
```

`rpc.Client.Call()` 把网络通信隐藏在方法调用背后——调用方只看到一个普通的函数签名，不知道底层经过了序列化、网络传输和反序列化。

### 3.3 gRPC Interceptor — 本质是代理链

```go
// UnaryServerInterceptor 签名
type UnaryServerInterceptor func(
    ctx context.Context,
    req interface{},
    info *UnaryServerInfo,
    handler UnaryHandler,     // ← 真实主体
) (interface{}, error)

// 鉴权拦截器 — 保护代理
func authInterceptor(ctx context.Context, req interface{},
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler,
) (interface{}, error) {
    if !isAuthorized(ctx) {
        return nil, status.Error(codes.Unauthenticated, "unauthorized")
        // ← 不调用 handler — 代理拦截
    }
    return handler(ctx, req) // ← 授权通过，转发
}

grpc.NewServer(grpc.UnaryInterceptor(authInterceptor))
```

gRPC 的 Interceptor 是函数式的代理模式：每个 interceptor 决定是否调用 `handler`（真实主体），与本项目的 `protectproxy` 异曲同工。

### 3.4 Envoy / Istio sidecar — 基础设施级代理

```
┌─────────────────────────────────┐
│           Pod                    │
│  ┌──────────┐   ┌─────────────┐ │
│  │  App      │──→│  Envoy      │─┼──→ 目标服务
│  │  Container│   │  (sidecar)  │ │
│  └──────────┘   └─────────────┘ │
└─────────────────────────────────┘
```

Envoy sidecar 是最纯粹的代理：
- 应用容器不知道流量经过了 Envoy（透明性）
- Envoy 控制 mTLS、限流、重试、熔断（保护代理）
- Envoy 收集所有调用指标（度量代理）
- Envoy 可以路由流量到不同版本（远程代理）

## 4 本项目的实现

### 4.1 核心接口 — `fetcher/fetcher.go`

```go
// Fetcher 从数据源获取数据。
// 所有代理和真实主体都实现此接口。
type Fetcher interface {
    Fetch(ctx context.Context, key string) (string, error)
}

// SlowFetcher 模拟一个昂贵的数据源。
type SlowFetcher struct {
    Latency time.Duration
    calls   int64
}
```

设计要点：
- `context.Context` 作为第一个参数 — Go 的惯用模式，支持超时和取消
- `Calls()` 方法暴露调用计数 — 测试中验证代理是否正确拦截了请求
- 接口只有一个方法 — 保持最小，符合 Go 的单方法接口哲学

### 4.2 缓存代理 — `cacheproxy/cacheproxy.go`

```go
type Proxy struct {
    real  fetcher.Fetcher       // 真实主体
    ttl   time.Duration          // 缓存有效期
    mu    sync.RWMutex
    cache map[string]entry       // key → {value, expiresAt}
}

func (p *Proxy) Fetch(ctx context.Context, key string) (string, error) {
    // 1. 缓存命中 → 直接返回，不调用 real
    p.mu.RLock()
    if e, ok := p.cache[key]; ok && time.Now().Before(e.expiresAt) {
        p.mu.RUnlock()
        return e.value, nil
    }
    p.mu.RUnlock()

    // 2. 缓存未命中 → 调用真实 Fetcher
    value, err := p.real.Fetch(ctx, key)
    if err != nil {
        return "", err    // 错误不缓存
    }

    // 3. 存入缓存
    p.mu.Lock()
    p.cache[key] = entry{value: value, expiresAt: time.Now().Add(p.ttl)}
    p.mu.Unlock()
    return value, nil
}
```

关键行为：
- **缓存命中时不调用真实主体** — 这是代理（而非装饰器）的核心特征
- **错误不缓存** — 防止瞬时错误被持久化
- **RWMutex 读写分离** — 缓存命中（读多）用读锁，缓存更新（写少）用写锁
- **TTL 过期** — 避免缓存数据过时

### 4.3 保护代理 — `protectproxy/protectproxy.go`

```go
type Proxy struct {
    real         fetcher.Fetcher
    allowedRoles map[string]bool
}

func (p *Proxy) Fetch(ctx context.Context, key string) (string, error) {
    role, _ := ctx.Value(ctxKey{}).(string)
    if !p.allowedRoles[role] {
        return "", ErrUnauthorized   // ← 不调用 real
    }
    return p.real.Fetch(ctx, key)    // ← 授权通过，转发
}
```

关键行为：
- **角色信息通过 context 传递** — 符合 Go HTTP 中间件的惯用模式
- **未授权请求直接拒绝** — 真实 Fetcher 不会收到任何调用
- **允许多角色** — `New(real, "admin", "editor")` 支持灵活的权限配置

### 4.4 度量代理 — `metricsproxy/metricsproxy.go`

```go
type Proxy struct {
    real    fetcher.Fetcher
    calls   int64
    errors  int64
    totalNs int64
}

func (p *Proxy) Fetch(ctx context.Context, key string) (string, error) {
    start := time.Now()
    value, err := p.real.Fetch(ctx, key)
    elapsed := time.Since(start)

    atomic.AddInt64(&p.calls, 1)
    atomic.AddInt64(&p.totalNs, int64(elapsed))
    if err != nil {
        atomic.AddInt64(&p.errors, 1)
    }
    return value, err
}
```

度量代理总是转发请求——它更接近装饰器的边界。将它归为代理的理由：
- 它的职责是**监控访问**（观测谁在调用、调用了多少次、延迟多少）
- 它记录的是**访问行为**本身，而非增强数据处理能力
- 在 Envoy/Istio 中，这类功能由 sidecar proxy 承担

### 4.5 调用方

```go
import (
    "go-notes/designpattern/proxy/fetcher"
    "go-notes/designpattern/proxy/cacheproxy"
    "go-notes/designpattern/proxy/protectproxy"
    "go-notes/designpattern/proxy/metricsproxy"
)

func main() {
    // 真实主体：模拟 10ms 延迟的数据源
    slow := &fetcher.SlowFetcher{Latency: 10 * time.Millisecond}

    // 缓存代理：避免重复调用
    cached := cacheproxy.New(slow, 5*time.Second)

    // 保护代理：只允许 admin 访问
    protected := protectproxy.New(cached, "admin")

    // 度量代理：记录所有调用
    monitored := metricsproxy.New(protected)

    // 对调用方而言，monitored 就是一个普通的 Fetcher
    ctx := protectproxy.WithRole(context.Background(), "admin")
    value, _ := monitored.Fetch(ctx, "user:1")
    fmt.Println(value)
}
```

代理可以**链式组合**：`metricsproxy → protectproxy → cacheproxy → SlowFetcher`。每层代理只关注自己的职责，组合顺序决定了行为：度量代理记录所有请求（含被拒绝的），保护代理在缓存代理之前执行鉴权。

## 5 代理 vs 装饰器

这是最常被问到的设计模式面试题之一。两者在代码结构上几乎相同——都是"持有接口、实现同一接口"。区别在于**意图**：

| 维度 | 代理 | 装饰器 |
|------|------|--------|
| **意图** | 控制访问 | 增强功能 |
| **是否总是转发** | 不一定（可能拦截/替换） | 总是转发 |
| **与真实主体的关系** | 通常在构造时绑定 | 可以包装任意同接口对象 |
| **典型行为** | 缓存、鉴权、限流、延迟初始化 | 压缩、缓冲、加密、日志格式化 |
| **Go 标准库** | `httputil.ReverseProxy` | `bufio.Reader`（装饰 `io.Reader`） |
| **移除后的影响** | 行为改变（失去缓存/权限控制） | 功能降级（失去压缩/缓冲） |

实际判断只需问一个问题：

> **真实主体是否总是被调用？**
> - 总是 → 装饰器
> - 不总是 → 代理

```go
// 装饰器：bufio.Reader 总是调用底层 Reader
func (b *Reader) Read(p []byte) (n int, err error) {
    // ... 缓冲逻辑 ...
    _, err = b.rd.Read(b.buf)   // ← 总是调用
    // ...
}

// 代理：CacheProxy 可能不调用真实 Fetcher
func (p *Proxy) Fetch(ctx context.Context, key string) (string, error) {
    if cached {
        return cachedValue, nil  // ← 不调用真实主体
    }
    return p.real.Fetch(ctx, key)
}
```

## 6 设计决策解析

### 6.1 为什么 Fetcher 接口只有一个方法？

Go 社区推崇"小接口"：

```go
type Fetcher interface {
    Fetch(ctx context.Context, key string) (string, error)
}
```

- 一个方法 = 一个职责，符合接口隔离原则
- 代理只需实现一个方法即可"伪装"为真实主体
- 与 `io.Reader`、`http.Handler`、`sort.Interface` 的设计哲学一致
- 如果需要更多操作（Create、Update、Delete），应该定义独立的接口

### 6.2 为什么缓存代理用 RWMutex 而非 sync.Map？

`sync.Map` 看起来更简洁，但有两个问题：
1. **无法原子地检查过期 + 读取值** — `sync.Map` 的 `Load` 返回后还需要检查 TTL，存在竞态
2. **无法统计缓存大小** — `sync.Map` 没有 `Len()` 方法

`RWMutex + map` 虽然稍显冗长，但语义清晰、行为可预测。

### 6.3 为什么保护代理用 context 传递角色？

三种备选方案：

| 方案 | 优点 | 缺点 |
|------|------|------|
| `Fetch(ctx, key, role)` | 显式，编译期检查 | 修改接口签名，破坏代理透明性 |
| `proxy.SetRole(role)` | 简单 | 非并发安全，需要锁 |
| **`context.WithValue`** | **不修改接口，请求级别隔离** | 类型安全弱，需要文档约定 |

选择 context 的核心原因：**不能修改 `Fetcher` 接口**。如果代理要求调用方使用不同的接口，就失去了透明性——这是代理模式的根基。在实际项目中，HTTP 中间件（gin、echo）和 gRPC interceptor 都用 context 传递鉴权信息。

### 6.4 为什么度量代理用 atomic 而非 mutex？

度量代理只需要简单的计数器递增和读取：
- `atomic.AddInt64` 和 `atomic.LoadInt64` 是无锁操作
- 比 `sync.Mutex` 性能高一个数量级（无 goroutine 调度开销）
- 与观察者模式中 `MetricsObserver` 的设计一致

适用条件：字段之间没有一致性要求。如果需要"调用次数和错误次数的快照一致"，则应该用 mutex。

## 7 适用场景与局限

### 适用

- **缓存层**：API 网关缓存、DNS 缓存、CDN 缓存
- **鉴权/授权**：API 鉴权中间件、数据库访问控制、微服务 sidecar
- **限流**：令牌桶/漏桶代理，保护下游服务不被打爆
- **延迟初始化**：数据库连接池（`database/sql`）、大对象的按需加载
- **远程访问**：RPC 客户端、反向代理、服务网格
- **监控/审计**：调用计数、延迟记录、链路追踪

### 局限

- **增加延迟**：每层代理都有额外开销，多层嵌套可能累积
- **调试复杂性**：调用链被代理隐藏，堆栈跟踪中看不到真实调用路径
- **状态管理**：有状态代理（如缓存代理）需要考虑缓存一致性、过期策略
- **过度设计**：简单场景不需要代理，直接调用更清晰
- **与装饰器混淆**：代码结构相同容易分类错误，详见本文第 5 节

## 8 代理 vs 装饰器 vs 门面

| 维度 | 代理 | 装饰器 | 门面 |
|------|------|--------|------|
| **意图** | 控制访问 | 增强功能 | 简化调用 |
| **是否总是转发** | 不一定 | 总是 | 总是（聚合多个调用） |
| **接口关系** | 同一接口 | 同一接口 | 统一的新接口 |
| **子系统数量** | 1 个 | 1 个 | 多个 |
| **Go 标准库** | `httputil.ReverseProxy` | `bufio.Reader` | `http.ListenAndServe` |

### 缓存代理的击穿 / 穿透 / 并发重复请求

缓存代理在生产中面临三个经典问题：

| 问题 | 定义 | 解法 |
|------|------|------|
| **缓存击穿** | 热点 key 过期瞬间大量请求直达后端 | `singleflight.Group`：同一 key 只执行一次查询 |
| **缓存穿透** | 查询不存在的 key，每次都到后端 | 布隆过滤器 / 缓存空值 |
| **缓存雪崩** | 大量 key 同时过期 | 随机化 TTL：`ttl + rand(0, jitter)` |

本项目的 `cacheproxy` 可以通过以下方式增强：

```go
// 用 singleflight 防止击穿
var group singleflight.Group

func (p *Proxy) Fetch(ctx context.Context, key string) (string, error) {
    // ... 检查缓存 ...
    v, err, _ := group.Do(key, func() (interface{}, error) {
        return p.real.Fetch(ctx, key)
    })
    // ... 存入缓存 ...
}
```

## 9 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| 缓存命中 | 第二次 Fetch 不调用 real（检查 Calls() 计数） |
| 缓存过期 | TTL 后再次 Fetch 调用 real |
| 错误不缓存 | real 返回 error 后不缓存，下次重新调用 |
| 权限拒绝 | 无角色或错误角色返回 ErrUnauthorized |
| 权限通过 | 正确角色调用 real 并返回结果 |
| 度量准确 | Calls/Errors/AvgLatency 与实际一致 |
| 代理透明 | 代理和 real 实现同一接口（编译期断言） |
| 链式组合 | metrics(protect(cache(real))) 全链路正确 |

## 10 成本模型

### 何时值得用代理

- 需要缓存层——减少对昂贵数据源的调用
- 需要鉴权——在访问资源前做权限检查
- 需要度量——记录调用频率和延迟
- 对调用方透明——代理和真实主体实现同一接口

### 何时是过度设计

- 只有简单的直接调用——代理层没有意义
- 缓存/鉴权逻辑已内置在框架中——不需要手写代理
- 代理逻辑与业务强耦合——可能需要重新设计接口
