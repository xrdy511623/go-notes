# 桥接模式详解

桥接模式（Bridge Pattern）将**抽象**与**实现**分离，使二者可以独立变化。当系统同时存在两个（或更多）独立变化的维度时，桥接模式能避免类数量的笛卡尔积爆炸，并让每个维度各自演化、互不影响。

本目录以"消息通知"为场景：**消息类型**（告警、营销）和**投递渠道**（邮件、短信、Webhook）是两个独立维度，通过桥接模式将它们解耦。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Decouple an abstraction from its implementation so that the two can vary independently.

翻译：将抽象部分与其实现部分分离，使它们可以独立地变化。

### 核心结构

```
            ┌─────────────────────┐
            │   Abstraction       │
            │   (Message)         │
            │                     │
            │ + Send(to, impl)    │──────────┐
            └─────────┬──────────┘           │
                      │ extends              │ bridge (持有接口引用)
            ┌─────────┴──────────┐           │
            │  RefinedAbstraction │           │
            │  (AlertMessage,    │     ┌─────┴──────────────┐
            │   MarketingMessage)│     │   Implementor       │
            └────────────────────┘     │   (channel.Sender)  │
                                       │                     │
                                       │ + Send(to,subj,body)│
                                       └─────────┬───────────┘
                                                  │ implements
                                    ┌─────────────┼─────────────┐
                                    │             │             │
                              ┌─────┴─────┐ ┌────┴─────┐ ┌────┴──────┐
                              │EmailSender│ │SMSSender │ │WebhookSender│
                              └───────────┘ └──────────┘ └───────────┘
```

**"桥"在哪里？** 桥是 Abstraction 持有的 Implementor 接口引用。`Message.Send(to, ch)` 中的 `ch channel.Sender` 参数就是这座桥——它将消息格式化逻辑与投递渠道逻辑连接起来，同时保持两侧可以独立扩展。

### 为什么不直接继承？

在支持继承的语言中，常见做法是让 `AlertEmailNotifier` 同时继承 `Alert` 和 `Email`。这会导致：

1. **笛卡尔积爆炸**：M 种消息 × N 种渠道 = M×N 个子类
2. **修改传播**：修改邮件发送逻辑需要修改所有 `*Email*` 子类
3. **紧耦合**：格式化和投递被绑死在一起

桥接模式用**组合替代继承**，把乘法变成加法：M + N 个类型即可覆盖所有组合。

## 2 标准库与生态中的先例

Go 标准库和主流框架中大量使用了桥接思想：

| 场景 | Abstraction（抽象） | Implementor（实现） | 说明 |
|------|---------------------|---------------------|------|
| `io.Copy` | 读/写算法 | `io.Writer` / `io.Reader` | 算法不关心底层是文件、网络还是内存 |
| `database/sql` | `sql.DB` / `sql.Tx` | `driver.Driver` / `driver.Conn` | 查询逻辑与数据库驱动完全解耦 |
| `image` | `image.Image` 接口 | 各格式编解码器 (`png`, `jpeg`) | 图像操作不关心编码格式 |
| `sort` | `sort.Sort` 算法 | `sort.Interface` 实现 | 排序算法与数据结构解耦 |
| `log/slog` (Go 1.21+) | `slog.Logger` | `slog.Handler` (`JSONHandler`, `TextHandler`) | 日志记录逻辑与输出格式/目标分离 |
| `net/http` | `http.Handler` | `http.ResponseWriter` | 请求处理逻辑与响应写入方式分离 |
| `crypto/cipher` | `cipher.Stream` / `cipher.Block` | 各加密算法实现 | 加密模式与具体算法解耦 |

### 深入示例：`database/sql`

```go
// 抽象层 (Abstraction)
db, _ := sql.Open("mysql", dsn)     // sql.DB 不知道 MySQL 的细节
rows, _ := db.Query("SELECT ...")    // 统一的查询接口

// 实现层 (Implementor)
import _ "github.com/go-sql-driver/mysql"  // 注册 MySQL 驱动
import _ "github.com/lib/pq"               // 换成 PostgreSQL 只需换驱动
```

`sql.DB` 持有 `driver.Connector` 接口的引用——这就是桥。应用代码（抽象）不需要修改，只需更换驱动（实现）。

## 3 本项目的实现

### 整体架构

```
消息类型 (Abstraction)          投递渠道 (Implementor)
┌────────────────────┐         ┌────────────────────┐
│ Message interface   │────桥──→│ Sender interface    │
│   Send(to, ch)      │         │   Send(to,subj,body)│
├────────────────────┤         ├────────────────────┤
│ AlertMessage        │         │ EmailSender         │
│ MarketingMessage    │         │ SMSSender           │
└────────────────────┘         │ WebhookSender       │
                               └────────────────────┘

2 种消息 × 3 种渠道 = 6 种组合，只需 2 + 3 = 5 个类型
```

### Implementor 侧：`channel` 包

```go
// Sender 是消息投递渠道的抽象（桥接模式中的 Implementor）。
type Sender interface {
    Send(to, subject, body string) error
}
```

三个具体实现均满足 `Sender` 接口，各自处理投递细节：

- **`EmailSender`**：校验收件地址包含 `@`，记录投递
- **`SMSSender`**：校验收件人非空，模拟短信网关发送
- **`WebhookSender`**：校验 URL 非空，模拟 HTTP POST

所有实现都包含 `mu sync.Mutex` 保证并发安全，并通过 `Sent() []Record` 暴露发送记录供测试验证。

### Abstraction 侧：`message` 包

```go
// Message 是消息类型的抽象（桥接模式中的 Abstraction）。
type Message interface {
    Send(to string, ch channel.Sender) error
}
```

两个具体消息类型各自负责格式化：

- **`AlertMessage`**：subject 格式为 `[ALERT][severity] title`，body 包含告警详情
- **`MarketingMessage`**：subject 为活动名称，body 自动追加退订页脚

### 便利层：`notifier` 包

```go
n := notifier.New(emailCh)

// 使用默认渠道
n.Notify("admin@example.com", message.NewAlert("CPU 过载", "critical"))

// 覆盖默认渠道
n.NotifyVia("+8613800138000", alert, smsCh)

// 广播给多人
errs := n.Broadcast(recipients, alert)
```

`Notifier` 持有默认渠道，提供 `Notify`、`NotifyVia`、`Broadcast` 三个便利方法。它不是桥接模式的必要组成部分，而是对桥接的上层封装。

### 完整调用流程

```
用户代码
  │
  ▼
Notifier.Notify("admin@example.com", alertMsg)
  │
  ▼
AlertMessage.Send("admin@example.com", emailSender)
  │ 格式化 subject = "[ALERT][critical] CPU 过载"
  │ 格式化 body = "告警等级: critical\n..."
  ▼
EmailSender.Send("admin@example.com", subject, body)
  │ 校验邮箱格式
  │ 记录到 sent []Record
  ▼
返回 nil (成功)
```

## 4 设计决策解析

### 4.1 为什么 Message.Send 接收 channel 参数？

```go
Send(to string, ch channel.Sender) error  // 当前设计
```

而非在构造时绑定：

```go
msg := NewAlert("CPU 过载", "critical", emailSender)  // 构造时绑定
msg.Send("admin@example.com")
```

**理由**：接收参数方式允许同一消息通过不同渠道发送，无需重新构造消息对象。这在 `NotifyVia` 和多渠道广播场景中至关重要：

```go
alert := message.NewAlert("紧急告警", "critical")
alert.Send("admin@example.com", emailCh)    // 同一消息
alert.Send("+8613800138000", smsCh)          // 不同渠道
alert.Send("oncall-channel", webhookCh)      // 再次复用
```

### 4.2 为什么使用 Record 类型做测试验证？

`Record` 提供了一种**无副作用的可观测性**机制。实际项目中渠道会真正发送邮件/短信，但测试中我们需要验证"发了什么"而不是"真的发了"。

`Sent() []Record` 返回副本而非引用，避免测试代码意外修改内部状态。配合 `sync.Mutex`，在并发测试场景下也是安全的。

### 4.3 为什么需要 Notifier 包装层？

桥接模式的核心是 `Message` + `Sender`，`Notifier` 是可选的便利层：

- **默认渠道**：避免每次调用都传递渠道
- **批量操作**：`Broadcast` 封装了循环 + 错误收集
- **扩展点**：未来可加入重试、日志、限流等横切关注点

没有 `Notifier`，直接 `msg.Send(to, ch)` 也完全可行。`Notifier` 的存在不改变桥接结构，只是提升使用体验。

### 4.4 为什么告警消息将严重等级嵌入 subject？

```
[ALERT][critical] CPU 过载
```

这是运维领域的通用约定：

- 邮件客户端可以根据 subject 前缀设置过滤规则
- 短信接收者一眼就能判断紧急程度
- Webhook 消费方可以据此做告警分级路由

## 5 与相近模式的对比

桥接模式容易与策略、适配器、抽象工厂混淆。核心区别在于**解决的问题不同**：

| 维度 | Bridge 桥接 | Strategy 策略 | Adapter 适配器 | Abstract Factory 抽象工厂 |
|------|------------|--------------|----------------|--------------------------|
| **意图** | 解耦两个独立变化的维度 | 运行时切换算法 | 让不兼容接口协作 | 创建一族相关对象 |
| **变化维度** | 两个维度独立变化 | 一个维度变化 | 零个（转换已有接口） | 产品族维度 |
| **组合方向** | 抽象 → 实现（双向扩展） | 上下文 → 策略（单向替换） | 客户端 → 适配器 → 被适配者 | 工厂 → 产品 |
| **关键区别** | 设计阶段就规划好的分离 | 重点在行为可替换 | 事后补救的胶水层 | 重点在创建过程 |

### Bridge vs Strategy

最常见的困惑。区分要点：

- **Strategy**：只有一个维度变化。例如排序算法（快排/归并/堆排）替换，数据结构不变。
- **Bridge**：两个维度**同时**独立变化。例如消息类型和投递渠道都在扩展。

如果你只有 `Message` 一种，但有多种 `Sender`，那就是 Strategy。
如果 `Message` 和 `Sender` 都在增长，那就需要 Bridge。

### Bridge vs Adapter

- **Adapter**：已经有两个不兼容的接口，需要转换让它们能一起工作。是事后补救。
- **Bridge**：在设计阶段就预见到两个维度会独立变化，提前做分离。是事前规划。

### Bridge vs Abstract Factory

- **Abstract Factory**：创建一族相关的对象（如 Windows 风格的按钮 + 文本框 + 菜单）。
- **Bridge**：不关心对象如何创建，只关心抽象和实现的分离。

实践中二者可以配合：用 Abstract Factory 创建 Bridge 的 Implementor。

## 6 常见陷阱 / 反例

### 6.1 笛卡尔积爆炸（参见 `trap/cartesianexplosion/`）

不使用桥接模式时，每种 (消息类型, 投递渠道) 组合都需要一个独立的结构体：

```
AlertEmailNotifier      MarketingEmailNotifier
AlertSMSNotifier        MarketingSMSNotifier
AlertWebhookNotifier    MarketingWebhookNotifier
```

2×3 = 6 个类型。新增一种消息类型需要加 3 个结构体，新增一种渠道需要加 2 个结构体。

投递逻辑（如邮件格式验证）在每个 `*Email*` 类型中重复；格式化逻辑（如告警前缀）在每个 `Alert*` 类型中重复。修改任一逻辑都要修改多处，极易遗漏。

**规模感受**：3 种消息 × 4 种渠道 = 12 个类型，而桥接只需 3 + 4 = 7 个。5 × 5 = 25 vs 10。差距随规模指数级扩大。

### 6.2 只有一个维度变化时误用桥接

如果系统中只有一种消息类型，但有多种投递渠道：

```go
type Alert struct{}
func (a *Alert) Send(to string, ch Sender) error { ... }
```

此时 `Message` 接口只有一个实现，"抽象"侧没有变化的需求。这种场景用**策略模式**更直接，桥接是过度设计。

**判断标准**：如果 M=1 或 N=1，桥接退化为策略模式，不值得引入额外的抽象层。

### 6.3 过度抽象稳定的实现

如果投递渠道永远只有邮件一种，且消息类型也相对固定，引入桥接只增加了间接层，没有带来灵活性收益。

**经验法则**：只在确信两个维度都会增长时才使用桥接。"可能会变"不是充分理由。

### 6.4 实现细节穿透抽象

反面示例：

```go
type Message interface {
    Send(to string, ch channel.Sender) error
    FormatForEmail() string    // 泄漏了邮件渠道的细节
    FormatForSMS() string      // 泄漏了短信渠道的细节
}
```

一旦抽象中出现与特定实现绑定的方法，桥接就名存实亡。抽象应该对实现**完全无知**。

正确做法：让抽象只定义"做什么"（发送消息），如何格式化由各 Message 实现自行决定，但不针对特定渠道做特殊处理。

## 7 测试要点

| 测试场景 | 测试函数 | 验证点 |
|----------|---------|--------|
| 告警 → 邮件 | `TestAlert_ViaEmail` | 记录数=1，收件人正确 |
| 告警 → 短信 | `TestAlert_ViaSMS` | 短信投递成功 |
| 告警 → Webhook | `TestAlert_ViaWebhook` | Webhook 投递成功 |
| 营销 → 邮件 | `TestMarketing_ViaEmail` | subject=活动名，body 含退订页脚 |
| 覆盖默认渠道 | `TestNotifyVia_OverridesDefault` | 默认渠道无记录，指定渠道有记录 |
| 广播多人成功 | `TestBroadcast_MultipleRecipients` | 3 条记录全部正确 |
| 广播部分失败 | `TestBroadcast_PartialFailure` | 失败地址在 errs 中，成功地址有记录 |
| 严重等级格式 | `TestAlert_SeverityFormat` | subject 包含 `[ALERT][critical]` |
| 空收件人报错 | `TestSend_EmptyRecipient_Error` | 返回非 nil 错误 |

### 测试策略说明

1. **使用 Record 而非 Mock**：渠道实现自带记录能力，无需引入 mock 框架
2. **验证格式而非精确匹配**：使用 `strings.Contains` 而非完整字符串比较，避免格式微调导致测试脆弱
3. **错误路径覆盖**：邮件地址不含 `@`、收件人为空等边界场景
4. **并发安全**：`Record` 使用 `sync.Mutex` 保护，支持未来的并发测试扩展

## 8 成本模型

### 何时值得使用桥接

| 条件 | 说明 |
|------|------|
| 两个维度独立变化 | 消息类型和渠道都在增长 |
| M × N 显著大于 M + N | 如 3×4=12 远大于 3+4=7 |
| 两侧需要独立部署/测试 | 渠道团队和业务团队分开迭代 |
| 需要运行时组合 | 同一消息可能走不同渠道 |

### 何时是过度设计

| 条件 | 说明 |
|------|------|
| 只有一个维度变化 | 用策略模式更直接 |
| 总共只有 2-3 个实现 | 抽象层的成本超过收益 |
| 两个维度强关联 | 每种消息必须走特定渠道，不存在自由组合 |
| 抽象层会频繁变化 | 桥接假设抽象层相对稳定 |

### 复杂度对比

```
无桥接:
  类型数 = M × N
  新增消息成本 = +N 个结构体
  新增渠道成本 = +M 个结构体

桥接:
  类型数 = M + N + 2 (两个接口)
  新增消息成本 = +1 个结构体
  新增渠道成本 = +1 个结构体
```

当 M=2, N=3 时：6 vs 7（桥接略多，因为接口开销）。
当 M=3, N=4 时：12 vs 9（桥接开始显现优势）。
当 M=5, N=5 时：25 vs 12（优势明显）。

**拐点**：大约在 M×N > 2×(M+N) 时，桥接模式的收益超过成本。即 M 和 N 都 ≥ 3 时。

## 9 适用场景与局限

### 典型适用场景

**1. 通知系统**（本项目示例）

消息类型（告警、营销、验证码、系统通知）× 投递渠道（邮件、短信、推送、站内信）。业务方不断新增消息类型，基础设施团队不断接入新渠道。

**2. UI 渲染引擎**

组件类型（按钮、输入框、列表）× 渲染平台（Web、iOS、Android、桌面）。组件抽象定义交互行为，平台实现负责绘制。

**3. 数据库访问层**

查询构建器（SELECT/INSERT/UPDATE）× 数据库驱动（MySQL、PostgreSQL、SQLite）。Go 标准库的 `database/sql` 正是此模式的典范。

**4. 日志系统**

日志级别与格式化（`slog.Logger`）× 输出目标（控制台、文件、远端服务）。Go 1.21 的 `log/slog` 就是 Logger（抽象）和 Handler（实现）的桥接。

**5. 支付系统**

支付方式（扫码支付、H5 支付、APP 支付）× 支付渠道（微信、支付宝、银联）。每种支付方式定义流程，各渠道负责对接具体 API。

### 局限性

1. **间接层增加调试难度**：调用链变长（用户 → Notifier → Message → Sender），排查问题需要跨多个包追踪
2. **接口设计要求高**：Implementor 接口需要足够通用以支撑所有抽象，设计不当会导致"最大公约数"接口过于宽泛或过于狭窄
3. **性能开销**：每次调用经过两层虚方法（接口）分派，对于极高频调用场景可能产生可测量的开销（通常可忽略）
4. **前期设计成本**：需要提前识别出哪些维度会独立变化，判断失误会导致不必要的复杂性


### 包依赖关系

```
notifier
  ├── message
  │     └── channel    (Message.Send 的参数类型)
  └── channel          (Notifier 持有的默认渠道)
```

`channel` 是最底层的包，不依赖其他包；`message` 依赖 `channel`（因为 `Send` 方法接收 `channel.Sender`）；`notifier` 依赖二者。

`trap/cartesianexplosion` 是独立的反例包，不参与正式的依赖链。
