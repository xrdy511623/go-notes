# Go 设计模式：常用模式 + 并发模式 + 韧性模式

本目录从 Go 工程实践出发，精选了 **25 种在 Go 生产代码中真正高频使用的模式**，覆盖四大类别：

- **经典设计模式**（GoF 子集 + 工程补充）：只收录在 Go 隐式接口 + 组合哲学下仍有价值的模式，外加依赖注入这一 SOLID 实践
- **Go 并发模式**：管道、扇出扇入、迭代器——这些是 Go 独有或 Go 表达最自然的模式
- **韧性/稳定性模式**：熔断器、舱壁、对象池——微服务治理的基本功

每篇文档遵循统一的 10 节模板，包含：原理、标准库先例、本项目实现、设计决策、对比、陷阱、测试要点、成本模型。

## 易混淆模式矩阵

### 适配器 / 装饰器 / 代理 / 门面 / 桥接 / 责任链

这六个结构型+行为型模式在代码结构上极其相似——都涉及"持有一个接口"。区别在**意图**：

| 维度 | 适配器 | 装饰器 | 代理 | 门面 | 桥接 | 责任链 |
|------|--------|--------|------|------|------|--------|
| **意图** | 翻译接口 | 增强功能 | 控制访问 | 简化入口 | 解耦两维度 | 传递处理权 |
| **输入/输出接口** | 不同 | 相同 | 相同 | 新接口 | 双接口 | 相同 |
| **是否总是转发** | 是 | 是 | 不一定 | 是（编排） | 是 | 不一定 |
| **可否叠加** | 通常不 | 无限叠加 | 可链式 | 不叠加 | 不叠加 | 可链式 |
| **包装对象数** | 1 个 | 1 个 | 1 个 | N 个子系统 | 1 个（另一维度） | 1 个（next） |
| **Go 标准库** | `HandlerFunc` | `bufio.Reader` | `ReverseProxy` | `ListenAndServe` | `io.Writer` 体系 | HTTP 中间件 |
| **判断口诀** | 两接口不同→适配器 | 同接口+总转发→装饰器 | 同接口+可不转发→代理 | 协调多子系统→门面 | 两维度独立变化→桥接 | 可能不调next→责任链 |

快速判断流程：

```
你在协调多个子系统吗？
├── 是 → 门面（简化入口）
└── 否 → 有两个独立变化的维度吗？
    ├── 是 → 桥接（解耦维度）
    └── 否 → 持有的类型和自身实现的接口相同吗？
        ├── 不同 → 适配器（翻译）
        └── 相同 → 总是调用内层？
            ├── 是 → 装饰器（增强）
            └── 不一定 → 可能有多个处理者串联？
                ├── 是 → 责任链（传递）
                └── 否 → 代理（控制）
```

### 策略 / 模板方法 / 命令

三者都用接口实现多态行为，但关注点不同：

| 维度 | 策略 | 模板方法 | 命令 |
|------|------|---------|------|
| **意图** | 替换整个算法 | 定制算法中的某些步骤 | 封装请求为对象 |
| **接口方法数** | 通常 1 个 | 通常 3+ 个 | 2 个（Execute + Undo） |
| **谁控制流程** | 调用方 | 模板函数 | Invoker |
| **生命周期** | 注入后被调用 | 传入模板函数 | 创建→排队→执行→保存 |
| **有无状态** | 通常无状态 | 通常无状态 | 有状态（携带参数和 undo 数据） |
| **Go 标准库** | `sort.Slice(less)` | `sort.Sort(Interface)` | `cobra.Command` |
| **判断口诀** | 一个方法代表完整算法→策略 | 多个方法被固定骨架调用→模板方法 | 需要排队/撤销/日志→命令 |

### 简单工厂 / 注册工厂 / 依赖注入

三者都解决"如何创建和获取依赖"：

| 维度 | 简单工厂 | 注册工厂 | 依赖注入 (Wire/fx) |
|------|---------|---------|-------------------|
| **选择机制** | `switch` 编译期确定 | `map[string]` 运行时查找 | 类型系统编译期生成 |
| **新增实现** | 改工厂 switch | 新包 + `init()` | 新 Provider 函数 |
| **开闭原则** | 违反 | 遵循 | 遵循 |
| **编译期安全** | ✅ 枚举常量 | ❌ 字符串 | ✅ 类型匹配 |
| **全局状态** | 无 | 有（全局注册表） | 无（容器显式传递） |
| **适用规模** | 少量固定实现 | 驱动/插件 | 大型服务 |
| **Go 标准库** | `crypto.Hash.New()` | `database/sql.Register` | — |
| **升级信号** | switch 分支 > 10 个 | 注册表散落各处 | — |

升级路径：`简单工厂 → 注册工厂 → 依赖注入`。大多数项目从简单工厂起步，随规模增长逐步升级。

### 状态机（FSM） / 状态（GoF State） / 策略

三者都用接口替代 switch/case，但建模对象不同：

| 维度 | 状态机（FSM） | 状态（GoF State） | 策略 |
|------|-------------|-----------------|------|
| **建模对象** | 转换规则 | 状态行为 | 算法 |
| **状态在哪** | 外部转换表 `map[{event,from}]to` | 每个状态对象内部决定下一状态 | 无状态转换 |
| **行为在哪** | 回调/钩子 | 状态对象的方法 | 策略对象的方法 |
| **谁决定转换** | 引擎查表 | 当前状态对象 | 调用方 |
| **新增状态** | 加表项 | 加 State 实现 | 不适用 |
| **适用** | 状态多、转换规则明确 | 状态少、每个状态行为差异大 | 无状态切换 |
| **本项目** | `statemachine/` | `state/` | `strategy/` |
| **判断口诀** | 关注"什么条件下从 A 到 B"→FSM | 关注"在状态 A 时做什么"→GoF State | 关注"用哪个算法"→策略 |

## 每篇文档结构（统一模板）

所有模式文档遵循以下 10 节结构：

```
1.  模式定义          — GoF/社区定义 + Go 视角解读
2.  标准库与生态中的先例 — 这不是自创模式，标准库里到处都是
3.  本项目的实现       — 核心 API、具体实现、使用方式
4.  设计决策解析       — 为什么这样设计，备选方案对比
5.  与相近模式的对比    — 消除混淆，给出判断流程
6.  常见陷阱 / 反例    — trap/ 目录中的代码 + 生产踩坑
7.  测试要点          — 这个模式写对了应该验证什么
8.  成本模型          — 何时值得用，何时是过度设计
9.  适用场景与局限     — 用 / 不用的决策依据
10. 目录结构          — 本目录的文件布局
```

部分文档还包含 **Go 版本与前置知识** 小节（如迭代器需要 Go 1.23+）。
