# 单例模式详解

单例模式（Singleton Pattern）是最简单也最容易被误用的创建型设计模式。它确保一个类型在整个进程中**只有一个实例**，并提供全局访问点。Go 语言的 `sync.Once` 为这一模式提供了简洁且并发安全的实现方式，几乎可以视为"语言内置的单例原语"。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Ensure a class only has one instance, and provide a global point of access to it.

翻译：确保一个类只有一个实例，并提供一个全局访问点。

模式结构：

```
┌──────────────────────────────────┐
│           Singleton              │
├──────────────────────────────────┤
│ - instance: *Singleton           │
│ - once:     sync.Once            │
├──────────────────────────────────┤
│ + Instance(): *Singleton         │
│ - load():    *Singleton          │
└──────────────────────────────────┘
          │
          │ 全局唯一
          ▼
    ┌───────────┐
    │ instance  │ ← 所有调用方拿到的都是同一个指针
    └───────────┘
```

核心约束：

- **唯一性**：整个进程中只存在一个实例
- **全局可达**：通过 `Instance()` 函数从任何地方访问
- **延迟或提前创建**：可以在首次使用时创建（懒汉），也可以在程序启动时创建（饿汉）

---

## 2 标准库与生态中的先例

单例模式在 Go 标准库和生态中无处不在：

| 场景 | 机制 | 说明 |
|------|------|------|
| `sync.Once` | `Do(f)` | Go 单例的核心原语，保证 f 只执行一次 |
| `http.DefaultClient` | 包级变量 | 全局共享的 HTTP 客户端 |
| `http.DefaultServeMux` | 包级变量 | 默认的 HTTP 路由器 |
| `slog.Default()` | `sync.Once` + `atomic` | Go 1.21 结构化日志的默认 logger |
| `sql.Open()` | 连接池单例 | 同一 DSN 通常只需打开一次 |
| `rand.globalRand` | 包级私有变量 | `math/rand` 的全局随机源（Go 1.22 前） |
| K8s client-go | `rest.InClusterConfig()` | 集群内配置通常全局初始化一次 |
| uber-go/zap | `zap.L()` / `zap.ReplaceGlobals()` | 全局 logger 单例 |

`sync.Once` 是 Go 单例的基石，它的核心保证：

```go
var once sync.Once
var instance *Config

once.Do(func() {
    instance = &Config{...}    // 只执行一次
})
// 此处 instance 一定已初始化完成（happens-before 保证）
```

关键语义：
1. **只执行一次**：即使 100 个 goroutine 同时调用 `Do`，f 也只执行一次
2. **happens-before**：`Do` 返回后，f 中的所有写入对所有 goroutine 可见
3. **永不重试**：如果 f panic，后续的 `Do` 调用也不会再执行 f

第 3 点尤其重要——这意味着如果初始化失败，错误会被"永久缓存"。这是有意为之的设计，详见第 4.2 节。

## 3 本项目的实现

### 3.1 sync.Once 懒加载单例 — `configmgr/config.go`

这是 Go 中最推荐的单例实现方式：

```go
type Config struct {
    AppName    string `json:"app_name"`
    Debug      bool   `json:"debug"`
    ServerPort int    `json:"server_port"`
    DBHost     string `json:"db_host"`
    DBPort     int    `json:"db_port"`
}

var (
    instance *Config
    once     sync.Once
    initErr  error
)

func Instance() (*Config, error) {
    once.Do(func() {
        instance, initErr = load()
    })
    return instance, initErr
}
```

核心 API：

| 函数 | 作用 | 说明 |
|------|------|------|
| `Instance()` | 获取唯一实例 | 首次调用触发初始化，后续直接返回 |
| `load()` | 执行实际初始化 | 从文件或环境变量加载配置 |
| `ResetForTesting()` | 重置单例状态 | 仅用于测试，重新赋值 `sync.Once` |

`load()` 函数的策略：
- 如果 `CONFIG_PATH` 环境变量已设置 → 从 JSON 文件加载
- 如果未设置 → 返回内置默认值

```go
func load() (*Config, error) {
    cfg := &Config{
        AppName:    "my-app",
        ServerPort: 8080,
        DBHost:     "localhost",
        DBPort:     3306,
    }

    path := os.Getenv("CONFIG_PATH")
    if path == "" {
        return cfg, nil
    }

    data, err := os.ReadFile(path)
    if err != nil {
        return nil, fmt.Errorf("configmgr: read %s: %w", path, err)
    }

    if err := json.Unmarshal(data, cfg); err != nil {
        return nil, fmt.Errorf("configmgr: parse %s: %w", path, err)
    }

    return cfg, nil
}
```

### 3.2 包级变量饿汉式单例 — `connpool/pool.go`

饿汉式更简单——包级变量在 `import` 时即完成初始化：

```go
type Pool struct {
    mu      sync.Mutex
    conns   []string
    maxSize int
    nextID  int64
}

var instance = newPool(10)

func Instance() *Pool {
    return instance
}
```

`Instance()` 函数体只有一行 `return instance`，没有锁、没有 `sync.Once`，因为 Go 的包初始化机制保证了：

1. 包级变量按声明顺序初始化
2. 单个包的 `init()` 函数按出现顺序执行
3. 上述过程在单个 goroutine 中串行完成
4. 所有 `init()` 执行完毕后才会启动 `main()`

因此，`instance` 在任何业务代码运行之前就已经就绪。

### 3.3 反面示例：双重检查锁 — `trap/doublecheck/`

从 Java/C++ 移植过来的经典反模式：

```go
var (
    instance *Config
    mu       sync.Mutex
)

func Instance() *Config {
    if instance == nil {    // ← DATA RACE: 无保护的读取
        mu.Lock()
        defer mu.Unlock()
        if instance == nil {
            instance = &Config{Name: "default"}
        }
    }
    return instance
}
```

**为什么这是错的？**

外层 `if instance == nil` 是无锁读取，与 `mu.Lock()` 内部的写操作构成 **data race**。Go memory model 明确规定：对共享变量的并发读写，如果没有同步原语保护，行为未定义。

具体来说：
- goroutine A 正在执行 `instance = &Config{...}`
- goroutine B 同时读取 `instance`，可能看到：
  - `nil`（旧值）
  - 非 nil 但指向**未完全初始化**的 `Config`（部分写入）

用 `go test -race` 可以检测到这个问题。正确做法：使用 `sync.Once`，它内部用 `atomic.StoreUint32` + `Mutex` 保证了正确的 happens-before 关系。

### 3.4 调用方

```go
import (
    "go-notes/designpattern/singleton/configmgr"
    "go-notes/designpattern/singleton/connpool"
)

func main() {
    // sync.Once 懒加载单例
    cfg, err := configmgr.Instance()
    if err != nil {
        panic(err)
    }
    fmt.Printf("Config: app=%s port=%d\n", cfg.AppName, cfg.ServerPort)

    // 多次调用拿到同一实例
    cfg2, _ := configmgr.Instance()
    fmt.Println("同一实例:", cfg == cfg2) // true

    // 饿汉式单例
    pool := connpool.Instance()
    conn := pool.Get()
    fmt.Printf("连接池: got %s, idle=%d\n", conn, pool.Len())
    pool.Put(conn)
}
```

## 4 设计决策解析

### 4.1 为什么 sync.Once 是 Go 单例的首选？

`sync.Once` 的实现只有约 30 行代码（Go 1.21），但提供了三个关键保证：

```
┌─────────────────────────────────────────────┐
│              sync.Once.Do(f)                │
├─────────────────────────────────────────────┤
│ 1. 原子性：f 只执行一次                      │
│ 2. 可见性：Do 返回后，f 的副作用对所有          │
│    goroutine 可见（happens-before）           │
│ 3. 阻塞性：并发调用会等待首次 Do 完成          │
└─────────────────────────────────────────────┘
```

对比手动实现（Mutex、atomic、double-check locking）：

| 维度 | `sync.Once` | 手动 Mutex | Double-Check |
|------|-------------|-----------|-------------|
| 正确性 | 标准库保证 | 需自行确保 | ❌ data race |
| 性能 | fast path 只需一次 atomic load | 每次加锁 | fast path 无锁但不安全 |
| 代码量 | 3 行 | 8-10 行 | 8-10 行 |
| 可维护性 | 意图清晰 | 需注释说明 | 容易被误认为正确 |

`sync.Once` 的 fast path（已初始化后）只执行一次 `atomic.LoadUint32`，性能等同于无锁读取。

### 4.2 为什么 Instance() 返回 (*T, error) 而不是 *T？

对比两种签名：

```go
// 方案 A：不返回 error
func Instance() *Config {
    once.Do(func() {
        instance = mustLoad()  // 失败就 panic
    })
    return instance
}

// 方案 B：返回 error（本项目的选择）
func Instance() (*Config, error) {
    once.Do(func() {
        instance, initErr = load()
    })
    return instance, initErr
}
```

选择方案 B 的理由：

- **配置加载可能失败**：文件不存在、JSON 格式错误、权限不足——这些是可预期的运行时错误
- **调用方有选择权**：可以 fallback 到默认配置、展示友好错误信息、或决定 panic
- **Go 惯例**：不应在库代码中 panic，error 是一等公民

何时用方案 A（直接 panic）：

- 初始化逻辑不可能失败（如纯内存操作）
- 在 `init()` 中调用，失败意味着程序无法启动
- 标准库的 `regexp.MustCompile` 就是这种思路

### 4.3 懒汉 vs 饿汉：如何选择？

```
懒汉式（Lazy Initialization）          饿汉式（Eager Initialization）
┌────────────────────────────┐      ┌────────────────────────────┐
│ var once sync.Once         │      │ var instance = newPool(10) │
│ var instance *Config       │      │                            │
│                            │      │ func Instance() *Pool {    │
│ func Instance() *Config {  │      │     return instance        │
│     once.Do(func() {       │      │ }                          │
│         instance = load()  │      │                            │
│     })                     │      │                            │
│     return instance        │      │                            │
│ }                          │      │                            │
└────────────────────────────┘      └────────────────────────────┘
```

| 维度 | 懒汉式（sync.Once） | 饿汉式（包级变量） |
|------|-------------------|-----------------|
| 初始化时机 | 首次调用 `Instance()` | `import` 时 |
| 启动开销 | 按需，不影响启动速度 | 拖慢启动（如连接数据库） |
| 错误处理 | 可以返回 error | 只能 panic 或 log.Fatal |
| 依赖外部资源 | ✅ 适合（文件、网络、DB） | ⚠️ 不适合（init 中不应阻塞） |
| 代码复杂度 | 稍高（once + 变量） | 最简单 |
| 测试友好性 | 可通过 Reset 重新初始化 | 难以重置 |

**选择建议**：

- 需要读取配置文件、连接数据库、调用外部服务 → **懒汉式**
- 纯内存数据结构、不可能失败的初始化 → **饿汉式**
- 不确定时 → **默认用懒汉式**（更灵活、更安全）

### 4.4 为什么要提供 ResetForTesting？

```go
func ResetForTesting() {
    once = sync.Once{}
    instance = nil
    initErr = nil
}
```

单例的天然敌人是**可测试性**。`sync.Once` 保证 f 只执行一次，但测试需要在不同条件下反复验证初始化逻辑：

- 默认配置 vs 文件配置
- 正常文件 vs 损坏文件
- 并发初始化

`ResetForTesting()` 通过重新赋值 `sync.Once{}` 来重置状态。注意：

1. 只能用于测试——生产环境中重置单例会导致数据不一致
2. 不是并发安全的——但测试通常是串行执行同一包的测试函数
3. `sync.Once` 的零值是可用的——`sync.Once{}` 就是一个未触发的 Once

这种模式在 Go 社区中被广泛使用，uber-go/zap 的 `ReplaceGlobals()` 本质上也是同一思路。

### 4.5 单例与依赖注入

单例模式最大的争议在于它引入了**隐式的全局依赖**：

```go
// 隐式依赖：调用者不知道 ProcessOrder 依赖了 configmgr
func ProcessOrder(orderID string) error {
    cfg, _ := configmgr.Instance()
    if cfg.Debug {
        log.Printf("processing order %s", orderID)
    }
    ...
}

// 显式依赖注入：依赖关系清晰可见
func ProcessOrder(cfg *Config, orderID string) error {
    if cfg.Debug {
        log.Printf("processing order %s", orderID)
    }
    ...
}
```

**Go 社区的务实共识**：

1. **进程级基础设施**用单例：配置、日志、指标收集、连接池
2. **业务逻辑**用依赖注入：服务层、Handler、用例
3. 单例作为"最顶层的依赖源"，注入到业务层

```
main()
  ├── cfg := configmgr.Instance()    ← 单例：顶层获取一次
  ├── db  := sql.Open(cfg.DSN)
  ├── svc := service.New(cfg, db)    ← 注入：业务层接收依赖
  └── http.ListenAndServe(handler)
```

这样既享受了单例的便利性（全局基础设施不用层层传递），又保持了业务逻辑的可测试性。

## 5 三种实现方式对比

| 维度 | sync.Once 懒汉式 | 包级变量饿汉式 | ❌ 双重检查锁 |
|------|-----------------|--------------|-------------|
| 并发安全 | ✅ atomic + mutex | ✅ 包初始化串行 | ❌ data race |
| 延迟初始化 | ✅ 首次调用时 | ❌ import 时 | ✅ 首次调用时 |
| 错误处理 | ✅ 返回 error | ⚠️ 只能 panic | ⚠️ 只能 panic |
| 性能 | fast path: 1 次 atomic load | 无开销 | 不安全，不讨论性能 |
| 代码量 | 约 10 行 | 约 5 行 | 约 10 行 |
| Go 惯用性 | ⭐ 推荐 | ✅ 简单场景适用 | ❌ 永远不要用 |

**结论**：Go 中实现单例只需要两种方式——`sync.Once`（通用）和包级变量（简单场景）。不要从 Java/C++ 移植 double-check locking。

## 6 适用场景与局限

### 适用

- **全局配置**：应用配置、Feature Flags、运行时参数
- **连接池**：数据库连接池、HTTP 客户端、gRPC 连接
- **日志器**：全局 logger 实例（如 zap.L()）
- **指标收集**：Prometheus Registry、OpenTelemetry Provider
- **缓存**：进程内缓存（如 sync.Map、bigcache）
- **ID 生成器**：Snowflake ID、UUID 生成器

### 局限

- **隐式依赖**：调用者看不出函数依赖了哪个单例，降低代码可读性
- **测试困难**：需要 `ResetForTesting()` 等技巧来重置状态，且无法并行测试
- **生命周期不可控**：单例与进程同生命周期，无法针对请求/会话创建独立实例
- **错误永久缓存**：`sync.Once` 一旦执行，即使失败也不会重试——如果依赖的外部服务临时不可用，进程需要重启
- **滥用风险**：容易退化为全局变量的"体面包装"，应严格限制在基础设施层

## 7 单例 vs 依赖注入决策表

| 场景 | 选择 | 理由 |
|------|------|------|
| 全局 logger | 单例 | 进程级基础设施，到处需要 |
| 数据库连接池 | 单例创建 + DI 注入 | main 中创建，注入到服务层 |
| 业务服务 (OrderService) | DI | 需要可测试性，依赖多个组件 |
| Feature Flags | 单例 | 全局只读配置 |
| 请求级别的 trace context | DI (通过 context) | 每请求不同，不是全局唯一 |
| Prometheus Registry | 单例 | 全局指标收集器 |
| 测试中的 mock 依赖 | DI | 单例无法按测试替换 |

### 经验法则

> 基础设施用单例，业务逻辑用 DI。单例是"依赖图的根节点"，DI 是"根节点往下的所有东西"。

### 测试污染与生命周期管理

单例的三大测试痛点：

1. **状态泄漏**：测试 A 修改了单例状态，影响测试 B
2. **不可并行**：`t.Parallel()` 时多个测试共享同一单例，产生竞态
3. **ResetForTesting 不是银弹**：它不是并发安全的，只能在串行测试中使用

生产级做法：

```go
// main.go — 单例创建，注入到业务层
func main() {
    cfg, _ := configmgr.Instance()
    db, _ := sql.Open("mysql", cfg.DSN)
    svc := service.New(cfg, db)     // DI：业务层不直接访问单例
    http.ListenAndServe(":8080", svc.Handler())
}

// service_test.go — 测试中直接构造，不依赖单例
func TestOrderService(t *testing.T) {
    cfg := &Config{Debug: true}      // 测试专用配置
    db := newTestDB(t)               // 测试专用数据库
    svc := service.New(cfg, db)      // 无单例依赖
    // ...
}
```

## 8 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| 唯一性 | 多次调用 Instance() 返回同一指针 |
| 并发安全 | 100 个 goroutine 同时调用 Instance() 不 panic |
| 初始化错误 | 配置文件不存在时返回 error |
| 错误缓存 | 初始化失败后再次调用仍返回相同 error |
| Reset 有效 | ResetForTesting 后可重新初始化 |
| 饿汉式唯一性 | connpool.Instance() 返回同一指针 |

## 9 成本模型

### 何时值得用单例

- 进程级基础设施：配置、日志、指标、连接池
- 初始化昂贵且只需一次
- 全局只读或极少修改

### 何时是过度设计

- 对象可以轻松创建——不需要全局共享
- 业务逻辑中使用——隐式依赖降低可测试性
- 需要请求级/会话级实例——单例的生命周期是进程级，不匹配
- 只是"不想传参数"——这是偷懒，不是设计决策
