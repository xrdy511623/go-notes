# 策略模式详解

策略模式（Strategy Pattern）是 Go 语言中最"无形"的设计模式。得益于接口和一等公民函数（first-class functions），Go 天然就在用策略模式——`sort.Slice`、`http.Transport`、`crypto.Hash` 都是活生生的例子，只是你可能没意识到而已。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it.

翻译：定义一系列算法，逐个封装，使它们可互换。策略模式让算法的变化独立于使用它的客户端。

Go 中有两种天然实现方式：

```
┌────────────────────────────────────────────────────┐
│              方式一：接口策略                         │
│        （http.RoundTripper 风格）                    │
├────────────────────────────────────────────────────┤
│                                                     │
│    Strategy (interface)                             │
│        ▲         ▲         ▲                       │
│        │         │         │                       │
│    Alipay    WechatPay  CreditCard                 │
│                                                     │
│    Context 持有 Strategy 接口，运行时替换实现          │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│              方式二：函数类型策略                      │
│        （sort.Slice(data, lessFunc) 风格）           │
├────────────────────────────────────────────────────┤
│                                                     │
│    type BackoffFunc func(attempt int) Duration      │
│                                                     │
│    Constant(d)      → BackoffFunc                  │
│    Linear(base)     → BackoffFunc                  │
│    Exponential(b,m) → BackoffFunc                  │
│    WithJitter(fn,f) → BackoffFunc  （可组合！）      │
│                                                     │
│    直接传函数，不需要定义接口和结构体                   │
└────────────────────────────────────────────────────┘
```

核心约束：

- **可互换性**：不同策略实现相同契约（接口或函数签名）
- **独立变化**：新增策略不修改任何已有代码（OCP）
- **运行时替换**：Context 可以在运行时切换策略

### 与简单工厂的区别

策略模式和简单工厂模式是最容易混淆的两个模式，因为它们都涉及"根据条件选择不同实现"。但关注点完全不同：

| 维度 | 简单工厂（Factory） | 策略（Strategy） |
|------|--------------------|--------------------|
| 关注点 | **创建**：根据参数生产不同对象 | **算法**：在运行时替换行为 |
| 决策时机 | 创建时一次性决定 | 运行时可随时切换 |
| 代码位置 | 决策逻辑在工厂函数中 | 决策逻辑在调用方（或上层） |
| 扩展方式 | 修改工厂的 switch/map | 新增一个策略实现 |
| OCP | 每次新增类型都要改工厂 ❌ | 新增策略不改已有代码 ✅ |
| Go 典型 | `NewSender(scene)` | `sort.Slice(data, lessFunc)` |

简单记忆：**工厂管"生什么"，策略管"怎么做"**。

实际中两者经常配合：工厂创建策略，Context 使用策略：

```go
// 工厂创建策略
strategy := NewBackoffFromConfig(cfg.RetryPolicy)

// 策略被使用
retry.Retry(ctx, maxAttempts, strategy, callRemoteAPI)
```

## 2 标准库与生态中的先例

### 2.1 sort.Slice — 函数类型策略的典范

Go 1.8 引入的 `sort.Slice` 是函数类型策略的教科书：

```go
// 策略 = less 函数，不同的比较逻辑就是不同的策略
sort.Slice(people, func(i, j int) bool {
    return people[i].Age < people[j].Age   // 按年龄升序
})

sort.Slice(people, func(i, j int) bool {
    return people[i].Name < people[j].Name // 按姓名字母序
})
```

不需要接口，不需要结构体——一个函数参数就是一个策略。这是 Go 社区最推崇的做法。

相比 Java 需要 `Comparator<T>` 接口 + 匿名内部类 / Lambda，Go 的函数类型天然就是策略。

### 2.2 http.Transport — 接口策略

`http.Client` 的 `Transport` 字段是 `http.RoundTripper` 接口：

```go
type RoundTripper interface {
    RoundTrip(*Request) (*Response, error)
}

client := &http.Client{
    Transport: &http.Transport{...},  // 默认策略
}

// 测试时替换为 mock
client.Transport = roundTripperFunc(func(r *http.Request) (*http.Response, error) {
    return mockResponse, nil
})
```

这正是接口策略的应用：
- `http.Transport` 是默认策略
- 测试时用 mock 策略
- 需要自定义行为（如添加 header、重试）时用包装策略

### 2.3 crypto.Hash — 标识符选策略

`crypto` 包通过常量标识不同的哈希算法策略：

```go
h := crypto.SHA256.New()  // SHA-256 策略
h.Write(data)
sum := h.Sum(nil)

h2 := crypto.SHA512.New() // SHA-512 策略
```

`crypto.Hash` 是一个 `uint`，每个值对应一个 `func() hash.Hash` 工厂函数——这是"标识符 + 注册表"的策略选择方式。

### 2.4 go-zero breaker — 函数类型策略

go-zero 的熔断器允许自定义判断策略：

```go
type Acceptable func(err error) bool

breaker.NewBreaker(
    breaker.WithName("order-api"),
    breaker.WithAcceptable(func(err error) bool {
        // 自定义哪些错误算失败
        return err == nil || isClientError(err)
    }),
)
```

`Acceptable` 就是一个函数类型策略——判断请求是否"可接受"。

### 2.5 各种 Retry 库的退避策略

几乎所有 Go retry 库都用策略模式实现退避算法：

| 库 | 策略类型 | 示例 |
|---|---------|------|
| `cenkalti/backoff` | `BackOff` 接口 | `ExponentialBackOff`、`ConstantBackOff` |
| `avast/retry-go` | `DelayTypeFunc` 函数 | `FixedDelay`、`BackOffDelay` |
| `sethvargo/go-retry` | `Backoff` 接口 | `Fibonacci`、`ExponentialBackoff` |

退避策略是纯函数、无副作用、可组合——是策略模式的最佳土壤。

## 3 本项目的实现

### 3.1 重试退避策略 — `retry/retry.go`

用纯函数类型实现退避策略，展示 Go 中"函数即策略"的优雅：

```go
type BackoffFunc func(attempt int) time.Duration
```

内置四种策略：

| 工厂函数 | 算法 | 说明 |
|---------|------|------|
| `Constant(d)` | `delay = d` | 固定等待 |
| `Linear(base)` | `delay = base × attempt` | 线性增长 |
| `Exponential(base, max)` | `delay = base × 2^attempt`，上限 max | 指数退避 |
| `WithJitter(fn, factor)` | 在原策略上叠加随机抖动 | 策略装饰器！可与任意策略组合 |

`WithJitter` 特别值得注意——它接收一个 `BackoffFunc`，返回一个新的 `BackoffFunc`：

```go
// 策略组合：指数退避 + 随机抖动
backoff := WithJitter(Exponential(100*time.Millisecond, 30*time.Second), 0.3)
```

这实际上是**装饰器 + 策略**的组合——装饰器增强策略，策略替换算法。

使用方式：

```go
err := Retry(ctx, 5, Exponential(100*time.Millisecond, 30*time.Second), func() error {
    return callRemoteAPI()
})
```

### 3.2 支付策略 — `payment/payment.go`

用接口 + 函数类型适配器的双重方式实现，展示两种策略的互通：

**接口定义**：

```go
type Strategy interface {
    Pay(amount float64) (transactionID string, err error)
}
```

**函数类型适配器**（与 `http.HandlerFunc` → `http.Handler` 同一模式）：

```go
type StrategyFunc func(amount float64) (string, error)

func (f StrategyFunc) Pay(amount float64) (string, error) {
    return f(amount)
}
```

**运行时切换**：

```go
co := NewCheckout(&Alipay{MerchantID: "M001"})
co.Pay(99.99)  // → "ALIPAY-M001-99.99"

co.SetStrategy(&WechatPay{AppID: "wx123"})
co.Pay(99.99)  // → "WECHAT-wx123-99.99"

// 甚至可以用匿名函数作为策略（测试时很方便）
co.SetStrategy(StrategyFunc(func(amount float64) (string, error) {
    return "MOCK-OK", nil
}))
```

核心 API：

| 函数 | 作用 | 说明 |
|------|------|------|
| `NewCheckout(s)` | 创建结账上下文 | 注入支付策略 |
| `SetStrategy(s)` | 运行时切换策略 | 不修改 Checkout 代码 |
| `Pay(amount)` | 委托给当前策略 | 调用方无感知具体实现 |
| `StrategyFunc(fn)` | 函数→接口适配器 | 测试、临时策略的便捷写法 |

### 3.3 反面示例：switch 代替策略 — `trap/switchinside/`

最常见的反模式——在方法内部用 switch 分支实现"策略选择"：

```go
// ❌ 每新增一种支付方式，都要修改这个方法
func (c *Checkout) Pay(amount float64) (string, error) {
    switch c.Method {
    case "alipay":
        // ...
    case "wechat":
        // ...
    case "creditcard":
        // ...
    // 每次新增一个 case...
    default:
        return "", fmt.Errorf("unknown: %s", c.Method)
    }
}
```

问题一目了然：

1. **OCP 违反**：新增支付方式必须修改已有代码
2. **不可独立测试**：无法单独测试某一种支付逻辑
3. **无法依赖注入**：测试时无法 mock 特定支付方式
4. **臃肿膨胀**：随着支付方式增多，方法体越来越长

策略模式的解法：把每个 case 提取为独立的 `Strategy` 实现，通过注入替换。

### 3.4 调用方

```go
import (
    "go-notes/designpattern/strategy/payment"
    "go-notes/designpattern/strategy/retry"
)

func main() {
    // 支付策略：接口方式 — 运行时切换
    co := payment.NewCheckout(&payment.Alipay{MerchantID: "M001"})
    co.Pay(99.99)

    co.SetStrategy(&payment.WechatPay{AppID: "wx456"})
    co.Pay(99.99)

    // 退避策略：函数类型方式 — 传函数即传策略
    err := retry.Retry(ctx, 5,
        retry.WithJitter(retry.Exponential(100*time.Millisecond, 30*time.Second), 0.3),
        callRemoteAPI,
    )
}
```

## 4 设计决策解析

### 4.1 接口策略 vs 函数策略 — 何时用哪个？

| 维度 | 接口策略 | 函数策略 |
|------|---------|---------|
| 方法数 | 多个方法时首选 | 单方法时首选 |
| 状态 | 可以持有状态（配置、连接等） | 通过闭包捕获状态 |
| Mock | 用 mock 框架生成 | 直接传匿名函数 |
| 可读性 | 类型名自解释（`*Alipay`） | 需要注释或变量名说明意图 |
| 标准库范例 | `http.RoundTripper`、`hash.Hash` | `sort.Slice` 的 `less`、`http.HandlerFunc` |

经验法则：

- **一个方法** → 优先函数类型（如 `BackoffFunc`）
- **两个以上方法** → 用接口
- **需要配置/状态** → 接口 + 结构体
- **测试临时策略** → 函数类型适配器（如 `StrategyFunc`）

### 4.2 函数类型适配器 — Go 的杀手锏

Go 允许为函数类型定义方法，这让函数类型和接口可以无缝互通：

```go
// 标准库的经典模式
type Handler interface { ServeHTTP(ResponseWriter, *Request) }

type HandlerFunc func(ResponseWriter, *Request)
func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) { f(w, r) }
```

本项目的 `StrategyFunc` 遵循完全相同的模式。这是 Go 独有的优势——Java/C# 没有这种为函数类型添加方法的能力。

### 4.3 策略模式的可组合性

策略模式的一个被低估的威力是**策略可以装饰策略**：

```go
// 基础策略
base := Exponential(100*time.Millisecond, 30*time.Second)

// 装饰策略：添加抖动
jittered := WithJitter(base, 0.3)

// 还可以继续组合...
```

这与装饰器模式的组合思想一脉相承。不同的是：

- **装饰器**：`io.Reader` → `io.Reader`（增强同一接口的不同维度）
- **策略组合**：`BackoffFunc` → `BackoffFunc`（在同一维度上叠加修改）

### 4.4 策略选择的三种方式

在实际项目中，策略的选择通常有三种方式：

```go
// 1. 调用方直接注入（最常见）
co := NewCheckout(&Alipay{MerchantID: "M001"})

// 2. 配置驱动 + 工厂创建（策略 + 工厂配合）
strategy := NewStrategyFromConfig(cfg.PaymentMethod)
co := NewCheckout(strategy)

// 3. 注册表 + 标识符（crypto.Hash 模式）
crypto.SHA256.New()
```

方式 2 是策略模式和工厂模式的经典组合——工厂负责"根据配置创建哪个策略"，策略负责"如何执行算法"。

### 4.5 为什么 Go 的策略模式比 Java 更自然？

Java 的策略模式需要定义接口 + 实现类 + Context 类：

```java
// Java: 接口 + 实现类 + Lambda（Java 8+）
interface PaymentStrategy {
    String pay(double amount);
}
class AlipayStrategy implements PaymentStrategy { ... }
class WechatStrategy implements PaymentStrategy { ... }
```

Go 的做法更轻量：

1. **函数类型天然是策略**：不需要接口，不需要类，`func(int) Duration` 就是策略
2. **隐式接口**：不用写 `implements`，实现了方法就满足接口
3. **函数类型可定义方法**：`HandlerFunc` / `StrategyFunc` 模式让函数与接口无缝互通
4. **闭包捕获状态**：不需要为简单策略定义结构体

Go Proverbs 的体现：

> Accept interfaces, return structs.

策略接受者（Context）持有接口，策略提供者返回具体类型——这正是策略模式在 Go 中的天然形态。

## 5 适用场景与局限

### 适用

- **排序算法**：`sort.Slice` + 不同比较函数
- **重试/退避**：固定、线性、指数、抖动——纯函数策略
- **支付/通知渠道**：不同渠道不同处理逻辑
- **序列化格式**：JSON、Protobuf、MessagePack——编解码策略
- **认证方式**：JWT、OAuth、BasicAuth——`http.RoundTripper` 包装
- **缓存淘汰**：LRU、LFU、FIFO——不同淘汰算法
- **限流算法**：令牌桶、滑动窗口、漏桶——`Limiter` 接口
- **熔断判断**：go-zero `breaker.Acceptable` 函数策略

### 局限

- **策略过多**：如果策略数量爆炸式增长（50+），需要配合注册表或工厂管理
- **策略间依赖**：如果不同策略共享大量状态，可能说明拆分粒度有问题
- **过度设计**：只有 2-3 个固定分支且未来不会扩展时，switch 可能更简单直接
- **运行时开销**：接口调用通过虚方法表，比直接调用多一次间接寻址（但在 99.9% 场景中可忽略）

## 6 运行时换策略的并发安全

`Checkout.SetStrategy` 在运行时替换策略，如果多个 goroutine 同时调用会产生 data race：

```go
// ❌ 不安全
go co.SetStrategy(&Alipay{})
go co.Pay(99.99) // 可能读到 half-written 的 strategy 指针
```

解法：

| 方案 | 适用场景 | 开销 |
|------|---------|------|
| `sync.RWMutex` | 读多写少（Pay 多，SetStrategy 少） | 读路径加读锁 |
| `atomic.Value` | 策略对象不可变（替换而非修改） | 无锁 |
| 不允许运行时切换 | 构造时注入后不变 | 零开销 |

大多数生产代码选择**构造时注入后不变**——策略在 `New` 时确定，不提供 `SetStrategy`。需要切换时创建新实例。

### 反例：只有两个分支却强行上策略

```go
// ❌ 过度设计
type Logger interface { Log(msg string) }
type StdoutLogger struct{}
type FileLogger struct{}

// 只有两个实现，且不会增长
// 直接 if/else 更清晰：
if config.LogToFile {
    log.SetOutput(file)
} else {
    log.SetOutput(os.Stdout)
}
```

策略模式的价值在于**开放扩展**。如果实现是封闭的且数量极少（2-3 个），switch/if 更直接。

## 7 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| 每种策略正确 | Alipay/WechatPay/CreditCard 各自返回正确的 transactionID |
| 运行时切换 | SetStrategy 后 Pay 使用新策略 |
| StrategyFunc 适配 | 匿名函数通过 StrategyFunc 适配后正常工作 |
| nil 策略防御 | 未设置策略时 Pay 返回 error 而非 panic |
| 退避策略正确性 | Constant/Linear/Exponential 的延迟计算正确 |
| WithJitter 范围 | 抖动后的值在 `[delay*(1-factor), delay*(1+factor)]` 范围内 |
| Retry 成功 | 前几次失败后成功时 Retry 返回 nil |
| Retry 耗尽 | 全部重试失败后返回最后一个 error |
| Context 取消 | ctx 取消后 Retry 立即返回 |

## 8 成本模型

### 何时值得用策略模式

- 算法有 3+ 种变体，且未来可能继续增长
- 需要运行时切换或配置驱动选择
- 算法之间可以组合（如 WithJitter 装饰退避策略）

### 何时是过度设计

- 只有 2 个固定分支——if/else 更清晰
- 算法不会变化——硬编码比抽象更简单
- 为了"以后可能扩展"而提前抽象——YAGNI 原则
