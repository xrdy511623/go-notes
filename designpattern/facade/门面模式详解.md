# 门面模式详解

门面模式（Facade Pattern）是最常用的结构型设计模式之一。它为一组复杂的子系统提供一个**统一的高层接口**，让调用方无需了解子系统的内部细节和调用顺序。Go 语言中没有继承层次的负担，门面模式的实现天然简洁——一个 struct 持有子系统引用，一组方法做编排即可。

---

## 1 模式定义

GoF《设计模式》中的定义：

> Provide a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use.

翻译：为子系统中的一组接口提供一个统一的接口。门面定义了一个更高层的接口，使得子系统更加容易使用。

模式由三个角色组成：

```
                    ┌─────────────────────┐
                    │       Client        │
                    └──────────┬──────────┘
                               │
                       PlaceOrder / CancelOrder
                               │
                    ┌──────────▼──────────┐
                    │       Facade        │
                    │  (orderfacade.Facade)│
                    └──┬───────┬───────┬──┘
                       │       │       │
              ┌────────▼──┐ ┌──▼─────┐ ┌▼──────────┐
              │  Payment  │ │Inventory│ │ Notifier  │
              │  Service  │ │ Service │ │  Service  │
              └───────────┘ └────────┘ └───────────┘
```

- **Facade（门面）**：持有子系统引用，对外暴露简化的高层方法
- **Subsystem（子系统）**：独立的业务模块，各自完成具体工作
- **Client（客户端）**：只与 Facade 交互，不直接调用子系统

## 2 标准库与生态中的先例

门面模式的思想在 Go 标准库和生态中随处可见：

| 场景 | 门面 | 被封装的子系统 | 说明 |
|------|------|---------------|------|
| `net/http` | `ListenAndServe` | `net.Listener` + `Server` + `Handler` | 一行代码启动 HTTP 服务，内部创建 listener、构建 server、绑定 handler |
| `database/sql` | `sql.DB` | driver + 连接池 + stmt cache | 调用方只用 `db.Query`，无需管理连接获取、归还、预编译语句缓存 |
| `os/exec` | `exec.Cmd` | `os.Process` + pipe + env | `cmd.Run()` 封装了进程创建、stdin/stdout pipe 绑定、环境变量传递 |
| `net/http/httptest` | `httptest.NewServer` | `net.Listener` + `http.Server` + TLS config | 一行创建测试服务器，内部处理随机端口、证书生成等细节 |
| K8s client-go | `kubernetes.Clientset` | CoreV1Client + AppsV1Client + ... | `Clientset` 聚合了几十个 API group 的客户端，调用方无需逐个初始化 |

以 `net/http.ListenAndServe` 为例：

```go
func ListenAndServe(addr string, handler Handler) error {
    server := &Server{Addr: addr, Handler: handler}
    return server.ListenAndServe()
}
```

调用方只传地址和 handler，底层的 TCP listener 创建、连接管理、graceful shutdown 信号处理全部被 `Server` 内部消化。这正是门面模式的典型应用。

## 3 本项目的实现

### 3.1 子系统

本项目模拟一个电商下单场景，拆分为三个独立子系统：

| 子系统 | 包 | 职责 |
|--------|------|------|
| `payment.Service` | `payment/` | 订单扣款和退款 |
| `inventory.Service` | `inventory/` | 库存预留和释放 |
| `notifier.Service` | `notifier/` | 发送通知消息（邮件等） |

每个子系统是独立的包，有自己的 struct 和构造函数，可以独立测试和复用。

### 3.2 门面 — `orderfacade/orderfacade.go`

```go
type Facade struct {
    payment   *payment.Service
    inventory *inventory.Service
    notifier  *notifier.Service
}

func New(p *payment.Service, i *inventory.Service, n *notifier.Service) *Facade
```

Facade 通过构造函数接收三个子系统的实例，不自行创建——这使得测试时可以注入特定状态的子系统。

### 3.3 PlaceOrder 流程与回滚

```
PlaceOrder(req)
    │
    ├─ 1. inventory.Reserve ──── 失败 → 直接返回 error
    │
    ├─ 2. payment.Charge ─────── 失败 → inventory.Release → 返回 error
    │
    ├─ 3. notifier.Send ──────── 失败 → payment.Refund
    │                                    → inventory.Release → 返回 error
    │
    └─ 成功 → 返回 PlaceOrderResult
```

回滚遵循**后进先出**原则：最后完成的操作最先撤销。这是 Facade 的核心价值——调用方不需要知道这些回滚细节。

### 3.4 CancelOrder 流程

```
CancelOrder(orderID)
    │
    ├─ 1. payment.Refund ────── 失败 → 返回 error（订单不存在）
    │
    ├─ 2. inventory.Release ─── 失败 → 返回 error
    │
    └─ 3. notifier.Send ────── 失败 → 返回 error
```

### 3.5 调用方视角

```go
import (
    "go-notes/designpattern/facade/orderfacade"
    "go-notes/designpattern/facade/payment"
    "go-notes/designpattern/facade/inventory"
    "go-notes/designpattern/facade/notifier"
)

func main() {
    p := payment.New()
    i := inventory.New(map[string]int{"sku-001": 100})
    n := notifier.New()

    facade := orderfacade.New(p, i, n)

    result, err := facade.PlaceOrder(orderfacade.PlaceOrderRequest{
        OrderID:       "order-123",
        ItemID:        "sku-001",
        CustomerEmail: "user@example.com",
        Qty:           2,
        Amount:        199.90,
    })
    // 调用方只需处理一个 error，无需关心三个子系统的协调和回滚
}
```

## 4 设计决策解析

### 4.1 为什么接收具体类型而不是 interface？

```go
func New(p *payment.Service, i *inventory.Service, n *notifier.Service) *Facade
```

门面模式中，Facade **拥有**其子系统。与策略模式、观察者模式不同，门面的子系统不是可替换的——它们是固定的业务模块，且 Facade 了解每个子系统的具体能力（如 `Refund` 的返回值）。

使用 interface 意味着引入一层不必要的抽象：
- 子系统不会有多种实现
- Facade 的测试通过注入特定状态的真实子系统即可完成
- 遵循 Go 的惯例：**Accept interfaces, return structs** — 但这是对调用方而言，Facade 本身是子系统的使用者

### 4.2 为什么 PlaceOrder 做回滚？

回滚逻辑是 Facade 存在的核心理由。如果调用方自己编排三个子系统：

```go
// 没有 Facade 时，调用方需要自己处理回滚
err := inventory.Reserve(orderID, itemID, qty)
if err != nil { return err }

err = payment.Charge(orderID, amount)
if err != nil {
    inventory.Release(orderID)   // 别忘了！
    return err
}

err = notifier.Send(msg)
if err != nil {
    payment.Refund(orderID)      // 别忘了！
    inventory.Release(orderID)   // 别忘了！
    return err
}
```

每个调用方都要重复这段回滚逻辑，且遗漏任何一步都会导致数据不一致。Facade 把这个知识集中到一处。

### 4.3 为什么返回 struct 而不是 (string, float64, error)？

```go
type PlaceOrderResult struct {
    OrderID       string
    ChargedAmount float64
}
```

- **可读性**：`result.ChargedAmount` 比匿名的 `float64` 返回值清晰
- **可扩展性**：未来增加 `ReservedAt time.Time` 不需要修改函数签名
- **文档性**：struct 字段名本身就是文档

### 4.4 错误使用 %w 包装

```go
return fmt.Errorf("orderfacade: reserve inventory: %w", err)
```

使用 `%w` 而非 `%v`，让调用方可以通过 `errors.Is` / `errors.As` 检查底层错误。门面不应该吞掉子系统的错误信息。

## 5 与相近模式的对比

| 维度 | Facade（门面） | Adapter（适配器） | Mediator（中介者） | API Gateway |
|------|---------------|-------------------|-------------------|-------------|
| **意图** | 简化子系统的使用 | 转换不兼容的接口 | 解耦多个对等对象 | 统一多个微服务入口 |
| **耦合方向** | Client → Facade → Subsystems | Client → Adapter → Adaptee | Colleague ↔ Mediator | Client → Gateway → Services |
| **子系统数量** | 通常 2+ | 通常 1 | 通常 2+ 对等对象 | 通常多个微服务 |
| **子系统是否知道门面** | 不知道 | 不知道 | 知道中介者 | 不知道 |
| **Go 示例** | `database/sql.DB` | `io.ReadCloser` 适配 | `sync.Cond` | K8s API Server |

### 快速决策

```
需要简化一组子系统的调用？     → Facade
需要让旧接口兼容新接口？       → Adapter
多个对象需要相互通信但不想直接耦合？ → Mediator
微服务架构需要统一入口？        → API Gateway
```

Facade 和 Mediator 的关键区别：Facade 是**单向**的（Client → Subsystems），子系统不知道 Facade 的存在；Mediator 是**双向**的（Colleagues ↔ Mediator），参与者需要持有中介者的引用。

## 6 常见陷阱 / 反例

### 6.1 上帝门面（God Facade）

参见 `trap/godfacade/godfacade.go`。

```go
// ❌ 反模式：门面内联了所有子系统的逻辑
type GodFacade struct {
    charged  map[string]float64      // 本应在 payment.Service
    stock    map[string]int           // 本应在 inventory.Service
    reserved map[string]map[string]int
    emails   []string                 // 本应在 notifier.Service
}
```

问题：
- 违反 SRP：门面应该只做编排，不实现业务逻辑
- 无法独立测试子系统
- 任何子系统的改动都要修改门面代码
- 随着业务增长，门面会迅速膨胀成不可维护的巨型 struct

**判断标准**：如果你的 Facade struct 里有不属于"协调"的字段（如 `stock`, `charged`），它就在变成 God Facade。

### 6.2 门面作为唯一入口

```go
// ❌ 反模式：强制所有调用都经过门面
// 子系统被设为 internal 或 unexported，只能通过门面访问

// ✅ 正确做法：门面是可选的快捷方式
// 需要细粒度控制的调用方可以直接使用子系统
facade.PlaceOrder(req)              // 普通场景：用门面
inventory.Reserve(orderID, item, 1) // 高级场景：直接用子系统
```

门面的价值在于简化，而不是限制。子系统应该保持 exported，让高级用户有绕过门面的自由。

### 6.3 业务逻辑泄漏到门面

```go
// ❌ 反模式：门面里做业务判断
func (f *Facade) PlaceOrder(req Request) error {
    if req.Amount > 10000 {
        // 大额订单需要人工审核——这是业务规则，不属于门面
        return errors.New("amount exceeds limit, manual review required")
    }
    ...
}

// ✅ 正确做法：业务规则由子系统或独立的规则引擎处理
// 门面只负责按顺序调用子系统
```

### 6.4 门面吞掉错误

```go
// ❌ 反模式：门面返回自己的错误，丢弃子系统的原始错误
if err := f.payment.Charge(orderID, amount); err != nil {
    return fmt.Errorf("payment failed")  // 原始错误丢失
}

// ✅ 正确做法：用 %w 包装，保留错误链
if err := f.payment.Charge(orderID, amount); err != nil {
    return fmt.Errorf("orderfacade: charge payment: %w", err)
}
```

## 7 测试要点

| 测试场景 | 验证内容 | 对应测试函数 |
|---------|---------|-------------|
| 正常下单 | 库存扣减、扣款成功、通知发送 | `TestPlaceOrder_Success` |
| 库存不足 | 返回错误，不扣款、不通知 | `TestPlaceOrder_InsufficientStock` |
| 支付失败 | 返回错误，库存已回滚、不通知 | `TestPlaceOrder_PaymentFails` |
| 通知失败 | 返回错误，支付已退款、库存已释放 | `TestPlaceOrder_NotificationFails` |
| 重复扣款 | 同一订单 ID 第二次下单失败 | `TestPlaceOrder_DuplicateCharge` |
| 正常取消 | 退款成功、库存释放、发送取消通知 | `TestCancelOrder_Success` |
| 取消不存在的订单 | 退款失败返回错误 | `TestCancelOrder_NotFound` |
| 下单后取消，库存恢复 | 取消后可以重新下单相同数量 | `TestPlaceAndCancel_StockRestored` |

测试策略：注入真实的子系统实例（而非 mock），通过子系统的查询方法（如 `notifier.Sent()`）验证门面的编排是否正确。这样既测试了门面的协调逻辑，也间接验证了子系统的基本功能。

## 8 成本模型

### 何时值得使用门面

- **3 个以上子系统**需要按特定顺序协调完成一个业务流程
- **存在回滚/补偿逻辑**——如果调用方自己做编排很容易遗漏回滚步骤
- **多个调用方**需要相同的编排逻辑——集中到门面避免重复
- **调用方不关心子系统细节**——只想"下单"而不是分别处理库存、支付、通知

### 何时是过度设计

- **只有 2 个协作者**且调用顺序固定 — 直接写在一起更清晰
- **调用方需要细粒度控制** — 门面反而成了障碍
- **子系统之间没有协调需求** — 只是聚合字段不算门面
- **业务规则在变化** — 如果编排逻辑频繁变化，考虑用工作流引擎或 saga 而非硬编码的门面

### 复杂度对比

| 场景 | 无门面 | 有门面 |
|------|--------|--------|
| 调用方代码量 | O(n × m)，n 个调用方各写 m 步编排 | O(n)，n 个调用方各一行调用 |
| 回滚正确性 | 每个调用方独立维护，容易出错 | 集中维护，一处修正全局生效 |
| 新增子系统 | 修改所有调用方 | 只修改 Facade |
| 调试复杂度 | 直接调用链，易于追踪 | 多一层间接调用 |

## 9 适用场景与局限

### 适用场景

- **订单处理**：库存 + 支付 + 物流 + 通知（本项目的例子）
- **支付网关**：风控 + 扣款 + 记账 + 回调
- **用户注册**：创建账号 + 初始化配置 + 发送欢迎邮件 + 埋点
- **部署流水线**：构建 + 测试 + 发布 + 通知（CI/CD orchestrator）
- **报表生成**：查询多个数据源 + 聚合 + 格式化 + 导出

### 局限

- **增加间接层**：调试时需要穿透门面才能看到子系统的行为
- **可能退化为上帝对象**：如果不严格控制门面的职责边界
- **不适合需要灵活编排的场景**：如果不同调用方需要不同的编排顺序，一个门面无法满足
- **事务一致性有限**：本项目的回滚是"尽力而为"，不提供分布式事务保证；生产环境可能需要 saga 或 TCC
