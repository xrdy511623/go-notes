# 扇出扇入模式详解

扇出扇入模式（Fan-Out / Fan-In）是 Go 并发编程中最实用的模式之一。它将一批工作**分散（Fan-Out）**给多个并发 worker 处理，再将结果**汇聚（Fan-In）**到一起。几乎所有需要"并行处理一批数据"的场景——批量 HTTP 请求、并发数据库查询、并行文件处理——都是这个模式的变体。

---

## 1 模式定义

Fan-Out / Fan-In 的本质是**分治**：

```
                         Fan-Out                          Fan-In
                    ┌─→ worker 0 ──→ result[0] ─┐
                    │                             │
inputs[] ──────────┼─→ worker 1 ──→ result[1] ─┼──→ results[]
                    │                             │
                    ├─→ worker 2 ──→ result[2] ─┤
                    │         ...                 │
                    └─→ worker N ──→ result[N] ─┘

                    有界并发：最多 M 个 worker
                    同时运行（M ≤ N）
```

三个关键要素：

- **Fan-Out（扇出）**：将 N 个输入分配给 M 个并发 worker（M ≤ N）
- **Fan-In（扇入）**：收集所有 worker 的结果，汇聚为最终输出
- **有界并发**：限制同时运行的 goroutine 数量，防止资源耗尽

## 2 标准库与生态中的先例

| 场景 | 机制 | 说明 |
|------|------|------|
| `golang.org/x/sync/errgroup` | `g.Go()` + `g.SetLimit()` | **最佳实践**：有界并发 + 错误传播 + context 取消 |
| `context.Context` | 超时 / 取消 | 管道生命周期的控制平面 |
| `net/http.Transport` | `MaxIdleConnsPerHost` | HTTP 客户端的连接级扇出限制 |
| `runtime.GOMAXPROCS` | CPU 并行度 | goroutine 调度器的物理并行上限 |
| go-zero `mr.MapReduce` | MapReduce 封装 | 生产级并行 Map + 顺序 Reduce |
| sourcegraph/conc `pool.New()` | 类型安全的 goroutine 池 | `Pool[T].Go()` + `Pool[T].Wait()` |
| `database/sql` | 连接池 | `SetMaxOpenConns` 限制并发查询数 |

`errgroup` 是 Go 社区公认的扇出最佳实践：

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(10)                        // 最多 10 个并发

for _, url := range urls {
    g.Go(func() error {
        return fetch(ctx, url)        // 任一失败 → ctx 取消 → 其余退出
    })
}

err := g.Wait()                       // 等待全部完成，返回第一个 error
```

相比手动管理 `sync.WaitGroup` + channel + semaphore，`errgroup` 一行 `SetLimit` 解决了有界并发、错误传播、context 取消三大问题。

## 3 本项目的实现

本项目提供三种扇出扇入变体，覆盖不同的生产场景：

| 变体 | 包 | 一句话 |
|------|------|------|
| Scatter / ForEach | `parallel/` | 有界并发映射：N 个输入 → M 个 worker → N 个输出（保序） |
| MapReduce | `mapreduce/` | 并行 Map + 顺序 Reduce → 单个聚合值 |
| Race (First) | `race/` | 多源竞速：最快的成功响应获胜，其余取消 |

### 3.1 Scatter — 有界并发映射

```go
func Scatter[In, Out any](
    ctx context.Context,
    inputs []In,
    concurrency int,
    fn func(context.Context, In) (Out, error),
) ([]Out, error)
```

核心语义：
- `inputs[i]` 的结果一定写入 `results[i]`（**保序**）
- 最多 `concurrency` 个 goroutine 同时运行
- 任一 fn 返回 error → errgroup 取消 ctx → 剩余工作停止

```go
results, err := parallel.Scatter(ctx, urls, 10,
    func(ctx context.Context, url string) (Response, error) {
        return httpGet(ctx, url)
    },
)
```

`ForEach` 是 Scatter 的简化版——只关心成功/失败，不收集返回值：

```go
err := parallel.ForEach(ctx, records, 8,
    func(ctx context.Context, r Record) error {
        return db.Insert(ctx, r)
    },
)
```

### 3.2 MapReduce — 并行映射 + 顺序归约

```go
func MapReduce[In, Mid, Out any](
    ctx context.Context,
    inputs []In,
    concurrency int,
    mapFn func(context.Context, In) (Mid, error),
    reduceFn func(Out, Mid) Out,
    initial Out,
) (Out, error)
```

两阶段执行：

```
Phase 1: Map（并行）
  inputs[0] ──→ mapFn ──→ mapped[0]
  inputs[1] ──→ mapFn ──→ mapped[1]     （最多 M 个并发）
  inputs[2] ──→ mapFn ──→ mapped[2]

Phase 2: Reduce（顺序）
  initial ──→ reduceFn(acc, mapped[0])
          ──→ reduceFn(acc, mapped[1])    （按输入顺序）
          ──→ reduceFn(acc, mapped[2])
          ──→ result
```

Reduce 阶段在所有 Map 完成后按**输入顺序**执行，确保结果确定性。

```go
total, err := mapreduce.MapReduce(ctx, urls, 8,
    func(ctx context.Context, url string) (int, error) {
        return fetchWordCount(ctx, url)
    },
    func(acc, count int) int { return acc + count },
    0,
)
```

### 3.3 Race (First) — 最快响应获胜

```go
func First[T any](
    ctx context.Context,
    fns ...func(context.Context) (T, error),
) (T, error)
```

并发执行所有 fn，第一个成功的结果立即返回，通过 `context.WithCancel` 通知其余 goroutine 退出：

```
fn-0 (100ms) ─────────────→ "slow"     ← 被取消
fn-1  (10ms) ──→ "fast" ✓               ← 获胜，立即返回
fn-2  (50ms) ──────→ "medium"           ← 被取消
```

这就是 Google *"The Tail at Scale"* 论文中的 **Hedged Request** 模式：向多个副本同时发送请求，用最快的响应，取消其余。牺牲少量冗余工作换取大幅降低尾延迟。

```go
result, err := race.First(ctx,
    func(ctx context.Context) (string, error) { return fetchFrom(ctx, "mirror-A") },
    func(ctx context.Context) (string, error) { return fetchFrom(ctx, "mirror-B") },
    func(ctx context.Context) (string, error) { return fetchFrom(ctx, "mirror-C") },
)
```

### 3.4 调用方

```go
import (
    "go-notes/designpattern/fanoutin/parallel"
    "go-notes/designpattern/fanoutin/mapreduce"
    "go-notes/designpattern/fanoutin/race"
)
```

调用方只需选择合适的变体：
- 需要每个输入的处理结果 → `parallel.Scatter`
- 只需 side effect（写入、通知） → `parallel.ForEach`
- 需要聚合（求和、拼接、统计） → `mapreduce.MapReduce`
- 需要最快响应 → `race.First`

## 4 设计决策解析

### 4.1 为什么用 errgroup.SetLimit 而非手动信号量？

有界并发有三种常见实现：

```go
// 方式一：channel 信号量（手动）
sem := make(chan struct{}, limit)
for _, item := range items {
    sem <- struct{}{}
    go func() {
        defer func() { <-sem }()
        process(item)
    }()
}

// 方式二：worker pool（手动）
work := make(chan T, limit)
for range limit {
    go func() { for item := range work { process(item) } }()
}
for _, item := range items { work <- item }

// 方式三：errgroup.SetLimit（推荐）
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(limit)
for _, item := range items {
    g.Go(func() error { return process(ctx, item) })
}
return g.Wait()
```

| 维度 | channel 信号量 | worker pool | **errgroup.SetLimit** |
|------|--------------|-------------|---------------------|
| 错误传播 | 需手动加 chan error | 需手动加 chan error | **内置** |
| context 取消 | 需手动检查 | 需手动检查 | **内置（WithContext）** |
| 等待完成 | 需 WaitGroup | 需关闭 channel + WaitGroup | **内置（Wait）** |
| 代码行数 | ~15 行 | ~20 行 | **~5 行** |
| 并发限制 | ✓ | ✓ | **✓** |

`errgroup.SetLimit` 是三合一方案——有界并发、错误传播、context 取消，一步到位。

### 4.2 为什么 Scatter 保证结果有序？

```go
results := make([]Out, len(inputs))
for i, input := range inputs {
    g.Go(func() error {
        results[i] = fn(ctx, input)    // 每个 goroutine 写唯一的 i
        return nil
    })
}
g.Wait()    // happens-before edge: Wait 返回时所有写入已完成
```

关键点：
- 每个 goroutine 写入 `results[i]`，i 各不相同 → 没有数据竞争
- `g.Wait()` 提供了 happens-before 保证：Wait 返回后，所有 `results[i]` 对调用方可见
- 无需 mutex，无需 channel，无需额外排序

这比"先收集到 map/channel 再排序"的方案更简洁、更高效。

### 4.3 为什么 Race.First 用缓冲 channel？

```go
ch := make(chan result, len(fns))    // 缓冲 = fn 数量
```

如果用无缓冲 channel：

1. First 返回后，`defer cancel()` 取消 context
2. 其余 goroutine 可能已经执行完 fn，尝试发送到 ch
3. 无缓冲 channel 没有接收方 → goroutine 永远阻塞 → **泄漏**

缓冲 channel 保证每个 goroutine 都能发送（即使没有接收方），然后正常退出。channel 会在没有引用后被 GC 回收。

### 4.4 为什么 fn 统一接受 context.Context 参数？

```go
fn func(context.Context, In) (Out, error)
```

context 是管道生命周期的**控制平面**：

- **超时**：`context.WithTimeout` → fn 内通过 `ctx.Done()` 感知
- **取消**：某个 fn 出错 → errgroup 取消 ctx → 其余 fn 立即观测到
- **外部中断**：调用方取消父 ctx → 所有 fn 收到信号

如果 fn 不接受 context：
- 无法响应取消 → goroutine 继续运行直到自然结束
- 超时场景退化为"等最慢的那个"
- 生产环境中这是资源泄漏和级联超时的根源

### 4.5 ForEach vs Scatter — 什么时候用哪个？

```go
// Scatter: 需要返回值
results, err := parallel.Scatter(ctx, urls, 10, fetchPage)

// ForEach: 只需 side effect
err := parallel.ForEach(ctx, events, 10, publishToKafka)
```

| 场景 | 选择 | 原因 |
|------|------|------|
| HTTP 批量请求 + 收集响应 | Scatter | 需要每个 URL 的 Response |
| 批量写数据库 | ForEach | 只关心全部成功/第一个失败 |
| 并发发送通知 | ForEach | 不需要返回值 |
| 并行计算 + 汇总 | MapReduce | 需要聚合为单一值 |
| 多副本取最快 | First | 只需第一个成功的 |

## 5 与管道模式的关系

管道模式和扇出扇入模式是 Go 并发的两大支柱，经常配合使用：

```
┌──────────────────── Pipeline ────────────────────────┐
│                                                       │
│  Source ──→ Filter ──→ ┌─→ Worker 0 ─┐ ──→ Sink      │
│                        ├─→ Worker 1 ─┤               │
│                        └─→ Worker 2 ─┘               │
│                        └── Fan-Out ──┘               │
│                                                       │
└───────────────────────────────────────────────────────┘
```

| 维度 | 管道模式 (`pipeline/`) | 扇出扇入 (`fanoutin/`) |
|------|----------------------|----------------------|
| 数据流 | **线性**：A → B → C → D | **分散-汇聚**：1 → N → 1 |
| 核心原语 | channel 连接各阶段 | errgroup 协调各 worker |
| 适用场景 | 多步骤流式处理 | 批量并行同一操作 |
| 生命周期 | channel close 级联 | errgroup.Wait 统一等待 |
| 背压 | 无缓冲 channel 天然背压 | SetLimit 控制并发上限 |
| API 风格 | `Generate → Filter → Map → Collect` | `Scatter(inputs, fn)` |

实际项目中常组合使用：Pipeline 的某个阶段内部使用 FanOut 并行处理。

## 6 go-zero MapReduce 与本项目对比

go-zero 的 `mr.MapReduce` 是生产级实现，功能更丰富：

| 维度 | 本项目 `mapreduce/` | go-zero `mr.MapReduce` |
|------|-------------------|-----------------------|
| Map 阶段 | 写入 `[]Mid`，Wait 后 Reduce | 通过 channel 流式传递给 Reduce |
| Reduce 阶段 | 批量顺序 Reduce | 流式 Reduce（内存更省） |
| 错误处理 | errgroup 取消 | 独立 error channel |
| 并发控制 | `errgroup.SetLimit` | `WithWorkers(n)` |
| 泛型 | Go 1.18 泛型 | `interface{}` + 类型断言 |
| 依赖 | `x/sync/errgroup` | 零依赖 |

本项目选择"批量 Map → 顺序 Reduce"的两阶段模型，因为：
- 实现更简单，适合教学
- Reduce 在 Map 全部完成后按输入顺序执行 → 结果确定性
- 对于中等规模数据（千至万级），内存开销可忽略

go-zero 的流式 Reduce 适合百万级数据——Map 结果不在内存中积压，边 Map 边 Reduce。

## 7 适用场景与局限

### 适用

- **批量 API 调用**：并发请求 N 个微服务接口，汇总结果
- **数据库批量操作**：并行 INSERT/UPDATE，限制连接数
- **文件处理**：并发读取、解析多个文件
- **搜索聚合**：向多个数据源查询，合并去重
- **Hedged Request**：多副本竞速降低尾延迟

### 局限

- **不适合流式处理**：Scatter 等待全部完成才返回；需要流式处理用管道模式
- **错误粒度粗**：errgroup 只返回第一个 error，无法获取"哪些成功了、哪些失败了"
- **FanOut 不保序**：channel 上的竞争读取顺序不确定；Scatter 通过 index 写入绕过此限制
- **非幂等操作需谨慎**：错误取消后已执行的 fn 副作用无法回滚

## 8 有序收集 vs 无序收集

| 方式 | 行为 | 适用场景 |
|------|------|---------|
| **无序** | 谁先完成谁先输出 | 延迟敏感：快的不等慢的 |
| **有序** | 按输入顺序输出 | 结果顺序有业务意义 |

本项目 `parallel.Scatter` 实现了有序收集——通过 index 直接写入 `results[i]`。FanOut + Merge 则是无序的（channel 竞争读取）。

### Bounded Concurrency 和 Worker Pool 的关系

两者都限制并发，但抽象层次不同：

| 维度 | Bounded Concurrency (errgroup.SetLimit) | Worker Pool |
|------|----------------------------------------|-------------|
| 生命周期 | 任务级（每批任务独立） | 池级（池可以跨多批任务复用） |
| goroutine | 按需创建，完成后退出 | 预创建，常驻等待任务 |
| 适用场景 | 一次性批量操作 | 持续的任务流 |
| 本项目 | `fanoutin/parallel/` | `objectpool/workerpool/` |

选择指南：
- 一次性批量处理 → `errgroup.SetLimit`（简单）
- 持续接受任务的服务 → WorkerPool（复用 goroutine）

## 9 测试要点

| 测试场景 | 验证内容 |
|---------|---------|
| Scatter 结果有序 | `results[i]` 对应 `inputs[i]` |
| 并发上限 | 同时运行的 fn 不超过 concurrency |
| 错误取消 | 某个 fn 出错后剩余 fn 被取消 |
| 全部成功 | 所有 fn 成功时返回完整结果 |
| ForEach 完整性 | 所有输入都被处理 |
| MapReduce 有序 Reduce | Reduce 按输入顺序执行 |
| Race 最快获胜 | 返回最快成功的结果 |
| Race 取消输家 | 获胜后其余 fn 被取消（检查 ctx） |
| Context 超时 | 外部 ctx 超时后所有操作停止 |
| 空输入 | 空 inputs 返回空结果，不死锁 |

## 10 成本模型

### 何时值得用扇出扇入

- 批量 I/O 操作（HTTP 请求、数据库查询）
- 需要限制并发数（保护下游）
- 需要收集所有结果或聚合为单值

### 何时是过度设计

- 只有 1-2 个并发操作——直接 `go func()` + `sync.WaitGroup`
- 操作是顺序依赖的——不能并行
- 数据量极小——并发调度开销 > 节省的时间
