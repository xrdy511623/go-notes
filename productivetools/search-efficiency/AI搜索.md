# 如何提高搜索效率（AI搜索篇）

**传统搜索引擎给你10条链接，AI搜索直接给你答案。但答案可能是错的——知道何时信任、何时验证，才是AI时代的核心搜索力。**

> **配套阅读**：本文讲的是"如何用好 AI 搜索"。另一半能力——用 `site:` `filetype:` `intitle:` 等语法把传统搜索引擎榨干——见 [如何提高搜索效率（谷歌搜索篇）](谷歌搜索.md)。两者是互补关系，[1.3 最佳实践：互补使用](#13-最佳实践互补使用) 给出了分工对照表。
>
> **时效说明**：本文最后更新于 2026-09。**AI 工具是本仓库里衰减最快的主题**——模型一两个月一迭代，产品功能、免费额度、订阅价格随时在变。因此本文**刻意不写具体的模型版本号、价格和额度**，只写各家的能力特征和使用方法论；涉及具体数字时请以官网为准。
>
> **关于文中的示意输出**：本文多处会展示"AI 大概会这样回答"。凡带 ⚠️ 标记的引用块都是**示意，用于说明回答的形态**，其中的数字、版本号和引用编号**未经核实，请勿直接引用**——这正是第 5 章要讲的事。

**适用读者与准备**：面向会使用浏览器、希望把 AI 搜索用于学习、排错和技术调研的开发者。先准备任务约束、目标版本和可公开或获准使用的资料；需要新信息时确认账号有联网搜索权限，执行 Go 验证示例时需安装 Go。本文的提问模板需替换其中的占位内容。

**先找，再判断，再动手**：搜索的核心价值仍然是快速找到别人已经做过的工作，减少重复摸索。AI 又帮你把分散资料整理成问题、候选方案和行动路线；但“找到现成答案”不等于“它适用于我的场景”。

## 1 AI搜索 vs 传统搜索

### 1.1 AI搜索的核心优势

**直接给答案，减少初步阅读和整理的时间**

传统搜索引擎需要你浏览多条结果、比较判断，才能得到靠谱的答案。AI搜索直接给出结构化的回答，
帮助你完成初步筛选和综合。比如你问"Go语言的context包有哪些常见的使用陷阱"，传统搜索需要你翻阅多篇博客文章，
AI工具则直接列出要点并附带代码示例。**省下的是整理时间，不是判断责任**：哪些结论有依据、是否适用于你的版本，仍需核对。

**多轮追问，越问越深**

传统搜索得到的答案如果有不明白的地方，你没法让给出答案的人替你解释，只能再次搜索。
AI搜索支持多轮对话，遇到不懂的可以直接追问"这个概念能举个例子说明吗""能用更通俗的语言解释吗"，
层层深入直到理解。

**多问题一次性提交**

比如你想同时了解：Redis和Memcached的区别、各自适用场景、性能对比、持久化方案、集群方案。
传统搜索你得搜5次，AI搜索你可以一口气问完，一次性得到结构化的对比回答。

**比较分析和推理能力**

AI擅长将两个或多个事物进行结构化对比，给出各自的优劣和适用场景。也能基于假设条件做合理推测——
"如果我的QPS从1000增长到10万，现有的MySQL架构需要做哪些调整？"，这类推理问题传统搜索很难直接回答。

### 1.2 传统搜索仍然不可替代的场景

AI搜索很强，但以下场景传统搜索引擎仍然更优：

- **查找特定文档/报告**：`filetype:pdf 行业研究报告`，直接检查发布者、版本和下载链接；部分 AI 工具也能找到文件，但总结不能替代原件
- **搜索特定网站内的内容**：`site:github.com Go rate limiter`，精确定位到某个站点
- **获取实时信息**：优先看原始公告及其发布时间；联网 AI 也能检索新信息，但不保证已经收录或读到最新版本
- **以图搜图 / 视频搜索**：需要逐项比较原图、出处和视频片段时，专门的搜索界面更便于直接检查；图像理解和查找原图不是同一件事
- **验证AI的回答**：AI可能产生幻觉，关键信息必须用传统搜索交叉验证原始来源
- **查找具体的数据和统计**：需要权威来源（政府网站、学术论文）的精确数据

### 1.3 最佳实践：互补使用

| 阶段 | 使用工具 | 原因 |
|------|---------|------|
| 快速了解一个陌生领域 | AI搜索 | 直接给结构化概览 |
| 深入学习某个知识点 | AI搜索 + 追问 | 多轮对话逐步深入 |
| 查找官方文档/源码 | 传统搜索 | 精确定位特定资源 |
| 获取最新资讯 | 传统搜索 / 已启用联网的 AI | 检查原始来源的日期和更新情况 |
| 验证AI给的答案 | 传统搜索 | 找到原始来源交叉验证 |
| 下载文件/报告 | 传统搜索 | `filetype:` 语法直接定位 |
| 比较技术方案 | AI搜索 | 结构化对比是AI强项 |
| 排查代码错误 | 先AI后传统搜索 | AI给思路，传统搜索找具体issue |

一句话记忆：**AI 负责"收敛"，语法负责"定位"。** 模糊的问题交给 AI 收敛成精确的问题，精确的原件交给搜索语法去定位。

### 1.4 先确认回答来自哪里

**别先问“哪家模型最聪明”，先问“这次回答实际读到了什么”。** 同一个产品也可能在以下模式间切换：

| 模式 | 回答依据 | 适合做什么 | 不能据此保证什么 |
|---|---|---|---|
| 普通对话 | 模型已有知识与对话内容 | 解释概念、拆解问题、生成检索词 | 信息最新、引用真实 |
| 联网搜索 | 本次搜到并读取的网页或片段 | 查新信息、找来源 | 覆盖全网、已读完引用全文 |
| 资料问答 | 上传或连接后实际可访问的资料 | 对照文档、提取条款、理解代码 | 整份文件无遗漏、资料天然正确 |
| Deep Research | 多轮检索、阅读与综合 | 多问题调研、跨来源比较 | 搜索完备、结论已经验证 |

使用前检查三件事：

1. **能力是否启用**：看界面的搜索模式、检索记录和来源列表；仅凭“我已联网”这句自述不够。思考更久也不等于查了更多资料。
2. **内容是否读到**：要求说明读到了全文、摘要还是搜索片段。网页打不开、登录受限或附件解析失败时，标记“未读取”，不要让它补全。
3. **范围是否匹配**：目标版本、资料更新时间、语言和已选来源是否覆盖问题。链接多不等于来源独立，也不等于覆盖完整。

如果工具不能联网，可以先让它生成检索词，再手动找原文；如果拿不到原文，就把相关结论保留为“待核实”。这是降级路径，不是让模型猜一个答案。

## 2 主流AI搜索工具

> 下面这几个是我日常在用的。**刻意不写价格和免费额度**——这些数字变动频繁，以各家官网为准。以下按工作流介绍，不作为模型能力排行榜；功能还受账号、地区、客户端和管理员设置影响。

### 2.1 Perplexity AI

**定位：最接近"AI搜索引擎"的产品**

Perplexity 以搜索、综合回答和来源引用为主要体验，适合作为事实查询的入口。
点击引用可以查看出处，降低验证成本，但仍要逐条检查引用是否支持结论。[官方工作原理](https://www.perplexity.ai/help-center/en/articles/10352895-how-does-perplexity-work)

> 注意措辞：是**降低验证成本**，不是**免除验证**。带引用不等于引用可信——参见 [5.3 引用不等于事实](#53-引用不等于事实三种带引用的幻觉)。

适用场景：
- 需要带来源引用的事实性查询
- 快速调研某个话题（自动搜索多个来源并综合）
- 需要新信息（联网检索能补充训练后的信息，但仍受收录和访问范围限制）
- 学术研究的初步文献发现

使用建议：
- 简单问题先用普通搜索；复杂追问可用 Pro Search，多轮调研报告使用 Research，区别见 [3.1.5](#315-perplexity-research)
- 善用 Follow-up 功能继续深入
- 关注引用来源的质量，优先信任权威来源
- 需要限定来源时，检查当前界面的来源设置，并在问题中明确优先网站；提示词中的要求是否被执行，要看实际引用

例如你搜索"Go 1.24有哪些重要的新特性"，Perplexity会返回类似这样的回答：

> ⚠️ **示意输出**（说明回答形态，编号为占位符，非真实可点击链接）
>
> Go 1.24引入了以下重要变化：
> 1. **泛型类型别名**：类型别名现在可以带类型参数 [1]
> 2. **map 改用 Swiss Tables 实现**：运行时开销降低 [2]
> 3. **新增 testing/synctest 包**：用于测试并发代码 [3]
> ...
>
> 来源：[1] go.dev/blog [2] go.dev/doc/go1.24 [3] pkg.go.dev

真实界面中的引用标记用于打开来源；上面的占位编号不是证据。其他联网 AI 也能提供引用，选工具时更应比较实际的核对体验。

### 2.2 ChatGPT

**定位：通用对话与搜索结合**

ChatGPT适合需要深度理解、多轮探讨的复杂搜索场景。开启联网搜索后也能获取实时信息。

适用场景：
- 复杂问题的多轮深入探讨
- 代码问题的调试和解释
- 长文档的理解和总结
- 多语言翻译和内容创作
- 数据分析和可视化

使用建议：
- 在自定义指令或当前问题中写清背景、约束和输出标准，参见 [4.5](#45-角色设定一个被高估的技巧)
- 上传文件让它基于你的资料回答问题
- 根据任务选择可用的搜索、文件分析或研究能力，别把模型档位当作正确性的保证
- 联网搜索功能在时效性问题上很有用——**但要留意它是否真的联网了**，没联网时它会用训练数据回答且不一定提示你

### 2.3 Claude

**定位：文档、代码分析与多轮研究**

Claude 可用于文档和代码分析；需要外部证据时，要区分普通对话、联网搜索和 Research。[官方模式说明](https://support.claude.com/en/articles/11095361-when-should-i-use-web-search-extended-thinking-and-research)

适用场景：
- 长篇论文/报告的阅读和提炼
- 代码仓库的理解和分析
- 需要逐项列出依据、限制条件和待验证问题的场景
- 复杂技术方案的评估和比较

使用建议：
- **把资料交给它读，而不是让它回忆**；先确认文件已成功读取
- 做代码分析时，提供目标函数、相关调用链、依赖版本和必要文件，按缺口补充，不必一开始塞进整个仓库
- 要求它**先列出缺失的证据，再给结论**；这个做法也适用于其他工具
- 命令行里可以用 Claude Code 直接对着本地仓库提问，省掉复制粘贴

### 2.4 Google Gemini

**定位：与Google生态深度整合**

Gemini的优势在于与Google搜索、Gmail、Google Docs等产品的深度整合。

适用场景：
- Google Workspace用户的效率提升
- 需要结合Google搜索实时信息的问答
- 多模态搜索（图片理解、视频分析）

使用建议：
- 需要 Google 搜索与 Workspace 资料结合时，可以尝试；接入搜索不等于实际检索覆盖面一定比其他工具广
- 多模态是它的强项：截图报错、拍照片问问题、丢一张架构图让它解释，都比纯文字描述高效
- 调研结果可以**一键导出到 Google Docs**，需要二次编辑或团队协作时省掉一次搬运
- 对重要的取舍判断，检查它是否使用了你的约束和证据，不按品牌预判结论质量——见 [3.1.3](#313-gemini-deep-research)

### 2.5 NotebookLM

**定位：基于你自己的资料做深度问答**

NotebookLM 允许你导入文档、网页等来源，也支持搜索、发现并选择新来源，再围绕资料集问答。
它强调依据来源回答和引用定位，但不应承诺“每句话都能逐句溯源”或“不会用错资料”。

> **导入成功不等于完整读取原件。** 例如，HTML 网页导入不包含嵌入视频和下级页面；YouTube 来源导入的是字幕文本。检查来源查看器中实际可见的内容，再判断问题能否回答。官方帮助当前部分页面使用 Gemini Notebook 名称，本文保留原有 NotebookLM 称呼便于查找。[来源类型与限制](https://support.google.com/notebooklm/answer/16215270?hl=en)

适用场景：
- 基于特定文档集合的深度研究
- 学术论文的交叉分析
- 技术文档的快速理解
- 会议记录/笔记的整理和提炼

使用建议：
- **最佳用法是"一个主题一个 notebook"**：把某个技术的官方文档、几篇关键论文、几篇高质量博客一起丢进去，然后针对这个封闭资料集提问
- 对回答中的引用，**养成点开核对的习惯**；没有定位信息的关键结论要求补证据
- 没有资料时可先发现来源，再筛选导入；不要把自动推荐的资料集当成完整、权威的文献库
- 注意来源是副本还是同步内容，核对同步状态和版本；回答依据的可能不是你以为的最新原件
- 可以让它生成资料集的**大纲、时间线、常见问题**，作为通读前的导航

### 2.6 工具选择速查

| 需求 | 可选工具 | 选择依据 |
|------|---------|------|
| 带引用的事实查询 | Perplexity / 其他联网 AI | 能否打开来源并核对关键结论 |
| 深度技术问答 | ChatGPT / Claude | 多轮对话 + 代码能力强 |
| 长文档分析 | Claude / NotebookLM | 实际读取范围与引用定位能力 |
| 实时信息 | Perplexity / ChatGPT(联网) | 联网搜索获取最新信息 |
| 基于授权资料问答 | NotebookLM / 支持文件的 AI | 来源可控，同时满足资料权限要求 |
| 补充不同来源 | 多个搜索入口 | 比较实际原件，不比较品牌宣传 |
| Google生态集成 | Gemini | 与Google产品深度整合 |

## 3 Deep Research：AI深度研究

普通对话也可以调用搜索工具。Deep Research 的区别主要是**把任务拆成多个子问题，自主进行多轮检索、阅读和综合，最终输出带来源的研究报告**，而不是简单地“联网 / 不联网”。

这对于需要**广泛搜集资料、对比分析、撰写研究报告**的场景很有价值：它能减少初步检索和报告起草的人工投入。不过，搜索页数、耗时和遗漏率依任务而变；报告生成快，不代表验证、实验和决策也能同样快。

> **但它不是免验证的。** Deep Research 的报告更长、更结构化、引用更多，读起来**更像真的**——这恰恰让它的错误更难被发现。篇幅和格式不是可信度的证据。第 5 章的所有验证方法，对 Deep Research 报告同样适用，而且更该做。

### 3.1 各家Deep Research对比

> 下面比较**工作流入口与使用边界**，不是准确率排名。底层模型、入口和额度会变，使用前以当前界面和链接中的官方说明为准。

#### 3.1.1 ChatGPT Deep Research

使用 ChatGPT 做深度研究时，把目标设为“可追溯的研究简报”，而不只是“长报告”。

- 提供获准使用的材料、问题范围和输出标准，检查当前可用的研究、搜索和文件能力
- 要求按主题列出证据、分歧、方法局限和待核实的主张
- 最终逐条回到原件核对，不能因为生成了研究报告就视为完成验证

这也是 OpenAI 官方研究工作流强调的交付方式：[整理研究证据](https://learn.chatgpt.com/use-cases/synthesize-research-evidence)。本文不把某个模型档位、固定耗时或来源数量当作功能保证。

#### 3.1.2 Claude Research

Claude Research 会进行相互衔接的多轮搜索，也可结合已授权连接的内部资料。

- 使用前确认 Research 与联网搜索都已开启；仅开启更深入的思考不等于开启研究
- 如果应当使用的内部文档没被检索到，明确点名来源，并检查它是否实际读取
- 多轮检索与长回答会增加用量；资料权限和额度以当前账号为准

功能与前置条件见 [Claude Research 官方说明](https://support.claude.com/en/articles/11088861-use-research-on-claude)。不要把“语气谨慎”当成比其他产品更准确的证据。

#### 3.1.3 Gemini Deep Research

Gemini Deep Research 默认包含 Google 搜索来源，支持编辑研究计划，也可按权限添加文件或 Workspace 来源。

- 开始前检查来源选择：公开网页调研和内部资料调研不必混在一起
- 先编辑研究计划，补上关键约束，再开始研究
- 需要协作时，可将报告导出到 Google Docs；导出后仍应保留引用与限制条件

操作方式见 [Gemini Deep Research 官方说明](https://support.google.com/gemini/answer/15719111?hl=en)。接入 Google 搜索不等于穷尽其索引，也不能由此推导“覆盖最广”或“推理较弱”。

#### 3.1.4 Grok DeepSearch

Grok 曾以 **DeepSearch** 名称发布研究功能，官方示例包括分析 X 上的讨论；不要把各家名称统一写成 “Deep Research” 后误认为它们是同一个功能。[官方发布说明](https://x.ai/news/grok-3)

- 可用于寻找社区反馈线索，但要打开原帖，检查作者、日期、复现条件和后续更正
- **社区舆情天然带情绪偏差**——X 上骂得最凶的和吹得最狠的都不代表中位数体验，拿它做选型依据要格外小心
- 不把帖子数量当采用率，也不把单个平台的反馈当整个社区的共识；当前研究入口以产品界面为准

#### 3.1.5 Perplexity Research

**Pro Search 和 Research 是不同模式，Pro 则还可能指订阅方案，不要混用。**

- **Pro Search**：面向复杂查询的搜索与综合，可继续追问，适合围绕具体问题逐步收敛。[官方说明](https://www.perplexity.ai/help-center/en/articles/10352903-what-is-pro-search)
- **Research**：自主反复检索、阅读和调整研究路径，生成综合报告；支持导出和分享。[官方说明](https://www.perplexity.ai/help-center/en/articles/10738684-what-is-research-mode)

需要多问题调研时确认选的是 Research；只查一个 API 的存在性，用普通搜索或本地文档通常更直接。不要为简单问题默认消耗深度研究额度。

### 3.2 选择建议

| 研究场景 | 可选工具 | 重点检查 |
|---------|---------|------|
| 技术选型调研 | 各家研究模式 | 约束、版本和证据是否可比 |
| 单点事实查询 | 普通联网搜索 / 本地文档 | 能否直接找到原始证据，不必生成长报告 |
| 学术文献初步综述 | 研究模式 + Scholar / 领域数据库 | 检索式、纳入范围、全文可访问性；不冒充系统综述 |
| 文档协作 | Gemini 等支持导出的工具 | 导出后引用、限制条件是否保留 |
| 结合内部资料研究 | 支持资料连接的工具 | 获准使用、读取范围、共享权限 |
| 社区反馈线索 | Grok / 搜索平台原帖 | 样本偏差和可复现证据 |

**实用技巧：重要调研可以用两个工具各跑一次 Deep Research，对比两份报告中结论不一致的地方——这些差异往往是你需要深入思考的关键决策点。**

可以让两个 AI “互相打架”，但**找分歧是排查手段，不是验收标准**。先排除资料版本、需求理解和权重不同，再追到各自的原始来源；即使两家都引用同一篇错误博客，也可能得到完全一致的结论。会改变决策的共同结论同样要查，不应只查分歧。

### 3.3 实战案例：用Deep Research做技术选型

以下是一个贴近程序员真实工作的完整案例：**为Go微服务项目选择消息队列中间件**。

#### 3.3.1 背景

你的团队需要为一个新的Go微服务项目引入消息队列，备选方案有Kafka、RocketMQ、Pulsar和NATS JetStream。
传统做法是搜索对比文章、翻官方文档、看社区讨论，再自己写一份对比报告。
这里让 Deep Research 完成初步资料整理，人负责约束澄清、证据核验和小规模验证。**这是流程示例，不是完成过的选型实验，也不承诺固定耗时。**

#### 3.3.2 第一步：提交研究任务

> 请帮我做一份详细的消息队列选型调研报告，用于Go微服务项目。
>
> 项目背景：
> - Go语言技术栈，微服务架构
> - 日均消息量约2000万条，峰值QPS约5000
> - 需要至少一次投递，消费者可做幂等处理；请先明确确认、持久化、副本和故障模型，不把 at-least-once 等同于任何故障下都不丢消息
> - 消费延迟要求P99 < 200ms
> - 团队目前没有消息队列运维经验，学习成本是重要考量
>
> 请对比以下方案：Kafka、RocketMQ、Pulsar、NATS JetStream
>
> 每个方案请覆盖以下维度：
> 1. 核心架构和设计理念
> 2. Go 客户端库的成熟度（版本兼容、发布记录、维护响应、API 易用性；star 数只作辅助）
> 3. 性能证据（列明版本、硬件、消息大小、副本、持久化与确认配置；条件不同的 benchmark 不直接排名）
> 4. 运维复杂度和部署方式（Docker/K8s支持）
> 5. 消息可靠性保障机制
> 6. 社区活跃度和生态
> 7. 已知的坑和注意事项
>
> 开始前列出缺失的关键条件，例如消息大小、保留时间、可接受的重复消费和恢复目标。
> 优先官方文档、仓库和可复现实验，标明来源日期及适用版本。
> 最后给出有条件的推荐排序、会改变排序的因素，以及需要本地验证的最小实验。
> 每个关键结论附具体出处；找不到证据就写“未知”，不要为填表编数字。

**提问要点**：这个 prompt 有四段结构，缺一不可——

| 段落 | 作用 | 缺了会怎样 |
|---|---|---|
| **背景约束**（技术栈、规模、可靠性、团队现状） | 让建议落到你的场景 | 得到一篇泛泛的"Kafka 吞吐高、RabbitMQ 简单"科普 |
| **对比对象**（点名四个方案） | 圈定范围 | AI 自由发挥，可能漏掉你真正在考虑的选项 |
| **对比维度**（七条） | 保证每个方案被同样地审视 | 各方案详略不一，没法横向比 |
| **输出要求**（推荐排序 + 理由） | 逼它做取舍，而不是罗列 | 得到一堆"各有优劣"的废话 |

其中**"团队目前没有消息队列运维经验"这一句的信息量最大**——它是一个软约束，但会显著改变结论排序。技术选型的 prompt 里，这类"非技术约束"往往比技术参数更能决定最终选谁。

#### 3.3.3 第二步：等待研究完成

耗时依任务、产品与访问情况而变。这期间预期的研究过程是：

1. 规划研究路径；如果界面不展示计划，就在启动前要求先输出计划
2. 搜索并阅读官方文档、GitHub 仓库、基准测试报告和必要的社区讨论
3. 交叉对比不同来源的信息
4. 生成结构化报告，附关键结论的引用，以及无法访问的来源和证据缺口

**建议在这一步就开始留意它的研究计划**：如果你发现它规划的路径漏掉了你关心的维度（比如只查性能不查运维），可以直接中断并补充要求，比拿到报告后再返工便宜得多。

#### 3.3.4 第三步：换一家交叉验证

将同样的问题提交给另一家的 Deep Research（比如 ChatGPT 跑完换 Claude），重点关注两份报告中**结论不一致**的地方。

比如一家可能基于性能和生态推荐 Kafka，另一家可能更看重"团队无运维经验"而推荐 NATS JetStream。先查它们使用的部署方案与证据；**如果事实一致、只有权重不同，这种分歧可能是不同权重下的合理推导**——恰恰帮你看清了决策的核心权衡点：你到底更怕性能不够，还是更怕运维扛不住？

这个问题 AI 替你回答不了，但它帮你把问题**问清楚了**。这就是 Deep Research 交叉验证的真正价值——不是找出正确答案，是找出你必须自己做的那个决定。

#### 3.3.5 第四步：针对性追问

基于报告中你特别关心的点，继续深入追问：

> 报告中提到Kafka的Go客户端有segmentio/kafka-go和confluent-kafka-go两个选择，
> 请详细对比这两个库：
> 1. 性能差异（有没有benchmark数据？）
> 2. API设计风格（哪个更Go-idiomatic？）
> 3. 对Kafka新特性的支持程度
> 4. 在生产环境中的已知问题

#### 3.3.6 第五步：传统搜索补充验证

对于报告中的关键数据点（尤其是性能指标和"某某库有某某问题"这类断言），回到传统搜索验证原始来源：

```
Kafka NATS JetStream benchmark site:github.com
```

```
confluent-kafka-go vs segmentio/kafka-go performance site:github.com
```

先定位可复现的测试，再检查版本和条件。需要限定某次版本升级之后的数据时再加 `after:`，不要一上来排掉仍适用的旧资料；搜索显示的日期也不能代替报告中的测试日期。语法细节见 [谷歌搜索篇 2.2.15](谷歌搜索.md#2215-限定时间范围-before--after)。

**这一步不能省。** 前四步产出的是"一份看起来很专业的报告"，第五步才开始让它成为有证据的决策材料。先核对可能推翻选择的断言：可靠性语义、故障恢复、版本兼容、性能和运维限制；架构理解错误也可能直接导致选错。公开 benchmark 不能证明你的项目满足 P99 目标，最后还要做贴近实际负载与故障模型的验证。

#### 3.3.7 效果对比

| 维度 | 传统搜索方式 | Deep Research方式 |
|------|------------|-------------------|
| 人工投入 | 自己组织查询、阅读与综合 | 可减少初步检索和起草工作，仍需核验 |
| 来源覆盖 | 取决于检索策略和访问权限 | 同样受策略、权限和索引限制；来源多不保证完整 |
| 报告质量 | 取决于证据与个人分析 | 结构化较方便，但格式不能证明结论可靠 |
| 出错形态 | 可能漏查、误读、采信错误来源 | 除上述问题外，还可能编造引用、拼接出来源不支持的结论 |
| 需要验证 | 原文也要检查日期、条件和可信度 | **额外核对“原文 → AI 结论”是否成立** |
| 验收标准 | 关键结论有证据，适用性已检查 | 相同标准，不因使用 AI 而降低 |

最值得强调的是新增的错误环节：**AI 可能把真实来源整理成并不真实的结论**，而且写得比你自己总结的还要工整。效率应该看“得到可采纳结论的总成本”，而不只是“报告多久生成”。

## 4 高效提问技巧

提问质量决定了AI回答质量。以下技巧专门针对**搜索场景**优化。

### 4.1 明确意图和约束条件

差的提问：
> Redis怎么用？

AI会给你一篇泛泛的Redis入门介绍，从安装到基本数据类型到简单命令，和你随便搜到的教程没什么区别。

好的提问：
> 我在一个Go Web服务中需要用Redis做缓存，QPS大约5000，数据量约100万条记录，
> 平均value大小2KB。请推荐合适的缓存策略，包括过期策略、缓存穿透/雪崩的防护方案，
> 以及Go语言推荐使用的Redis客户端库。

这样的背景有助于得到针对性的候选方案，但还不足以确定 TTL、缓存容量或是否需要布隆过滤器。
继续补充一致性要求、更新频率、命中率目标和内存预算，并要求它解释每个建议成立的条件。

**差距的本质**：提供背景信息（技术栈、规模、约束）能让AI的回答从泛泛而谈变为有针对性的方案。

**这是全章最重要的一条**。如果你只想记一件事，就记：**把你的约束条件写出来**。

### 4.2 要求引用来源

> 请推荐Go语言中处理并发的最佳实践，**并附上每个建议的来源链接或官方文档出处**。

这个要求有两重作用：一是促使它基于更可靠的知识作答，二是**给了你一个可核对的抓手**。

但务必清楚它的边界：**要求引用不等于得到真引用**。没有联网能力的模型可能直接编造出格式完全合法的 URL；有联网能力的工具也可能给出真实但并不支持该结论的链接。三种"带引用的幻觉"及其识别方法，见 [5.3](#53-引用不等于事实三种带引用的幻觉)。

一个更可核对的变体——**要求“结论—证据”对应表**：

> 请实际检索并打开来源，逐条列出：结论、原始链接及章节 / 页码、适用版本与条件、证据状态。
> 证据状态使用“原文明示 / 基于证据推断 / 未找到依据”。
> 推断请写清依赖哪些事实；只读到摘要或搜索片段时注明，不要当成已读全文。
> 不要为满足数量要求编造来源；无法访问就列入证据缺口。

检查时，不只看链接是否存在，还要看它是否支持**这一条结论**。模型自报“高置信度”不是经过校准的正确概率；可以用来安排追问，但不能代替证据。

### 4.3 指定输出格式

> 请用表格对比以下消息队列：Kafka、RabbitMQ、RocketMQ、Pulsar。
> 对比维度包括：吞吐量、延迟、消息持久化、集群方案、学习曲线、Go生态支持程度。

AI会直接输出一张整齐的对比表格：

> ⚠️ **示意输出**（仅展示如何表达证据缺口，不提供产品性能排名）
>
> | 维度 | 当前结论 | 还需要什么证据 |
> |---|---|---|
> | 四个候选的吞吐量排名 | 未知，缺少同条件测试 | 相同硬件、负载、确认和副本配置 |
> | 是否满足本项目 P99 | 待验证 | 目标负载下的端到端测试 |
> | Go 客户端适用性 | 待逐项核对 | 目标版本、功能支持、维护记录 |

指定格式（表格、列表、代码、步骤）能让回答更加结构化、易读、可操作。

> **⚠️ 表格的整齐外观容易让人误以为“这些数字都核对过”。** 缺证据时，模型也可能填入貌似合理的数字。星级评分（★★★★）如果没有评分标准、样本和来源，就只是意见，不是测量结果。
>
> 实用做法：要表格，但在 prompt 里加一句——**"没有可靠来源的格子请填'未知'，不要猜测"**。

### 4.4 迭代优化：追问的艺术

第一轮回答往往是泛泛的概览。真正的价值在后续的追问中：

- "这个方案在高并发场景下有什么潜在问题？"
- "能给一个完整的Go代码示例吗？"
- "如果我的场景是xxx，方案需要怎么调整？"
- "有没有更简单的替代方案？"
- "你刚才没有提到 xxx，是有意省略还是遗漏了？"

每一轮追问都在缩小范围、增加精度。

**但有一类追问要小心。** 当你怀疑它说错了，不要问：

> ❌ 这个说法和我在官方文档里看到的不一致，**你确定吗？**

这种句式会触发模型的迎合倾向——它很可能直接推翻原本**正确**的答案来附和你。应该改成要求它出示证据：

> ✅ 我在官方文档里看到的是 X，和你说的 Y 不一致。**请给出你那个说法的具体出处，我们对一下。**

区别在于：前者让它猜"你想听什么"，后者让它回到证据本身。详见 [5.4 迎合：追问的反作用力](#54-迎合追问的反作用力)。

### 4.5 角色设定：一个被高估的技巧

你可能见过这种写法：

> 你是一个有10年经验的Go后端架构师，精通高并发系统设计。请review以下代码的并发安全性问题……

**身份描述不能当作能力保证。** “有 10 年经验”并没有给模型增加真实的工作经历，也没有提供它原本缺少的源码、日志或评审标准。角色提示的效果依任务和模型而变，本文不把它作为稳定提效的前提。

更值得警惕的是它可能**帮倒忙**：过度的人设会让模型去模仿那个角色的**语气**（自信、笃定、爱下结论），而这恰恰是你在做技术判断时最不需要的。一个"10年经验的资深架构师"人设，可能比中性提问更不容易说出"这里我不确定"。

**真正有效的替代品，是给约束、给标准、给评判维度**——也就是 [4.1](#41-明确意图和约束条件) 讲的那件事：

| ❌ 给身份 | ✅ 给约束和标准 |
|---|---|
| 你是资深 Go 架构师 | 这是一个 QPS 5000 的支付回调服务，任何数据不一致都不可接受 |
| 你是严格的代码审查员 | 按这四个维度逐条检查：数据竞争、goroutine 泄漏、错误吞掉、defer 时机 |
| 你是技术面试官 | 针对每个知识点，先问我一个问题，等我答完再讲解 |

**角色设定仍然有用的场景**，是当你要的是特定的**视角或受众**，而不是特定的能力水平：

- "请用**给刚入职的实习生讲解**的方式说明这段代码" —— 控制的是表达层次
- "请**站在攻击者的角度**分析这个接口有哪些可利用点" —— 换的是分析视角
- "请**扮演唱反调的人**，尽力反驳我刚才的技术选型" —— 主动索取对立面

这三类的共同点是：**角色改变的是任务本身，而不是假装提高模型的能力。**

### 4.6 组合问题，节约时间

当你有多个相关问题时，一次性提交比逐个提问高效得多：

> 关于Go的sync.Pool，请回答以下问题：
> 1. 它的内部实现原理是什么？
> 2. 什么场景下使用它能带来明显的性能提升？
> 3. 使用时有哪些常见的陷阱？
> 4. 它与对象复用模式的区别是什么？
> 5. 请给一个生产环境中的最佳实践示例。

**一个边界**：问题之间应该是**相关**的。把不相关的问题塞进一次提交，更难检查每一项是否回答充分。判断标准是：这些问题是否共享同一套背景？共享，就合并并要求逐项回应；不共享，就分开问。

### 4.7 长资料：先检查再综合

**资料给得多，不等于模型读得全；先确认读到了什么，再问它能得出什么。** 对论文合集、规格书和代码库，建议分三步：

1. **列资料清单**：文件名、来源、版本、主题、读取状态。先解决打不开、重复版本、缺页等问题；不要用模型生成的摘要替代原始材料作为后续唯一证据。
2. **按问题提取证据**：先问“哪些原文涉及重试与幂等”，再问“它们是否冲突”。要求指向文件和章节；扫描 PDF、复杂表格与图片中的数字，要回到页面核对 OCR、单位、表头和脚注。
3. **最后跨资料综合**：分开记录事实、推断和未知。声称“所有文档都没有提到 X”需要检查完整范围；只检索到部分片段时，只能说“本次未找到”。

可复制的提问模板：

> 先列出你能读取的资料与版本，以及读取失败或范围不完整的部分。
> 只围绕“<本次问题>”提取相关原文位置，再综合回答。
> 若不同文档冲突，分别列出处、日期和适用条件，不要自行拼成一个确定结论。

多轮对话开始混用旧假设时，整理一份“已确认事实 + 原始来源 + 当前约束 + 未解决问题”，再开新对话继续。这样是在整理上下文，**不是用新对话给答案做正确性认证**。

## 5 AI搜索的陷阱与验证

> 这是全文最重要的一章。前面四章教你**怎么更快地拿到答案**，这一章教你**怎么不被答案坑到**。速度只有在准确的前提下才有意义。

### 5.1 AI幻觉：最大的陷阱

AI可能会非常自信地给出完全错误的信息。这叫做"幻觉"(Hallucination)。常见表现：

- **编造不存在的API/函数**：告诉你某个库有某个方法，但实际不存在
- **编造论文/引用**：给出看起来很真实但完全虚构的论文标题和作者
- **过时的信息当作最新的讲**：用旧版本的语法或已废弃的特性来回答
- **自信地给出错误的数字**：统计数据、性能指标等信息可能不准确
- **把相似的东西混为一谈**：把另一个库的 API 安到这个库上，把另一个版本的行为说成当前版本的

**幻觉最危险的特征不是"错"，而是"错得毫无征兆"。** 错误内容也可能使用和正确内容一样流畅、笃定的措辞。这意味着**你无法靠"读起来像不像真的"来判断**，需要外部验证。

### 5.2 幻觉反例：不存在的 API

抽象的警告不如一个具体案例。下面用 Go API 演示一种很容易让人信以为真的错误；它是教学反例，不是对某个模型的实测记录：

**提问**：`sync.Map 怎么获取元素个数？`

**典型的幻觉回答**：

> ⚠️ **示意输出——这段是错的，用于演示幻觉的形态**
>
> 使用 `Len()` 方法即可获取 `sync.Map` 中的元素数量：
>
> ```go
> package main
>
> import (
>     "fmt"
>     "sync"
> )
>
> func main() {
>     var m sync.Map
>     m.Store("a", 1)
>     m.Store("b", 2)
>     fmt.Println(m.Len()) // 错误：sync.Map 没有 Len 方法
> }
> ```

**事实**：本次用 Go 1.24.0 的本地文档核验，`sync.Map` **没有** `Len()` 方法。可以用 `Range` 遍历计数，但官方说明明确指出它**不保证对应任何一致快照**；存在并发修改时，不能把计数当作某个时刻的精确长度。这个语义限制不是“没有 Len 的设计原因”的证据。目标工具链不同时，重新运行下面的核验命令。

**为什么这个错误容易骗过人**：因为它太合理了。`map` 有 `len()`，`sync.Map` 名字里也有 Map，人就容易接受一个“应该存在”的 `Len()`。但 API 不能靠类比补全。**凡是符合直觉、你几乎不会想去核对的地方，恰恰是幻觉最容易藏身的地方。**

**如何快速识破**——先查当前工具链，再查具体方法：

```bash
# 记录核验使用的版本；再列出该版本 sync.Map 的方法
go version
go doc sync.Map

# 核对并发遍历的语义；预期文档说明 Range 不保证一致快照
go doc sync.Map.Range

# 反例检查：Go 1.24.0 中预期失败，提示没有 Len 方法
go doc sync.Map.Len
```

**这个案例的普适教训**：对于“某个类型有没有某个方法”“某个函数的签名是什么”，**目标版本的本地文档和编译器比另一个 AI 的赞同更直接**。但编译通过只能证明语法和类型等检查通过，不能证明业务逻辑、并发行为或性能正确；这些还需要对应的测试和实验。

### 5.3 引用不等于事实：三种带引用的幻觉

带引用的工具（Perplexity、各家 Deep Research）大幅降低了验证成本，但**"有引用"和"引用支持这个结论"是两件事**。实际会遇到三种情况，隐蔽程度递增：

| 类型 | 表现 | 识别成本 |
|---|---|---|
| **① 来源无法核实，可能是编的** | URL 格式合法，但打不开、跳首页，或标题和作者对不上 | **较低**——先查原站；也可能是迁移或访问受限，不能只凭 404 判造假 |
| **② 链接真实，但内容不支持该结论** | 页面确实存在、主题也相关，但里面根本没有 AI 声称的那句话或那个数字 | **高**——必须真的读一遍 |
| **③ 链接真实、内容也有，但被断章取义或已过时** | 原文说的是"在 X 条件下成立"，AI 引用时丢掉了条件；或引用了不适用于目标版本的旧说明 | **最高**——必须读懂上下文 |

**② 是最危险的一类**，因为它完美骗过了"点开看看链接是不是真的"这个最常见的验证动作。链接能打开、网站很权威、主题也对——大多数人到这一步就放心了，而错误恰恰在这一步之后。

**验证动作：先快速筛查，再核对支撑关系**：

1. 先挑 **2–3 条会影响决策的结论**做试查；发现问题就扩大检查。正式采纳前，所有可能推翻决策的关键断言都要核实，不能用固定抽查数量替代验收。
2. 打开引用，确认发布者、文档标题、版本、日期，以及它是原始资料还是转述。
3. 用 **`Ctrl/Command+F` 搜关键词或数字来定位**，然后读附近段落、表头和脚注，核对前提、单位和否定条件。定位到词不等于验证了结论。
4. 找不到时尝试同义词、文档目录或原始 PDF；确认是否只拿到了摘要、动态页面或 OCR 文本。仍无法核实就标记“待核实”，不要宣称它已被证明为假。
5. 把结果记成“支持 / 部分支持 / 不支持 / 无法访问”。若只有部分支持，就缩小结论范围，或补找独立证据。

例如，原文说“在指定负载下，开启批量写入后吞吐提高”，不能推出“这个方案在你的低延迟业务中一定更快”。**验证的对象是“结论与证据的关系”，不只是链接和关键词。**

学术引用可以从 Google Scholar 搜完整标题，再对照作者、年份、DOI 和出版社或预印本原页。搜不到可能是未收录或标题有差异，不是虚构的充分证据；只读过摘要，也不能把论文的方法和实验细节当作已核实。

### 5.4 迎合：追问的反作用力

这是一个很多人没意识到的陷阱：**当你表达出怀疑或倾向时，模型有相当强的倾向去附和你，哪怕它原本是对的。**

典型触发句式：

- "你确定吗？"
- "我觉得不对吧？"
- "但是我看到的是 X 啊"
- "真的是这样吗？"

模型可能回你一句"抱歉，您说得对，我刚才的回答有误……"然后把**正确**的答案改成**错误**的。道歉、改口和更笃定的语气，都不能代替新增证据。

**麻烦在于**：反复施压可能让答案不断变化，最后你既不知道原答案对不对，也不知道改后的对不对。幻觉本身也不一定稳定，不能靠回答是否一致来区别两者。

**怎么绕开**：

| ❌ 触发迎合 | ✅ 回到证据 |
|---|---|
| 你确定吗？ | 请给出这个结论的具体出处（文档章节/源码文件/论文页码） |
| 我觉得应该是 X | 请分别列出支持 X 和支持 Y 的证据，然后判断哪个更可靠 |
| 这个不对吧 | 我在 <具体来源> 看到的是 X，请解释这个差异从何而来 |
| （反复追问同一点） | 提供原始证据，请它指出哪一条证据改变了结论 |

必要时可以开新对话，用中性措辞重新拆解问题，减少旧假设的影响。但**换对话是整理思路，不是外部验证**；重复答对或重复答错都会表现为“一致”。

### 5.5 交叉验证方法

对于重要信息，必须验证。优先选择能直接回答该断言的证据，成本依任务而变：

1. **让机器判定可验证的部分**：API 是否存在用 `go doc`；代码行为用最小复现和测试；配置先用检查模式或隔离环境验证，不为核验而直接改动生产系统。测试通过只覆盖实际测试到的条件。
2. **查官方文档**：AI 说某个 API 的用法、某个参数的默认值，去官方文档确认。用 `site:` 语法直奔官方站，见 [谷歌搜索篇 6.2](谷歌搜索.md#62-搜索官方文档)
3. **精确匹配搜索它给的原话**：用双引号定位关键句或 API 名；搜不到时去掉引号、换译名或查原站。未收录、访问限制和措辞不同都会造成零结果。见 [谷歌搜索篇 2.2.1](谷歌搜索.md#221-精确匹配-)
4. **核对引用与独立来源**：按 [5.3](#53-引用不等于事实三种带引用的幻觉) 核验。三篇文章都转述同一份报告，仍然只有一条证据链；尽量找维护者说明、原始实验或独立复现。
5. **多个 AI 工具辅助找分歧**：不同模型可能使用相同来源，也可能因假设或权重不同而意见相左。把它们当作提出反例和指出缺口的助手，最终仍靠来源和实验裁决。

> **⚠️ 一个流传很广但不可靠的方法：问 AI"你的训练数据截止到什么时候"。**
>
> 模型对自身信息的回答也可能出错。产品说明中的知识截止日期与本次是否实际联网，又是两个不同问题。
>
> 判断本次回答的时效性，应检查检索记录、来源日期和目标版本。答对一道近期事实题，也不能证明下一题会使用最新资料。需要近期信息而没有检索依据时，明确要求搜索，或自己打开官方公告。

### 5.6 哪些信息需要重点验证

| 风险等级 | 信息类型 | 验证方式 |
|---------|---------|---------|
| 高 | 具体的API用法、函数签名、方法是否存在 | **编译器 / `go doc`**，其次官方文档 |
| 高 | 统计数据、性能指标、benchmark 结果 | 找原始来源，并检查测试环境和版本 |
| 高 | 安全相关的配置和实践 | 查官方安全指南，绝不采信单一来源 |
| 高 | 版本兼容性断言（"X 从 Y 版本开始支持"） | 查 release notes / CHANGELOG |
| 中 | 架构设计建议 | 检查约束、可靠性假设和反例；落地前做原型验证 |
| 中 | 最佳实践和设计模式 | 查社区讨论和权威书籍 |
| 中 | 第三方库的选型建议 | 检查发布记录、目标版本、维护响应和许可证；star 数不是质量证明 |
| 低 | 概念解释和原理说明 | 可作入门线索；关键定义回到教材或官方文档 |
| 低 | 代码风格、命名建议 | 对照团队规范及语言约定，避免改变语义 |

一条实用的分界线：**凡是会被写进生产代码或决策文档的，都要验证；只用来入门理解的，可以先作为线索。** 风险还取决于后果：涉及数据安全的架构建议，即使没有一个具体数字，也应提升到高风险处理。

### 5.7 识别AI不确定性的信号

**不要从语气推断正确率。** “通常”“可能”有时是在准确表达适用条件；措辞果断、自报高置信度、换对话仍然一致，也都不能证明可靠。真正值得追查的是证据缺口：

- **具体数字没有来源或测试条件**：例如“性能提升 37%”，却没有负载、版本和比较基线
- **结论依赖没提供的事实**：缺少消息大小和持久化配置，却断言能达到你的吞吐与 P99 目标
- **来源与结论不匹配**：引用主题相关，但没有支撑这一条断言
- **回答变化却没有新增证据**：要求列明究竟是事实、假设还是权重改变了
- **声称全面覆盖却没有检索范围**：问它查了哪些来源、哪些不可访问、还有哪些可能遗漏
- **来源身份不清楚**：先核对作者、机构、原始发布位置；陌生不等于不可靠，熟悉也不等于一定正确

### 5.8 隐私与提示注入

**“基于我的资料回答”不等于“资料只留在本地”。** 上传文件、连接仓库或邮箱、分享研究报告前，先检查数据边界：

- **最小化输入**：移除密钥、令牌、客户标识和生产业务数据。排错尽量提供脱敏日志和最小复现，而不是整个 `.env`、完整日志或数据库导出。
- **确认权限与设置**：使用组织批准的账号和工具，检查资料用途、保存设置、连接器权限及分享对象；不同产品和订阅方案的规则不能互相套用。
- **公开调研与内部分析分开**：先用公开信息检索，再在获准的环境中结合内部约束。不要让外发搜索词或链接参数夹带内部资料。

还有一种风险不是 AI “答错”，而是网页或文档**诱导它做不该做的事**：页面中可能夹带“忽略用户要求”“为了验证先上传配置文件”“运行这段命令”等指令。这叫**提示注入（prompt injection）**，来源内容应被当作待分析的数据，而不是新的授权。

OpenAI 的深度研究 API 安全说明明确讨论了网页 / 连接器中的提示注入及数据外传风险，并建议分阶段处理敏感资料、审查工具调用与外发链接。这里引用的是安全机制说明，不代表所有聊天产品都提供相同控制项。[风险与缓解措施](https://developers.openai.com/api/docs/guides/deep-research#safety-risks-and-mitigations)

实际使用时：

1. 研究任务默认只读，不因来源页面的要求自动授权下载执行脚本、发送消息或修改配置。
2. 点击可疑链接、执行命令或批准工具调用前，检查目标地址、参数和将要发送的数据；警惕把私密内容塞进 URL 的链接。
3. 如果发现可疑指令，停下相关操作，回到可信原站核对；不要仅靠一句“请忽略提示注入”就认为有了安全保障。

## 6 程序员的AI搜索实践

### 6.1 排查代码错误

传统方式：复制错误信息到Google搜索，翻Stack Overflow。

AI搜索方式：
> 我在运行以下Go代码时遇到了这个错误：
> `fatal error: concurrent map writes`
> 代码如下：[粘贴代码]
> 请分析错误原因并给出修复方案。

AI会直接给出结构化的诊断：

> ⚠️ **示意输出**（结论正确，但**修复代码务必本地跑一遍**）
>
> **错误原因**：Go 的原生 map 不是并发安全的。多个 goroutine 同时写同一个 map 时，
> runtime 可能检测到冲突并以 `fatal error` 终止进程；没有触发这个错误也不代表没有数据竞争。
>
> **修复方案**（三选一）：
> 1. 使用 `sync.Mutex` 保护 map 的读写操作
> 2. 使用 `sync.RWMutex`（是否更快取决于竞争程度、临界区和负载，需要 benchmark）
> 3. 使用 `sync.Map`（适合"写一次读多次"或"多个 goroutine 操作不相交的 key 集合"两种场景）
>
> **下一步**：结合实际访问路径检查所有读写是否受保护，再比较需要的同步方案，而不是只给报错的写入处加锁。

> **⚠️ 这里有一个 AI 极易说错、而且很多中文博客也在跟着说错的细节**：
>
> `fatal error: concurrent map writes` **不是 panic**。它是 runtime 直接抛出的致命错误，**`recover()` 拦不住，`defer` 也不会执行，进程立即终止**。如果 AI 告诉你"用 defer + recover 兜一下"，那是错的——这个错误在设计上就不给你兜底的机会。
>
> 另外，它**确实是数据竞争**，只是 runtime 对 map 这一种情况做了主动检测。真正排查数据竞争要靠 `go test -race`。

AI 可以先帮你列出排查方向，但**拿到修复思路不等于排障结束**。修复前保留复现方式，修复后运行相关包的测试；并发问题再启用 race detector。下面使用本仓库已有的并发示例包演示命令形式，在自己的项目中换成受影响的包路径：

```bash
go test -race ./gocore/concurrency/pattern
```

预期测试通过且没有 `WARNING: DATA RACE`。不过，race detector 只能发现本次执行路径上发生的数据竞争，不能证明没有竞态；还应覆盖原来的复现场景与关键并发路径。检查器边界见 [Go 官方说明](https://go.dev/doc/articles/race_detector)。

搜索错误信息的传统技巧（去掉个性化片段、保留错误码、加双引号）见 [谷歌搜索篇 6.1](谷歌搜索.md#61-搜索错误信息)。

### 6.2 快速学习新技术

传统方式：搜教程 → 找视频 → 看文档 → 拼凑理解。

AI搜索方式：
> 我是一个有3年Go开发经验的后端工程师，现在需要学习gRPC。
> 我已熟悉 HTTP API 和基本序列化，但没用过 Protocol Buffers，也不了解 RPC 的 deadline 和重试语义。
> 请给我一个循序渐进的学习路线，从基础概念到生产实践，每个阶段推荐关键学习资源。

**注意这个 prompt 里“已熟悉什么、没用过什么”的作用**：年限只能粗略描述经验，不能保证掌握了 RPC 或序列化。明确起点，AI 才更容易减少重复讲解，同时补上真正缺失的基础。

拿到路线之后的三个动作：

1. **让它把路线压缩成一张检查表**："请把上面的学习路线转成一个 checklist，每项写清'学完之后我应该能做出什么'"——把"看完了"变成"做出来了"
2. **每个阶段结束后回来追问**：遇到不懂的概念直接问，形成个性化的学习路径
3. **让它出题考你**："针对第二阶段的内容出 5 道题，先别给答案"——这是检验自己是真懂还是错觉最快的方式

**但学习资源的推荐要单独验证**：AI 推荐的书名、课程、博客链接是幻觉高发区（见 [5.3](#53-引用不等于事实三种带引用的幻觉)）。拿到书单先去搜一下确认这本书真的存在。

### 6.3 技术方案选型

传统方式：搜索"A vs B"，翻多篇对比文章，自己综合判断。

AI搜索方式（简单对比）：
> 我的场景是：Go微服务，日均消息量500万条，需要保证消息不丢失，消费延迟要求<100ms。
> 请对比Kafka和RocketMQ在这个场景下的优劣，并给出推荐。

AI能基于你的具体场景给出有针对性的建议，比泛泛的对比文章更有价值。
但最终决策前，要检查原始文档、可比条件下的 benchmark 和可复现的社区反馈，再用自己的负载验证关键要求；换一个搜索产品本身不算验证。

如果是更复杂的选型（多个候选方案、多维度对比），建议直接使用 Deep Research 功能，
参见 [3.3 实战案例](#33-实战案例用deep-research做技术选型) 中的完整流程。

### 6.4 阅读和理解源码

> 请解释以下Go标准库源码的实现原理：[粘贴代码]
> 重点说明：
> 1. 核心数据结构的设计思路
> 2. 关键的并发控制机制
> 3. 性能优化的设计考量

AI 能帮助梳理代码路径、数据结构和可能的设计权衡。提供源码减少了凭空回忆的需求，但它仍可能误读分支、遗漏跨文件状态，或者把自己的推测当成作者意图。

**把这个优势用满的几个技巧**：

- **提供足够的上下文，不是越多越好**。先给目标函数、调用关系、相关状态和版本；需要时再补完整文件或依赖实现。未提供的实现必须标为未知，不让它自行假设
- **追问"为什么不这样写"**："这里为什么用数组而不是 map？""为什么这个锁的粒度是这样划的？"——比问"这段代码做了什么"有价值得多，逼它讲设计权衡而不是复述代码
- **让它标注可疑点**："这段代码里有哪些地方是你不确定其意图的？"——把它的理解边界暴露出来
- **配合 `git log` 和 issue**：把某段代码对应的 commit message 或相关 issue 一起贴进去，它能还原出"这行代码是为了修什么 bug 加的"，这是纯读代码得不到的信息

**分清三类回答**：“代码做了什么”应指向具体分支并可用测试验证；“为什么这样设计”没有设计文档时只是推断；“哪个版本引入”要查提交、发布说明或 issue。有源码，不等于这三类问题都已有答案。

### 6.5 生成搜索关键词

当你不确定该搜什么时，可以让AI帮你：

> 我遇到了一个问题：Go服务在高并发下内存持续增长不释放。
> 请给我5组可以在Google上搜索的关键词，帮我找到相关的排查方法和解决方案。

AI能帮你从模糊的问题描述中提炼出精确的搜索关键词，相当于搜索前的"预处理"。

**这是 AI 和传统搜索配合得最漂亮的一个用法**，值得再加一层——直接让它生成**带语法的**查询串：

> ……请给出 5 组 Google 搜索查询串，要求：
> 1. 至少两组使用 `site:` 限定在官方文档或 GitHub
> 2. 至少一组用双引号做精确匹配
> 3. 说明每组词对应的排查假设；仅当问题有明确版本或时间要求时添加日期过滤
> 4. 中英文各覆盖一部分

拿到的结果可以直接粘进 Google，例如：

```
"goroutine leak" pprof site:github.com
Go 内存 持续增长 不释放 (site:go.dev | site:github.com)
"runtime.MemStats" HeapInuse HeapReleased 差异
```

**为什么这招有效**：搜索能力的瓶颈往往不在"会不会用语法"，而在**"不知道这个问题在专业上叫什么"**。你只会说"内存不释放"，而真正能搜到答案的词是 `goroutine leak`、`heap fragmentation`、`MADV_FREE`。AI 最擅长的就是把外行表述翻译成行话——**这一步的价值，比它直接给你答案还高**。

但这些词只是候选方向，不是诊断结果。让它同时给出替代假设和区分方法，避免只搜“泄漏”就漏掉正常缓存增长、内存统计口径或运行时释放策略等可能性。

语法本身见 [谷歌搜索篇第 7 章速查表](谷歌搜索.md#7-搜索语法速查表)。

## 7 一页纸速查

### 7.1 完整工作流

**从问题到可采纳结论**（箭头表示顺序，右侧数字对应本文小节）：

```text
① 分流      选搜索模式，确认资料权限与读取范围      → 1.3 / 1.4 / 5.8
                ↓
② 提问      写清约束、目标版本、起点和交付要求      → 4.1 / 7.2
                ↓
③ 取证      追问缺口，用检索词定位原件              → 4.2 / 6.5
                ↓
④ 验证      核对关键断言、适用条件，必要时做实验    → 5.3 / 7.3
                ↓
⑤ 沉淀      保存结论、来源、版本和未决问题          → 7.5
```

复杂调研在 ② 和 ③ 之间插入 Deep Research（第 3 章）；第二家报告可辅助找分歧，不是必经步骤，也不能代替 ④。证据不足时退回 ③ 补查，或保留“未知”并转向实验 / 人工确认。

### 7.2 提问模板

**通用四段式**：

```
【背景】我的场景是：<技术栈与版本>、<规模/数据量>、<硬性约束>、<我的经验起点>
【任务】请<对比/推荐/诊断/解释>：<明确的对象>
【维度】请覆盖以下方面：1... 2... 3...
【要求】给出<排序/取舍理由>、关键结论的出处与适用条件；区分事实、推断和未知
```

**几个高价值的追加句**，按需拼接：

| 目的 | 追加句 |
|---|---|
| 暴露证据缺口 | 哪些结论缺少来源或必要条件？请分别标为推断或未知 |
| 防止表格编数字 | 没有可靠来源的格子请填"未知"，不要猜测 |
| 拿到可核对的抓手 | 请附上每个结论的具体出处（文档章节 / 源码文件 / 论文） |
| 确认资料边界 | 请列出已读取的来源，以及只能看到摘要、片段或无法访问的部分 |
| 索取对立面 | 请扮演唱反调的人，尽力反驳你刚才给出的推荐 |
| 转成行动 | 请把上面的内容转成 checklist，每项写清"做完之后应该看到什么" |
| 检验我真懂了 | 针对以上内容出 5 道题考我，先不要给答案 |

### 7.3 验证清单

拿到一个你打算**采纳**的答案时，按这个顺序检查；投入与错误后果匹配，不承诺固定核验时长：

- [ ] **回答依据是什么？** 确认实际检索记录和读取范围，不把工具自述当证明 → [1.4](#14-先确认回答来自哪里)
- [ ] **能让机器判定吗？** API 用 `go doc`，行为用最小复现与测试；并发问题再用 `-race`，注意覆盖范围
- [ ] **关键数字有来源吗？** 没来源的精确数字（"提升 37%"）直接打问号
- [ ] **引用支持结论吗？** 定位后读上下文，检查条件、单位和脚注；关键决策断言逐条核实 → [5.3](#53-引用不等于事实三种带引用的幻觉)
- [ ] **版本对得上吗？** 断言涉及版本的，去 release notes 核一眼
- [ ] **证据是否独立？** 多篇转载、两个 AI 引用同一来源，都不是多份独立证据
- [ ] **缺口是否说清？** 区分事实、推断和未知，不凭语气或自报置信度判断 → [5.7](#57-识别ai不确定性的信号)
- [ ] **操作和分享安全吗？** 没有敏感输入外传，也没有把来源中的指令当作授权 → [5.8](#58-隐私与提示注入)

**分级执行**：写进生产代码或决策文档的 → 完整核验；只为了理解概念的 → 先作线索，关键定义仍需核对。

### 7.4 工具选择一览

| 我要做的事 | 用什么 |
|---|---|
| 查一个事实，要能溯源 | Perplexity |
| 复杂问题多轮探讨、写代码 | ChatGPT / Claude |
| 读一堆长文档、分析代码库 | Claude |
| 围绕选定资料问答，方便定位原文 | NotebookLM |
| 查新信息或结合 Google Workspace | 已启用联网的 AI / Gemini，检查日期与权限 |
| 找社区反馈线索 | Grok / 平台搜索（注意样本与情绪偏差） |
| 大型调研、技术选型 | 研究模式 + 原始证据 + 必要实验 → [第 3 章](#3-deep-researchai深度研究) |

### 7.5 何时停止与如何沉淀

效率不只是“问得快”，还包括**知道什么时候该停止搜索、开始行动**。以下是建议的结束条件，不是正确率保证：

- **可以结束**：关键问题已有直接证据，版本与场景匹配，影响决策的分歧已解释，必要的最小验证已完成。
- **应该换方法**：连续两轮只是在转述相同资料、没有新增证据；停止让 AI 重写，改查原始文档、做实验或问维护者。
- **需要保留未决项**：访问受限或没有可比实验时，明确“未知”、影响范围和下一步；不要为了交付一张完整表格编出结论。

保存一条能复用的笔记，而不只是一段聊天记录：

```text
问题与场景：目标、约束、技术版本
结论：当前选择及适用条件
证据：原始链接 + 章节 / 页码 + 核验日期
验证：命令 / 实验条件 + 实际结果（未执行就写未执行）
未决问题：还有什么可能改变结论，接下来由什么证据解决
复查触发：版本升级、需求变化或来源更正
```

下次遇到相似问题，先检索自己的笔记，检查适用条件，再决定是否重新调研。**把一次搜索变成可以复用的证据，才是持续提效。**

---

**最后一句**：这篇文档讲了很多让 AI 更好用的技巧，但真正的分水岭只有一条——**你是否养成了验证的习惯**。用得快的人很多，用得准的人很少，差别全在第 5 章。

> **维护约定**：建议每季度复核；工具名称 / 入口、来源读取规则、权限或 Go API 发生变化，以及读者反馈“按文档操作失败”时，提前更新。官方链接用于核对功能和边界，不用于证明品牌间准确率排名。
